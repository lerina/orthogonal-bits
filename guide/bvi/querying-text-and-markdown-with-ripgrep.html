The Core Idea

A large collection of text or Markdown files does not need to be read from beginning to end.

Treat it as a queryable body of text.

Instead of asking:

Where should I start reading?

ask:

What am I looking for?

Then search directly for it.

The main tool for this is ripgrep, usually invoked as rg.

It searches files recursively, shows matching lines, reports line numbers, and can restrict the search to particular file types.

Basic Searching

Search the current directory and its subdirectories:

rg "authentication"

Search for a term in Markdown files only:

rg "authentication" -g "*.md"

Search case-insensitively:

rg -i "authentication"

Show line numbers:

rg -n "authentication"

Line numbers are especially useful when you want to return to a specific location in an editor.

Finding Which Files Contain a Term

Sometimes the matching lines are not important. You only want to know which files contain the subject.

rg -l "authentication"

This produces a list of matching filenames.

For Markdown files:

rg -l "authentication" -g "*.md"

This is often the fastest way to discover which documents are relevant.

Reading the Context Around a Match

A search result may not provide enough information by itself.

Show three lines before and after each match:

rg -n -C 3 "authentication"

Show five lines after a match:

rg -n -A 5 "authentication"

Show five lines before a match:

rg -n -B 5 "authentication"

This lets you understand the surrounding passage without opening the entire document.

Searching Markdown Structure

Markdown headings can be searched directly.

Find every heading:

rg -n "^#" file.md

Find top-level headings:

rg -n "^# " file.md

Find level-two headings:

rg -n "^## " file.md

Search every Markdown file for headings:

rg -n "^#{1,2} " -g "*.md"

This gives you a quick structural overview of a collection of documents.

Searching for Several Terms

Use a regular expression when you want alternatives.

For example:

rg -ni "todo|fixme"

This finds either TODO or FIXME, without caring about capitalization.

You can also search for several related concepts:

rg -ni "ownership|borrowing|lifetime"

This is useful when investigating a technical subject whose terminology varies.

Searching by Whole Word

Use -w when you want an exact word rather than part of another word.

rg -nw "read" file.md

This searches for read as a word rather than matching it inside another word.

Searching a Particular Directory

You can give rg a directory to search:

rg "authentication" docs/

Or restrict the search to Markdown files inside that directory:

rg "authentication" docs/ -g "*.md"

The Basic Investigation Workflow

For a new collection of documents, a simple sequence is enough.

Step One: Survey the headings

rg -n "^#{1,2} " -g "*.md"

This gives you a rough structural map.

Step Two: Search for your subject

rg -n -i "ownership" -g "*.md"

Step Three: Identify the relevant files

rg -l -i "ownership" -g "*.md"

Step Four: Read the relevant passage

Use the filename and line number from the search result to jump directly to the relevant location in your editor.

Step Five: Search again

Once you understand the terminology used by the documents, search for additional terms, related concepts, or names.

This creates an iterative process:

Search → locate → read → identify terms → search again.

The document is no longer a linear stream that has to be consumed from beginning to end.

It becomes a body of information that can be investigated.

A Small ripgrep Reference

  • rg "pattern" — Search recursively.
  • rg -n "pattern" — Show line numbers.
  • rg -i "pattern" — Ignore capitalization.
  • rg -l "pattern" — Show filenames only.
  • rg -w "pattern" — Match whole words.
  • rg -C 3 "pattern" — Show three lines of context around each match.
  • rg -A 3 "pattern" — Show three lines after each match.
  • rg -B 3 "pattern" — Show three lines before each match.
  • rg "pattern" -g "*.md" — Search Markdown files only.
  • rg "^#" -g "*.md" — Search Markdown headings.
  • rg "term1|term2" — Search for either of two terms.

Why ripgrep Is Enough Here

The purpose of this manual is document investigation, not mastery of the Unix command line.

For that purpose, ripgrep already provides the essential operations:

  • Search recursively.
  • Search specific file types.
  • Show line numbers.
  • Show surrounding context.
  • List matching files.
  • Search case-insensitively.
  • Use regular expressions.
  • Search structural patterns such as Markdown headings.

find, xargs, sed, cut, sort, and complex pipelines are useful Linux skills, but they are not necessary for this particular workflow.

Start with one powerful search tool.

Learn the other commands when a real task gives you a reason to need them.

Part 2: regex to query Rust codebase

The right way to approach this is not “learn regex syntax” in isolation. We want to build a small query language for a Rust codebase.

Your mental model can be:

Rust source is a structured artifact. rg + regex lets me interrogate that artifact for the structural cues that would otherwise be obtained visually.

We can learn regex progressively, using actual Rust code as the material.

1. First: what regex is doing

Suppose your project contains:

pub struct Router {
    routes: Vec<Route>,
}

impl Router {
    pub fn new() -> Self {
        Self {
            routes: Vec::new(),
        }
    }

    pub fn add(&mut self, route: Route) {
        self.routes.push(route);
    }
}

A normal search asks:

rg "Router"

Regex lets you ask structural questions.

For example:

rg "^pub struct"

means:

Find lines that begin with pub struct.

You have already moved from:

“Where does this word occur?”

to:

“Where are public structs declared?”

That distinction is the foundation.

2. The first six regex concepts

You don't need the entire regex language.

Start with these:

^beginning of line $end of line .any character *zero or more +one or more ?optional

And these character groups:

[abc]a, b, or c [a-z]any lowercase letter [0-9]any digit [^/]anything except /

And these grouping operators:

(...)group |OR

That's enough to become surprisingly powerful.

3. ^ is extremely important for source code

Consider:

pub struct Router
pub struct Request
pub struct Response

Search:

rg '^pub struct' -g '*.rs'

You are saying:

The line must begin with pub struct.

Compare:

rg 'pub struct' -g '*.rs'

This searches for pub struct anywhere in the line.

While:

rg '^pub struct' -g '*.rs'

searches specifically for declarations beginning the line.

For source-code interrogation, anchors are extremely valuable.

4. Find all struct declarations

Start broadly:

rg 'struct' -g '*.rs'

Then refine:

rg '^\s*struct' -g '*.rs'

Here we've introduced:

\swhitespace

So:

^\s*struct

means:

Beginning of line → any amount of whitespace → struct.

This catches both:

struct Router

and:

    struct Router

Then:

rg '^\s*(pub\s+)?struct\s+' -g '*.rs'

Now we have something much more interesting.

It means:

^           beginning
\s*         optional indentation
(pub\s+)?   optional "pub" followed by whitespace
struct      literal word
\s+         at least one whitespace character

It matches:

struct Router
pub struct Router
pub(crate) struct Router

Actually, note that last one doesn't fully match correctly because pub(crate) isn't covered by (pub\s+)?. This is useful: regex teaches us to be precise about what our query actually means.

5. Extract names

Now suppose we want:

pub struct Router
pub struct Request
pub struct Response

We can query:

rg '^\s*pub\s+struct\s+\w+' -g '*.rs'

\w+ means:

one or more word characters.

So:

\w+

matches:

Router
Request
Response

This is our first declaration query.

6. OR: asking several related questions

Suppose we want all major Rust type declarations:

rg '^\s*(pub\s+)?(struct|enum|trait)\s+' -g '*.rs'

The important part is:

(struct|enum|trait)

which means:

struct OR enum OR trait.

Now:

rg '^\s*(pub\s+)?(struct|enum|trait)\s+' -g '*.rs'

becomes:

Find declarations of structs, enums, or traits, optionally public, allowing indentation.

This is beginning to look like a source-code query rather than ordinary text search.

7. Query functions

Functions are one of the most useful things to query.

Start:

rg 'fn ' -g '*.rs'

Then:

rg '^\s*(pub\s+)?fn\s+' -g '*.rs'

Now include methods that have modifiers:

pub async fn run(...)
pub unsafe fn access(...)
pub const fn create(...)

We can ask:

rg '^\s*(pub\s+)?(async\s+)?fn\s+' -g '*.rs'

But Rust has several possible modifiers, so we can build a more general query later.

For now, learn the principle:

Regex lets you describe the shape of the declaration.

8. Search only the artifacts we care about

Our project has three important textual artifacts:

*.rs
*.toml
*.md

So establish this habit immediately:

rg 'QUERY' -g '*.rs' -g '*.toml' -g '*.md'

For example:

rg '^#' -g '*.md'

Find Markdown headings.

rg 'dependencies' -g '*.toml'

Find dependency declarations.

rg '^\s*(pub\s+)?struct\s+' -g '*.rs'

Find Rust struct declarations.

This gives us three related layers:

Rust source     → program structure
Cargo.toml      → project/dependency structure
Markdown        → human documentation

Together they form our queryable codebase.

9. Context is part of the query

Suppose:

rg 'struct Router' -g '*.rs'

returns:

src/router.rs:14:pub struct Router {

That's useful, but you may want surrounding material.

Use:

rg -n -C 5 'struct Router' -g '*.rs'

-C 5 means:

five lines of context before and after.

Or:

rg -n -A 10 'struct Router' -g '*.rs'

means:

the matching line plus ten lines after it.

This is particularly useful when the match identifies a structural landmark and the surrounding lines provide its definition.

10. Regex for Rust's visual landmarks

A programmer normally gets many structural cues visually:

  • indentation
  • pub
  • struct
  • enum
  • trait
  • impl
  • fn
  • braces
  • modules
  • use
  • types
  • attributes
  • comments
  • Markdown headings

We can turn these into queries.

Modules

rg '^\s*(pub\s+)?mod\s+' -g '*.rs'

Imports

rg '^\s*use\s+' -g '*.rs'

Structs

rg '^\s*(pub\s+)?struct\s+' -g '*.rs'

Enums

rg '^\s*(pub\s+)?enum\s+' -g '*.rs'

Traits

rg '^\s*(pub\s+)?trait\s+' -g '*.rs'

Implementations

rg '^\s*impl\s+' -g '*.rs'

Functions

rg '^\s*(pub\s+)?fn\s+' -g '*.rs'

Attributes

rg '^\s*#\[' -g '*.rs'

Tests

rg '^\s*#\[test\]' -g '*.rs'

Markdown structure

rg '^#{1,6}\s+' -g '*.md'

The last one introduces another important regex concept.

11. {} repetition

This:

#{1,6}

means:

Between 1 and 6 # characters.

Therefore:

rg '^#{1,6}\s+' -g '*.md'

finds Markdown headings:

# Chapter
## Section
### Subsection

We can distinguish levels:

rg '^#\s+' -g '*.md'

Top-level headings.

rg '^##\s+' -g '*.md'

Second-level headings.

rg '^###\s+' -g '*.md'

Third-level headings.

This is a very useful pattern for turning documentation into a navigable artifact.

12. Your first real query vocabulary

I would teach you regex through a vocabulary like this:

Location

^beginning of line $end of line

Where is it on the line?

Character

.any character \swhitespace \wword character \ddigit

What kind of character is here?

Quantity

*zero or more +one or more ?optional (zero or one) {n}exactly n {n,m}between n and m

How many?

Alternatives

(a|b|c)a, b, or c

Which one?

Character sets

[abc]a, b, or c [a-z]any lowercase letter [0-9]any digit [^x]anything except x

Which characters?

Grouping

(...)treat as one unit

Group this together.

That is the core language.

13. Don't memorize regex. Build queries.

This is important for our eventual system.

When you want to ask:

Where are all the traits?

You construct:

trait

Then refine:

^trait

Then account for indentation:

^\s*trait

Then account for public visibility:

^\s*(pub\s+)?trait

Then require the trait name:

^\s*(pub\s+)?trait\s+\w+

The progression itself is the skill.

Query → inspect result → refine query.

14. The bigger goal: source-code reconnaissance

Eventually, I want you to be able to interrogate an unfamiliar Rust repository with queries such as:

rg '^\s*(pub\s+)?mod\s+' -g '*.rs'
What modules exist? 
rg '^\s*(pub\s+)?(struct|enum|trait)\s+' -g '*.rs'
What are the major types? 
rg '^\s*impl\s+' -g '*.rs'
Where are implementations? 
rg '^\s*(pub\s+)?fn\s+' -g '*.rs'
What functions exist? 
rg '^\s*use\s+' -g '*.rs'
What does each file depend on? 
rg '^\s*#\[test\]' -g '*.rs'
Where are tests? 
rg '^\s*#\[derive' -g '*.rs'
Which types derive traits automatically? 
rg '^#{1,3}\s+' -g '*.md'
What is the documentation structure?

And eventually, much more interesting questions:

  • Who creates this type?
  • Who calls this function?
  • Which files know about this module?
  • Where is this trait implemented?
  • Which types contain this type?
  • Which functions return this type?

Those require progressively more sophisticated patterns and eventually combinations of rg searches.

Our learning path

I suggest we don't study Regex as a general computer-science subject.

We'll study it as:

Regex for interrogating Rust.

Stage 1 — Pattern recognition

Learn:

Stage 2 — Rust declarations

Build queries for:

Stage 3 — Rust relationships

Query:

Stage 4 — Attributes and macros

Query:

#[derive(...)]

macro_rules!

Stage 5 — Markdown and Cargo

Interrogate:

*.md
*.toml

for headings, dependencies, features, packages, workspace members, and documentation structure.

Stage 6 — Structural reconnaissance

Combine rg with context and multiple searches to produce a textual map of an unfamiliar repository.

That is where this becomes much more than learning regex. It becomes a replacement for the visual source-code map that an IDE normally gives you.

And I think that is the right target for us: not “I know regex,” but “I can interrogate a Rust repository.”
