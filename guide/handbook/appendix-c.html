Appendix C: Question-Code Spiking for Comprehending a New Codebase

Purpose

When entering an unfamiliar codebase, the objective is not to read every file.

The objective is to build a reliable model of:

  • what the system does,
  • where its major parts are,
  • how execution moves through them,
  • what data moves between them,
  • where important decisions are made,
  • and which parts matter to the change you need to make.

Use question-code spikes to discover this structure.

Each spike answers one concrete question.

The spike is temporary.

The understanding is retained.

1. The Central Question

Begin with one question:

How does this codebase actually work?

Do not try to answer it immediately.

Break it into eight investigation areas.

A useful starting set is:

  1. Purpose — What does the system do?
  2. Entry points — Where does execution begin?
  3. Structure — What are the major components?
  4. Data — What information moves through the system?
  5. Control flow — How does execution move between components?
  6. Contracts — What does each component expect and produce?
  7. State and policy — Where are important decisions and state changes made?
  8. Tests and boundaries — How does the codebase demonstrate and constrain its behavior?

These eight areas form the initial map.

They are questions, not conclusions.

2. First Pass: Reconnaissance

Do not open random source files.

First establish the repository's shape.

Use the tools available to you:

  • directory listing,
  • rg,
  • find,
  • git,
  • language-specific tooling,
  • build and test commands,
  • documentation,
  • package or dependency manifests.

For a Rust repository, for example:

  • Cargo.toml
  • Cargo.lock
  • workspace members
  • src/
  • tests/
  • binaries
  • libraries
  • examples
  • build scripts
  • feature definitions

The first question is:

What kind of repository am I looking at?

Produce a short reconnaissance result:

This is a workspace containing X crates.
These appear to be libraries.
These appear to be binaries.
Tests are located here.
The primary entry points appear to be here.

Do not explain the implementation yet.

3. Find the Entry Points

The first major code question is:

Where does execution enter the system?

Look for:

  • main
  • library initialization
  • exported APIs
  • command handlers
  • event handlers
  • HTTP handlers
  • callbacks
  • service constructors
  • public functions
  • test entry points

For Rust, useful searches include:

rg 'fn main'
rg 'pub fn'
rg 'pub struct'
rg 'impl'

The exact searches depend on the codebase.

Do not read every result.

Identify the few locations from which significant execution begins.

Then ask:

What happens immediately after entry?

That becomes the first code-reading spike.

4. Trace One Real Execution Path

Choose one concrete operation.

For example:

What happens when the user invokes command X?

Follow it from beginning to end.

Record only the important transitions:

entry point → dispatcher → service → core operation → output

Do not attempt to understand every function encountered.

At each transition, ask:

  • Who calls this?
  • What does it receive?
  • What does it produce?
  • Why does control move here?

This creates the first execution spine.

The execution spine is more useful than a file-by-file summary.

5. Build the Eight Investigation Areas

Now expand each major question into concrete spikes.

Purpose

Questions might include:

  • What problem does the program solve?
  • What is its primary user operation?
  • What are its major modes?
  • What behavior is explicitly promised?

Entry Points

Questions might include:

  • Where does execution begin?
  • What public APIs matter?
  • What commands or events enter the system?
  • Which functions are externally callable?

Structure

Questions might include:

  • What are the major modules?
  • Which modules depend on which others?
  • Where is the core domain logic?
  • Which components are infrastructure?

Data

Questions might include:

  • What are the important types?
  • What data enters the system?
  • What transformations occur?
  • What data leaves the system?

Control Flow

Questions might include:

  • What calls what?
  • Where are branches made?
  • Where are loops or retries?
  • Where does asynchronous work occur?

Contracts

Questions might include:

  • What does each important function require?
  • What does it return?
  • How are errors represented?
  • Which invariants does it rely on?

State and Policy

Questions might include:

  • Where is state stored?
  • Where is state changed?
  • Where are important decisions made?
  • Which code expresses policy rather than mechanism?

Tests and Boundaries

Questions might include:

  • What behavior is tested?
  • Which components are tested independently?
  • Where are external systems accessed?
  • What assumptions are enforced by tests?

6. Turn Questions into Spikes

Every important unknown becomes a small investigation.

Examples:

Question: Where is the parser's output consumed?

Spike:

Search for the parser's return type and follow its uses.

Question: Who owns this state?

Spike:

Find where the type is constructed, stored, mutated, and dropped.

Question: What happens when this operation fails?

Spike:

Trace the error from its creation to the externally visible result.

Question: Is this module policy or mechanism?

Spike:

Find its callers and determine whether it makes decisions or merely performs operations.

Question: What is the real public interface?

Spike:

Inspect exported symbols and their external callers.

The spike can be as simple as a search.

Question code does not always mean writing new code.

The principle is:

Use the smallest executable investigation that can answer the question.

That may be:

  • rg,
  • ast-grep,
  • a compiler experiment,
  • a tiny Rust program,
  • a test,
  • a debugger session,
  • a benchmark,
  • or a controlled modification.

7. Definition, Users, Owners

For important symbols, use three questions.

Definition

Where is this thing defined?

Find the struct, enum, trait, function, constant, or module.

Users

Who uses it?

Find callers, constructors, implementations, pattern matches, and consumers.

Owner

Which part of the system is responsible for its behavior?

This is more important than merely knowing where the symbol is defined.

A type may be defined in one module while its meaning is determined by another.

The goal is to discover responsibility, not just location.

8. Follow Data Before Reading Details

When control flow becomes confusing, follow the data.

Ask:

What enters this component?

Then:

What happens to it?

Then:

Where does it go?

For each important type:

  1. Find where it is created.
  2. Find where it is transformed.
  3. Find where it is consumed.
  4. Find where it is stored.
  5. Find where it is destroyed or leaves the system.

This often reveals the architecture faster than reading functions from top to bottom.

9. Follow Ownership and State

For Rust code, ownership can reveal architectural responsibility.

For an important value, ask:

  • Who creates it?
  • Who owns it?
  • Is it borrowed?
  • Is it cloned?
  • Is it moved?
  • Where does it become mutable?
  • Where does it cross a component boundary?

These are architectural questions disguised as Rust questions.

A function signature can therefore be a useful design document.

For example:

fn process(input: &Input) -> Result<Output, Error>

immediately raises questions:

  • Who owns Input?
  • Why is it borrowed?
  • Who owns the resulting Output?
  • What failures are possible?
  • Which layer defines Error?

Each question can become a spike.

10. Use Tests as Behavioral Evidence

Tests are often easier to understand than implementation.

Start with a test that exercises the behavior you care about.

Ask:

What behavior does this test consider important?

Then trace:

test → public interface → implementation → dependencies

Tests provide evidence about intended behavior.

Implementation shows how that behavior is currently achieved.

When the two disagree, record the discrepancy instead of immediately deciding which one is correct.

11. Use the Compiler as an Investigator

In a Rust codebase, compilation can answer questions directly.

Examples:

What happens if this type is changed?

Make a temporary change.

Compile.

Observe the compiler's dependency chain.

Or:

Which code depends on this trait?

Temporarily modify the trait or signature and inspect the resulting diagnostics.

The compiler becomes a dependency probe.

This is especially useful when static reading becomes difficult.

12. Use rg for Textual Relationships

rg answers:

Where does this name or pattern occur?

Use it to find:

  • definitions,
  • callers,
  • constructors,
  • implementations,
  • error messages,
  • configuration,
  • tests,
  • feature flags.

Do not interpret every match.

Use successive searches to narrow the question.

A typical investigation is:

symbol
→ definition
→ constructors
→ callers
→ consumers
→ tests

The result is a relationship map.

13. Use Structural Search for Structural Questions

Text search is insufficient when the question concerns syntax.

Use structural search when you need to ask:

  • Which functions return this type?
  • Which structs contain this field?
  • Which implementations provide this trait?
  • Which calls occur inside this pattern?
  • Which modules contain this kind of declaration?

For Rust, ast-grep can complement rg.

The division is:

  • rg → textual evidence
  • ast-grep → structural evidence
  • Helix → close reading and navigation
  • rust-analyzer → semantic relationships
  • compiler → dependency evidence
  • LLDB → runtime behavior

No single tool needs to explain the entire codebase.

14. Runtime Spikes

Static analysis eventually reaches a limit.

Then run the system.

A runtime spike asks:

What actually happens?

Examples:

  • Run one command.
  • Feed one real input.
  • Trigger one error.
  • Set one debugger breakpoint.
  • Inspect one stack trace.
  • Measure one operation.
  • Log one state transition.

The purpose is not debugging in the traditional sense.

The purpose is architecture discovery through execution.

15. Build the Skeleton Map

After several spikes, you should be able to state:

The system enters here.

It passes through these components.

This component owns this responsibility.

This data is transformed here.

This boundary separates these concerns.

This failure travels through these layers.

That is your skeleton map.

Do not fill it with every function.

Keep only the relationships necessary to navigate the system.

16. The Codebase 64-Spike

You can now use the 64-item structure as an investigation inventory.

The center is:

Comprehend this codebase.

The eight surrounding questions are:

  1. Purpose
  2. Entry points
  3. Structure
  4. Data
  5. Control flow
  6. Contracts
  7. State and policy
  8. Tests and boundaries

Each expands into eight concrete investigation questions.

For example:

Entry Points

  1. Where does execution begin?
  2. What public APIs exist?
  3. What commands enter the system?
  4. What events enter the system?
  5. What initializes the system?
  6. What configuration enters the system?
  7. What external callers exist?
  8. What is the simplest complete execution path?

That produces eight useful spikes without requiring you to invent arbitrary tasks.

Do the same for the other seven areas.

The result is a 64-question codebase investigation map.

You do not have to answer all 64.

Use the map to choose the next question.

17. Prioritize by Information Gain

The best next spike is not necessarily the easiest one.

Prefer questions whose answers will explain many other things.

For example:

Where is the central data type transformed?

may explain:

  • several modules,
  • multiple functions,
  • several tests,
  • and the primary execution path.

That is a high-information spike.

A useful rule is:

Choose the question that is most likely to collapse several unknowns at once.

This is more useful than simply working from the top of the file tree.

18. The Comprehension Loop

Use this loop continuously:

  1. Locate. Find the relevant symbol or component.
  2. Define. Determine what it is.
  3. Trace users. Find who calls or consumes it.
  4. Trace ownership. Determine who is responsible for its behavior.
  5. Trace data. Follow important values through it.
  6. Run a spike. Test an uncertain assumption.
  7. Recall. Close the source and explain the path from memory.
  8. Verify. Check your explanation against the code or runtime.
  9. Harvest. Record only the essential understanding.
  10. Update the map. Add newly discovered relationships.
  11. Delete the scaffolding. Remove temporary experiments.
  12. Choose the next question.

19. When Are You Done?

You do not need to understand every line.

You have sufficient comprehension when you can answer, without reopening the entire repository:

  • What does this system do?
  • Where does execution enter?
  • What are its major components?
  • What is the main execution path?
  • What are the important data types?
  • Where does important data change?
  • Which component owns each major responsibility?
  • Where are important decisions made?
  • How are errors propagated?
  • What are the important external boundaries?
  • Which tests demonstrate the behavior?
  • Where should a proposed change probably live?
  • What assumptions are still uncertain?

The final question is important:

What do I still not know?

Unknowns are not failures.

They are the next spikes.

20. The Final Harvest

When the investigation reaches a useful stopping point, produce a compact codebase model.

It should contain:

Purpose

What the system exists to do.

Architecture

Its major components and responsibilities.

Execution spine

The principal path through the system.

Data spine

The important data and how it changes.

Contracts

The important interfaces and failure boundaries.

Ownership

Which component is responsible for what.

Evidence

The tests, runtime behavior, and source relationships supporting the model.

Open questions

What remains uncertain.

This is the durable result of the investigation.

The temporary spikes can disappear.

The Principle

Do not read a codebase from beginning to end.

Interrogate it.

Ask a question.

Find the smallest investigation that can answer it.

Run the investigation.

Recall the result.

Verify it.

Harvest the essence.

Update the map.

Then ask the next question.

The codebase gradually changes from an unfamiliar collection of files into a network of known relationships.

Locate. Trace. Probe. Recall. Harvest. Map. Repeat.

The goal is not to remember the code.

The goal is to know where the answer lives, how the parts relate, and what evidence supports your understanding.
