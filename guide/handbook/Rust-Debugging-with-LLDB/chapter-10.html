Chapter 10: Option, Result, and Panics

Almost every Rust program is built on three related ideas:

  • Option<T>: a value that might be present or absent.
  • Result<T, E>: an operation that might succeed or fail.
  • panic!: the mechanism for signaling an unrecoverable failure.

These three are so pervasive that a large fraction of real-world Rust debugging consists of answering questions about them. Which variant is active? Where did the error come from? Why did this unwrap panic?

This chapter is about answering those questions in the debugger. We will look at how Option and Result render, how to trace a value of either type backward toward its origin, and how to debug a panic.

Rust Option

Rust programs frequently use:

Option<T>

When debugging an Option, determine whether the value is:

Some(...)

or:

None

For example:

let config = find_config();

Stop after the call.

Then:

(lldb) frame variable config

Now you have evidence.

If it is None, move backward.

Ask:

Why did find_config return None?

Set a breakpoint inside find_config.

Then repeat.

How Option renders

With the Rust pretty-printers active, an Option renders as its variant name and, if it is a Some, the value inside.

Suppose you have:

let maybe_name: Option<String> = Some(String::from("Alice"));

Ask:

(lldb) frame variable maybe_name
(Option<String>) maybe_name = Some("Alice")

For an absent value:

let nothing: Option<String> = None;
(lldb) frame variable nothing
(Option<String>) nothing = None

For a numeric Option:

let maybe_count: Option<u32> = Some(42);
(lldb) frame variable maybe_count
(Option<u32>) maybe_count = Some(42)

For a nested Option:

let nested: Option<Option<i32>> = Some(Some(7));
(lldb) frame variable nested
(Option<Option<i32>>) nested = Some(Some(7))

In every case, the debugger tells you exactly which variant is active, and if it is Some, what data it carries. This is one of the places where the Rust integration in LLDB pays off the most, because the corresponding raw layout (a discriminant tag plus a union) would be very hard to read by hand.

When the pretty-printers are not active, you may see something like:

(core::option::Option<alloc::string::String>) maybe_name = {
    __0 = {
        value = "Alice"
    }
}

This is technically correct but far less convenient. If you see this form, check that you are launching the debugger via rust-lldb.

Tracing an Option backward

The most common debugging task involving Option is tracing a None back to its origin. Suppose you are looking at this program:

fn find_user(id: u32) -> Option<User> {
    let user = database_lookup(id);
    user
}

fn greet_user(id: u32) -> String {
    let user = find_user(id);
    match user {
        Some(u) => format!("Hello, {}!", u.name),
        None => String::from("Hello, stranger."),
    }
}

fn main() {
    let greeting = greet_user(42);
    println!("{greeting}");
}

If the program prints “Hello, stranger.” and you expected a real greeting, the final symptom is the None branch. The next question is: why did find_user return None?

A practical workflow:

  1. Set a breakpoint inside find_user at the line where it returns.
  2. Inspect the value being returned.
  3. If the value is already None, the bug is inside find_user. If it is Some, the bug is elsewhere.
  4. If the bug is inside find_user, set a breakpoint inside database_lookup and repeat.

At each step, inspect the value with frame variable and compare it with what you expected. The first place where an expected Some becomes a None is the origin.

This is a direct application of the “first wrong state” discipline from the previous chapter.

The question mark and Option

The ? operator on an Option propagates None to the caller. When you see a function returning None, it may be doing so directly, or it may be propagating a None from a callee.

Consider:

fn load_settings() -> Option<Settings> {
    let raw = read_file()?;
    let parsed = parse(raw)?;
    Some(parsed)
}

If load_settings returns None, the cause is either read_file or parse. To find out which, set breakpoints at the returns of both:

(lldb) breakpoint set --name read_file
(lldb) breakpoint set --name parse
(lldb) run

At each stop, inspect the return value. The first function that returns None is the origin of the propagated None.

This pattern is very common. The ? operator is convenient in source, but it hides the origin of a failure. The debugger reveals it.

Option in real structs

Options are often fields inside structs. For example:

struct Config {
    name: String,
    timeout: Option<u64>,
}

When inspecting a config, ask directly about the field:

(lldb) frame variable config.timeout
(Option<u64>) config.timeout = Some(30)

Or, if it is unset:

(Option<u64>) config.timeout = None

A common bug pattern: a field is expected to be set, but has never been assigned. The debugger shows the field as None, which tells you that the initialization path did not populate it. The next step is to trace where the config was constructed.

Rust Result

The same approach applies to:

Result<T, E>

Inspect the result before it is transformed.

For example:

let config = load_config()?;

Stop before or inside the relevant operation.

Determine:

Was the result Ok?

Was it Err?

What is the error value?

Where was the error created?

A useful debugging chain is:

Result
→ Err
→ error constructor
→ underlying cause
→ original input

How Result renders

A Result renders as its variant name plus the data inside, just like Option.

Success:

let ok: Result<i32, String> = Ok(42);
(lldb) frame variable ok
(Result<i32, String>) ok = Ok(42)

Failure:

let err: Result<i32, String> = Err(String::from("not found"));
(lldb) frame variable err
(Result<i32, String>) err = Err("not found")

When the error type is a custom enum or struct, the pretty-printer renders its fields as well:

#[derive(Debug)]
enum LoadError {
    NotFound(String),
    InvalidFormat { line: usize },
}

let result: Result<Config, LoadError> = Err(LoadError::InvalidFormat { line: 42 });
(lldb) frame variable result
(Result<Config, LoadError>) result = Err(InvalidFormat {
    line = 42
})

The debugger tells you which variant of the error is active and what data it carries. This is often enough to identify the bug, even without tracing any further.

Tracing a Result backward

Suppose a function returns an Err, and you want to know where the error was created. A practical strategy:

  1. Set a breakpoint at the point where the Err becomes visible (usually a return statement, or the point right after the failing call).
  2. Inspect the error value with frame variable.
  3. Use the error’s variant or message to narrow down where it was constructed.
  4. Set a breakpoint in the function that constructs that specific error variant.
  5. Repeat until you reach the original input that triggered the error.

This works especially well when the error type is a custom enum, because the variant name in the debugger points directly to the code path that created it.

For example, if the debugger shows:

(Result<Config, LoadError>) result = Err(InvalidFormat { line = 42 })

you know to search for the construction site of LoadError::InvalidFormat. A text search for InvalidFormat will typically find it immediately.

The question mark and Result

The ? operator on a Result propagates Err to the caller, converting the error type along the way if a From implementation exists. This is convenient in source but obscures the origin of the error.

Consider:

fn process_file(path: &str) -> Result<Summary, ProcessError> {
    let raw = std::fs::read_to_string(path)?;
    let parsed: Config = toml::from_str(&raw)?;
    let summary = summarize(&parsed)?;
    Ok(summary)
}

If process_file returns an Err, the cause could be:

  • An I/O error from read_to_string.
  • A TOML parse error from toml::from_str.
  • A domain error from summarize.

Because each ? converts its error to ProcessError, the returned Err may have lost the original error type. The debugger shows the converted form. To find the origin:

  1. Set a breakpoint at the entry of process_file.
  2. Step over each line.
  3. After each line, inspect the result of the operation just performed. If it is Err, the last line executed is the origin.

An alternative, when the error type has a source chain (as it does with thiserror and anyhow), is to inspect the error’s source field. The debugger will show the nested error, often down to the original I/O error or parse error. This is covered further below.

unwrap() and expect()

A panic from:

value.unwrap()

is a particularly useful debugging location.

Set a breakpoint at the source line or run until the panic occurs.

Then inspect:

value

The important question is not:

Why did unwrap panic?

The important question is:

Why was this value None or Err here?

unwrap() is usually the final symptom.

The cause is earlier.

Unwraps in source

An unwrap() in source is a claim by the programmer: “I believe this value will be Some or Ok.” When that belief is wrong, the program panics. Debugging the panic is, in a sense, debugging the belief: why did reality diverge from the assumption?

The most useful place to look is not the line with the unwrap. It is the line where the value was constructed. The unwrap just happens to be where the assumption became visible.

A practical approach:

  1. Note the source location of the unwrap (from the panic message or from the backtrace).
  2. Identify the expression being unwrapped.
  3. Trace that expression back to the point where it was produced.
  4. Inspect the value there.

In many cases, the value is wrong at the point of production, not at the point of use. The unwrap only reveals the problem.

Unwraps in libraries

When a library unwraps internally, the panic message points into the library, not into your code. The useful frame is the first one belonging to your own crate, which is the frame that called into the library.

Set a breakpoint at that call site. Inspect the arguments you are passing. If the arguments satisfy the library’s documented preconditions, the library’s unwrap is a bug in the library. If they do not, the bug is in your code.

This is a common pattern in third-party crate debugging. Your task is often not to fix the library but to understand what input you passed that caused the library to reach an impossible state.

Debugging a panic

When Rust panics, LLDB may stop because of the underlying signal or exception behavior rather than directly at the Rust panic! source line.

A practical approach is:

  1. Run under LLDB.
  2. Observe the stop.
  3. Run:
(lldb) bt
  1. Inspect the current frame.
  2. Move through relevant frames.
  3. Identify the first frame belonging to your application.
  4. Inspect its locals.
  5. Trace backward toward the invalid state.

Do not assume the top frame is the root cause.

The top frame often shows where the program finally stopped.

The useful frame may be several levels below it.

How Rust panics work

Understanding the mechanism helps interpret what the debugger shows.

When you call panic!, or when a standard-library operation panics, the Rust runtime:

  1. Constructs a PanicInfo with the panic message, location, and payload.
  2. Calls the panic hook, which by default prints a message to standard error.
  3. Begins unwinding the stack, running destructors for every frame.
  4. If unwinding reaches the top of the thread, terminates the thread. If the thread is the main thread, terminates the program with a non-zero exit status.

Under LLDB, the stop occurs somewhere in this sequence. Depending on the platform and LLDB configuration, the stop may be:

  • At the panic hook, where the message is printed.
  • At the point where unwinding raises a C++ exception.
  • At the C++ runtime's abort call, if the panic strategy is abort.
  • At the signal handler that converts the unwinding exception into a signal.

In all cases, the backtrace shows where the stop occurred. Your job is to find the frame that belongs to your own code and that is closest to the original panic site.

Finding the panic site

When the program stops on a panic, use the backtrace:

(lldb) bt

Look for frames that mention your crate name and your source files. The first such frame from the top is usually the panic site or the frame just below it.

For example:

frame #0  std::panicking::begin_panic
frame #1  std::panicking::begin_panic_handler
frame #2  core::panicking::panic_fmt
frame #3  core::panicking::panic
frame #4  core::option::expect_failed
frame #5  my_crate::load_config at src/config.rs:42
frame #6  my_crate::main at src/main.rs:10
frame #7  std::rt::lang_start_internal
...

The panic was triggered by an expect call (frame #4), which was inside load_config (frame #5). The application frame of interest is frame #5, not frame #0.

Use:

(lldb) frame select 5
(lldb) frame variable

Now you can inspect the state of load_config at the moment the panic was triggered.

Break on the panic machinery

A more direct strategy is to set a breakpoint on the panic function itself, before it unwinds the stack. The exact symbol name depends on the Rust version and standard library, but common candidates are:

std::panicking::begin_panic
core::panicking::panic_fmt
core::panicking::panic

For example:

(lldb) breakpoint set --name std::panicking::begin_panic
(lldb) run

When the breakpoint fires, the stack is not yet unwound. The backtrace is closer to the panic site. This is often easier to read than the default stop.

The exact symbol may vary across Rust versions. If begin_panic does not resolve, try panic_fmt or panic. Use image lookup to search if you are unsure:

(lldb) image lookup --name panic

The panic message

The default panic hook prints a message to standard error. In a normal (non-debugger) run, that is often the first thing you see:

thread 'main' panicked at src/config.rs:42:10:
Cannot open configuration file: No such file or directory
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

Under LLDB, the message may or may not appear before the debugger stops, depending on where the stop occurs relative to the panic hook. If it does not appear, you can sometimes read it from the PanicInfo argument to the panic function. This is an advanced technique and often not necessary, because the source location in the backtrace usually gives you the same information.

Custom panic hooks

Some programs install a custom panic hook, for example to log panics to a file, to send them to a monitoring service, or to suppress the default message. If you are debugging such a program and no panic message appears, the custom hook may be responsible.

Custom panic hooks are typically installed at the very start of main:

std::panic::set_hook(Box::new(|info| {
    // custom handling
}));

If you suspect a custom hook is interfering, set a breakpoint on the hook function itself and inspect what it does.

Unwind versus abort

Rust supports two panic strategies: unwind and abort. The default is unwind, which runs destructors as it unwinds the stack. In some environments, such as embedded systems or when panic = "abort" is configured in Cargo.toml, panic aborts immediately.

If you are debugging a program with panic = "abort", the unwinding behavior is different. The stop occurs at the abort call, and there may be no unwinding frames. The stack is still intact at the point of panic, which can make debugging slightly easier in some ways, but destructors are not run, which may leave resources in an unexpected state.

To check which strategy your binary uses, inspect the Cargo profile:

[profile.dev]
panic = "unwind"   # default

[profile.release]
panic = "unwind"   # default

# Alternatively:
[profile.release]
panic = "abort"

The dev profile uses unwind by default. The release profile also uses unwind unless overridden. Embedded builds often set panic = "abort" at the workspace level.

Panics in async code

An async task that panics does not necessarily panic the entire program. The panic unwinds the task’s future, and the runtime may or may not propagate the panic depending on how the task was spawned.

When debugging async panics, the backtrace often shows runtime frames near the top, followed by application frames. The first application frame is usually the panic site. From there, tracing backward reveals the chain of async calls that led to it.

The same discipline applies as for synchronous panics: do not stop at the top frame. Find the first frame belonging to your own code. That is where the investigation begins.

Panic during unwinding

If a panic occurs while another panic is already unwinding the stack, the program aborts. This is called a double panic. The runtime does not attempt to recover, because the state is considered unrecoverable.

If you see the program aborting with a message such as “thread panicked while panicking,” the cause is a destructor that panicked during unwinding. The debugger can show you both panic sites if you set breakpoints on the panic machinery.

This is a rare case, but worth knowing about. If a program is aborting with a double panic, the more interesting panic is the first one, not the second.

Error chains in thiserror and anyhow

Two crates are especially common in Rust error handling: thiserror for defining error types, and anyhow for general-purpose error propagation. Both provide ways to chain errors, and the debugger can show you the chain.

thiserror

With thiserror, you define your own error enum. Each variant may carry a source error, often annotated with #[source] or #[from]:

use thiserror::Error;

#[derive(Error, Debug)]
enum ConfigError {
    #[error("failed to read config file")]
    Io(#[from] std::io::Error),

    #[error("failed to parse config")]
    Parse(#[from] toml::de::Error),
}

When the program returns a ConfigError::Io that wraps an std::io::Error, the debugger shows the outer error and, if you inspect the source field, the inner error as well:

(lldb) frame variable err
(ConfigError) err = Io(Os { code: 2, kind: NotFound, message: "No such file or directory" })

The inner Os value is the source error. You can often read the underlying cause directly from this display.

anyhow

anyhow::Error is a type-erased error that can wrap any error and add context. In the debugger, an anyhow::Error renders as a message plus an optional chain of sources.

(lldb) frame variable err
(anyhow::Error) err = Failed to read config file
    Caused by:
        No such file or directory (os error 2)

The exact formatting depends on the pretty-printer, but the chain is visible. The first line is the outermost context; the following lines are the causes, from most recent to oldest.

This is one of the strongest arguments for using a well-structured error type in Rust: the debugger can show you the complete chain, often enough to identify the root cause without further tracing.

Rust 2024 notes on Option, Result, and panics

A few Rust 2024 specifics affect what you see when debugging Option, Result, and panics.

Edition 2024 and errors

The Rust 2024 edition does not change the fundamental layout of Option or Result. They are still enums, and they still render as variant name plus data. The pretty-printers handle them the same way as in earlier editions.

What may change is the exact standard-library source path shown in backtraces, because the standard library is compiled with the edition in use. The shape of the display remains the same; the file paths and function names may differ slightly.

Panic hooks and 2024

The panic hook mechanism is unchanged in Rust 2024. Custom hooks still receive a PanicHookInfo (the type formerly named PanicInfo, renamed for clarity). If you inspect a custom panic hook in the debugger, the argument type may show the new name.

unsafe extern blocks and errors

When an FFI call returns an error code, wrapping that code into a Rust Result is one of the most common patterns at the language boundary. In Rust 2024, the declaration of the foreign function is inside an unsafe extern block, but the error type you construct is a regular Rust enum or struct. When you inspect that error at a breakpoint, it renders as a normal Result.

The practical difference is that the call to the foreign function and the construction of the error are two separate steps in the source. When debugging an FFI error, set breakpoints on both: the call to the foreign function, to inspect the raw error code, and the point where the error is wrapped, to inspect the resulting Rust error value.

A complete worked example

To bring the ideas in this chapter together, consider the following small program:

use std::env;

#[derive(Debug)]
enum AppError {
    MissingVariable(String),
    EmptyVariable(String),
}

fn read_path(name: &str) -> Result<String, AppError> {
    let value = env::var(name)
        .map_err(|_| AppError::MissingVariable(name.to_string()))?;

    if value.is_empty() {
        return Err(AppError::EmptyVariable(name.to_string()));
    }

    Ok(value)
}

fn main() {
    let path = read_path("CONFIG_PATH").expect("failed to read CONFIG_PATH");
    println!("Using config: {path}");
}

Suppose you run this program without setting CONFIG_PATH. The program panics with a message along the lines of:

thread 'main' panicked at src/main.rs:19:47:
failed to read CONFIG_PATH: MissingVariable("CONFIG_PATH")

The panic message already tells you a lot. But suppose you wanted to inspect the state at the panic.

Set a breakpoint on the panic machinery:

(lldb) breakpoint set --name std::panicking::begin_panic
(lldb) run

When the breakpoint fires:

(lldb) bt

Look for the first frame belonging to your crate. It will be in main, just before the expect call. Select that frame:

(lldb) frame select N
(lldb) frame variable

Now inspect the Result that expect was about to unwrap. If expect was inlined into main, the Result may not be directly visible as a named variable, but the value of the read_path call may still be inspectable. In a debug build, the compiler often keeps the intermediate value in a temporary.

If you want a clearer observation, set a breakpoint inside read_path:

(lldb) breakpoint set --name read_path
(lldb) run

At each stop, inspect the arguments and the return value. Trace the error back to where it was created: either at the map_err call (for a missing variable) or at the explicit Err (for an empty variable).

This illustrates the general principle: expect and unwrap are the final symptom. The evidence you want is one frame up the call stack, in the function that produced the value.

Summary

In this chapter, we covered three closely related topics:

  • Option<T>: how it renders in the debugger, how to tell Some from None, and how to trace a None backward toward its origin. We looked at how the ? operator propagates None and how to find the origin by setting breakpoints on each contributing function.
  • Result<T, E>: how it renders, including custom error enums, and how to trace an Err backward using the error’s variant to identify the construction site. We also looked at ? with Result, and the interaction between error conversion and error origin.
  • unwrap() and expect(): why the panic site is a symptom rather than the cause, and how to trace the value backward to where it became None or Err.
  • Debugging a panic: the mechanism of Rust panics, where LLDB stops, how to find the panic site in the backtrace, how to break on the panic machinery before unwinding begins, and how to interpret panic messages and custom panic hooks.
  • Error chains in thiserror and anyhow: how the debugger shows the chain of causes for structured errors, often revealing the root cause directly.
  • Rust 2024 specifics: edition changes do not alter the fundamental layout of these types, but they do change some type names and source paths that may appear in the debugger.

The unifying theme is that Option, Result, and panics are all about the difference between expectation and reality. The debugger’s job is to show you where that difference first appears.
