Chapter 7: Breakpoints

A breakpoint is a request to the debugger:

Stop execution here.

Everything else in a debugging session is built on top of this simple idea. You stop the program at a location you have chosen, inspect its state, and decide what to do next. Without breakpoints, you would be reduced to watching a program run to completion, with no way to interrupt it in the middle.

In this chapter, we will look at how breakpoints work in Rust with LLDB. We will cover the two main ways to set a breakpoint, how to see what breakpoints exist, and how to remove them. We will also look at what happens when a breakpoint fails to resolve, and how to place breakpoints strategically so that each debugging session is efficient.

Two ways to place a breakpoint

LLDB supports many ways to set a breakpoint, but two of them account for almost every case you will encounter in Rust:

  • By function name: breakpoint set --name parse_config
  • By source file and line: breakpoint set --file src/main.rs --line 42

Each has strengths and weaknesses. Learning when to use each is one of the earliest and most useful skills in Rust debugging.

Function name breakpoints

A function name breakpoint stops execution at the entry of a named function:

(lldb) breakpoint set --name parse_config

When the program enters parse_config, LLDB pauses. This is usually the easiest way to investigate a function: you see what it receives before it does anything.

Advantages:

  • You do not need to know the file or line.
  • It works from anywhere, as long as the function exists in the compiled binary.
  • Arguments are immediately visible at the breakpoint.

Disadvantages:

  • Ambiguous when several functions share the same name across modules or generic instantiations.
  • May fail to resolve when the function was inlined or when its mangled name does not match the source name.
  • Cannot distinguish between multiple call sites of the same function.

For a Rust function that is not generic, is not inlined, and has a unique name, this works reliably. For a method, a generic function, or an inlined helper, it may not resolve at all, or may resolve to several locations at once.

Source-line breakpoints

A source-line breakpoint stops execution at a specific line in a specific file:

(lldb) breakpoint set --file src/main.rs --line 8

This is often the more predictable option in Rust, because it does not depend on how the compiler named or instantiated the function. It targets a specific line of source, which is usually exactly what you want.

Advantages:

  • Works inside closures, iterator chains, and generic functions where a name-based breakpoint would be ambiguous.
  • Unaffected by name mangling.
  • Targets a specific statement or expression.
  • Can be placed inside inlined functions, because LLDB can still map the line to a machine instruction.

Disadvantages:

  • You need to know the line number in advance.
  • If the file has been reorganized since you last read it, the line may have shifted.
  • Cannot be used before you know which file to look in.

For source-line breakpoints, the file path is relative to the working directory of the process when LLDB loaded the binary. In a Cargo project, this is usually the crate root, so src/main.rs is the right form.

Choosing between the two

A useful rule:

  • Use a function name breakpoint when you want to see what a function receives, and the name is unique and unambiguous.
  • Use a source-line breakpoint when you want a specific line, when the function name is ambiguous, or when the function might be inlined.

In practice, many sessions start with a name breakpoint on the function you suspect, and then add source-line breakpoints inside it once you have confirmed the entry point.

Set your first breakpoint

At the LLDB prompt, set a breakpoint on a function:

(lldb) breakpoint set --name add

LLDB responds with something like:

Breakpoint 1: where = first_session`first_session::add, address = 0x...

Read this line carefully:

  • Breakpoint 1: The breakpoint has been assigned ID 1. Every breakpoint gets a unique numeric ID, which you use to refer to it later.
  • where = first_session`first_session::add: The symbol where the breakpoint resolved, in demangled form. The crate name (first_session) is shown, followed by the module path (first_session) and the function name (add).
  • address = 0x...: The machine address at which execution will pause. You rarely need this, but it confirms that the breakpoint is not pending.

Short form:

(lldb) b add

Both forms are equivalent. Use whichever you find easier to type and remember.

Break at a Rust source line

To break at a specific line:

(lldb) breakpoint set --file src/main.rs --line 8

Short form:

(lldb) breakpoint set -f src/main.rs -l 8

Use this when you already know the suspicious location. It is especially useful in the following cases:

  • You are inside a closure and want to stop at one specific line inside it. Closures have compiler-generated names that are difficult to reference by hand.
  • You are inside an iterator chain and want to stop at one specific method call. The intermediate types have names that are unstable across compiler versions.
  • You want to stop at a line inside a generic function without having to reason about monomorphized instantiations.
  • You want to stop at a line inside an inlined function, which has no separate symbol in the binary.

The trade-off is that you have to look up the line number first. For small files, this is trivial. For large files, the rg command or your editor’s line-number display is faster than counting lines by hand.

If you do not know the exact line and want to break at the beginning of a function body, consider using a name breakpoint and then stepping forward. Alternatively, most editors will show you line numbers, and you can set a source-line breakpoint once you see the exact number.

List breakpoints

Use:

(lldb) breakpoint list

This answers:

  • What breakpoints exist?
  • Are they enabled?
  • Did LLDB resolve them?
  • Where are they located?

The distinction between a breakpoint being created and having a resolved location is important.

A breakpoint can exist before LLDB can resolve it to executable code.

A sample output might look like:

Current breakpoints:
1: name = 'add', locations = 1, resolved = 1, hit count = 0
  1.1: where = first_session`first_session::add, address = 0x..., resolved, hit count = 0

2: file = 'src/main.rs', line = 20, locations = 1, resolved = 1, hit count = 0
  2.1: where = first_session`first_session::main, address = 0x..., resolved, hit count = 0

Read this carefully:

  • Breakpoint 1: name = 'add', locations = 1, resolved = 1: Breakpoint 1 is a name-based breakpoint. It resolved to one location.
  • 1.1: This is the specific location. A breakpoint with multiple locations would show 1.1, 1.2, and so on.
  • resolved: The breakpoint has been matched to a real address. An unresolved breakpoint would say pending.
  • hit count = 0: The breakpoint has not fired yet. After it fires once, the hit count becomes 1.

To see just one breakpoint:

(lldb) breakpoint list 1

For a screen-reader workflow, listing breakpoints one at a time is often more manageable than listing them all, especially in a session where many breakpoints have accumulated.

Pending breakpoints

If a breakpoint does not resolve, LLDB shows it as pending:

1: name = 'parse_config', locations = 0 (pending)

A pending breakpoint is not an error. It means LLDB has recorded the request but has not found a matching symbol in the currently loaded binaries.

There are several reasons a breakpoint might be pending:

  • The function does not exist: You may have misspelled the name, or the function may have been renamed during development.
  • The function was inlined: The compiler replaced the call with the function body, so no separate symbol exists.
  • The name does not match the compiled symbol: Rust name mangling can produce symbol names that do not exactly match the source name, especially for generic functions and methods.
  • The binary has not been loaded yet: If a dynamic library is loaded at runtime, symbols from it may not be known until the library loads.

The most useful response is to use image lookup:

(lldb) image lookup --name parse_config

This searches the loaded binaries for symbols that might match. If it finds one, you can see the exact mangled name and source location. If it finds nothing, the symbol is genuinely absent from the binary, and you need to either rebuild (if it should be there) or use a source-line breakpoint (if it was inlined).

Pending breakpoints are sometimes useful. If you know that a symbol will be loaded later, you can set the breakpoint now, and it will resolve when the symbol appears. This is common when debugging dynamically loaded plug-ins or shared libraries.

Delete a breakpoint

Delete one breakpoint:

(lldb) breakpoint delete 1

Delete all breakpoints:

(lldb) breakpoint delete

Be careful with the second form. It removes the entire breakpoint set.

For a screen-reader workflow, the safer pattern is always to list first, then delete by ID:

(lldb) breakpoint list
(lldb) breakpoint delete 3

This avoids the risk of accidentally removing breakpoints you still want. It also produces less output than re-creating a set of breakpoints after a mass deletion.

Disable and enable

Sometimes you want to keep a breakpoint but stop it from firing, without deleting it.

Disable a breakpoint:

(lldb) breakpoint disable 1

Re-enable a breakpoint:

(lldb) breakpoint enable 1

Disable all breakpoints:

(lldb) breakpoint disable

Re-enable all breakpoints:

(lldb) breakpoint enable

Disabled breakpoints remain in the list, showing disabled status. This is useful when you want to temporarily remove a breakpoint from the active set without losing its configuration, especially when the breakpoint is a conditional or has commands attached.

A common use case: you have a breakpoint at a function that fires very frequently during the initial setup of the program, but you only care about its calls later in the session. Disable it at startup, and enable it once the relevant phase begins.

Break on a method

Rust methods may have more complicated symbol names after compilation. Start with:

(lldb) breakpoint set --name method_name

If that is ambiguous or unresolved, investigate the symbols. Use:

(lldb) image lookup --symbol method_name

or:

(lldb) image lookup --name method_name

The exact symbol representation can depend on compilation and mangling.

For example, a method:

impl Config {
    fn load(&self) -> Result<Config, Error> { ... }
}

might appear in the symbol table as something like:

_ZN7my_crate6Config4load17h...

The image lookup output will show the demangled form, which helps you confirm you have found the right method.

The practical rule is:

Start with the human Rust name. If LLDB cannot resolve it, inspect the executable’s symbols.

In many cases, a source-line breakpoint at the first line of the method body is the most reliable approach. This is especially true when the method is inside a generic implementation, where the same name may exist for multiple concrete types.

Break on a source location first

When function-name matching becomes complicated, use:

(lldb) breakpoint set --file src/parser.rs --line 42

This avoids symbol-name ambiguity.

For source debugging, file-and-line breakpoints are often the most predictable starting point.

A source-line breakpoint is unaffected by name mangling, unaffected by monomorphization, and unaffected by whether the function is generic, a method, a closure, or an inlined helper. It simply maps one source location to whatever machine instructions correspond to that line.

When a name-based breakpoint is unresolved and you are unsure why, a source-line breakpoint is almost always the fastest fallback. It tells you at once whether the issue is with name matching or with the code itself.

Breakpoints in libraries

You can set breakpoints in library crates, provided their debug information is available.

(lldb) breakpoint set --name serde_json::from_str

For a fully qualified name like this, the crate prefix narrows the match. If the crate is compiled with debug information, the breakpoint will resolve.

When you break inside a library, the frame belongs to that library, not to your code. Use bt to see how you reached the library frame. The first frame belonging to your own crate is usually the one that called into the library, and that is where the value entering the library is most visible.

A common pattern for library debugging:

  1. Set a breakpoint at the call site in your own code.
  2. Inspect the arguments you are passing.
  3. If the arguments look correct, use step to enter the library.
  4. Watch what the library does with them.

This keeps the observation focused on your inputs and the library's response, without trying to understand the entire library internals.

Breakpoints in the standard library

With the rust-src component installed, you can often step into the standard library and inspect its behavior. For example:

(lldb) breakpoint set --name std::vec::Vec<T>::push

Whether this works depends on how the standard library was compiled and whether debug information is available for the specific instantiation. Standard-library code is often inlined into your own functions, so a name-based breakpoint may not resolve.

In practice, most Rust developers do not break inside the standard library directly. Instead, they break at their own code and observe what they pass to or receive from the standard library. This keeps the investigation focused and avoids stepping through code that is correct by construction.

If you do need to inspect standard library behavior, the most reliable approach is often to copy the relevant function into your own code temporarily, or to reproduce the situation in a small test program, where you have full control over the code.

Where to place breakpoints

Now that we know how to set breakpoints, the question becomes: where should we set them?

Inefficient breakpoints produce long, tedious debugging sessions. Efficient breakpoints produce short ones. A few rules of thumb:

Start at the boundary

Boundaries are the interfaces between components. They are places where data enters or leaves a function, module, or service. Boundaries are excellent breakpoint locations because you can see exactly what crosses the boundary.

Examples of boundaries:

  • A public API function that receives user input.
  • A function that parses a string into a domain object.
  • A function that calls a database or network service.
  • A function that formats a result for the user.

Set breakpoints at boundaries when you suspect data is being corrupted somewhere along the path. This gives you observations at both ends of each layer.

Start near the symptom

If you know that something goes wrong at a particular place, start there. Set a breakpoint at the location where the wrong behavior becomes visible. Then work backward.

The wrong output is the first observation. From there, trace back: what produced this output? What did that producer receive? And so on, until you find the first wrong state.

Start near the cause

If you have a hypothesis about where the cause lies, start near that hypothesis. Set a breakpoint at the function you believe is responsible, inspect its inputs and outputs, and see whether your hypothesis holds.

If the hypothesis is confirmed, you have found the bug. If it is refuted, you have learned something, and your next hypothesis will be sharper.

Avoid breaking everywhere

One of the most common mistakes in a debugging session is to set too many breakpoints at once. Twenty breakpoints fire twenty times, and the session becomes a blur of stops.

Start with one breakpoint. Run. Inspect. Continue. Then decide whether you need another breakpoint, and where.

This discipline keeps the session focused and makes each observation meaningful. If you catch yourself adding breakpoints faster than you are inspecting them, stop and reconsider whether you are making progress or simply producing more output.

Rust 2024 notes on breakpoints

The Rust 2024 edition introduces some changes that affect which breakpoint techniques are best in certain cases.

#[unsafe(no_mangle)] and extern "C"

In Rust 2024, the attribute is written #[unsafe(no_mangle)]. A function marked this way appears in the symbol table under its exact source name, without mangling. A name-based breakpoint on such a function resolves reliably. This is useful when debugging FFI, where you can set a breakpoint on the C-visible symbol name directly.

#[unsafe(no_mangle)]
pub extern "C" fn process_buffer(ptr: *mut u8, len: usize) -> i32 { ... }

A breakpoint on process_buffer will resolve cleanly, because the symbol name has not been changed by the compiler.

unsafe extern blocks

In Rust 2024, all extern blocks must be written as unsafe extern. The symbols declared inside come from an external library. When you set a breakpoint on a symbol from an unsafe extern block, the name is the external library's symbol name, not a Rust mangled name. Use image lookup if the name does not resolve directly.

unsafe_op_in_unsafe_fn

Rust 2024 warns when unsafe operations appear inside an unsafe fn without an explicit unsafe { ... } block. This is a source-level change, but it affects debugging in an interesting way: the explicit unsafe { ... } blocks give you natural breakpoint locations. A breakpoint at the opening of an unsafe block stops execution just before the unsafe operation begins, which is often exactly what you want when investigating unsafe code.

static mut restrictions

Rust 2024 disallows references to static mut. If you are debugging code that previously used &static mut, you will now see raw pointers or interior-mutability primitives instead. This does not affect how breakpoints work, but it does affect what you see when you inspect global state at a breakpoint.

A practical sequence

Putting it together, here is a practical sequence for setting breakpoints in a Rust program:

  1. Start with a single function-name breakpoint on the function you suspect, or a source-line breakpoint at the location you know is wrong.
  2. Run the program.
  3. Inspect the frame and locals at the first stop.
  4. Continue.
  5. If the first breakpoint was not informative, adjust it: use image lookup for name-based breakpoints that did not resolve, or move to a source-line breakpoint.
  6. If a breakpoint fires too often, disable it and re-enable it later, or make it conditional (covered in a later chapter).
  7. When you have located the origin of the bug, delete the temporary breakpoints so the list stays clean.

The goal is to keep the breakpoint list small and meaningful throughout the session. A clean breakpoint list is easier to reason about than a large one, and it makes the flow of the session easier to follow.

Summary

In this chapter, we covered breakpoints in LLDB for Rust:

  • Two ways to set a breakpoint: by function name (--name) and by source line (--file and --line). Each has strengths and weaknesses.
  • What the breakpoint output tells you: the ID, the resolved symbol, and the machine address.
  • Listing breakpoints with breakpoint list, and the distinction between resolved and pending breakpoints.
  • Pending breakpoints: why they occur and how to investigate them with image lookup.
  • Deleting, disabling, and re-enabling breakpoints, and the safe pattern of listing before deleting.
  • Breaking on methods, in libraries, and in the standard library, with guidance on when source-line breakpoints are more reliable than name-based ones.
  • Where to place breakpoints: start at a boundary, start near the symptom, start near the cause, and avoid breaking everywhere.
  • Rust 2024 notes: how #[unsafe(no_mangle)], unsafe extern blocks, unsafe_op_in_unsafe_fn, and static mut restrictions affect breakpoint strategies.

With breakpoints in hand, we can move on to the next layer: stepping through execution, reading frames and backtraces, and understanding the call stack.
