Chapter 17: Breakpoint Strategy and the First Wrong State

You now have the full vocabulary of Rust debugging with LLDB: breakpoints, stepping, frames, backtraces, value inspection, conditional breakpoints, watchpoints, threads, async, tests, unsafe, FFI. What remains is strategy: knowing where to put the breakpoint, and what question to ask when you get there.

This chapter is about that strategy. It is the difference between a debugging session that produces clarity and one that produces a long list of stops without a conclusion. The tools are the same; the discipline is different.

Two ideas thread through everything here:

  • Breakpoint strategy: the choice of where to stop is the most important decision in a debugging session.
  • The first wrong state: a bug is often best understood by finding the first place where reality diverges from expectation, not by examining the symptom.

The rest of the chapter is these two ideas, expanded.

Breakpoint strategy

Avoid setting twenty breakpoints immediately.

Start with one.

For example:

breakpoint set --name parse_config

Run.

Inspect.

Then ask:

What do I know now?

If necessary, add another breakpoint.

This creates a controlled investigation.

The single-breakpoint discipline

The most common mistake in debugging is to approach it as a bulk activity. The urge is to set many breakpoints, run once, and “see everything.” In practice, this produces a flood of output that is difficult to interpret and does not correspond to a specific question.

A better approach: each breakpoint is the answer to a question. Before setting it, state the question. For example:

  • “What value does parse_config receive?”
  • “Which branch is taken at this if?”
  • “What is the state of cache when handle_request is entered?”

Then place the breakpoint that answers that question. Run. Inspect. Close that question. Then decide whether you have another one.

This discipline scales. In a session with twenty breakpoints and no specific questions, the session becomes a matter of reading the debugger’s output passively. In a session with three breakpoints and three questions, the session becomes a matter of answering those questions directly.

The single-breakpoint discipline does not mean never using more than one breakpoint. It means: add a breakpoint when it answers a question you have. Otherwise, resist the urge.

Breakpoint at entry

A useful pattern is:

break at function entry
→ inspect arguments
→ step
→ inspect state
→ continue

This answers:

What does this function receive, and what does it do with it?

The entry breakpoint is the workhorse of debugging. Because arguments are always present at function entry, and because the entry point is easy to identify from source, this pattern is reliable in almost any context.

A refinement: if a function is called many times and you only care about one call, use a conditional breakpoint at entry. For example:

(lldb) breakpoint set --name handle_request
(lldb) breakpoint modify 1 --condition 'request.id == 42'

Now the entry breakpoint fires only for the call you care about. This is often the cleanest way to observe a specific invocation of a heavily-used function.

Breakpoint at state change

A more advanced pattern is:

break before mutation
→ inspect old state
→ step
→ inspect new state

This answers:

Exactly where did the state change?

This is often more useful than breaking at the eventual failure.

Consider a bug where a counter has the wrong value at the end of a program. There are two ways to investigate:

  1. Set a breakpoint where the counter is read (near the symptom), and try to figure out why it has the wrong value.
  2. Set a watchpoint on the counter, and let the debugger stop you the moment the value becomes wrong.

The second approach is usually faster. It identifies the exact transition where reality diverged from expectation, and it does so without requiring you to guess where the bug is.

A practical technique: even without a watchpoint, you can simulate one with a breakpoint before a suspected mutation. Inspect the old value, step to the line after the mutation, inspect the new value. If the new value is wrong, you have found the transition.

Breakpoint at the boundary

Many bugs become easier when debugging at boundaries.

Examples:

input
→ parser

parser
→ domain object

domain object
→ database

database
→ response

response
→ user interface

Set breakpoints at the boundaries.

Inspect what enters and what leaves.

This is a practical form of causal debugging.

Why boundaries are useful:

  • They are stable: the source line where a component calls another component changes less often than the internal logic of either component.
  • They have clear contracts: at a boundary, the expected input and output are usually easy to describe. Comparing the actual values with the expected values is direct.
  • They localize the bug: if the value entering a component is correct and the value leaving it is wrong, the bug is inside the component. If the value entering is already wrong, the bug is upstream.

A typical boundary investigation for a bug in a parser pipeline:

  1. Break at the entry to parse. Inspect the raw input.
  2. Break at the exit from parse. Inspect the parsed result.
  3. If the raw input is correct and the parsed result is wrong, the bug is inside parse.
  4. If the raw input is already wrong, the bug is in the code that produced it.

Two breakpoints, two inspections, one conclusion. This is a much better use of the debugger than stepping through the parser line by line.

How many breakpoints?

A practical guideline: one breakpoint per unanswered question. If you have three questions, three breakpoints. If you have one, one. If a breakpoint no longer answers a question, delete it.

During a long session, it is common to accumulate breakpoints that no longer serve a purpose. The list grows, and it becomes hard to remember what each one was for. Periodically run:

(lldb) breakpoint list

and remove the breakpoints that no longer correspond to an active question. This keeps the session focused and the output manageable.

The first wrong state

A powerful rule:

Find the first point where reality differs from your expectation.

Suppose the final output is wrong.

Do not start at the output.

Trace:

output
← transformation
← intermediate state
← input

At each boundary ask:

Is this value correct?

Eventually:

correct
correct
correct
wrong

The transition is the important location.

That is where you investigate.

Why this rule works

The first wrong state rule works because it turns a vague question (“Why is the output wrong?”) into a sequence of specific questions (“Is this value correct?”). Each specific question is answerable by a single inspection. The sequence of answers eventually localizes the bug to a small region of code.

The rule also protects against a common failure mode: starting the investigation at the symptom. The symptom is usually far from the cause. A function at the end of a long pipeline may report the wrong value because its input was wrong, not because its logic is wrong. Tracing the value backward from the symptom reveals where the wrongness enters the pipeline.

A simple illustration: suppose a JSON parser returns a malformed result. The symptom is in the parser. But the input to the parser might be truncated because an upstream reader stopped too early. Investigating the parser directly would miss this; tracing the input backward from the parser reveals the truncation.

A worked example

Consider a program that reads a configuration file, parses it, and uses the parsed value:

fn read_config(path: &str) -> Result<String, std::io::Error> {
    std::fs::read_to_string(path)
}

fn parse_config(raw: &str) -> Result<Config, ParseError> {
    // Parses `raw` into a Config
}

fn main() {
    let raw = read_config("config.toml").expect("read failed");
    let config = parse_config(&raw).expect("parse failed");
    println!("port: {}", config.port);
}

Suppose the program prints the wrong port. Several places could be responsible:

  • read_config returned the wrong contents.
  • parse_config parsed the contents incorrectly.
  • The config file itself has the wrong value.

Following the first-wrong-state rule:

  1. Set a breakpoint after the read_config call. Inspect raw. If raw does not contain the expected text, the bug is in read_config or in the file.
  2. If raw is correct, set a breakpoint after the parse_config call. Inspect config.port. If it is wrong, the bug is in parse_config.
  3. If both values are correct, the bug is in the println! or later.

Two breakpoints, two inspections, one conclusion. The bug is localized without stepping through the entire program.

The shape of a first-wrong-state investigation

Every first-wrong-state investigation follows the same shape:

  1. Identify the value whose wrongness you want to explain. This is usually a value that appears in the wrong output or a value that is checked incorrectly.
  2. Identify the chain of production for that value. Where does it come from? Who wrote it? What upstream values contributed to it?
  3. Set breakpoints along the chain, at the points where the value is produced or transformed.
  4. Inspect the value at each point, comparing against your expectation.
  5. Find the first point where the value is already wrong. That point is the origin.

The chain can be long, but the investigation converges. Each step is a specific question with a specific answer, and the chain terminates when the wrongness enters.

“Correct” means what you said it should be

A subtle but important point: “correct” only has meaning when you have stated what you expect. An inspection that produces a value, without a stated expectation, is not evidence about correctness. It is just a value.

Before each inspection, say out loud what you expect the value to be. For example:

  • “I expect raw to be the content of config.toml, which is port = 8080.”
  • “I expect config.port to be 8080.”
  • “I expect connection_count to be three at this point.”

Then inspect. The inspection confirms or refutes the expectation. If it confirms, move on. If it refutes, you have found a transition.

This discipline is what makes the first-wrong-state rule work. Without stated expectations, the rule has no teeth.

Handling multiple candidates

Sometimes, a value can be produced by more than one code path. For example, a config might be loaded from a file, from environment variables, or from a default. If the value is wrong, you first need to know which path produced it.

One technique: set breakpoints at each producing path. Run the program. The breakpoint that fires is the path that produced the value. Now you have localized the investigation to a single path.

Another technique: add a temporary field or marker to the value that records its origin. This is a source change, but it converts a runtime question (“which path?”) into a static one (“the value says it came from here”). Both techniques are valid; the choice depends on the complexity of the program.

When the first wrong state is not the bug

There is an important caveat: the first wrong state is not necessarily the bug. It is the first observable divergence from expectation. The actual bug may be earlier, in a value that was not checked, or in an assumption that was never validated.

For example, if a program produces a wrong output because of an incorrect comparison, the first wrong state may be the result of the comparison. But the actual bug may be in the definition of the comparison, in the types being compared, or in the source of one of the compared values.

To continue past the first wrong state:

  1. Once you have found a first wrong state, ask: what produced this value?
  2. Set breakpoints on the producers of that value.
  3. Repeat the investigation upstream.

In practice, this means that a first-wrong-state investigation often proceeds in two phases: first, from the symptom back to the first observable divergence; second, from that divergence back to the deeper cause.

Branching and looping

Two control-flow patterns deserve special attention because they are so common in real code: branches and loops. Each has a specific debugging discipline.

Debugging a wrong branch

Suppose:

if config.debug {
    enable_debug();
} else {
    enable_normal();
}

You want to know:

Which branch executes?

Break before the if.

Inspect:

config.debug

Then:

next

Now observe where execution goes.

You have directly answered the question.

No guessing.

Why this is a common bug

Wrong-branch bugs are common because the branch condition often depends on a value that was computed earlier. If that value is wrong, the branch takes the wrong path, and the symptom appears far from the branch.

For example, a config flag might be set by an environment variable that was misspelled, or by a parse that defaulted to the wrong value. The branch itself is correct; the input to the branch is wrong.

This is why breaking before the branch and inspecting the condition value is often the fastest way to investigate a wrong-branch bug. If the value matches the branch, the bug is downstream; if the value does not match the branch, the bug is upstream in the value’s production.

Branches with multiple conditions

Real branches often have multiple conditions:

if config.debug && cache.is_empty() && !force_refresh {
    enable_debug();
} else {
    enable_normal();
}

When inspecting, ask about each sub-condition separately:

(lldb) frame variable config.debug
(bool) config.debug = true

(lldb) frame variable cache
(...) cache = size=0 { }

(lldb) frame variable force_refresh
(bool) force_refresh = false

Each inspection narrows down which part of the condition is causing the wrong branch. The debugger’s expression evaluator can also compute the entire condition, but inspecting sub-conditions individually is often clearer and less error-prone.

Debugging loops

Suppose:

for item in items {
    process(item);
}

Set a breakpoint inside the loop.

At each stop:

(lldb) frame variable item

Then:

next

You can observe:

iteration 1
iteration 2
iteration 3
...

If the failure occurs only for one item, use a conditional breakpoint or inspect the iteration state.

Loops that run too many times

If a loop runs more iterations than expected, three questions arise:

  • Is the collection larger than expected?
  • Is the loop condition wrong?
  • Is something inside the loop modifying the collection or the condition?

Inspect the collection before the loop:

(lldb) frame variable items
(...) items = size=N { ... }

If N matches the expected size, the issue is likely the loop condition or a modification inside the loop. If N is larger than expected, the issue is upstream, in the code that produced the collection.

Modifications inside the loop are less common in Rust because the borrow checker usually prevents them, but they can happen with interior mutability, with channels that feed new items, or with raw pointers in unsafe code. In those cases, inspect the collection at each iteration to see whether it grows.

Loops that produce wrong values

If a loop produces the wrong output but the collection is correct, the bug is in the loop body. Two strategies:

  1. Narrow to a specific iteration: Use a conditional breakpoint such as item.id == 42 to focus on the problematic iteration. Then step through the loop body for that iteration only.
  2. Watch an accumulator: If the loop accumulates a value, set a watchpoint on the accumulator. The watchpoint will fire on each iteration, showing you the progression. If the value becomes wrong at some iteration, the watchpoint shows you exactly when.

The second strategy is often faster when the loop runs many iterations, because it avoids the need to identify the problematic iteration in advance.

Loops with early exit

Loops with break or return inside are a common source of surprise. The loop exits earlier than expected, and the code after the loop sees a partially processed state.

To debug:

  1. Set a breakpoint on the break or return line.
  2. Run the program.
  3. If the breakpoint fires, the loop is exiting early. Inspect the surrounding state to understand why.
  4. If the breakpoint does not fire, the loop is exiting by reaching the end of the collection or by a condition you did not anticipate.

For loops with return, the return value is often the key evidence. Inspect it at the return site to see what the loop decided.

State machines and enums

Rust enums are often used to represent state machines. Debugging state machines has a specific shape, and enums in the debugger provide exactly the evidence you need.

Debugging state machines

Rust enums are often used to represent state:

enum State {
    Idle,
    Loading,
    Ready,
    Failed,
}

When stopped:

(lldb) frame variable state

Ask:

Which variant?

How did execution reach this variant?

Which transition happens next?

Then place breakpoints at transition points.

This is especially useful for parsers, protocols, UI state, and asynchronous systems.

The pattern for debugging a state machine:

  1. Set a breakpoint in the code that transitions between states.
  2. At each stop, inspect the current state and the event that triggered the transition.
  3. If the state is wrong, trace backward to find the transition that set it.
  4. If the state is correct but the transition is wrong, the bug is in the transition logic itself.

Debugging enums

Enums are particularly valuable debugging landmarks.

If the program unexpectedly enters:

Failed

trace the transition:

Ready
→ operation
→ Failed

Then inspect the data carried by the variant.

The important question becomes:

What event caused the state transition?

Variants with data

When a variant carries data, the debugger shows the data along with the variant. This is often enough to identify the bug:

(lldb) frame variable result
(Result) result = Failed(ConnectionError { code: 1001, message: "timeout" })

The variant Failed carries a ConnectionError with a specific code and message. This is often a direct clue to the origin of the failure. The message “timeout” suggests the failing operation was a network call, and the code 1001 can be traced to the source of that error.

This is one of the best arguments for using data-carrying enums in Rust: they make the runtime state of the program self-describing, and the debugger exposes that state directly.

Nested enums

Enums can contain other enums. For example:

enum Response {
    Success(Data),
    Error(ErrorKind),
}

enum ErrorKind {
    Network(NetworkError),
    Parse(ParseError),
    Auth(AuthError),
}

In the debugger, a Response::Error(ErrorKind::Network(...)) is shown with both levels of nesting:

(Response) response = Error(Network(ConnectionRefused { host: "api.example.com" }))

The nesting tells you the category and the specific error in a single view. This is often enough to identify the cause without further investigation.

Comparing enum states across time

When debugging a state machine, it is useful to see how the state evolves. There are two techniques:

  • Break at each transition: Set a breakpoint at the transition function. At each stop, inspect the state. This gives you a sequence of states across time.
  • Log the transitions: If the state machine runs many transitions quickly, logging each transition (with a temporary println! or a proper logger) is often more practical than breakpoints. The logs give you the full sequence, and the debugger can then be used for a specific transition that looks suspicious.

The choice depends on the density of transitions. For a handful of transitions, breakpoints are fine. For a stream of transitions, logging is better.

Hypothesis-driven debugging

Do not randomly step through code.

State a hypothesis.

Example:

I think Config::load() returns None because the path is empty.

Then test it.

Set a breakpoint.

Inspect:

path

If the path is correct:

Hypothesis rejected.

Create the next hypothesis.

This produces:

Hypothesis
→ breakpoint
→ observation
→ confirmed/rejected
→ next hypothesis

That is debugging.

The shape of a good hypothesis

A good hypothesis has three properties:

  1. Specific: it names a specific value, a specific function, or a specific transition.
  2. Testable: it makes a prediction that can be confirmed or refuted by a single inspection.
  3. Falsifiable: it can be wrong. A hypothesis that cannot be wrong is not a hypothesis; it is an assumption.

Weak hypothesis:

“The parser is broken.”

Strong hypothesis:

“The parser returns Err(EmptyInput) because the input string is empty.”

The strong version predicts specific values: the error variant and the input state. One breakpoint and one inspection confirm or refute it.

When a hypothesis is rejected

A rejected hypothesis is not a failure. It is progress. You now know one thing that is not the cause, and you have narrowed the search space.

The risk is to spend too much time on a hypothesis that is very unlikely. A useful rule: if a hypothesis requires more than two or three inspections to test, it is too vague. Break it into smaller, more specific hypotheses that are easier to test.

Another useful rule: when a hypothesis is rejected, immediately state the next one. Do not leave a session without an active hypothesis. An active hypothesis keeps the investigation focused and prevents aimless stepping.

When a hypothesis is confirmed

A confirmed hypothesis is not necessarily the answer. It is a step. The confirmed hypothesis often raises a new question: what caused the value that the hypothesis predicted?

For example, if the hypothesis “the input is empty” is confirmed, the next question is: “why is the input empty?” The investigation continues upstream.

The process ends when the confirmed hypothesis is itself the cause: no further upstream investigation is possible, and the code can be changed to fix the behavior.

Hypothesis-driven versus exploratory debugging

Hypothesis-driven debugging is efficient when you have a specific idea about what might be wrong. It is less useful when you have no idea, and you need to explore the program to understand it.

For exploratory debugging, use a different approach:

  • Start with a breakpoint at a boundary and follow the execution path.
  • Inspect key values at each stop, building a picture of the program’s behavior.
  • When something looks surprising, form a hypothesis and switch to hypothesis-driven mode.

Both approaches have their place. The mistake is to use one when the other is appropriate: to hypothesize when you do not yet understand the program, or to explore when you already have a specific idea.

Documenting the investigation

For complex bugs, a written record of the investigation helps.

The debugging notebook

For difficult bugs, record four things:

Observation:
What actually happened?

Hypothesis:
What do I think causes it?

Evidence:
What did LLDB show?

Next experiment:
What will I inspect next?

Example:

Observation:
Config is None after load_config().

Hypothesis:
The config path is wrong.

Evidence:
path = "/home/user/project/config.toml"

Next experiment:
Break inside find_config().

This keeps the investigation externalized.

Why externalize

Debugging has a short-term memory problem. Each inspection produces a value that is meaningful in the context of the investigation, but the context fades as the session grows. After twenty inspections, it becomes easy to forget which values were confirmed, which hypotheses were rejected, and what question is currently open.

Writing down the observation, hypothesis, evidence, and next step keeps the context external. It also forces you to articulate hypotheses clearly, which often reveals that a hypothesis is not as specific as it should be.

A notebook can be as simple as a text file, a note in an editor, or a sticky note. The format matters less than the habit.

What to record

For each step of the investigation:

  • The specific value you inspected. Not “checked the config” but “inspected config.timeout, got 30”.
  • The expected value. Not just what you got, but what you expected. The comparison is where meaning comes from.
  • The hypothesis you were testing. This keeps the inspection from being random.
  • Whether the hypothesis was confirmed or rejected. This is the actual conclusion of the step.
  • The next step. Every step should end with a clear next action, even if that action is “give up on this hypothesis.”

With these elements, the notebook becomes a compact record of the investigation that you can return to later, share with a colleague, or convert into a regression test.

The notebook as a hypothesis ledger

One pattern that works especially well: keep a running list of hypotheses and mark them as confirmed or rejected. The list becomes a ledger of what you have learned.

Hypotheses:
  [rejected] The path is empty.
  [rejected] The file does not exist.
  [confirmed] The file exists but is empty.
  [open] The empty file is the wrong path.

At the end of the session, the ledger tells the whole story of the investigation. It also shows which hypotheses remain open, which is often the clue for the next session.

From notebook to regression test

Once the bug is fixed, the notebook provides the material for a regression test. The confirmed hypothesis and the evidence become the test’s assertion. The reproduction steps become the test’s setup.

For example, if the notebook says:

Hypothesis (confirmed):
  read_config("") returns Err(MissingPath).

Evidence:
  input = ""
  result = Err(MissingPath)

Then the regression test is:

#[test]
fn read_config_empty_path_returns_missing_path_error() {
    let result = read_config("");
    assert!(matches!(result, Err(ConfigError::MissingPath)));
}

The notebook reduces the work of writing the regression test to transcription. This is one of the ways debugging produces durable value beyond the immediate fix.

Rust 2024 notes on breakpoint strategy

A few Rust 2024 specifics affect how the strategies in this chapter are applied.

unsafe blocks as natural boundaries

Rust 2024 requires explicit unsafe { ... } blocks inside unsafe fn bodies. This creates natural boundaries in the source: the transition from safe to unsafe code is now marked explicitly. When investigating a bug that involves unsafe code, the opening of an unsafe block is a natural breakpoint: the state just before the unsafe operation begins is often what determines whether the operation is sound.

unsafe extern blocks as boundaries

Similarly, all extern blocks are now unsafe extern. The boundary between Rust and foreign code is more explicit in the source. When debugging an FFI bug, the call site of a foreign function is a natural breakpoint. The arguments and pointers passed to the call are the values you want to inspect.

static mut restrictions affect global-state investigations

Because Rust 2024 disallows references to static mut, global-state investigations must now go through raw pointers or interior-mutability primitives. When you inspect global state at a breakpoint, you will see the wrapper type (Mutex, AtomicUsize, UnsafeCell) rather than a bare reference. The value inside the wrapper is what you want to inspect, and it is often accessible as a field of the wrapper in the debugger.

Edition 2024 and enum layouts

Rust 2024 does not change the layout of enums. Enums still render as their variant plus the associated data. The strategies for debugging state machines remain the same. If anything, the edition’s tightening of rules around unsafe and FFI makes the state machines in those contexts slightly easier to inspect, because the boundaries are more explicit.

The core of strategic debugging

Two ideas summarize the strategic content of this chapter:

  1. Each breakpoint answers a question. If you cannot state the question, do not set the breakpoint. If a breakpoint no longer answers a question, delete it.
  2. Find the first wrong state. Trace values backward from the symptom, comparing them against expectations at each step. The first place where reality diverges is where the investigation continues.

These two ideas, applied consistently, are what separate a debugging session that converges from one that wanders. The commands are the same in both cases. The strategy is what makes the difference.

Summary

In this chapter, we moved from mechanics to strategy:

  • Breakpoint strategy: each breakpoint answers a specific question. Start with one, add others only when the previous ones are answered. Use entry breakpoints, state-change breakpoints, and boundary breakpoints depending on the question.
  • First wrong state: trace values backward from the symptom, comparing against expectations at each step. The first point where reality diverges is where the investigation continues.
  • Branch and loop debugging: for branches, break before the branch and inspect the condition. For loops, use conditional breakpoints or watchpoints on accumulators. For loops with early exit, break on the exit site.
  • State machines and enums: enums are debugger landmarks. Inspect the variant and its data at each transition. Data-carrying enums make the runtime state self-describing.
  • Hypothesis-driven debugging: state a specific, testable hypothesis, test it with one inspection, and update the hypothesis based on the result. Avoid vague or unfalsifiable hypotheses.
  • The debugging notebook: write down observations, hypotheses, evidence, and next steps. The notebook externalizes context and becomes the source material for a regression test once the bug is fixed.
  • Rust 2024 specifics: explicit unsafe blocks and unsafe extern blocks provide natural boundaries for breakpoints; static mut restrictions change what global state looks like in the debugger; enum layouts are unchanged.

The unifying principle: debugging is a controlled investigation. Each step is a question, an observation, and a conclusion. When this discipline is maintained, the debugger becomes a tool for producing clarity rather than for producing output.
