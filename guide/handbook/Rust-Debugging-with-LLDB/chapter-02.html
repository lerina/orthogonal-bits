Chapter 2: What Debugging Actually Is

Debugging is not guessing what the program does.

Debugging is observing what the program actually does.

When a program behaves incorrectly, there are usually several possible explanations.

The debugger lets you replace speculation with evidence.

A useful debugging loop is:

Observe
→ Stop
→ Locate
→ Inspect
→ Trace
→ Form a hypothesis
→ Test the hypothesis
→ Fix
→ Verify

LLDB is the instrument used to perform that investigation.

Rust adds another layer:

Rust source
→ Cargo
→ rustc
→ executable + debug information
→ LLDB

The debugger sees the compiled program.

Debug information connects that compiled program back to Rust source locations, functions, types, variables, and lines.

Debugging is observation, not guessing

Many programmers, when they first learn to debug, start by reading source code and forming a theory. They read a function, decide what it “should” do, and then search for the place where reality might diverge from that theory. This is a fine starting point, but it is not debugging. It is speculation.

Real debugging has a different shape. It starts from a concrete, observable behavior: the program printed the wrong number, returned None when it should have returned Some, hung during an .await, or panicked on some specific input. From that observation, we make a hypothesis, and then we run an experiment that the debugger can verify.

The experiment is what makes it debugging rather than guesswork. In an experiment, we do the following:

  • Choose one specific fact we want to establish.
  • Choose the smallest observation that will confirm or refute that fact.
  • Run the program under the debugger.
  • Look at the actual value at that point.
  • Update our understanding based on what we observed.

This is why the debugger matters. Without it, we are forced to reason about a program from the outside, using only the code and the observable output. With it, we can stand inside the program at a specific point in time and look at the actual state.

The debugging loop in detail

The loop we introduced at the beginning of this chapter is worth expanding, because each step has a specific purpose.

Observe

Something happened. The program printed the wrong output. A test failed. A panic occurred. A request timed out. The first task of debugging is to describe the observation clearly, in terms the debugger can help you investigate.

A weak observation:

“The program is broken.”

A strong observation:

“When I run the program with input config.json, it prints no config instead of loaded.”

The stronger observation gives you a place to attach a hypothesis, and it gives you a way to know when you have fixed the bug.

Stop

Debugging is easier when the program is paused. A breakpoint stops the program at a specific point so you can inspect the state. Without a stop, you are watching a moving target.

This is why almost every debugging session begins with a breakpoint. The breakpoint does not have to be perfect. It just has to be somewhere near the behavior you are investigating.

Locate

Once the program is stopped, ask where it is. Use:

(lldb) frame info

You want to know the function, the source file, and the line. If you do not know where you are, everything else you inspect will be difficult to interpret.

Inspect

Now that you know where you are, look at what you have. Use:

(lldb) frame variable

This shows the arguments and locals available in the current frame. This is the moment where you compare what the program thinks the state is with what you expected the state to be.

Trace

If the state you see is not yet enough, trace how it got there. Use:

(lldb) bt

The backtrace shows the call stack: the path of function calls that led to this point. It answers the question, “how did I get here?”

Form a hypothesis

Now you have evidence. Form a hypothesis that explains the evidence. A useful hypothesis is specific enough to be tested.

A weak hypothesis:

“The config loading is broken.”

A strong hypothesis:

“The environment variable CONFIG_PATH is empty, so find_config returns None.”

Test the hypothesis

Place a breakpoint where the hypothesis predicts the evidence. Inspect the state. If the prediction is confirmed, the hypothesis is supported. If it is refuted, you have learned something, and you can form a new hypothesis.

Fix

Once the cause is understood, change the code. A fix that is based on a verified cause is much more likely to work than a fix based on a guess.

Verify

Run the program again, with the same input that produced the bug, and confirm that the behavior has changed. If possible, add a regression test. A bug that cannot be reproduced by a test is easier to reintroduce.

Debugging is a skill, not a command list

It is tempting to think of debugging as a collection of commands. Run the program. Set a breakpoint. Print the variable. Step. Continue. That is a beginning, but it is not the whole skill.

The skill is in knowing which observation will be most informative, when to stop and inspect, what to inspect, and how to interpret what you see. Commands are the vocabulary. The sentence is written by the programmer.

You will get much further by learning a small number of commands and using them thoughtfully than by memorizing dozens of commands and using them randomly. The rest of this manual is designed with that in mind.

The cost of guessing

Why is guessing so costly? Several reasons:

  • Guessing produces plausible but wrong fixes. A guess that matches a symptom can easily produce a change that hides the symptom without addressing the cause. The bug returns in a slightly different form, and the original understanding was never corrected.
  • Guessing does not compose. If you fix one bug by guessing, you have not learned anything that transfers to the next bug. Debugging with evidence, on the other hand, builds a growing model of the system that makes future debugging faster.
  • Guessing damages trust. When you cannot explain why a fix works, you cannot defend it in a review. When you can explain it, with evidence from the debugger, the conversation is entirely different.
  • Guessing wastes time. It feels fast, because it lets you start typing immediately. But it often leads to a chain of changes that never quite find the cause. Evidence-based debugging feels slower at first, but almost always ends sooner.

The debugger is what makes evidence-based debugging practical. It is the instrument that turns “maybe” into “yes” or “no.”

Two kinds of questions: static and dynamic

Rust programmers ask two kinds of questions about their code, and it is important to keep them separate.

Static questions

Static questions are about the code as written, independent of any execution. For example:

  • Does this type implement this trait?
  • Does this value get moved or borrowed here?
  • Will this generic instantiate for the type I intend?
  • Is this unsafe block sound?
  • Does this lifetime satisfy the borrow checker?

These questions are answered by the compiler, by static analysis tools such as cargo check, by reading the source, and by running cargo clippy or Miri. LLDB is not the right instrument for these questions.

Dynamic questions

Dynamic questions are about a specific execution. For example:

  • Which concrete implementation of this trait method was actually called?
  • What was the value of this variable at this point in this run?
  • Which branch of this match was taken?
  • Which thread first observed this state as invalid?
  • Which .await suspended the task that is now hung?

These questions cannot be answered by static analysis alone. They require observing a program that is running. This is where LLDB comes in.

The distinction matters because a very common mistake is to reach for the debugger when the problem is static, or to reach for the compiler when the problem is dynamic. A borrow-checker error is a static problem: the fix is in the source, and the compiler already told you why. A variable holding the wrong value at runtime is a dynamic problem: the compiler has no opinion on it, and the debugger is the right instrument.

What LLDB sees

LLDB does not see Rust. It sees machine code, registers, memory, threads, and addresses. What makes LLDB useful for Rust debugging is the debug information that rustc embeds in the binary. Debug information tells LLDB how to map machine-level facts back to source-level concepts.

Concretely, when you write:

(lldb) frame variable greeting

what actually happens is:

  1. LLDB looks at the current program counter to determine the current instruction address.
  2. It consults the debug information to find which source-level frame and variable greeting corresponds to that address.
  3. It reads the runtime storage associated with greeting (a stack slot, a register, or a piece of a heap allocation).
  4. It reads the type of greeting from debug information.
  5. It renders the value using a Rust-aware pretty-printer, if one is available.

Every step in that sequence can fail. Debug information might be missing for a given function. The optimizer might have moved the variable into a register that is now reused for something else. The pretty-printer might not be loaded. Understanding what LLDB sees, and how it sees it, helps you interpret its output when things go wrong.

Why this shapes the rest of the manual

The rest of this manual is organized around two ideas:

  • Use the right tool for the question. Compiler diagnostics for static questions. LLDB for dynamic questions. Logging for long-running observations. Tests for reproducibility.
  • Use the debugger to gather evidence. Not to guess. Not to prove a hypothesis you already believe. But to observe what is actually true about a specific execution, so that your reasoning about the program is grounded in reality.

With that mental model, we can turn to the features of Rust that make this kind of debugging different from debugging a simpler language, and then to the actual mechanics of using LLDB on a Rust program.

Summary

In this chapter, we established the foundation for everything that follows:

  • Debugging is observation, not guessing. It replaces speculation with evidence gathered from the running program.
  • The debugging loop moves through observe, stop, locate, inspect, trace, hypothesize, test, fix, and verify.
  • Debugging is a skill, not a command list. The commands are the vocabulary; the sentences are written by the programmer.
  • Guessing is costly. It produces plausible but wrong fixes, does not compose, damages trust, and often wastes more time than evidence-based investigation.
  • Static and dynamic questions are different. Compilers and static tools answer static questions. LLDB answers dynamic ones.
  • LLDB sees machine code, and debug information is the translation layer that lets it map machine facts back to Rust source concepts.
