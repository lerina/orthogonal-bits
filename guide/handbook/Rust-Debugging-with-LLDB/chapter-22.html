Chapter 22: The Progressive Learning Path

Debugging with LLDB is a skill that develops in stages. You do not become fluent by reading one chapter; you become fluent by practicing one level until it feels natural, then moving to the next. This chapter lays out a path of ten levels. Each level introduces a small set of capabilities, describes what to practice, and defines what mastery looks like before moving on.

The path is progressive: each level builds on the previous ones. Do not skip ahead. The early levels are the foundation for the later ones; a session that skips the basics will not be productive when the problems become harder.

The good news is that each level is small. You can move from one level to the next in a few days of deliberate practice. By the time you reach Level 5, you will be more comfortable in the debugger than most Rust developers. By Level 10, you will be able to approach unfamiliar runtime behavior with the same confidence you bring to reading code.

Level 1 — Stop and Continue

Learn:

run
breakpoint set
continue
quit

Goal:

Stop the program at a known location.

What to practice

At this level, the goal is to become comfortable launching a Rust program under LLDB and stopping it at a specific point. The tools are minimal:

  1. Build a small Rust program with cargo build.
  2. Launch it with rust-lldb target/debug/your_program.
  3. Set a breakpoint with breakpoint set --name main.
  4. Run with run.
  5. Observe the stop. Read the frame info and the source location.
  6. Continue with continue.
  7. Quit with quit.

Repeat this cycle with several small programs. Each time, change the breakpoint location: a function name, a source line, a method. Observe that the program stops at the location you chose.

What mastery looks like

You have mastered Level 1 when:

  • You can launch any Rust binary under LLDB without needing to look up the command.
  • You can set a breakpoint on a function name and on a source line.
  • You can read the stop output and understand where the program has paused.
  • You can continue and quit cleanly.
  • You know how to verify which binary you are debugging.

This level feels trivial, but it is the foundation. Every subsequent level assumes you can reliably start a debug session and stop at a chosen point.

Common mistakes at this level

  • Debugging the wrong binary: always check the path. Workspaces, examples, and tests produce binaries in different directories.
  • Forgetting to rebuild: if you changed the source, rebuild before launching.
  • Using plain lldb instead of rust-lldb: you will lose the Rust pretty-printers.

Rust 2024 notes at this level

Nothing in the Rust 2024 edition changes the basic workflow of starting a session and setting a breakpoint. The binary format, debug information, and LLDB interaction are the same as in previous editions. Ensure your project builds with the 2024 edition (rustc 1.85.0 or later) before launching, and the rest is identical.

Level 2 — Navigate Execution

Learn:

next
step
finish

Goal:

Control how execution moves through Rust functions.

What to practice

The goal at this level is to develop an internal model of what each step command does. Practice with small programs where you can see each step's effect:

  1. Write a program with several small functions, each one calling the next.
  2. Break at the entry of the outer function.
  3. Use next to walk through the function without entering its calls.
  4. Use step to enter the first call, and observe the new frame.
  5. Use finish to return to the outer function.
  6. Repeat, choosing different combinations of next and step.

The mental model to internalize:

next   → stay at this level
step   → go down one level
finish → go up one level

What mastery looks like

You have mastered Level 2 when:

  • You can predict what each step command will do before you run it.
  • You can navigate through a call chain of three or four functions without getting lost.
  • You can use finish to exit a function when you have seen enough.
  • You know when stepping is unproductive (long loops, library code) and can switch to a breakpoint instead.

If you find yourself asking "which command was that again?" you are still at Level 2. That is fine; the goal is to make the commands automatic.

The question to ask

Before each step, ask:

Am I interested in what happens inside this call, or only in what happens after it?

If the answer is "inside," use step. If it is "after," use next. If you have seen enough of the current function, use finish.

This question becomes second nature with practice. Until it does, ask it explicitly.

When stepping fails

Sometimes, stepping behaves in unexpected ways:

  • Functions that are inlined: step may not descend, because there is no separate frame. Switch to a debug build if you need to step into them.
  • Library code: step into a standard library call may lead through many implementation frames. Use finish to get back to your code.
  • Iterator chains: step into an iterator method may descend into adapter machinery. Avoid stepping through chains; use named intermediates instead.
  • Async functions: step into an async fn call may not enter the function body the way you expect; the future is returned immediately.

Recognizing these situations saves a great deal of frustration later.

Rust 2024 notes at this level

Because Rust 2024 requires explicit unsafe { ... } blocks inside unsafe fn bodies, stepping through unsafe code now produces more predictable transitions: the safe/unsafe boundary is visible in the source, and step typically moves between the two consistently. This is a small but real improvement in stepping reliability for code that involves unsafe.

Level 3 — Inspect State

Learn:

frame variable
frame info

Goal:

See what the current function actually knows.

What to practice

The goal at this level is to become comfortable inspecting the state at any point where the program is stopped. Practice with programs that have a variety of local variables:

  1. Write a program with several functions, each having two or three locals of different types: integers, strings, booleans, structs, vectors.
  2. At a breakpoint in each function, inspect the locals one at a time: 
    frame variable count
frame variable name
frame variable active
frame variable user
  3. Practice inspecting nested fields: 
    frame variable config.server.port
frame variable user.email
  4. Compare the value shown by the debugger with the value you expected from the source.

What mastery looks like

You have mastered Level 3 when:

  • You can inspect any local variable in the current frame with a single command.
  • You can inspect a nested field directly, without dumping the entire parent struct.
  • You understand the difference between frame variable and expression, and you reach for frame variable by default.
  • You recognize the pretty-printed forms of Rust types: strings in quotes, vectors as lists, enums as variant plus data.
  • You know what to do when a value appears as <optimized out>.

The most common question

The question you will ask most often at this level is:

Is this value what I expected it to be?

Inspection without a stated expectation is meaningless. Before each inspection, state what you expect. If the value matches, move on. If it does not, you have found evidence.

This discipline is what turns inspection into debugging, and it is the foundation for the first-wrong-state rule described in Chapter 17.

When a value is not available

If frame variable x reports that x is not available, the cause is almost always one of the following:

  • Wrong frame: x is defined in a different function. Use bt and frame select to move to the correct frame.
  • Wrong scope: x has not been declared yet at this point, or has gone out of scope. Check the source line.
  • Optimized out: x is not stored in a form the debugger can read, usually in optimized builds. Switch to a debug build, or restructure the code so x is genuinely needed at this point.

Each cause suggests a specific remedy. Recognizing the cause avoids wasting time trying different commands.

Rust 2024 notes at this level

The Rust 2024 edition does not change frame variable or the pretty-printer output. Enum variants, struct fields, and string values render exactly the same way as in earlier editions. The one small change worth noting is that unsafe blocks are now more explicit in source, which means the source locations you inspect (via frame info) will more often correspond to a specific unsafe block rather than a whole function.

Level 4 — Understand the Call Stack

Learn:

bt
frame select
up
down

Goal:

Understand how execution reached the current location.

What to practice

The goal at this level is to become comfortable reading backtraces and navigating between frames. Practice with programs that have a call depth of at least three:

  1. Write a program with a call chain: main calls outer calls middle calls inner.
  2. Set a breakpoint inside inner.
  3. Run. Inspect the backtrace with bt.
  4. Identify each frame by its function name.
  5. Use frame select 2 to move to the frame for outer.
  6. Inspect the locals of outer.
  7. Use up and down to move back and forth.
  8. Return to frame 0 with frame select 0.

The crucial insight: selecting a frame does not change the execution point. It only changes the target of inspection. You can look at any frame in the stack without moving execution.

What mastery looks like

You have mastered Level 4 when:

  • You can read a backtrace and identify which frames belong to your own code and which belong to libraries or runtime machinery.
  • You can select any frame and inspect its locals without confusing yourself about where execution is actually stopped.
  • You can move up and down the stack efficiently, without needing to look up the frame numbers.
  • You understand that up and down change the selected frame, not the execution point.

Reading a backtrace with confidence

A useful pattern for reading a backtrace in a Rust program:

  1. Start at the top (frame #0). This is where execution is currently stopped.
  2. Move down the stack, looking for the first frame whose name contains your crate's name.
  3. That frame is usually the most interesting one, because it is where your code begins doing something on this path.
  4. Below that frame are the runtime and library frames. Unless you are debugging the runtime itself, you can usually ignore them.

With practice, this pattern becomes automatic. You will glance at a backtrace and immediately see the frames that matter.

When frames are missing

If a backtrace seems to be missing frames, the cause is usually one of the following:

  • Inlining: the missing function was inlined into its caller. This happens frequently in optimized builds.
  • Missing debug info: the missing frame belongs to a library compiled without debug information.
  • Tail calls: the compiler replaced a call with a jump, so there is no separate frame for the callee.
  • Corrupted stack: the program has overwritten its stack, which is a serious bug. Unwinding the stack can then produce nonsense.

Each cause suggests a different remedy. Inlining and missing debug info are expected; corrupted stacks are a bug in themselves.

Rust 2024 notes at this level

Frames for functions exposed with #[unsafe(no_mangle)] now appear under their exact source names in Rust 2024, which makes them easy to identify in a backtrace. Ordinary Rust functions appear under their mangled names, which LLDB demangles for display. The overall shape of the backtrace—application frames at the top, runtime frames at the bottom—is unchanged.

Level 5 — Investigate Rust Values

Practice with:

struct
enum
Option
Result
references
mutable references
Vec
String
HashMap

Goal:

Become comfortable inspecting real Rust state.

What to practice

The goal at this level is to become fluent with the debugger’s view of Rust’s common types. Practice with a single program that exercises each type:

  1. Define a struct with a string, an integer, and a boolean field. Inspect it with frame variable and inspect each field individually.
  2. Define an enum with a data-carrying variant. Inspect it and confirm the variant name and data are visible.
  3. Create an Option<T> with a Some value, and a separate one with None. Inspect both.
  4. Create a Result<T, E> with an Ok value and another with a custom error variant. Inspect both.
  5. Create a &T and a &mut T. Inspect the referenced values.
  6. Create a Vec, a String, and a HashMap. Inspect each one and confirm the pretty-printer’s output matches your expectation.

Repeat until the display of each type is familiar. The pretty-printer output is the debugger’s interface to Rust’s types; knowing what to expect from each one saves time in every subsequent session.

What mastery looks like

You have mastered Level 5 when:

  • You can look at a Vec and immediately see its length and elements.
  • You can look at an enum and immediately identify its active variant and its data.
  • You can inspect an Option or Result and tell whether it is Some/None or Ok/Err.
  • You know how to inspect a field of a struct inside a reference, and how to dereference explicitly when needed.
  • You recognize the raw field layout of a String or Vec if the pretty-printer is not loaded, and you know how to fix the situation by using rust-lldb.

The pretty-printer contract

The Rust pretty-printers in LLDB present a view of each type that is intended to be human-readable. The contract is:

  • Strings render as their text content, in quotes.
  • Sequences render as their elements, with the length shown.
  • Enums render as their variant name plus the variant’s data.
  • References render as the value at the other end of the pointer.
  • Options and Results render as their variants with the inner values visible.

When the pretty-printer’s output does not match this contract, the most common cause is that the pretty-printers are not loaded. The fix is to launch via rust-lldb instead of plain lldb.

Going beyond pretty-printing

Sometimes the pretty-printer’s view is not enough. For example, you may need to see the raw pointer of a Vec, or the capacity field separately from the length. At this level, learn to access the raw fields:

frame variable items.ptr
frame variable items.len
frame variable items.cap

For a String, which wraps a Vec<u8>:

frame variable s.vec.ptr
frame variable s.vec.len
frame variable s.vec.cap

This level of detail is rarely needed in safe code, but it is essential when debugging unsafe code that manipulates these types directly. Practicing at this level prepares you for Chapter 16's material.

Rust 2024 notes at this level

Because Rust 2024 discourages references to static mut, global state now appears in the debugger as raw pointers or interior-mutability wrappers. If you inspect a global variable, you may see a Mutex, AtomicUsize, or UnsafeCell rather than a bare reference. This is expected: the wrapper is the source-level representation, and the debugger shows the wrapper’s internal value, which is what you want to inspect.

Level 6 — Conditional Investigation

Learn:

breakpoint modify --condition
watchpoint

Goal:

Stop only when the interesting state occurs.

What to practice

The goal at this level is to move beyond unconditional breakpoints and into the territory of conditions and watchpoints. Practice with programs that have repeated behavior:

  1. Write a loop that runs many times and processes items with an ID. Introduce a bug that only appears for one specific ID.
  2. Set a breakpoint inside the loop and observe that it fires many times.
  3. Add a condition: breakpoint modify 1 --condition 'item.id == 42'. Now the breakpoint fires only for the interesting case.
  4. Write a program with a counter that becomes wrong at some point. Set a watchpoint on the counter: watchpoint set variable counter. Observe the stop when the counter changes.
  5. Inspect the backtrace at the watchpoint to identify the code that changed the value.
  6. Try a conditional watchpoint: watchpoint modify 1 --condition 'counter > 100'.

What mastery looks like

You have mastered Level 6 when:

  • You can add a condition to a breakpoint and remove it later.
  • You know that conditions must be simple to evaluate reliably in Rust. You use field accesses and primitive comparisons rather than method calls or iterators.
  • You can set a watchpoint on a variable and observe the moment it changes.
  • You know the limits of watchpoints: they require a stable address, they do not work for temporaries or optimized-out values, and they are impractical for values that change very frequently.
  • You can choose between a conditional breakpoint and a watchpoint for a given problem. Use a conditional breakpoint when you know the location; use a watchpoint when you know the value.

Conditions as a narrowing tool

Conditions are a form of interactive filtering. Instead of running a loop thousands of times and inspecting each iteration manually, you describe what you are looking for with a condition, and the debugger does the filtering for you.

A useful heuristic: if you find yourself pressing continue more than a handful of times in a session, consider whether a condition could have told the debugger to stop only when the interesting case occurred. The condition might take a minute to write, but it can save an hour of manual continues.

Watchpoints as a detection tool

Watchpoints answer a specific question: “when did this value change?” This is different from the question answered by a conditional breakpoint (“when execution reaches this point and a condition holds”). Watchpoints are particularly useful when:

  • You know a value should be immutable, but it is being changed by something you cannot identify.
  • You know a value should remain constant over a period, but it changes at some point during that period.
  • You suspect a state corruption but cannot guess where it happens.

Watchpoints give you the moment of change without requiring you to guess the code that changed the value. This makes them one of the most powerful debugging tools in LLDB.

Rust 2024 notes at this level

For Rust 2024, watchpoints on interior-mutability primitives behave slightly differently than watchpoints on plain variables. A watchpoint on a Mutex watches the mutex structure, which contains both the lock and the wrapped value; a watchpoint on the inner value watches only the value. Use the inner value when you want to detect changes to the value itself.

Conditions that reference fields of a struct through a raw pointer may need an explicit dereference ((*ptr).field == value). This is normal and expected.

Level 7 — Threads

Learn:

thread list
thread select
thread backtrace all

Goal:

Understand concurrent execution.

What to practice

The goal at this level is to become comfortable with multithreaded programs under the debugger. Practice with programs that spawn several threads:

  1. Write a program that spawns three named worker threads, each running a loop.
  2. Set a breakpoint inside the worker function.
  3. Run. When the first breakpoint hits, inspect the thread list with thread list.
  4. Note which thread is selected. Inspect its backtrace with bt.
  5. Continue. When the breakpoint hits again, the selected thread may be different.
  6. Use thread select 2 to switch to a specific thread and inspect its state.
  7. Use thread backtrace all to see all threads at once.

What mastery looks like

You have mastered Level 7 when:

  • You can list threads, identify the selected one, and switch between them.
  • You can read a multithreaded backtrace and identify which thread belongs to which role.
  • You name threads in your own programs (using thread::Builder::new().name(...)), and you know that named threads are much easier to debug than unnamed ones.
  • You can recognize the signature of a deadlock: two or more threads blocked on lock acquisitions, with no progress possible.
  • You understand that a stopped thread is just paused, not terminated; continue resumes all threads.

Naming as a practice

Naming threads is one of the highest-leverage habits in concurrent debugging. It costs almost nothing in source code and pays off enormously when a session becomes complex:

thread::Builder::new()
    .name("cache-refresher".to_string())
    .spawn(|| { /* ... */ })
    .expect("spawn failed");

With named threads, thread list produces output that is immediately understandable:

* thread #1: name = 'main'
  thread #2: name = 'cache-refresher'
  thread #3: name = 'log-writer'
  thread #4: name = 'request-handler-0'

Without names, the list is a wall of thread numbers and OS IDs, which is much harder to reason about.

Deadlocks and inspection

When a program hangs, the debugger can confirm a deadlock. The technique:

  1. Run the program. When it hangs, interrupt the debugger (usually with Ctrl+C).
  2. Run thread list to see the threads.
  3. Run thread backtrace all to see where each thread is.
  4. Look for threads blocked in lock acquisition functions such as Mutex::lock, RwLock::read, or RwLock::write.
  5. Identify which thread holds the lock that another thread is waiting for.

The debugger does not diagnose the deadlock for you, but it provides the evidence. From the backtraces, the cycle of dependencies becomes visible.

Rust 2024 notes at this level

Rust 2024 stabilizes std::thread::scope more prominently, which allows threads to borrow data from the enclosing scope. Scoped threads behave like ordinary threads under the debugger: they appear in thread list, and their names (if set) appear alongside their IDs. The guarantee that scoped threads finish before the enclosing scope ends makes their behavior slightly more predictable, which is helpful in debugging.

Level 8 — Async Rust

Practice:

async fn
.await
Tokio tasks
runtime threads

Goal:

Distinguish application execution from executor machinery.

What to practice

The goal at this level is to become comfortable with the shape of an async backtrace. Practice with a small Tokio program:

  1. Write an async function that awaits a tokio::time::sleep and then does some work.
  2. Set a breakpoint inside the function.
  3. Run. Inspect the backtrace with bt.
  4. Identify which frames belong to your own crate, which to the Tokio runtime, and which to the OS thread.
  5. Inspect the local variables in the function. Note that the async state machine’s fields include the state and any captured values.
  6. Continue. The task may suspend and resume. When the breakpoint hits again, inspect the state to see how it changed.

What mastery looks like

You have mastered Level 8 when:

  • You can read an async backtrace and separate application frames from runtime frames without confusion.
  • You know that thread list shows OS threads, not tasks. A single thread may execute many tasks.
  • You set breakpoints at application-level boundaries rather than trying to step through runtime machinery.
  • You know that stepping into an async fn call does not enter the function body; it returns a future.
  • You can name tasks (using tokio::task::Builder or equivalent) so their identity is visible in logs and the debugger.
  • You recognize that a panicking task is caught by the runtime in many configurations and appears as an Err from the JoinHandle.

The state-machine mental model

The key insight for async debugging is that an async fn is compiled into a state machine. Each .await is a potential suspension point, and the compiled code stores the state between suspensions.

When you stop inside an async function, the frame you see is the poll method of the state machine, not a conventional function call. The state machine’s fields include:

  • The current state (a variant representing where in the function execution is).
  • Any values that need to survive across suspension points.
  • The future being awaited, if the function is currently suspended.

Understanding this structure is what makes async backtraces readable. Once you see the state machine, the runtime frames between application frames become predictable.

When to switch to logging

Async code is often the point where logging becomes more valuable than the debugger. The reasons:

  • Many tasks may be in flight, and the debugger only shows the ones currently being polled.
  • A single task may suspend and resume many times, and following it through all those resumptions in the debugger is impractical.
  • The runtime may migrate a task between threads, making the thread identity unstable.

A practical workflow for async debugging: use breakpoints to inspect the state at a specific point, and use logging to understand the flow across many points. Neither tool alone is sufficient; together they cover both perspectives.

Rust 2024 notes at this level

Rust 2024 stabilizes async closures and gen blocks. Both compile into state machines similar to async fn. The debugging techniques you practice at Level 8 apply equally to async closures and gen blocks: identify the state machine’s poll method, separate application frames from runtime frames, and set breakpoints at application boundaries.

Level 9 — Advanced Runtime Investigation

Learn:

expression
memory read
image lookup
breakpoint commands

Goal:

Investigate cases where ordinary source-level debugging is insufficient.

What to practice

The goal at this level is to add the advanced tools to your repertoire for cases where the standard ones are not enough. Practice with programs that involve FFI, unsafe code, or unfamiliar libraries:

  1. Write a small Rust program that calls a C function through FFI. The C function takes a pointer and a length.
  2. At a breakpoint before the FFI call, inspect the arguments with frame variable.
  3. Use memory region on the pointer to confirm it is in a valid region.
  4. Use memory read to inspect the bytes at the pointer.
  5. Set a breakpoint on the C function. If it is not resolvable by name, use image lookup --name.
  6. Attach commands to a breakpoint with breakpoint command add to automatically inspect state at each hit.
  7. Use expression for simple derived values, such as computing the total length of a pointer plus an offset.

What mastery looks like

You have mastered Level 9 when:

  • You can inspect memory at a pointer and interpret the bytes in the correct format.
  • You can verify a pointer’s validity with memory region before dereferencing it.
  • You can find symbols with image lookup when a name-based breakpoint does not resolve.
  • You can attach commands to a breakpoint to automate repetitive inspections.
  • You use expression for simple derived values, but you understand its limits and prefer frame variable for inspection.
  • You can follow a Rust-to-C boundary through the backtrace and inspect the arguments on both sides.

When advanced tools are necessary

The advanced tools come into play in a few specific situations:

  • FFI: the debugger cannot rely on Rust source for the C side, so memory inspection and symbol lookup become necessary.
  • Unsafe code: the invariants are not checked by the compiler, so inspecting pointers, lengths, and raw memory is the only way to verify them.
  • Libraries without debug info: source-level inspection is limited, so you fall back to assembly and memory inspection.
  • Repetitive observations: when a breakpoint fires many times and you want the same inspection at each, breakpoint commands automate it.

Each of these situations corresponds to a scenario where the ordinary tools are insufficient. The advanced tools fill the gap.

Combining advanced tools with Miri and sanitizers

LLDB is not the only advanced tool. Miri and sanitizers (ASan, TSan, MSan, UBSan) complement the debugger for unsafe code:

  • Miri detects undefined behavior in unsafe code by interpreting the program at the MIR level. Use Miri to find the bug, then LLDB to inspect the state at the moment it occurs.
  • AddressSanitizer detects memory errors such as use-after-free and buffer overflow. Use ASan to catch the error, then LLDB to inspect the state.
  • ThreadSanitizer detects data races. Use TSan to confirm a race, then LLDB to inspect the racing threads.

At this level, learn to combine LLDB with these tools rather than relying on the debugger alone for unsafe and FFI debugging.

Rust 2024 notes at this level

Rust 2024 requires unsafe extern for all external blocks. This makes the boundary between Rust and foreign code more explicit in the source, which helps you know where to set breakpoints and what to inspect. The FFI arguments are passed the same way as before; only the source syntax has changed.

The new unsafe attributes (#[unsafe(no_mangle)], #[unsafe(export_name = "...")]) affect symbol names. Use image lookup to confirm the exact name under which a function appears in the binary.

Level 10 — Debugging as Problem Solving

Stop thinking:

Which LLDB command should I use?

Start thinking:

What fact do I need to establish?

Then choose the command.

What to practice

At this level, the practice is no longer about individual commands. It is about the discipline of debugging as a whole:

  1. Take a real bug in a project you maintain or contribute to.
  2. Write down the observation, the hypothesis, and the prediction before touching the debugger.
  3. Choose the tool that fits the question, not the tool you enjoy using.
  4. Apply the first-wrong-state rule: trace values backward from the symptom until you find the first divergence.
  5. Keep a notebook of the investigation.
  6. Convert the confirmed hypothesis into a regression test.

Repeat with several bugs. The goal is not to use more commands, but to use fewer commands more precisely. The best debugging sessions use few breakpoints but ask sharp questions.

What mastery looks like

You have mastered Level 10 when:

  • You approach a bug by first asking what kind of question it is, then choosing the tool.
  • You can articulate a hypothesis, a prediction, and an experiment before you set a breakpoint.
  • You find the first wrong state reliably, without wandering through the program.
  • You can use the debugger alongside logging, tests, Miri, and profiling, choosing each when it fits.
  • You document your investigations, and your documentation is useful months later.
  • You turn every fixed bug into a regression test.
  • You recognize the situations where the debugger is not the right tool, and you switch to logging, tests, profiling, or Git history without hesitation.

The question that matters

At Level 10, the fundamental question is:

What fact do I need to establish?

Everything else follows from this question. Once the fact is clear, the tool is often obvious. If the fact is “what value does this variable hold?”, use frame variable. If the fact is “when did this value change?”, use a watchpoint. If the fact is “which branch was taken?”, break before the branch. If the fact is “how often does this happen?”, use logging. If the fact is “does this violate the semantics of unsafe Rust?”, use Miri.

The command is the last thing to choose, not the first. Commands are the vocabulary; the fact is the sentence.

Beyond commands

At this level, the debugger becomes an instrument rather than a puzzle. You no longer think about which command to type; you think about the fact you want to establish, and the command follows. This is the same shift that happens in any skill: from thinking about the mechanics of the tool to thinking about the problem the tool is helping to solve.

It is the shift from playing scales to playing music. Both are necessary, and the scales come first. But at some point, the scales become automatic, and the music becomes the point.

Rust 2024 notes at this level

At Level 10, the specific edition matters less than the discipline. Rust 2024 introduces new rules around unsafe extern, unsafe attributes, static mut, and new language features (async closures, gen blocks). Each of these changes the surface of the code that appears in the debugger, but none of them changes the fundamental questions you ask or the fundamental facts you need to establish. The edition is a source-level detail; the discipline is what makes the session productive.

The shape of the path

The ten levels are not a test. They are a map. Most developers do not move through them in strict order, and most are comfortable at different levels for different kinds of code. That is fine. The point is to know which level you are at for a given situation and to practice the level above it deliberately.

Typical time at each level

A rough sense of how much practice each level requires:

  • Levels 1–3: A few days of practice each. These are the basics of launching, stepping, and inspecting.
  • Levels 4–5: A week or two each. Reading backtraces and inspecting Rust types become second nature with repetition.
  • Levels 6–7: A few weeks each. Conditions, watchpoints, and threads require deliberate practice with realistic programs.
  • Level 8: A month or more. Async debugging is the hardest level for most developers because the mental model is unfamiliar.
  • Level 9: Ongoing. Memory inspection, symbol lookup, and breakpoint commands are learned as needed for specific problems.
  • Level 10: Continual. Debugging as problem solving is a lifelong practice, not a milestone.

These are not deadlines. They are rough expectations. Some developers move faster, some slower. What matters is deliberate practice at each level.

Signs of fluency

You can tell you are fluent at a level when you no longer think about the commands at that level. They become part of your automatic vocabulary. When you reach for a watchpoint, you do not think “is it watchpoint set variable or watchpoint set expression?”; you know, and your fingers type it while your mind is on the problem.

This automaticity is what frees up mental resources for the higher-level skills: hypothesis formation, experiment design, and interpretation of evidence. The goal of the progressive path is to push the mechanics below the level of conscious attention, so that debugging becomes about the problem, not about the tool.

Revisiting levels

Fluency is not permanent. If you have not used the debugger for a few months, you may find yourself back at Level 2 or Level 3 for a session or two. This is normal. The commands return quickly, and the higher-level skills are not lost.

When returning after a break, spend a session or two on a small program, practicing the early levels. The investment of an hour to sharpen the basics pays off many times over in the sessions that follow.

The arc of the path

Looking across the ten levels, a clear arc appears:

  1. Levels 1–3: The fundamentals. Stop, step, inspect.
  2. Levels 4–5: The Rust-specific skills. Backtraces, types, enums, Option, Result.
  3. Levels 6–7: The narrowing skills. Conditions, watchpoints, threads.
  4. Level 8: The async skills. State machines, runtimes, task management.
  5. Levels 9–10: The advanced skills. Memory, FFI, and the discipline of debugging as problem solving.

The arc moves from “operating the debugger” to “using the debugger as an instrument.” The early levels are about learning to use the tool; the later levels are about knowing when and why to use it.

Rust 2024 notes on the learning path

The Rust 2024 edition does not change the structure of the learning path. It changes some source-level details that appear at each level:

Levels 1–3 and Rust 2024

Launching, stepping, and inspecting work the same as before. The debug information format is compatible with LLDB; the pretty-printers are the same. No changes are needed for these levels.

Levels 4–5 and Rust 2024

Backtraces and value inspection look the same as before, with one small addition: functions exposed with #[unsafe(no_mangle)] appear under their exact source names, which can make certain frames easier to identify. Enum layouts, struct field layouts, and Option/Result representations are unchanged.

Levels 6–7 and Rust 2024

Conditions and watchpoints are unaffected by the edition. Threads behave the same way. Scoped threads, stabilized more prominently in Rust 2024, are just threads under the debugger; their guarantees make their behavior slightly more predictable.

Level 8 and Rust 2024

Async closures and gen blocks are new in Rust 2024, but they use the same underlying state-machine model as async fn. The debugging techniques you practice at Level 8 apply to all three. The main difference is that the compiler-generated names for async closures and gen blocks may include additional markers, but the structure is the same.

Levels 9–10 and Rust 2024

The advanced tools work the same way, but the source you inspect has changed. unsafe extern blocks make the FFI boundary more explicit, which is a small improvement for FFI debugging. The new unsafe attributes change symbol names, which affects symbol lookup. The restriction on static mut changes how global state appears in the debugger, but not the fundamental technique.

At Level 10, the edition fades into the background. What matters is the discipline.

Summary

In this chapter, we laid out a ten-level path for learning Rust debugging with LLDB:

  • Level 1 — Stop and Continue: launch a binary, set a breakpoint, run, continue, quit.
  • Level 2 — Navigate Execution: next, step, finish. The three directions of source-level navigation.
  • Level 3 — Inspect State: frame variable and frame info. Reading local state and comparing against expectations.
  • Level 4 — Understand the Call Stack: bt, frame select, up, down. Reading backtraces and navigating between frames.
  • Level 5 — Investigate Rust Values: structs, enums, Option, Result, references, Vec, String, HashMap. Becoming fluent with the pretty-printers’ view of Rust types.
  • Level 6 — Conditional Investigation: conditions and watchpoints. Stopping only when the interesting state occurs.
  • Level 7 — Threads: listing threads, selecting threads, reading multithreaded backtraces, recognizing deadlocks.
  • Level 8 — Async Rust: async functions, .await, Tokio tasks, runtime threads. Separating application execution from executor machinery.
  • Level 9 — Advanced Runtime Investigation: expression, memory read, image lookup, breakpoint commands. Investigating cases where source-level debugging is not enough.
  • Level 10 — Debugging as Problem Solving: shifting from “which command?” to “what fact do I need to establish?”

Each level builds on the previous ones. Each level has a defined goal and a clear sign of mastery. The path is not a race; it is a progression of skills that compound over time.

The unifying principle: fluency at each level frees mental resources for the next. The goal is not to know all the commands; the goal is to make the commands automatic, so that debugging becomes about the problem, not about the tool.
