Chapter 20: Output Discipline and Screen-Reader Workflow

A debugger is an instrument for producing evidence, and evidence is only useful when it can be read. LLDB is capable of producing a very large amount of output: whole structs, nested collections, multi-threaded backtraces, and long histories. Much of that output is useful in small doses, but overwhelming in bulk. For a screen-reader workflow, the problem is sharper still: output that is easy to scan visually can be impossible to parse when spoken aloud.

This chapter is about managing the debugger’s output so that the evidence remains readable. The ideas are useful to any user of the debugger, but they are especially important for screen-reader users, and they have been tuned with that audience in mind.

The chapter has four main parts: output discipline, the screen-reader workflow, the repeat-on-Enter behavior, and the help and completion system. Each of these is a tool for keeping the conversation with the debugger manageable.

Output discipline

For screen-reader use, avoid unnecessary output.

Instead of repeatedly dumping everything:

frame variable

ask for one value:

frame variable config

Then:

frame variable config.path

Then:

frame variable config.debug

The principle is:

Inspect the smallest useful piece of state.

This reduces auditory overload and makes changes easier to detect.

Why output discipline matters

The default behavior of the debugger is to show you everything it can. When you type frame variable, LLDB shows every local and argument in the current frame, formatted by the pretty-printers. When you type bt, LLDB shows every frame in the call stack, up to the runtime entry. When you type thread backtrace all, LLDB shows every thread’s stack.

For a small program with a small frame, this is fine. For a real program with a large frame and many threads, the output can easily exceed what can be held in working memory. For a screen reader, the problem is worse: the output is spoken sequentially, and the listener must hold the content in memory while parsing the next part. A dump of a hundred lines of structured output is effectively unreadable.

Output discipline is the practice of asking for only what you need. It is not a limitation of the debugger; it is a choice about how to use it.

The choice has two effects. First, it reduces the amount of output the user must process, which is important for screen readers and for humans reading terminal output in general. Second, it forces the user to state the question before running the command. Asking for config.path requires knowing that config.path is what you want; asking for frame variable does not. The first approach keeps the investigation focused.

The smallest useful piece of state

“The smallest useful piece of state” is not a precise rule. It depends on the question. A few examples illustrate the range:

  • Inspecting a specific field of a struct: frame variable config.timeout instead of frame variable config, when only the timeout is of interest.
  • Inspecting a specific element of a collection: frame variable items[3] instead of frame variable items, when a specific index is suspect.
  • Inspecting a specific frame’s locals: frame select 2 followed by frame variable, instead of dumping the whole backtrace first.
  • Inspecting a specific thread’s stack: thread select 2 followed by bt, instead of thread backtrace all.
  • Limiting backtrace depth: bt 5 instead of bt, when only the top of the stack is interesting.

In each case, the principle is the same: ask for the smallest scope that contains the answer.

When dumping everything is appropriate

Output discipline does not mean never asking for large output. There are situations where the full view is what you need:

  • Orientation: at the start of a session, you may want to see the full set of locals to know what is available.
  • Overview: when you have no hypothesis and want to see the shape of the current state.
  • Thread survey: when you do not know which thread is relevant and need to scan them.
  • Field discovery: when you have forgotten the exact field names of a struct and need a reminder.

In these cases, asking for the full output is appropriate. The discipline is to know when you are in one of these cases and to keep the full dumps short.

The auditory perspective

A screen reader delivers output as audio. Several properties of audio make it different from reading text on a screen:

  • It is sequential: you cannot skim; you must listen in order.
  • It is not persistent: the previous line is not visible while you read the next one.
  • It is slow: at typical screen-reader rates, reading a thousand characters takes several seconds.
  • It is hard to scroll back: going back to re-read a specific line requires re-navigating the buffer, which is often slower than reading forward.

Because of these properties, the cost of extra output is much higher with a screen reader than with a visual display. A hundred lines of output that would take a few seconds to scan visually might take a minute or more to hear, and much of it will be forgotten by the time the last line is reached.

Output discipline is not a courtesy; it is a practical necessity for efficient screen-reader debugging.

Applying output discipline to specific commands

Several LLDB commands produce more output than necessary for a focused inspection. The following table summarizes the common cases and their disciplined alternatives.

Command Disciplined Alternative When to Use
frame variable frame variable NAME or frame variable NAME.FIELD When you know which value you want
bt bt 5 When the top of the stack is what matters
thread backtrace all thread list then thread select N then bt When one thread is suspected
breakpoint list breakpoint list N When checking a specific breakpoint
watchpoint list watchpoint list N When checking a specific watchpoint
image lookup --name PATTERN Narrow the pattern or grep the output When the pattern matches many symbols
help help COMMAND When you need help with a specific command

The pattern is the same: use the narrowest form of the command that answers the question.

Recording and revisiting output

Because audio output is not persistent, it is useful to record the important observations as you go. Two approaches are common:

  • Debugging notebook: write down the key observations in a separate text file as you make them, as described in Chapter 18. This external memory is more reliable than the audio buffer.
  • Terminal logging: many terminals can log their session to a file. Running LLDB inside such a terminal captures all output to a file, which can be reviewed later or searched with rg.

For a screen-reader workflow, the debugging notebook is often the more practical option, because it captures the conclusions rather than the raw output. The notebook tells you what you learned; the terminal log tells you what you saw.

Screen-reader workflow

Debugger output can be overwhelming. Use output discipline.

Instead of:

frame variable

which may dump many variables, ask for one:

frame variable config

Then one field:

frame variable config.path

Then another:

frame variable config.debug

The principle:

Inspect the smallest useful piece of state.

Other screen-reader-friendly practices:

use full command names
use help to discover syntax
use breakpoint commands to automate repetitive inspection
avoid dumping entire backtraces unless needed
use bt 5 to limit output
use frame select to move deliberately
use thread select to avoid ambiguity

LLDB repeats the previous command on Enter. Use this deliberately, not accidentally.

If you need to preserve output, consider redirecting LLDB output to a file or using a terminal with accessible logging.

The case for full command names

LLDB provides short forms for many commands. b for breakpoint set, n for next, s for step, and so on. These short forms are convenient when typing, but they can be less clear when heard or when read aloud.

For a screen-reader workflow, full command names are often preferable:

  • They are self-describing: when the debugger echoes the command back, breakpoint set --name parse_config is clear; b parse_config requires knowing what b stands for.
  • They are easier to review: when reading back through a session log, the full command is unambiguous.
  • They are consistent: LLDB’s help system documents commands by their full names, so the full form matches what the documentation says.

This is not a rigid rule. Some commands (such as next, step, continue) are short enough that the full form and the short form are similar. But for anything with options, the full form is generally clearer.

Using help to discover syntax

The help command is the debugger’s built-in documentation. It answers questions about command syntax, options, and behavior.

The general forms:

help
help COMMAND
help CATEGORY

For example:

help breakpoint set
help frame variable
help watchpoint
help thread

The output is structured: a one-line description, a syntax line, the available options, and often a note about related commands or short forms. This structure is helpful for screen-reader use because it is predictable: the same fields always appear in the same order.

When you are unsure about the exact option name or the exact syntax, help is the fastest way to find the answer. It is not necessary to memorize every option; it is only necessary to know that help exists and how to use it.

Using breakpoint commands to automate

When a breakpoint fires many times, inspecting it manually each time produces a lot of output and a lot of typing. LLDB supports attaching commands to a breakpoint, so that each time the breakpoint fires, the same set of commands is executed automatically.

The general mechanism:

(lldb) breakpoint command add 1
> frame variable state
> bt 3
> DONE

The commands between the prompt and DONE are attached to breakpoint 1. Each time the breakpoint fires, these commands are executed, and the output is displayed as if you had typed them.

For a screen-reader workflow, breakpoint commands have two benefits:

  • Less typing: you write the inspection once and it runs automatically.
  • Consistent output: each firing produces the same structure of output, which is easier to compare across firings.

Breakpoint commands are described in more detail in the next chapter, but it is worth mentioning here because they are one of the most effective ways to reduce output-related effort.

Avoiding unnecessary backtraces

A backtrace is a powerful tool, but it is also one of the largest sources of output. For a small program, bt produces a handful of frames. For a larger program, or a program with deep library stacks, bt can produce dozens of frames, most of which are runtime or library machinery.

A practical approach: start with a limited backtrace, and expand only when needed.

(lldb) bt 5

This shows the top five frames, which usually include the current location and a few of its callers. If the interesting frame is not among them, expand to bt 15, and continue expanding only if necessary.

For a screen-reader workflow, this progressive expansion is often the difference between a manageable session and an overwhelming one. Each step adds only the frames you might need, and you can stop as soon as you have identified the frame that matters.

Moving deliberately through frames

frame select N moves the selection to a specific frame by index. This is useful when you have identified a frame from the backtrace and want to inspect it directly.

The alternative is up and down, which move one frame at a time. Both approaches are valid, but they have different effects on a screen-reader workflow:

  • frame select N jumps directly to a specific frame. If you already know the index, this is the fastest way to get there. But you need to remember the index, which requires you to have read the backtrace carefully.
  • up and down move one frame at a time. This is slower in terms of commands, but each movement is small and easy to follow. It is a good choice when you are not sure which frame you want to inspect and need to look at each in turn.

A practical pattern: use frame select N to jump to a known frame, and use up or down to move nearby once you are close. This combines the speed of direct navigation with the clarity of step-by-step movement.

Selecting threads carefully

In a multithreaded program, commands that target threads can produce a lot of output if applied to all threads at once. A more disciplined approach is to select a specific thread before inspecting its stack.

(lldb) thread list
(lldb) thread select 2
(lldb) bt 5

This shows only the selected thread’s stack, and only the top five frames. If the thread is the one you care about, this is often sufficient.

For a screen-reader workflow, the pattern is:

  1. List threads to see what is available.
  2. Select the thread that seems most relevant.
  3. Inspect its stack with a limited bt.
  4. If not informative, select a different thread and repeat.

This avoids the flood of output that thread backtrace all produces, and it keeps the investigation focused on one thread at a time.

Preserving output when needed

Sometimes, an output is important enough that you want to keep it. Two techniques are useful:

  • Redirect to a file: launch LLDB with output redirected to a file, or use a command to save the current output.
  • Terminal logging: configure the terminal to log its session. Many terminals support a session-log command or a menu option.
  • Copy-and-paste to a file: after inspecting a value, copy it into a text file if it is important for later reference.

For a screen-reader workflow, saving output to a file is especially useful because the file can be read at your own pace, searched with rg, and reviewed after the session. Terminal output is transient; a saved file is durable.

Repeat commands

LLDB repeats the previous command when you press Enter on an empty command line.

This is useful for commands that naturally produce progressive output, including backtrace inspection. LLDB documents this repeat behavior explicitly.

For example:

bt 5

followed by Enter can continue paging through a backtrace.

Use this carefully.

An empty Enter is a command repetition, not merely a blank interaction.

How repeat behavior works

The repeat behavior is simple: when you press Enter without typing anything, LLDB treats the input as the previous command. This is a feature inherited from earlier debuggers and is intended to make it easy to run the same command multiple times in a row.

Commands that benefit from this are typically ones that produce output in chunks, such as:

  • bt N: the first invocation shows the first N frames; the next invocation shows the next N frames; and so on.
  • disassemble without arguments: shows the next chunk of disassembly.
  • memory read without arguments: shows the next chunk of memory.
  • source list or its equivalent: shows the next chunk of source.

In each case, the repeated command advances the display by one step. This is exactly what you want when reviewing a long output.

The risks of accidental repeat

The repeat behavior is a double-edged tool. A stray Enter can trigger a command you did not intend, and in a session where the previous command had side effects (such as continue or step), an accidental repeat can move the program’s execution in an unwanted direction.

For a screen-reader workflow, the risk is higher because the input buffer is not always visible. A common scenario: you pause to think, press Enter by habit or by accident, and the debugger re-runs the previous command. If the previous command was continue, the program resumes execution, and the current stop is lost.

Mitigations:

  • Be aware of the previous command: before pressing Enter, recall what you ran last.
  • Use help as a no-op: if you need to press Enter but do not want to repeat, type help and press Enter. This executes a harmless command.
  • Interrupt if needed: if the program resumes unintentionally, send an interrupt (typically Ctrl+C) to stop it again.

Once you are aware of the behavior, the risk becomes manageable. The repeat feature is a convenience, not a hazard, once you know when it is active.

Deliberate use of repeat

The most productive use of repeat is for paging through output. When a backtrace is longer than the terminal can show, the first bt 5 shows the first five frames. A subsequent Enter shows the next five. Another Enter shows the next five, and so on.

For a screen-reader workflow, this progressive paging has two advantages:

  • Small chunks: each Enter produces a small, digestible output.
  • Controlled pace: the user controls when to advance, so each chunk can be fully processed before the next one is spoken.

This is often preferable to a single bt that dumps everything at once. The output is the same; the pacing is different, and the pacing is what makes the output usable with a screen reader.

Repeat in context

Repeat is a small feature, but it changes how you interact with the debugger. Instead of typing bt 5 repeatedly, you type it once and press Enter as needed. This is a small saving that adds up over a long session.

The key point is that repeat is a deliberate tool, not an accident waiting to happen. When you know the previous command, repeat is useful. When you do not, help is a safer substitute for a bare Enter.

Help is part of the debugger

When uncertain:

help

Specific command:

help breakpoint set

or:

help frame variable

or:

help watchpoint

LLDB's command system is designed to expose detailed command syntax through help.

You do not need to memorize LLDB.

You need to know how to interrogate LLDB.

The shape of help output

The output of help for a specific command follows a consistent structure. Understanding this structure makes the output easier to scan and easier to hear.

A typical help entry has the following sections:

  • A one-line description: what the command does.
  • Syntax: the general form of the command, with placeholders for arguments and options.
  • Command options: the flags and options the command supports, each with a short description.
  • Examples (for some commands): sample invocations showing typical usage.
  • See also (for some commands): related commands.

Because the structure is consistent, you can navigate it predictably. When you hear “Syntax” or “Command options,” you know what section you are in. This is particularly valuable with a screen reader, where the visual cues of formatting are absent.

Using help as documentation

The help system in LLDB is not a lightweight reference; it is the debugger’s documentation. When you are not sure what a command does, or what options it takes, help is the answer.

Some useful help invocations for common tasks:

  • help breakpoint set: how to set a breakpoint, including options for names, files, lines, conditions, and more.
  • help breakpoint modify: how to change a breakpoint after it has been set, including condition, enable, and other options.
  • help frame variable: how to inspect locals and arguments in the current frame.
  • help frame select: how to move the frame selection.
  • help thread backtrace: how to inspect thread stacks.
  • help watchpoint set: how to set a watchpoint.
  • help memory read: how to read memory at an address.

These are worth bookmarking mentally, or in a text file, because they cover the vast majority of routine queries.

Help versus memorization

A common misconception is that using a debugger requires memorizing commands. In practice, it requires knowing which commands exist and how to look up their syntax when needed. The help system is the tool for the second part.

For a screen-reader workflow, this is especially important. Memorizing a large number of commands is harder when the commands cannot be scanned visually, and the cost of forgetting an option is higher when the output is not visible. Relying on help is a safer and more sustainable strategy than trying to hold everything in memory.

The skill is not memorization; it is knowing how to ask. With LLDB, asking is done with help.

The help command as a pause

One small but useful side effect of help is that it is harmless. Running help with no arguments or with a specific command does not change the program’s state; it just prints information. This makes help a safe way to “do nothing” in a session.

This is useful in two situations:

  • When you need a moment to think: instead of leaving the prompt idle (which risks an accidental Enter), run help and read the output while you decide what to do next.
  • When you want to break a repeat chain: if you have been pressing Enter to page through output, running help resets the “previous command” to help, so that a subsequent Enter will not repeat the paging.

This is a small usability trick that fits well with a screen-reader workflow, where a stray Enter is both easy to trigger and costly to recover from.

Command completion

LLDB supports command completion.

Start typing:

breakpoint

and use completion to discover available subcommands.

This is useful for screen-reader users because it lets the debugger itself expose the command hierarchy.

Think:

breakpoint
    set
    list
    delete
    modify

rather than memorizing every command independently.

How completion works

Command completion is triggered by pressing Tab. When you press Tab after a partial command, LLDB displays the possible completions. If there is a single completion, it fills it in directly. If there are multiple, it lists them or extends the input to the longest common prefix.

For example, typing break and pressing Tab may complete to breakpoint, because breakpoint is the only command that begins with those characters. Typing breakpoint s and pressing Tab may complete to breakpoint set.

The behavior depends on your LLDB configuration and your terminal’s tab handling. In most cases, completion works as you would expect from a modern command line.

The command tree

LLDB’s commands form a tree. The first word is a category, the second word is an operation within that category, and further words are sub-operations. Completion navigates this tree:

breakpoint
    set
        --name
        --file
        --line
        --condition
    modify
        --condition
        --enable
        --disable
    list
    delete
    command
        add
        delete

frame
    info
    variable
    select

thread
    list
    select
    backtrace

watchpoint
    set
        variable
        expression
    list
    delete

memory
    read
    write
    region

Knowing the tree structure is more useful than memorizing individual commands, because it lets you infer where commands live. If you need to inspect a frame, you know to start with frame; if you need to inspect threads, you know to start with thread. Completion helps you discover the specific sub-command once you are in the right category.

Completion as a learning tool

For a screen-reader workflow, completion is more than a typing shortcut. It is a way for the debugger to teach you its own vocabulary. Each time you type a partial command and press Tab, the debugger tells you what the available completions are. This is like a help system that responds to your current position in the command.

Some practical implications:

  • Explore the tree as needed: if you know you need to do something with breakpoints but are not sure which operation, type breakpoint and press Tab to see the options.
  • Discover options: after breakpoint set, pressing Tab may show the available options (--name, --file, --line, and so on).
  • Confirm exact spellings: if you are unsure whether an option is --condition or --cond, completion will tell you.

This turns the debugger into a self-documenting environment. You do not need to have read the documentation ahead of time; you can discover the commands as you need them.

Completion and help together

Completion and help are complementary. Completion tells you what commands exist; help tells you what they do. Using them together:

  1. Type a partial command and press Tab to see the completions.
  2. Type the completed command and press Enter to run it.
  3. If the command fails or you are unsure about the syntax, use help COMMAND to read the documentation.

This workflow lets you learn the debugger incrementally. You do not need to know everything before you start; you need to know how to ask the debugger for what you need.

Completion and screen readers

For a screen-reader workflow, the challenge with completion is that the list of options is only visible for a moment and may not be reliably read by the screen reader. Some terminals handle completion output well; others do not.

Practical approaches:

  • Use completion to disambiguate: when you have typed enough of a command that only one completion is possible, Tab will fill it in, and the filled-in text is spoken as part of the command line.
  • Use help for discovering options: when you need the full list, help COMMAND is a more reliable way to read the options than Tab completion, because the help output is designed to be read sequentially.
  • Combine both: use completion to get to the command, and use help to learn its options.

With this combination, the debugger remains navigable without visual scanning.

Putting it all together

The practices in this chapter are small individually, but together they change the character of a session. A session that uses output discipline, help, and completion is smoother and less tiring than one that does not.

A worked sequence

A short sequence illustrating the practices:

(lldb) breakpoint set --file src/main.rs --line 42
(lldb) run
(lldb) frame variable
(lldb) frame variable config.timeout
(lldb) frame variable config.debug
(lldb) bt 5
(lldb) frame select 1
(lldb) frame variable input
(lldb) help frame variable
(lldb) breakpoint list 1
(lldb) breakpoint modify 1 --condition 'item.id == 42'
(lldb) continue
(lldb) frame variable item.id
(lldb) bt 3
(lldb) continue

At each step:

  • A source-line breakpoint was set, and the program was run to it.
  • Instead of dumping the whole frame, individual fields were inspected.
  • The backtrace was limited to five frames, then later to three.
  • A frame was selected to inspect the caller’s state.
  • help was used to remind the user of the syntax for frame variable.
  • The breakpoint was listed and then modified to add a condition.
  • After continuing, the conditional breakpoint fired only for the interesting case.

The sequence is short and focused. Each command has a clear purpose, and each produces a small amount of output. The user’s working memory is never overloaded, and the investigation proceeds smoothly.

Checklists

Two short checklists summarize the practices of this chapter.

Output discipline checklist:

  • Inspect one value at a time, not the whole frame, when the question is specific.
  • Limit backtraces with bt N.
  • Select a specific frame before inspecting its locals.
  • Select a specific thread before inspecting its stack.
  • List one breakpoint or watchpoint at a time when checking a specific one.
  • Record important observations in a notebook rather than relying on terminal scrollback.

Screen-reader workflow checklist:

  • Use full command names when the short forms would be ambiguous.
  • Use help COMMAND to discover or confirm syntax.
  • Use breakpoint commands to automate repetitive inspections.
  • Use bt 5 to keep backtraces short.
  • Use frame select to move deliberately rather than stepping blindly.
  • Use thread select to focus on one thread at a time.
  • Press Enter deliberately, knowing that it repeats the previous command.
  • Save important output to a file or a notebook for later review.

These checklists are not rules; they are habits. Adopting them takes some practice, but the payoff is a debugging session that is less tiring, more focused, and easier to return to.

The goal of output discipline

The goal is not to minimize output for its own sake. The goal is to make the output that is produced meaningful. A small amount of well-chosen output is more useful than a large amount of unfiltered output, because the small amount is easier to hold in memory and to compare with expectations.

For a screen-reader workflow, this is the difference between a session that can be conducted in real time and one that must be conducted in a series of slow, interrupted passes. The practices in this chapter make the first possible.

Rust 2024 notes on output and workflow

The Rust 2024 edition does not change the debugger’s output format or the commands available. The practices in this chapter apply equally to Rust 2024 projects and earlier editions.

A few small interactions with the edition are worth noting:

Unsafe blocks in source output

Because Rust 2024 requires explicit unsafe { ... } blocks inside unsafe fn bodies, the source displayed by the debugger for unsafe functions now shows more structure. When inspecting a frame inside an unsafe function, the source location may point to the opening of an unsafe block, which is a natural place to break and inspect. This does not change the output of the debugger, but it does change the meaning of the source line that is shown.

unsafe extern blocks in symbols

Functions declared inside unsafe extern blocks appear under their foreign symbol names. When listing breakpoints or inspecting backtraces, the names shown for these functions are the external symbols, not Rust source names. This is the same as in earlier editions, but the source shows the block explicitly as unsafe extern, which makes it easier to recognize.

static mut in inspection

Rust 2024 disallows references to static mut. When inspecting global state, the debugger shows raw pointers or interior-mutability wrappers instead of bare references. For output discipline, this means that the value of the global is accessed through the wrapper, which is one extra level of nesting. The disciplined approach is the same: inspect the specific field of the wrapper that contains the value, rather than dumping the wrapper.

Help and completion in 2024

The help system and command completion are unchanged in Rust 2024. The commands and their syntax are the same. The workflow described in this chapter applies without modification.

Summary

In this chapter, we covered how to keep the debugger’s output manageable:

  • Output discipline: inspect the smallest useful piece of state. Ask for a specific field, a specific element, a specific frame, or a specific thread, rather than the whole structure. Use bt N to limit backtraces and frame select to move deliberately.
  • Why output discipline matters: audio output is sequential, non-persistent, slow, and hard to scroll back. The cost of extra output is much higher with a screen reader than with a visual display.
  • Screen-reader practices: use full command names where clearer, use help to discover syntax, use breakpoint commands to automate repetitive inspections, use bt 5 to limit output, use frame select and thread select to move deliberately, and record important observations in a notebook or a file.
  • Repeat commands: pressing Enter on an empty line repeats the previous command. This is useful for paging through backtraces but risky if a stray Enter triggers an unintended command. Use help as a no-op when you need a pause.
  • Help is part of the debugger: the help command is a full documentation system. Learning to use it is more valuable than memorizing commands.
  • Command completion: tab completion navigates LLDB’s command tree. Combined with help, it makes the debugger a self-documenting environment.
  • Rust 2024 specifics: the edition does not change the debugger’s output format or commands, but the new syntax for unsafe blocks and unsafe extern blocks changes the source that appears in the debugger’s view.

The unifying principle: the debugger is a conversation, and the quality of the conversation depends on both sides. By asking precise questions and processing small answers, the programmer keeps the conversation useful. The practices in this chapter are what make that possible with a screen reader, and they improve the experience for any user of the debugger.
