Chapter 21: Breakpoint Commands and Automated Observation

Every debugging session is a conversation with the running program. Breakpoints are how you ask a question: “stop here.” Once stopped, inspection commands are how you ask follow-up questions: “what is the value of this variable,” “what is the call stack,” “which thread is executing.” Most sessions involve many rounds of this: stop, inspect, continue, stop, inspect, continue.

When the same inspection is needed every time, the conversation becomes repetitive. A breakpoint that fires a hundred times, with the same three inspection commands typed each time, produces a hundred rounds of identical input. This is tedious for a human and even more so for a screen-reader workflow, where each typed command requires time and attention.

This chapter is about breakpoint commands: a way to attach a list of LLDB commands to a breakpoint so that when the breakpoint fires, those commands are executed automatically. This turns the debugger into a lightweight tracing tool, and it is one of the most effective ways to reduce the amount of manual work in a debugging session.

The chapter covers the mechanism, the practical patterns, and the ways to keep the automatic output manageable. It also discusses when automatic observation is the right tool and when it is not.

Breakpoint commands

LLDB can associate commands with breakpoints.

For example, a breakpoint can automatically execute:

bt

when hit.

The general mechanism is:

breakpoint command add 1

Then enter:

bt
DONE

LLDB documents breakpoint command lists as a way to automatically perform actions when a breakpoint is hit.

This can be useful for repetitive investigations.

How the mechanism works

The mechanism has three parts:

  1. The breakpoint: an ordinary breakpoint, set with the usual commands. It has a numeric ID.
  2. The command list: a sequence of LLDB commands that should be executed each time the breakpoint fires.
  3. The attachment: the act of associating the command list with the breakpoint.

The attachment is done with the breakpoint command add command, followed by the breakpoint ID. LLDB then enters a multi-line editing mode, where each line is a command to be attached. The editing mode ends with the DONE keyword on its own line.

(lldb) breakpoint command add 1
Enter your debugger command(s). Type 'DONE' to end.
> frame variable state
> bt 5
> DONE
(lldb)

Now, whenever breakpoint 1 fires, LLDB executes frame variable state, then bt 5, then pauses and waits for the user to type the next command. The commands are run in sequence, and their output is displayed before the debugger stops and shows its prompt.

By default, breakpoint commands execute and then return control to the user. The breakpoint still stops execution. The difference is that by the time the prompt is shown, the requested output has already been produced.

One command per line

Each line in the command list is one LLDB command. The command is parsed exactly as if it had been typed at the prompt. This means that all the same options, arguments, and forms work inside a command list that would work at the prompt.

For example:

(lldb) breakpoint command add 1
> frame variable config.timeout
> frame variable config.debug
> frame variable items.len
> bt 3
> DONE

Each of these commands produces the same output inside a breakpoint command list as it would when typed directly. This is important: the command list is not a limited subset of LLDB. It is the full command language.

Viewing and removing commands

To view the commands attached to a breakpoint, use:

(lldb) breakpoint command list 1

This shows the sequence of commands currently attached to breakpoint 1, in the same order they were added. If no commands are attached, LLDB reports that the breakpoint has no command list.

To remove the commands from a breakpoint, use:

(lldb) breakpoint command delete 1

This deletes the command list but does not delete the breakpoint itself. The breakpoint continues to fire; it just does not run the attached commands.

To delete the breakpoint entirely, use breakpoint delete 1, as described in an earlier chapter. Deleting a breakpoint also deletes its command list, because the command list is part of the breakpoint.

A simple example

Consider a program that processes a list of items:

fn process_items(items: &[Item]) {
    for item in items {
        let result = compute(item);
        println!("{}: {}", item.id, result);
    }
}

Suppose you want to see, for each item, its ID and the computed result, without stopping the program at each iteration. Set a breakpoint at the line where result is computed, then attach a command list:

(lldb) breakpoint set --file src/main.rs --line 3
(lldb) breakpoint command add 1
> frame variable item.id
> frame variable result
> continue
> DONE

The command list includes a continue at the end. This is the key pattern: after the inspection commands, continue resumes the program, so the debugger does not stop for the user to press continue manually. The program runs from one breakpoint hit to the next, and each hit produces a small block of output.

The net effect is a trace of the loop: one line for each iteration, showing the ID and the result. The user did not have to type anything after the initial setup. This is automation in the simplest form.

The continue command in a command list

The continue command inside a command list is what turns a breakpoint into a tracing tool. Without it, the breakpoint fires, the commands execute, and the debugger stops for the user. With it, the breakpoint fires, the commands execute, and the program resumes.

This changes the character of the session entirely. Without continue, the breakpoint is a stopping point that requires user input. With continue, the breakpoint is a recording point that produces output as the program runs.

For a screen-reader workflow, this is particularly valuable. Each breakpoint hit produces a small, predictable block of output, and the program keeps running. The user can listen to the output as it is produced, or can redirect it to a file for later reading. Either way, the user is not required to press continue manually for each hit.

When to use continue, and when not to

The decision of whether to include continue in a command list depends on the goal:

  • Include continue when you want a trace. The breakpoint fires many times, and you want each firing to produce output without requiring manual intervention.
  • Omit continue when you want an inspection stop. The breakpoint fires, the commands produce output, and the debugger stops so that you can run additional commands interactively before deciding what to do next.

A useful pattern is to start without continue, verify that the inspection commands produce the output you expect, and then add continue once you are satisfied with the format. This avoids a session that runs the program to completion before you have verified the output.

To add or remove continue from an existing command list, delete the command list and re-add it with the desired commands. There is no in-place editing of a command list in LLDB; the commands are reattached as a block.

Attaching commands at creation time

Some versions of LLDB support attaching commands to a breakpoint when the breakpoint is created, using the --command option or its equivalent. The exact syntax depends on the version. The general idea is that a breakpoint can be created with an attached command list in a single step:

(lldb) breakpoint set --file src/main.rs --line 3 --command 'frame variable item.id' --command 'continue'

For multiple commands, the option can be repeated. This is convenient when the command list is short and known in advance. For longer lists, or for lists that are being developed interactively, the two-step approach (set the breakpoint, then add the commands) is often easier.

Because the exact syntax of this feature varies across LLDB versions, the two-step approach is the most portable. It uses only the core breakpoint set and breakpoint command add commands, which are available in all recent versions.

Automated observation

Suppose a function is called many times.

Instead of manually stopping every time:

breakpoint
→ inspect
→ continue

you can attach commands to the breakpoint.

For example:

breakpoint command add 1

then:

frame variable state
bt
DONE

Now every hit produces the same observation.

This turns LLDB into a lightweight tracing tool.

Why automated observation matters

In a debugging session without automation, the user is the bottleneck. Each breakpoint hit requires typing one or more commands, reading the output, and deciding whether to continue. For a breakpoint that fires a hundred times, this is a hundred rounds of manual work.

Automated observation removes the user from the loop. The debugger handles the repetitive work, and the user processes the output afterward. This has several benefits:

  • Speed: the program runs at full speed between breakpoint hits, rather than waiting for the user to type each command.
  • Consistency: every firing produces the same format of output, which is easier to compare across firings.
  • Reduced typing: the user does not need to type the same commands repeatedly.
  • Better focus: the user’s attention is on analyzing the output, not on remembering which commands to run.

For a screen-reader workflow, these benefits are even more pronounced. Reducing the amount of typing reduces the time spent navigating the command line, and having a consistent output format makes the audio easier to follow.

The shape of a tracing session

A tracing session has a characteristic shape:

  1. Identify the location to trace. This is usually a function or a source line that is reached once per event of interest.
  2. Set a breakpoint at that location.
  3. Attach a command list that inspects the relevant state and then continues.
  4. Run the program. The program traces itself, producing output at each hit.
  5. Inspect the output. Either read it live or redirect it to a file.
  6. Analyze the trace for patterns. The trace shows the sequence of values over time, which is often the evidence you need.

The trace is a form of temporal evidence. A single breakpoint stop shows a snapshot; a trace shows a movie. For bugs that depend on the sequence of events, the trace is often more useful than any number of snapshots.

What to trace

A good trace records the state that changes over time. Common targets include:

  • Loop iterations: the index, the current element, the accumulated result.
  • Function calls: the arguments, the return value, the call site.
  • State transitions: the current state, the event that triggered the transition.
  • Error paths: the error variant, the input that produced the error.
  • Resource usage: allocations, locks acquired, files opened.
  • Thread activity: which thread is executing, which task is running.

The general principle is the same as for a single inspection: record the smallest useful piece of state. A trace with one field per line is easier to read than a trace with ten fields per line. If you need more fields, add them incrementally.

Formatting the output

By default, each breakpoint command produces its output on its own line, in LLDB’s standard format. For example:

(int) item.id = 1
(int) result = 2

This is functional, but for a longer trace it can be verbose. Several techniques help:

  • Use expression output for compact lines: expr item.id produces just the value, without the type prefix. This is more compact than frame variable item.id.
  • Print a formatted line: expr "item \(item.id) result \(result)" produces a single line that combines the fields. The exact syntax of interpolation in LLDB expressions depends on the version, but the idea is to produce a single human-readable line per hit.
  • Use Python breakpoint commands: LLDB supports breakpoint commands written in Python, which can format the output however you want. This is more advanced but very powerful.

For a screen-reader workflow, compact output is especially valuable. A trace with one line per hit is easier to follow than a trace with multiple lines per hit. If you need to keep the type information, consider putting it in a header rather than repeating it on every line.

Redirecting the trace to a file

A long trace can overwhelm the terminal. Redirecting the trace to a file solves this and has two extra benefits:

  • Persistence: the trace is saved and can be reviewed after the session.
  • Searchability: the file can be searched with rg to find specific patterns.

LLDB itself supports logging to a file with the log command, but a simpler approach is to run the debugger inside a terminal that supports session logging, or to run the whole session with output redirected:

rust-lldb target/debug/my_program > trace.log 2>&1

The 2>&1 redirects standard error to standard output so that all the debugger’s output is captured in the same file. After the session, trace.log contains the full transcript.

For a screen-reader workflow, this is often the best approach for long traces. The trace is collected quietly in the background, and the user reviews it afterward at their own pace. Searching the file with rg is faster than listening to the whole trace.

Limiting the trace

A trace that runs for thousands of hits produces thousands of lines. Even if redirected to a file, this is a lot of evidence to process. Several techniques limit the trace to what is interesting:

  • Conditional breakpoints: attach a condition to the breakpoint so that it fires only when the interesting state occurs. For example, item.id > 100 would skip the first hundred iterations.
  • Counters in the command list: use a Python breakpoint command to maintain a counter and continue without printing until the counter reaches a threshold.
  • Filtering after the fact: write the trace to a file, then use rg to find specific lines. For example, search for lines containing a specific value.
  • Two-pass tracing: first run a trace with minimal output (just a hit count), to establish how many times the breakpoint fires. Then decide whether to trace in detail.

For a screen-reader workflow, filtering after the fact is often the most effective. The trace file becomes a database that can be queried with rg, and the user only listens to the specific lines that match a query.

A worked tracing example

Consider a program that computes a running sum:

fn compute_running_sum(values: &[i32]) -> i32 {
    let mut sum = 0;
    for value in values {
        sum += value;
    }
    sum
}

fn main() {
    let values = vec![1, 2, 3, 4, 5];
    let result = compute_running_sum(&values);
    println!("sum = {}", result);
}

Suppose the program reports an unexpected sum. Instead of stepping through the loop manually, trace the loop:

(lldb) breakpoint set --file src/main.rs --line 4
(lldb) breakpoint command add 1
> expr value
> expr sum
> continue
> DONE
(lldb) run

The program runs to completion, producing output like:

(int) value = 1
(int) sum = 1
(int) value = 2
(int) sum = 3
(int) value = 3
(int) sum = 6
(int) value = 4
(int) sum = 10
(int) value = 5
(int) sum = 15

Each pair of lines shows the value and the running sum at the point of the breakpoint. The trace shows how the sum accumulates as each value is added. If the sum is wrong at the end, the trace shows where it diverges: the first line where sum is not what you expected is the origin of the bug.

This is a direct application of the first-wrong-state principle, with the trace providing the sequence of states rather than a single snapshot.

The trace as evidence

A trace is evidence in the same sense as a single inspection. It has properties that make it useful:

  • It is reproducible: running the program again with the same input produces the same trace (assuming the program is deterministic).
  • It is complete: the trace records every firing of the breakpoint, not just the ones the user happened to notice.
  • It is persistent: written to a file, the trace can be analyzed and shared.
  • It is comparable: two traces can be diffed to see how a change affected behavior.

These properties make the trace a valuable debugging artifact. In many cases, a trace reveals the bug faster than a session of interactive stepping, because the pattern is easier to see in a sequence than in a series of individual observations.

When not to automate

Automated observation is powerful, but it is not always the right approach:

  • The breakpoint fires too many times: if a breakpoint fires millions of times, the trace will be enormous, and the debugger’s output will dominate the runtime. Use a conditional breakpoint or a hit count to reduce the trace.
  • The inspection is complex: if the inspection requires reasoning at each step, automation prevents the user from reacting to what is seen. Interactive stepping is better in that case.
  • The breakpoint fires from multiple paths: if the breakpoint fires both for interesting events and for noise, the trace will be noisy. Refine the breakpoint or add a condition.
  • The bug depends on precise timing: adding commands to a breakpoint changes the timing of the program, which can hide or reveal the bug. In a timing-sensitive case, log-based observation is often better than debugger-based tracing.

A practical rule: automate when the output is what you want and the number of hits is manageable. Do not automate when the inspection requires human judgment at each step, or when the trace would be overwhelmingly large.

Tracing versus logging

Both tracing and logging produce a sequence of records over time. They are often interchangeable in practice, but each has strengths:

  • Tracing with LLDB: works without source changes. The set of fields to record can be chosen at the debugger prompt, without rebuilding. This is useful for exploratory tracing, or for tracing code you do not want to modify.
  • Logging with the log crate: works in production and in long-running sessions. The log statements are part of the source, so the trace is reproducible across environments.

For a bug that has already been reproduced, tracing with LLDB is often faster to set up. For a bug that requires long-running observation, logging is the only option. Many investigations use both: tracing to understand the pattern locally, and logging to confirm that the pattern holds in production.

Python breakpoint commands

LLDB supports breakpoint commands written in Python. These are more powerful than LLDB command lists and are worth knowing about for cases where command lists are not flexible enough.

The basics

To attach a Python breakpoint command, use:

(lldb) breakpoint command add --python 1

LLDB then opens a Python editing mode. The function entered is expected to accept three arguments:

  • frame: the current stack frame.
  • bp_loc: the breakpoint location that was hit.
  • internal_dict: a dictionary of internal LLDB state.

A minimal Python breakpoint command looks like:

def breakpoint_function(frame, bp_loc, internal_dict):
    value = frame.FindVariable('item')
    print(f"item = {value}")
    frame.GetThread().GetProcess().Continue()

The function can read variables from the frame, format the output as needed, and call Continue() to resume the program. This is the Python equivalent of a command list that inspects a value and continues.

What Python enables

Python breakpoint commands enable several things that are difficult or impossible with plain LLDB commands:

  • Conditional printing: only print when a specific condition is true, even if the breakpoint fires unconditionally. This is more flexible than a breakpoint condition, because the condition can be based on state that is only available inside the Python callback.
  • Aggregate output: maintain counters, sums, or other aggregates across firings, and print only periodically. For example, print every hundredth hit.
  • Formatted output: produce output in any format, including JSON, CSV, or a custom format for later parsing.
  • Interacting with the process: access memory, call functions, or manipulate the process in ways that are cumbersome from the command line.
  • Automatic side effects: modify the program’s state for testing purposes, such as forcing a specific value into a variable at a specific point.

For a complex tracing session, Python breakpoint commands are often the right tool. They require more setup, but they provide much more control over the trace.

A Python tracing example

Consider a loop where the interesting hits are only the ones where a specific condition holds, but the condition is expensive to express as a breakpoint condition. Use a Python command:

def trace_interesting(frame, bp_loc, internal_dict):
    item = frame.FindVariable('item')
    if item.IsValid():
        value = item.GetValueAsUnsigned()
        if value % 100 == 0:
            print(f"interesting item: {value}")
    frame.GetThread().GetProcess().Continue()

This command inspects the item variable on each hit, but only prints when the value is divisible by 100. All other hits are silent. The program continues automatically.

The trace produced contains only the interesting hits, so the output is smaller and easier to process. This is a form of filtering at the source rather than after the fact.

Accessing values in Python

The frame argument provides access to the frame’s variables:

  • frame.FindVariable('name'): returns the variable with the given name, or an invalid variable object if it does not exist.
  • variable.IsValid(): returns True if the variable was found.
  • variable.GetValueAsUnsigned(): returns the value as an unsigned integer, useful for primitive types.
  • variable.GetValue(): returns the value as a string.
  • variable.GetChildMemberWithName('field'): for structs, returns the named field.
  • variable.GetNumChildren(): for collections, returns the number of elements.

With these methods, a Python command can inspect arbitrary state, format it as needed, and print it. The output can be filtered, aggregated, or written to a file, depending on the need.

The trade-off

Python breakpoint commands are more powerful than LLDB command lists, but they require:

  • Knowledge of the LLDB Python API: the API is documented, but it has many classes and methods.
  • More setup time: writing and debugging a Python breakpoint command takes longer than writing a two-line LLDB command list.
  • More chances for bugs: a Python command that accesses an invalid variable, or that calls the wrong API, may produce confusing errors or crash the debugger.

The general guidance is to use LLDB command lists for simple traces and Python breakpoint commands for complex traces. If the trace needs only a few fields and no filtering, an LLDB command list is faster to set up. If the trace needs filtering, aggregation, or custom formatting, Python is the better choice.

When Python is not the right tool

Python breakpoint commands are not the right tool for every tracing need. They are not the right choice when:

  • The command list is simple: an LLDB command list with a few lines is easier to write and easier to read.
  • The trace needs to be quick to set up: for a one-off investigation, the overhead of writing Python is not worth it.
  • The trace is being shared: LLDB command lists are easier to share because they are just LLDB commands that other users can paste directly.

Use Python breakpoint commands when the flexibility they provide is essential. Otherwise, prefer the simpler LLDB command list.

Combining breakpoint commands with other techniques

Breakpoint commands are most powerful when combined with other debugging techniques. A few common combinations:

With conditional breakpoints

A conditional breakpoint fires only when a condition is true. Combine it with a command list to trace only the interesting cases:

(lldb) breakpoint set --file src/main.rs --line 4
(lldb) breakpoint modify 1 --condition 'item.id > 100'
(lldb) breakpoint command add 1
> expr item.id
> expr sum
> continue
> DONE

The trace contains only hits where item.id > 100, so it is smaller and focused on the interesting region. This is a common pattern for tracing a hot loop where only the later iterations matter.

With watchpoints

A watchpoint stops when a value changes. Combine it with a command list to trace the sequence of changes:

(lldb) watchpoint set variable counter
(lldb) watchpoint command add 1
> expr counter
> bt 2
> continue
> DONE

Each time counter changes, the command list prints its value and the top two frames of the stack (showing where the change occurred). The trace is a sequence of state transitions with their sources, which is often exactly the evidence needed for a subtle state bug.

With thread selection

In a multithreaded program, a breakpoint can fire on different threads. A command list can inspect the current thread and print thread information along with the value:

(lldb) breakpoint command add 1
> thread list
> expr item.id
> continue
> DONE

Each hit produces a list of threads and the value being processed. The thread list shows which thread was active at that moment. For a bug that depends on interleaving, this trace shows the sequence of thread activity that led to the bug.

With async tasks

In async Rust, a breakpoint at a task boundary can be combined with a command list to trace task activity:

(lldb) breakpoint set --name process_request
(lldb) breakpoint command add 1
> expr request.id
> bt 3
> continue
> DONE

Each hit corresponds to a request being processed by the runtime. The trace shows which requests were processed, in what order, and from which call site. For bugs that depend on task ordering, the trace reveals the actual interleaving that occurred.

With Python for advanced tracing

For advanced cases, a Python breakpoint command can combine all the above:

import json

def trace_request(frame, bp_loc, internal_dict):
    request = frame.FindVariable('request')
    if request.IsValid():
        request_id = request.GetChildMemberWithName('id').GetValueAsUnsigned()
        print(json.dumps({"request_id": request_id}))
    frame.GetThread().GetProcess().Continue()

This prints a JSON record for each request, which can be collected and analyzed by other tools. The trace becomes a data stream, processed by scripts rather than read line by line. This is the natural extension of tracing for large or complex systems.

The discipline of automated observation

Automated observation is powerful, and like any power tool, it has discipline requirements.

Start small

Begin with a breakpoint without commands. Verify that it fires where you expect. Then add the inspection commands, still without continue. Verify that the output is what you want. Only then add continue and let the program run to completion.

This staged approach catches mistakes early. If the breakpoint fires in an unexpected place, or if the inspection commands produce unexpected output, you find out before the trace runs the whole program.

Limit the trace

Always consider how many times the breakpoint will fire. If the answer is “thousands,” reconsider the trace. Use a conditional breakpoint, or filter the trace after the fact, or add a Python counter that prints only occasionally.

For a screen-reader workflow, an unbounded trace is particularly problematic. The audio output cannot keep up, and the relevant information is buried in noise. A bounded or filtered trace is much more useful.

Record the trace

Redirect the trace to a file. Live reading of a long trace is difficult; reviewing a file is easier. The file can be searched, filtered, and diffed against other traces.

A useful convention: name trace files after the investigation, such as trace-requests-2024-01-15.log. Include the date and the purpose. Later, when you return to the same bug, the trace is easy to find.

Delete the automation

Once the trace has served its purpose, delete the breakpoint and its commands. A breakpoint that continues to fire automatically during unrelated investigations is a nuisance. Clean up after each tracing session.

For a persistent tracing need, consider creating a dedicated script or alias that sets up the trace on demand. This keeps the automation out of the way when it is not needed.

The trace is not the answer

A trace is evidence, not a conclusion. The trace shows the sequence of states; the user must interpret it. A trace that shows a value going wrong at some point still requires the same reasoning as a single inspection: what caused the value to be wrong, and where was it first produced.

This is why the tracing session is best followed by a focused investigation. The trace identifies the transition; the debugger (or another tool) investigates the transition in detail. Tracing and interactive debugging are complementary.

Rust 2024 notes on breakpoint commands

The Rust 2024 edition does not change the syntax or behavior of breakpoint commands. The commands and their options are the same. A few interactions with the edition are worth noting.

unsafe blocks and breakpoint commands

Because Rust 2024 requires explicit unsafe { ... } blocks inside unsafe fn bodies, the source location of a breakpoint inside an unsafe block is more precise than in earlier editions. A command list attached to such a breakpoint sees exactly the state at the opening of the unsafe region, which is often the state that determines whether the region is sound.

unsafe extern blocks and tracing

Functions declared inside unsafe extern blocks appear under their foreign symbol names. A breakpoint attached to such a function fires when the foreign function is called. A command list can inspect the arguments at the FFI boundary, which is valuable for tracing across the language boundary.

static mut and tracing global state

Because Rust 2024 disallows references to static mut, tracing global state now goes through interior-mutability primitives or raw pointers. A command list that inspects a Mutex or an AtomicUsize must use the appropriate accessor. In the debugger, the wrapper is inspected directly, and the value inside is a field of the wrapper.

Async closures and tracing

Rust 2024 stabilizes async closures. A breakpoint inside an async closure fires during each poll of the closure’s future. A command list can trace the values of the captured variables and the current state of the closure, providing a trace of the async computation across suspension points.

Python breakpoint commands and 2024

The LLDB Python API is unaffected by the Rust edition. Python breakpoint commands written for earlier editions continue to work in Rust 2024, as long as the underlying symbol names and types are the same. If the edition changes a symbol name (which it can, for functions exposed via #[unsafe(no_mangle)] or #[unsafe(export_name = "...")]), the Python command may need updating to match.

Summary

In this chapter, we covered breakpoint commands and automated observation:

  • The mechanism: attach commands to a breakpoint with breakpoint command add, enter one command per line, and end with DONE. Each hit executes the command list automatically.
  • The continue pattern: including continue at the end of a command list turns a breakpoint into a tracing tool. Without it, the breakpoint stops for the user; with it, the program runs continuously and produces a trace.
  • Automated observation: use command lists to record state across many firings without manual intervention. This is a form of tracing, and it is often the fastest way to see the sequence of states that leads to a bug.
  • Compact output: prefer expr over frame variable for smaller lines; consider Python for custom formatting or aggregation.
  • Redirection: redirect the trace to a file for persistence and searchability, especially with a screen reader.
  • Limiting the trace: use conditional breakpoints, counters, or post-hoc filtering to keep the trace manageable.
  • Python breakpoint commands: more powerful than LLDB command lists, with access to the full LLDB Python API. Use them for filtering, aggregation, or custom formatting.
  • Combining techniques: breakpoint commands work well with conditional breakpoints, watchpoints, thread selection, async tasks, and Python scripting.
  • Discipline: start small, limit the trace, record it, delete the automation when done, and remember that a trace is evidence rather than a conclusion.
  • Rust 2024 specifics: the edition does not change the breakpoint command syntax, but the new unsafe rules affect what appears in the source and in the debugger’s view, and may require updating Python commands that reference symbol names.

The unifying principle: the debugger is a tool for producing evidence, and breakpoint commands are a way to produce evidence at scale. They turn a series of manual inspections into a single automated trace, freeing the programmer to focus on analysis rather than on repetitive typing.
