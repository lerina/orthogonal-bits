Chapter 12: Conditional Breakpoints, Expressions, and Watchpoints

Plain breakpoints stop the program every time execution reaches a given location. This is often exactly what you want. But some bugs appear only when a specific condition holds: a loop index reaches a particular value, a string field has a particular content, or a shared state has been corrupted by one specific caller among many. Stopping every time is wasteful, and in some cases it is impractical because the loop runs millions of times.

This chapter introduces three tools that refine where and when the debugger stops:

  • Conditional breakpoints: stop only when a condition is true.
  • Expressions: evaluate simple conditions and small computations inside the debugger.
  • Watchpoints: stop when a value changes.

Each of these is a way of asking a more specific question. Instead of “stop here,” you ask “stop here, but only under these circumstances.” That precision is often the difference between a debugging session that converges quickly and one that produces a thousand useless stops.

Conditional breakpoints

Suppose:

for item in items {
    process(item);
}

You only care when:

item.id == 42

A conditional breakpoint can reduce noise.

The general LLDB form is:

breakpoint modify 1 --condition 'condition'

For example:

breakpoint modify 1 --condition 'item.id == 42'

Whether a particular Rust expression can be evaluated depends on the debug information, expression parser, optimized state, and the current frame.

When expression evaluation fails, simplify the condition or inspect the value first.

How to set a conditional breakpoint

There are two ways to attach a condition to a breakpoint:

  1. At creation time: some versions of LLDB support setting the condition directly when creating the breakpoint, using --condition:
(lldb) breakpoint set --file src/main.rs --line 15 --condition 'item.id == 42'
  1. After creation: modify an existing breakpoint with breakpoint modify:
(lldb) breakpoint set --file src/main.rs --line 15
(lldb) breakpoint modify 1 --condition 'item.id == 42'

The second form is useful when you set a breakpoint first, observe that it fires too often, and then decide to narrow it. The pattern of “break, observe, refine” is often smoother than trying to get the condition perfect on the first attempt.

Conditions in Rust

A condition is an expression that LLDB evaluates in the current frame. It must produce a value that can be interpreted as a Boolean. For Rust code, typical conditions look like:

item.id == 42
name.len() > 10
count != 0
state.is_active

Some of these work reliably. Others do not, depending on how the debugger’s expression evaluator handles Rust syntax.

Conditions that are reliable:

  • Comparisons against primitive values: x == 42, y < 10, b != 0.
  • Field accesses on structs: item.id == 42.
  • Boolean fields: config.debug, user.active.
  • Simple arithmetic: x + y == 10.

Conditions that are less reliable:

  • Method calls that require trait resolution: name.contains("admin").
  • Iterator operations: items.iter().any(|x| *x > 10).
  • Closures: (|x| x * 2)(5) == 10.
  • Generic methods: vec.first() == Some(&1).
  • Pattern matches: matches!(state, State::Ready).

When a condition uses an unreliable construct, LLDB may fail to evaluate it, or it may produce a result that does not match what the same expression would do in Rust source. In those cases, use a simpler condition, or set a breakpoint and inspect the value manually.

Conditions and optimized code

In an optimized build, the values used in a condition may be <optimized out>. When that happens, the condition cannot be evaluated, and LLDB treats the condition as unsatisfied. The breakpoint will not fire.

The remedy is either to switch to a debug build, or to restructure the code so the value is used at the point of the condition. In a debug build, conditions evaluate much more reliably.

For a screen-reader workflow, it is worth remembering that conditions that fail to evaluate produce no output at all. If a breakpoint with a condition never fires, check whether the condition could be evaluated at the point where the breakpoint is set.

Removing a condition

To remove a condition from a breakpoint:

(lldb) breakpoint modify 1 --condition ''

The empty string clears the condition. The breakpoint then fires at every hit.

To see whether a breakpoint has a condition:

(lldb) breakpoint list 1

If a condition is set, it appears in the output. If not, no condition line is shown.

A worked example

Consider a loop that processes a thousand items, and a bug that appears only for the item with id == 500:

fn process_all(items: &[Item]) {
    for item in items {
        process(item);
    }
}

fn process(item: &Item) {
    let result = compute(item);
    println!("{}: {}", item.id, result);
}

Set a breakpoint on the entry of process:

(lldb) breakpoint set --name process

Add a condition:

(lldb) breakpoint modify 1 --condition 'item.id == 500'

Run:

(lldb) run

Execution stops only when the item with ID 500 is processed. Now you can inspect the state of that specific call without stepping through the previous 499 iterations.

If the condition fails to evaluate (for example, because item is a reference and LLDB does not automatically dereference it for the condition), try:

(lldb) breakpoint modify 1 --condition '(*item).id == 500'

The explicit dereference gives LLDB a clearer path to the value. This is a common small adjustment in Rust debugging.

Do not confuse source syntax with debugger expression syntax

This matters especially in Rust.

LLDB is not a Rust compiler.

The expression evaluator is not guaranteed to accept arbitrary Rust syntax.

For example, a Rust expression involving:

iterators
closures
generic types
trait methods
async machinery
macros

may not evaluate the same way it would in Rust source.

Use debugger expressions for simple inspection.

For complicated logic:

inspect the variable
step through the source
or temporarily add explicit debugging code

Why the evaluator is different

The LLDB expression evaluator works differently from the Rust compiler in several ways:

  • It does not have the full Rust type system. It has enough to recognize primitive types and simple structs, but not enough to resolve complex trait bounds or generics.
  • It does not perform macro expansion. A macro invocation in a condition is not expanded the way the compiler would expand it; it is evaluated as if the macro were a function call.
  • It runs in the target process. Evaluating an expression may call functions in your program, allocate memory, or modify state. In some cases, this can change the behavior of the program you are debugging.
  • It is limited by the current frame. Only variables visible in the current frame are accessible. If the current frame is a library frame or a compiler-generated frame, your variables may not be in scope.
  • It interacts with optimization. In optimized builds, many values are not stored anywhere, so expression evaluation may fail or produce a wrong result.

These limitations are not bugs. They reflect the fundamental difficulty of evaluating arbitrary code from one language inside a process that is compiled from another. The debugger gives you a useful subset of what the compiler can do, and the subset is usually enough for the kinds of questions debugging needs to answer.

When to use expr

Use expr when you need to compute a value that is not already stored in a variable. For example:

  • Computing a derived value: expr x + y.
  • Checking a simple arithmetic condition: expr x * 2 == 10.
  • Reading memory at an address: expr *(int *)0x7fff....
  • Calling a simple function: expr strlen(name).

Avoid expr when:

  • The expression involves method calls on Rust types that require trait resolution.
  • The expression involves iterators, closures, or pattern matching.
  • The expression might have side effects you do not want.
  • The program is in a state where calling into it could cause a deadlock or crash (for example, inside a signal handler).

For most inspection, frame variable is enough. Use expr when you have a specific reason and know that the expression is likely to succeed.

The expression command

LLDB provides:

expression

or:

expr

for evaluating expressions.

For example:

expr variable
expr 1 + 2

This can be useful, but Rust users should treat it as an advanced feature.

The debugger's expression evaluator is not a replacement for compiling Rust code.

A good progression is:

frame variable
→ simple expr
→ source modification

Expression: inspection vs. intervention

Expressions in LLDB split into two kinds:

  • Inspection: reading a value that already exists. This is what frame variable does, and it is always safe.
  • Intervention: computing or changing a value. This is what expr can do, and it may have side effects.

For debugging, most questions are inspection questions: “What is this value?” frame variable answers them without any risk. Use expr only when the value you need does not already exist as a variable, and only when you are confident that evaluating the expression will not disturb the program.

Inspect without calling code

Prefer:

frame variable

when you simply need to inspect an existing value.

Use:

expr

when you genuinely need expression evaluation.

This matters because evaluating an expression can execute code.

When debugging a problematic program, observation should be separated from intervention whenever practical.

Safe uses of expr

Some uses of expr are essentially safe because they do not call code or modify state:

  • Arithmetic on existing values: expr x + y, where x and y are primitive locals.
  • Boolean checks: expr x == 42, expr count > 0.
  • Pointer arithmetic: expr ptr + 1, useful for understanding buffer positions.
  • Field access on existing structs: expr config.debug, when config is a local.
  • Casting: expr (int)value, useful when you want a value in a specific numeric type.

These expressions do not call into the target program and therefore cannot change its state. They are as safe as frame variable, with the additional ability to compute derived values.

Expressions that change state

Some uses of expr change program state:

  • Assignment: expr x = 42 modifies the local x. This is occasionally useful, but it changes the program.
  • Function calls: expr increment_counter() calls a function. The function may have side effects.
  • Mutating method calls: expr items.push(5) modifies a data structure.

These are interventions, not inspections. They can be useful for experimenting with alternate state, but they should be used with care. In particular, avoid them when the program is stopped inside a critical section or a signal handler, where a function call might deadlock or crash.

A practical pattern: use frame variable to inspect, and use expr to change a value only when you want to test a hypothesis by injecting a different value. For example, if you suspect that a bug depends on a specific field value, you can set the field with expr and observe whether the behavior changes. This is a legitimate debugging technique, but it is a different activity from pure observation.

Watchpoints

A breakpoint stops when execution reaches a location.

A watchpoint stops when memory changes.

Conceptually:

Breakpoint:
"Stop here."

Watchpoint:
"Stop when this value changes."

LLDB supports watchpoints through the watchpoint command family.

A typical form is:

watchpoint set variable variable_name

or:

watchpoint set expression expression

Watchpoints are especially useful when you know:

This value is correct here, but later it becomes wrong.

Then ask LLDB:

Stop when it changes.

Watchpoints in practice

A watchpoint stops when a value changes.

Suppose:

let mut counter = 0;

for _ in 0..10 {
    counter += 1;
}

You can set a watchpoint after counter is created:

(lldb) breakpoint set --file src/main.rs --line 3
(lldb) run
(lldb) watchpoint set variable counter
(lldb) continue

LLDB will stop when counter changes.

Then:

(lldb) bt
(lldb) frame variable counter

This tells you:

which code changed the value
what the value was before
what the value became

Watchpoints are most useful when:

the value has a stable address
the value is not optimized away
the value is not moved frequently

They are less useful for:

temporaries
moved values
optimized variables
values inside complex async state

Types of watchpoints

LLDB supports several types of watchpoints:

  • Write watchpoints: stop when the value is written. This is the default and by far the most common.
  • Read watchpoints: stop when the value is read. Useful for detecting unexpected reads.
  • Read-write watchpoints: stop on either read or write. Useful for comprehensive observation of an address, though the output can be very noisy.

The default form:

watchpoint set variable counter

sets a write watchpoint. To set a read watchpoint, use the --watch option with read:

watchpoint set variable counter --watch read
watchpoint set variable counter --watch read_write

Read watchpoints are useful in specific situations: for example, when you want to know where a value is being consumed, not just where it is being modified. In most debugging, the default write watchpoint is the right choice.

Listing watchpoints

Watchpoints are listed separately from breakpoints:

(lldb) watchpoint list

The output shows each watchpoint’s ID, the expression or address it watches, its current value, and its hit count.

To delete a watchpoint:

(lldb) watchpoint delete 1

To delete all watchpoints:

(lldb) watchpoint delete

As with breakpoints, it is safer to list first, then delete by ID.

Watchpoints and Rust ownership

Rust makes mutation explicit in source, but a debugger still sees machine-level memory and debug information.

A useful investigation is:

value correct
→ continue
→ value changes
→ debugger stops
→ inspect backtrace
→ identify the code responsible

This is particularly useful for:

unexpected mutation
state changes
caches
buffers
counters
shared state

For values that move, are optimized away, or live inside complex structures, a watchpoint may be impractical.

Use it when the value has a stable address and LLDB can observe it.

Why Rust values are sometimes hard to watch

Rust’s ownership model means that values can move. When a value moves, its address changes. A watchpoint set on the old address will not fire when the new address is modified. For values that move frequently, watchpoints are unreliable.

A more robust approach is to watch a value that stays in one place for the duration of interest:

  • A local variable that is not moved.
  • A field inside a struct that is already allocated and stays put.
  • A heap-allocated value behind a stable pointer.

For example, a Vec may reallocate when it grows, but the Vec struct itself stays in place. Its internal pointer changes, so watching the pointer’s target is difficult. Watching the vector’s length field is easy, because the length field is part of the struct.

Watchpoints on heap values

If a value lives on the heap and you know its address, you can watch it directly:

watchpoint set expression -- *(int *)0x7fff...

This tells LLDB to watch the memory at that address. You would obtain the address from a pointer variable in the current frame, either by inspecting it with frame variable or by evaluating it with expr.

This is a more advanced technique. It is useful when the value is genuinely on the heap and its pointer is stable, but the struct that owns it does not appear as a variable in the current frame.

Watchpoints versus conditional breakpoints

Both conditional breakpoints and watchpoints narrow the scope of a stop, but they narrow different things.

  • Conditional breakpoint: “Stop at this location only when this condition holds.” The narrow scope is the condition.
  • Watchpoint: “Stop whenever this value changes.” The narrow scope is the value.

Choose a conditional breakpoint when you know the location but not the condition under which it matters. Choose a watchpoint when you know the value but not the location where it changes.

Both can be combined. For example, you could set a conditional breakpoint that stops only for a specific value, then add a watchpoint on a related field to see when it changes. But combining them should be done carefully, because each additional mechanism adds output. Start with one, and add the other only if needed.

A worked watchpoint example

Consider:

struct State {
    connections: Vec<String>,
    active: bool,
}

fn main() {
    let mut state = State {
        connections: Vec::new(),
        active: true,
    };

    state.connections.push("first".to_string());
    state.connections.push("second".to_string());
    state.active = false;

    println!("{} connections", state.connections.len());
}

Suppose the bug is that active becomes false earlier than expected. Set a breakpoint after the state is created, then add a watchpoint on the active field:

(lldb) breakpoint set --file src/main.rs --line 10
(lldb) run
(lldb) watchpoint set variable state.active
(lldb) continue

Execution stops at the line where state.active is changed:

frame #0: main at src/main.rs:15
    state.active = false;

Inspect the old and new values:

(lldb) frame variable state.active
(bool) state.active = false

The watchpoint has told you exactly which line changed the value. If this line was reached earlier than expected (because of an earlier call to a helper function that the code did not visibly call), the watchpoint would have fired at that earlier line instead.

This is the essential value of watchpoints: they reveal the moment of change without requiring you to anticipate where that change occurs.

When watchpoints are not the right tool

Watchpoints are powerful, but they are not always the right approach. Avoid watchpoints when:

  • The value changes very frequently. A counter that increments on every iteration of a tight loop will fire constantly. Use a conditional breakpoint instead, or add a condition to the watchpoint.
  • The value is optimized out. In optimized builds, the compiler may not keep the value in any addressable location. Watchpoints require an address.
  • The value is a temporary. Temporaries may live in registers, and watchpoints only work on memory. Watchpoints on registers are not supported on all platforms.
  • The value has been moved. After a move, the original location may no longer contain the value, and the new location may not be known.
  • The value is inside a complex async state. Async state machines move values between states at each suspension point. Watching a specific field across .await boundaries is difficult.

When a watchpoint is impractical, fall back to a breakpoint at a specific line, a conditional breakpoint, or a temporary println! in the source. Each has its own trade-offs, and the right choice depends on the shape of the problem.

Combining conditions and watchpoints

Because conditions and watchpoints are separate mechanisms, they can be combined when a problem requires it.

Conditional watchpoints

A watchpoint fires whenever the watched value changes. In some cases, you may only care about changes that satisfy a further condition. For example, you may want to stop when counter changes, but only when it exceeds 100:

(lldb) watchpoint set variable counter
(lldb) watchpoint modify 1 --condition 'counter > 100'

The watchpoint fires only when counter changes and the new value is greater than 100. This is useful when you know the interesting change occurs late in an otherwise frequent pattern.

Combined breakpoint and watchpoint investigations

A common investigation involves both a conditional breakpoint and a watchpoint. For example:

  1. Set a conditional breakpoint at the entry of a function to stop only for a specific input.
  2. Set a watchpoint on a field of the input to catch where the field is modified.
  3. Use the two together to trace the modification back to the responsible code.

The conditional breakpoint ensures you are observing the right invocation. The watchpoint then reveals where that specific invocation’s data changed.

This kind of combined investigation is often how bugs that depend on subtle state changes are found. Neither the condition nor the watchpoint alone would be enough; together, they narrow the observation to exactly the interesting case.

Rust 2024 notes on conditions and watchpoints

A few Rust 2024 specifics affect conditions and watchpoints.

unsafe blocks and watchpoints

When a watchpoint fires inside an unsafe block, the backtrace shows the frame where the mutation occurred, and the source location is inside the explicit unsafe block. Because Rust 2024 requires explicit unsafe { ... } blocks inside unsafe fn bodies, the source location of a mutation in unsafe code is now more precise than in earlier editions. This makes it easier to attribute a change to a specific unsafe operation, rather than to a general area of code.

Interior mutability and watchpoints

Rust 2024 discourages &static mut in favor of interior-mutability primitives such as Mutex, AtomicUsize, and UnsafeCell. From a watchpoint perspective, this changes the observable pattern: instead of a simple assignment to a global reference, you will see method calls that perform atomic operations, lock a mutex, or dereference an UnsafeCell. The watchpoint still fires when the underlying memory changes, but the backtrace shows the interior-mutability wrapper, not the direct assignment. Reading the backtrace carefully will tell you which operation triggered the change.

Const generics and conditions

Rust 2024 continues to support const generics, and the compiler generates specialized code for each const value used. If you set a conditional breakpoint on a function that is generic over a const parameter, the condition may apply to a specific instantiation or to all of them, depending on how LLDB resolves the symbol. When in doubt, use a source-line breakpoint, which avoids the ambiguity entirely.

Summary

In this chapter, we covered three refinements to the debugging loop:

  • Conditional breakpoints: stop at a location only when a condition is true. Use them to focus a breakpoint on a specific invocation in a repeated loop. Conditions work well with primitive comparisons and simple field accesses. They are less reliable with method calls, iterators, closures, and pattern matching, because the debugger’s expression evaluator does not perform full trait resolution or macro expansion.
  • Expressions: useful for computing derived values and, occasionally, for intervening in the program’s state. Prefer frame variable for inspection; use expr only when you have a specific reason and can accept the limitations of the evaluator.
  • Watchpoints: stop when a value changes. Use them when you know the value that goes wrong but not the location where it changes. Watchpoints depend on the value having a stable address, and they are less useful for temporaries, moved values, and optimized-out state.

We also looked at how conditions and watchpoints can be combined to narrow observations even further, and how Rust 2024 changes the shape of some of these observations, particularly around unsafe blocks, interior mutability, and const generics.

The next chapter moves to a larger scale: threads and async Rust. The tools from this chapter, especially watchpoints and conditional breakpoints, reappear there, but with new complications: the program has multiple stacks, and the runtime scheduler adds its own layer between your code and the machine.
