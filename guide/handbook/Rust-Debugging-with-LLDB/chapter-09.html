Chapter 9: Inspecting Rust Values

Once you have stopped the program at a chosen location, the next task is to look at what is actually there. This is the heart of debugging: comparing the state the program has with the state you expected. Everything else, stepping, frames, backtraces, breakpoints, exists to bring you to a place where you can inspect a value and ask whether it is correct.

In this chapter, we will look at how to inspect Rust values in LLDB. We will start with the primary command, frame variable, and then work through the common Rust types: primitives, strings, vectors, maps, structs, enums, references, and the arguments that entered a function. Along the way, we will see the discipline of inspecting one value at a time, which is particularly important in a screen-reader workflow.

The right tool: frame variable

LLDB offers two families of commands for looking at values:

  • frame variable reads the current storage associated with a variable and formats it using debug information. It does not evaluate anything.
  • expression (or expr) tries to evaluate an expression in the current frame. It may call into user code, allocate memory, or run into language semantics the debugger’s expression evaluator does not fully support.

For inspecting Rust values, frame variable is almost always the right tool. It is fast, safe, and reliable. Because it does not evaluate, it has no side effects. Because it uses debug information, it can render complex values using the Rust pretty-printers.

The general form is:

frame variable
frame variable NAME
frame variable NAME.FIELD
frame variable NAME.0

Where NAME is a local variable, a function argument, or an expression referring to nested fields or tuple indices.

We will use frame variable almost exclusively in this chapter. We return to expression in a later chapter, when the situation calls for it.

Inspecting primitives

The simplest case is inspecting primitive values. Suppose you have:

let count: i32 = 42;
let ratio: f64 = 0.75;
let active: bool = true;
let letter: char = 'R';

With the program stopped inside the same function, ask:

(lldb) frame variable count

You should see something like:

(int) count = 42

Notice the type shown is int, not i32. This is because LLDB renders the underlying C-level type. For Rust primitives, the underlying machine-level representation is the same as the corresponding C integer or floating-point type, so the layout matches. The Rust type information is still present in debug information, but the pretty-printer chooses to display the C name for simple values.

The same command works for the other primitives:

(lldb) frame variable ratio
(double) ratio = 0.75
(lldb) frame variable active
(bool) active = true
(lldb) frame variable letter
(char) letter = 'R'

These outputs are compact and readable. For a screen-reader workflow, this is ideal: one value, one line, one clear type.

Two details are worth noting:

  • Bool: Rust’s bool is displayed as true or false, not as 0 or 1. The Rust pretty-printer is handling the formatting.
  • Char: Rust’s char is a Unicode scalar value, not a C char. LLDB renders it as a quoted character, which matches the way you would write the value in Rust source.

If you ask for a variable that does not exist in the current frame, LLDB will say something like:

error: no variable named 'count' in this frame

As we saw in the previous chapter, the most common cause is being in the wrong frame. Use bt and frame select to move to the correct one.

Inspecting strings

Strings are one of the first places where Rust’s type system becomes visible in the debugger. Rust has two string types that matter here:

  • &str: a borrowed string slice, consisting of a pointer and a length.
  • String: an owned, growable, heap-allocated string.

Both are rendered by the Rust pretty-printers in a readable form.

Suppose:

let name = "Alice";                  // &str
let owned = String::from("Bob");     // String

Ask:

(lldb) frame variable name
(const char *) name = 0x... "Alice"

(lldb) frame variable owned
(std::string) owned = "Bob"

The &str is shown as a C string pointer with the contents in quotes. The String is shown as a fully materialized string. Both give you the human-readable text, which is what you usually want.

When the pretty-printers are not active, the String is displayed as its internal fields instead:

(alloc::string::String) owned = {
    vec = {
        buf = {
            ptr = { pointer = 0x... }
            cap = 3
            alloc = { ... }
        }
        len = 3
    }
}

This is the same value, but the presentation is far less useful. If you see this form, check that you launched the debugger with rust-lldb rather than plain lldb.

A detail worth knowing: Rust strings are UTF-8 encoded. A String can contain any sequence of valid UTF-8 bytes, including multi-byte characters. The pretty-printer handles multi-byte characters correctly, displaying them as the characters they represent.

Inspecting vectors and slices

Vectors (Vec<T>) and slices (&[T]) are the primary sequence types in Rust. Both are rendered as their element lists.

Suppose:

let numbers = vec![10, 20, 30, 40];
let slice = &numbers[1..3];

Ask:

(lldb) frame variable numbers
(std::vector<int, ...>) numbers = size=4 {
    [0] = 10
    [1] = 20
    [2] = 30
    [3] = 40
}

(lldb) frame variable slice
(...) slice = size=2 {
    [0] = 20
    [1] = 30
}

The exact formatting varies with LLDB version and pretty-printer configuration, but the shape is consistent: the vector shows its length and its elements, and the slice shows the portion it refers to.

For a vector of strings:

let names = vec![
    String::from("Alice"),
    String::from("Bob"),
];

The output shows each element rendered as a string, not as a nested struct. This is the pretty-printer composing type-specific formatters across nested values.

When a vector is very long, LLDB may truncate the display. You can inspect individual elements directly:

(lldb) frame variable numbers[2]

This gives you just the third element, without the surrounding structure. For a screen-reader workflow, this is often more useful than dumping the entire vector.

Inspecting maps and other collections

Rust’s standard library also provides HashMap, BTreeMap, HashSet, and BTreeSet. The pretty-printers render these as their entry lists:

use std::collections::HashMap;

let mut scores: HashMap<String, u32> = HashMap::new();
scores.insert("Alice".to_string(), 100);
scores.insert("Bob".to_string(), 85);

Ask:

(lldb) frame variable scores
(std::unordered_map<...>) scores = size=2 {
    ["Alice"] = 100
    ["Bob"] = 85
}

The exact form and ordering of entries depend on the map type. HashMap entries are not in any particular order; BTreeMap entries are sorted by key. In both cases, you see the semantic content: keys and values.

Inspecting a single entry directly is also possible:

(lldb) frame variable scores["Alice"]

However, this can be unreliable for HashMap, because the index expression must be evaluated as an operator. In practice, it is safer to dump the whole map and read the entry you care about, or to inspect the map through a helper method in your code.

For very large collections, the output is naturally large. The strategy of inspecting one value at a time applies here: instead of dumping the entire collection, consider adding a temporary helper in your code that extracts the specific entry you want to inspect, and inspect that instead.

Inspecting structs

Structs are the fundamental way to group related data in Rust. LLDB renders them field by field.

Suppose:

struct User {
    name: String,
    age: u32,
    active: bool,
}

let user = User {
    name: String::from("Alice"),
    age: 30,
    active: true,
};

Ask:

(lldb) frame variable user
(User) user = {
    name = "Alice"
    age = 30
    active = true
}

This is a small, readable view. For a screen-reader workflow, the field-by-field presentation is easy to scan because each field is on its own line and has a clear label.

To inspect a single field:

(lldb) frame variable user.name
(std::string) user.name = "Alice"

(lldb) frame variable user.age
(unsigned int) user.age = 30

Nested field access works as you would expect:

(lldb) frame variable user.name.0

However, .0 on a String is not the string’s bytes; it is the underlying Vec<u8>. This is one of the few cases where the pretty-printed form ("Alice") is far more useful than the raw field access. Use field access for struct fields you have defined; use the pretty-printed form for types the standard library provides.

A note on tuple structs: they have fields accessed by index (.0, .1, and so on). LLDB renders them the same way as regular structs, but the field names are numbers:

(lldb) frame variable pair
(...) pair = {
    [0] = 10
    [1] = 20
}

Inspecting nested values

Real Rust programs often have deeply nested structures. A configuration might contain a server sub-struct, which itself contains a TLS sub-struct, which contains a certificate path. Dumping the top-level config in full produces a large, hard-to-read output. Inspecting one field at a time produces a much clearer picture.

Suppose:

struct Server {
    host: String,
    port: u16,
}

struct Config {
    server: Server,
    debug: bool,
}

let config = Config {
    server: Server { host: "localhost".to_string(), port: 8080 },
    debug: false,
};

Instead of dumping the entire config:

(lldb) frame variable config

which shows every field, inspect one path at a time:

(lldb) frame variable config.server.host
(std::string) config.server.host = "localhost"

(lldb) frame variable config.server.port
(unsigned short) config.server.port = 8080

(lldb) frame variable config.debug
(bool) config.debug = false

Three small, targeted outputs are easier to read than one large block. In a screen-reader workflow, this is the difference between a usable session and a frustrating one.

This also helps when the config contains a field you do not care about, such as a large data structure that would flood the output. By asking only for the fields you want, you avoid producing output you do not need.

Inspecting enums

Enums are more interesting than structs because a value of an enum type is one of several variants. LLDB shows which variant is active and, if the variant carries data, the data it carries.

Suppose:

enum Message {
    Quit,
    Write(String),
    Move { x: i32, y: i32 },
}

let msg = Message::Move { x: 10, y: 20 };

Ask:

(lldb) frame variable msg
(Message) msg = Move {
    x = 10
    y = 20
}

This tells you several things at once: the enum type, the variant name, and the data the variant carries. For a Move variant with two fields, both are shown. For a Quit variant with no data, the output is simply:

(lldb) frame variable msg
(Message) msg = Quit

For a tuple-style variant, the fields are numbered:

(lldb) frame variable msg
(Message) msg = Write("Hello")

Enums are one of the places where the debugger is most valuable. Because match can dispatch on the variant, the specific variant active at runtime is not always obvious from reading the source. The debugger shows you exactly which variant is in play.

We will return to enums in the next chapter, when we look at Option, Result, and panics in more detail. For now, the important point is that the debugger exposes the variant and its data.

Inspecting references and borrows

Rust code frequently contains references: &T and &mut T. When the debugger shows you a reference, you need to distinguish between two things:

  • The reference itself: a pointer with a lifetime, at a specific memory address.
  • The value referenced: the data at the address the reference points to.

For most debugging, you want the value referenced.

Suppose:

fn update(config: &mut Config) {
    // ...
}

Stop inside update. Inspect:

(lldb) frame variable config
(Config *) config = 0x... {
    server = { ... }
    debug = false
}

Depending on LLDB version and pretty-printer configuration, the reference may be dereferenced automatically for display, showing you the value at the other end of the pointer. If it is not, you may need to ask for a field of the referenced value:

(lldb) frame variable config->debug

Or, equivalently:

(lldb) frame variable (*config).debug

Both forms tell LLDB to dereference the pointer before accessing the field. In practice, most Rust references are rendered with the dereferenced value automatically, because the Rust pretty-printers understand the reference type. If you see a raw address instead of a value, it usually means the reference is to a type the pretty-printer does not handle, or that optimizations have eliminated the value.

For a &str, the debugger shows the string directly:

(lldb) frame variable name
(const char *) name = 0x... "Alice"

For a &[T], the debugger shows the slice:

(lldb) frame variable items
(...) items = size=3 {
    [0] = ...
    [1] = ...
    [2] = ...
}

For a &mut T, the same as for &T, but the mutation is now visible: as you step forward, the value at that address changes.

A common pitfall: frame variable config on a reference may show the pointer value rather than the referenced value. When in doubt, try accessing a field through the reference, such as config.field or (*config).field. If that works, the reference is being followed correctly.

Arguments

Function arguments are part of the current frame. They are, in practice, the most frequently inspected values in any debugging session, because arguments tell you what entered a function.

For:

fn parse(input: &str, strict: bool) -> Result<Config, Error>

use:

(lldb) frame variable

or inspect them individually:

(lldb) frame variable input
(const char *) input = 0x... "..."
(lldb) frame variable strict
(bool) strict = false

Ask the fundamental question:

What entered this function?

Then:

Is it already wrong?

Then:

Or does it become wrong here?

The answer determines the direction of the next investigation. If the argument is already wrong on entry, the bug is upstream, in the caller. If the argument is correct on entry, the bug is either inside this function or downstream, after the function passes the value on.

Arguments are especially useful as debugging landmarks because they are always present at the entry of a function. Even if some locals have been optimized away, the arguments are usually accessible. This makes a breakpoint at a function entry a reliable observation point.

One useful technique: when you are unsure which function is at fault, place breakpoints at the entry of every function in the call path and inspect their arguments. The first function that receives an incorrect argument is the one whose caller is at fault.

Locating the first bad value

Suppose the final error is:

invalid configuration

Do not immediately investigate the final error.

Trace the value backward.

Ask:

Where was the value created?

Where was it transformed?

Where did it become invalid?

Which function first received the invalid value?

Set breakpoints at those transitions.

Then inspect the value.

The debugger becomes a tool for locating the first incorrect state.

Worked example: first wrong state

Suppose this program prints the wrong result:

#[derive(Debug)]
struct Config {
    path: String,
    debug: bool,
}

fn find_config() -> Option<Config> {
    let path = std::env::var("CONFIG_PATH").ok()?;

    if path.is_empty() {
        return None;
    }

    Some(Config {
        path,
        debug: false,
    })
}

fn load_config() -> Option<Config> {
    let config = find_config()?;
    Some(config)
}

fn main() {
    let config = load_config();

    match config {
        Some(c) => println!("{}", c.path),
        None => println!("no config"),
    }
}

The final symptom is:

no config

Do not start at main. Start at the boundary:

(lldb) breakpoint set --name find_config
(lldb) run

At entry:

(lldb) frame variable

You may see nothing useful yet. Step over the std::env::var call:

(lldb) next

Inspect path:

(lldb) frame variable path

If path is correct, continue:

(lldb) next

Check the if branch. Inspect:

(lldb) frame variable path

If path is empty here, you have found the first wrong state.

The investigation is:

main
→ load_config
→ find_config
→ env var
→ empty path

Now you can ask the real question:

Why is CONFIG_PATH empty or missing?

That is much better than guessing at the final None.

Note the debugging discipline here. We did not start by inspecting main. We started at a boundary, inspected the value at a specific point, and moved backward step by step until we found the first place where reality diverged from expectation. This is the opposite of stepping forward from the beginning of the program, and it is far more efficient when you have a concrete symptom to trace.

Value inspection discipline

A debugging session is a sequence of small observations. The way you manage those observations determines how productive the session feels.

A few rules of thumb:

  • Inspect the smallest useful piece of state. Ask for a single field rather than an entire struct, when the whole struct is not needed.
  • Ask one question at a time. Instead of “what is the state of the config,” ask “what is config.server.port.”
  • Compare with expectations. An inspection only has meaning when you compare it with what you expected. Say the expectation out loud, or write it down: “I expect config.debug to be true here.” Then check.
  • Record the surprising values. When a value differs from your expectation, that difference is the evidence you were looking for. Note it before moving on.
  • Avoid dumping collections. A map with a hundred entries produces output that is hard to read. A single key access, or a temporary helper function in your code, produces a much clearer observation.

For screen-reader workflows, these rules are especially important. Output that is easy to scan visually can be overwhelming when spoken aloud. One value at a time is the safest and most effective pattern.

When the value looks wrong

Sometimes, the debugger shows a value that does not match what you know to be true. There are several possible explanations, and it is worth knowing which one applies before concluding that the program is broken.

Moved values

When a value is moved, the compiler marks the original variable as no longer valid. But the bytes may still be present in memory, and LLDB may still show them if you ask. This can produce the illusion that a moved-from value “still has data.” In practice, the source-level rules still apply: the moved-from value cannot be used, and any appearance to the contrary is a debugger artifact, not a signal about the program’s actual behavior.

Optimized-out values

In optimized builds, LLDB may report a value as <optimized out>. This means the compiler decided not to keep storage for the value at this point. There is no runtime data to read. This is expected behavior, not a debugger bug. If you need to inspect such a value, switch to a debug build, or restructure the code so the value is used at the point you care about.

Stale values

When you step backward through an execution history, or inspect a frame that has returned, the value may be from an earlier point in time. This is rare in normal forward-stepping debugging, but it can occur when you inspect frames deep in the stack whose variables are no longer in scope.

Reference visualization

A reference displays the value at the other end of the pointer, which is what you want most of the time. But occasionally the display shows the pointer itself, or a stale pointer, or a pointer into memory the program no longer owns. When the displayed value seems impossible, ask whether you are looking at the pointer or the referenced value. frame variable (*expr).field is often more explicit than relying on automatic dereference.

Rust 2024 notes on value inspection

A few Rust 2024 specifics affect what you see when inspecting values:

  • unsafe extern blocks: Values declared inside an unsafe extern block are external symbols. When you inspect them, the debugger shows the C-level type, because that is the type the external library declared. This is expected and matches the FFI boundary.
  • #[unsafe(no_mangle)]: Functions exposed with this attribute keep their source names. When you inspect their arguments, the names are the ones you declared in source, which is often clearer than the mangled names of other functions.
  • static mut restrictions: Because Rust 2024 disallows references to static mut, global state is accessed through raw pointers or through interior-mutability primitives such as Mutex, AtomicUsize, or UnsafeCell. When you inspect such values, you will see the interior-mutability wrapper, not a bare reference. For example, a Mutex<T> shows the lock and the contained value; you may need to inspect the contained value after acquiring the lock in your code, or check the internal fields at the debugger level.
  • Async state: Futures are compiler-generated state machines. When you inspect a future, you see the state machine’s fields, including the variant indicating which suspension point the future is currently at. This is useful but can be verbose. In practice, most async debugging focuses on application state (the values inside the future), not the state machine’s internal structure.

Summary

In this chapter, we covered how to inspect Rust values in LLDB:

  • frame variable is the primary tool. It reads existing storage and formats it with Rust pretty-printers. It does not evaluate, so it is fast, safe, and reliable.
  • Primitives display as their corresponding C types, with values rendered in Rust-friendly form (true/false for bool, quoted characters for char).
  • Strings: &str shows as a C string pointer with contents in quotes; String shows as a materialized string.
  • Vectors and slices: rendered as element lists with length information.
  • Maps and sets: rendered as entry lists, with keys and values visible.
  • Structs: field-by-field view, with each field labeled and its value rendered by its own pretty-printer.
  • Enums: variant name plus the data the active variant carries.
  • References: shown as either the pointer or the referenced value, depending on the pretty-printer and configuration. When in doubt, dereference explicitly.
  • Arguments: the most important values in a frame, because they tell you what entered a function.
  • Locating the first wrong state: trace values backward from the symptom, stopping at each function boundary to ask whether the value is already wrong or becomes wrong here.
  • Discipline: inspect one small piece of state at a time, compare with expectations, and record surprising values.

We also covered the common ways a value can look wrong in the debugger: moved values, optimized-out values, stale values, and reference-visualization quirks. None of these mean the debugger is broken; each has a specific explanation and a specific remedy.

In the next chapter, we will focus on the two most common Rust enums: Option and Result. These appear in almost every Rust program, and the debugger’s ability to show which variant is active and what data it carries is one of the most useful features of Rust debugging.
