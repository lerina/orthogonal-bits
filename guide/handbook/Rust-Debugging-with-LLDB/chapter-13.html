Chapter 13: Threads and Async Rust

So far, every program we have debugged has had a single thread of execution and a single synchronous call stack. This is a useful starting point, but most real Rust programs are concurrent: they use operating system threads, or they use async Rust on a runtime, or both. Debugging these programs is not fundamentally different from debugging single-threaded ones, but the structure of execution changes in ways that affect what you see, how you navigate, and what questions make sense to ask.

In this chapter, we will look at debugging concurrent Rust programs. We will start with threads, then move to async. We will see how to inspect multiple stacks, how to select the thread or task you care about, and how to distinguish application code from runtime machinery.

Threads

Rust programs can use multiple threads through:

std::thread
Tokio
async runtimes
thread pools
libraries

LLDB can inspect them.

Use:

thread list

Then:

thread backtrace all

The latter displays backtraces for all threads. LLDB documents thread list, thread selection, and thread backtrace all as core thread-inspection operations.

What a thread list shows

When you run a Rust program that spawns threads, and then stop the debugger (with a breakpoint, a signal, or a crash), thread list shows something like:

Process 12345 stopped
* thread #1: tid = 12345, 0x... libc.so.6`__poll, name = 'main_thread', stop reason = breakpoint 1.1
  thread #2: tid = 12346, 0x... libc.so.6`__futex_wait, name = 'worker_1'
  thread #3: tid = 12347, 0x... libc.so.6`__futex_wait, name = 'worker_2'
  thread #4: tid = 12348, 0x... libc.so.6`__futex_wait, name = 'worker_3'

Read this carefully:

  • The asterisk (*) marks the currently selected thread. This is the thread the debugger is showing you when you run commands such as bt and frame variable.
  • thread #1: The first thread. In a typical Rust program, this is the main thread, or a thread the runtime spawned as part of startup.
  • tid = 12345: The operating system's thread ID. This is the identifier the kernel uses to schedule the thread. It is different from the debugger's thread number.
  • 0x... libc.so.6\`__poll: The current instruction address and its symbolic location. Here, the thread is blocked in a poll call. This is common when a thread is waiting for something, such as I/O or a message.
  • name = 'worker_1': The thread's name. Rust lets you give a thread a name with std::thread::Builder::new().name("worker_1").spawn(...). Naming threads is a practice that greatly helps debugging.
  • stop reason = breakpoint 1.1: Why this thread stopped. Only one thread is typically stopped at a time (the one that hit the breakpoint); the others are still running or blocked, but the debugger has paused the whole process, so they are effectively frozen.

This is the top-level view of a multithreaded program: which threads exist, what each is doing, and which one is currently selected.

Selecting a thread

List threads:

thread list

Then:

thread select 2

Now subsequent frame commands refer to that thread.

Then:

bt

This gives you that thread's call stack.

The debugging sequence becomes:

thread list
→ select suspicious thread
→ bt
→ frame select
→ frame variable

This is the standard workflow for multithreaded debugging. You identify the thread whose state interests you, select it, and then use all the frame-inspection tools you already know.

A note on thread selection and stability: the debugger's thread numbers (1, 2, 3, ...) are stable within a session, but the operating system's thread IDs can be reused after a thread exits. When you use thread select, prefer the debugger's thread number, not the OS thread ID.

Backtraces across threads

To see the backtrace for all threads at once:

thread backtrace all

This produces a concatenated list of backtraces, one per thread. For programs with many threads, the output can be very long. In a screen-reader workflow, this is often overwhelming; consider using thread list first to identify the thread that is interesting, and then thread select N followed by bt to inspect only that thread's stack.

Still, thread backtrace all is valuable when:

  • You do not know which thread is relevant.
  • You want to confirm that a deadlock involves two specific threads.
  • You want to check whether a worker thread has finished its job or is still running.
  • You want to see the overall shape of the program's concurrency.

In those cases, the full output is exactly what you want, even if it is long.

A worked thread example

Consider:

use std::thread;
use std::time::Duration;

fn worker(id: u32) {
    for i in 0..5 {
        println!("worker {} step {}", id, i);
        thread::sleep(Duration::from_millis(100));
    }
}

fn main() {
    let handles: Vec<_> = (0..3)
        .map(|id| {
            thread::Builder::new()
                .name(format!("worker_{}", id))
                .spawn(move || worker(id))
                .expect("failed to spawn thread")
        })
        .collect();

    for handle in handles {
        handle.join().expect("thread panicked");
    }

    println!("all workers finished");
}

Build the program:

cargo build

Launch under LLDB:

rust-lldb target/debug/thread_demo

Set a breakpoint inside worker:

(lldb) breakpoint set --name worker
(lldb) run

The first breakpoint hit occurs in one of the worker threads. Immediately ask:

(lldb) thread list

You should see several threads: the main thread, waiting in join or in the runtime, and the worker threads, some of which may also have reached worker. The asterisk marks the currently selected thread—likely the one that hit the breakpoint.

Inspect its backtrace:

(lldb) bt

You should see worker, then the thread startup machinery, then the runtime.

Inspect its arguments:

(lldb) frame variable id

The value tells you which worker triggered the breakpoint. If it is id = 0, you know worker 0 reached worker first.

Continue:

(lldb) continue

Another thread may hit the breakpoint. Inspect again:

(lldb) bt
(lldb) frame variable id

Now the id may be 1 or 2, depending on scheduling. Continue a few more times. You will see the workers interleave, which is exactly what you expect from concurrent execution.

To see all threads at once:

(lldb) thread backtrace all

This output will show, for each thread, where it currently is. The main thread will likely be blocked in a join; the other worker threads will be in worker, in sleep, or possibly finished.

Quit:

(lldb) quit

This small session illustrates the essential multithreaded debugging workflow: list threads, select one, inspect its backtrace and locals, and continue to observe the next interesting stop.

Named threads

In the example above, we used thread::Builder::new().name(format!("worker_{}", id)). This is not just a convenience. It is one of the highest-leverage debugging practices in concurrent Rust.

When you inspect thread list, the name field is shown for each thread. If your threads are named, you can immediately tell which is which:

* thread #1: tid = ..., name = 'main'
  thread #2: tid = ..., name = 'worker_0'
  thread #3: tid = ..., name = 'worker_1'
  thread #4: tid = ..., name = 'worker_2'

Without names, the list shows only thread numbers and IDs, which is much harder to reason about. Naming threads is a small effort with a large payoff, especially when debugging a program you did not write or have not read in a while.

A convention that works well in practice: use the purpose of the thread as the name, and add a numeric suffix if there are multiple. For example:

request-handler-0
request-handler-1
log-writer
cache-refresher

When you see a stop in cache-refresher, you know exactly what that thread is for.

Findings in thread backtraces

Backtraces for threads have the same shape as backtraces for the main thread: current frame at the top, callers below, runtime machinery at the bottom. The frames you care about are, again, the ones belonging to your own code. Common patterns:

  • Worker thread in a library function: The top frame is libc or std machinery, such as __futex_wait or epoll_wait. Below that, you will see the application function that called the blocking operation.
  • Worker thread in a channel receive: The top frame is std::sync::mpsc machinery. Below that, the application function that called recv.
  • Worker thread in a lock acquisition: The top frame is std::sync::Mutex or parking_lot. Below that, the application code that tried to acquire the lock.
  • Worker thread that has finished: The thread may still exist briefly after it has finished its work, but the runtime will clean it up.

The pattern of “deepest frame of my own crate is where the interesting call happened” applies to all threads, not just the main thread.

Threads and deadlocks

A deadlock occurs when two or more threads are each waiting for a resource held by another. From the outside, a deadlocked program appears to hang: no output, no progress, no crash.

Under the debugger, a deadlock is easy to confirm:

  1. Run the program.
  2. When it hangs, interrupt the debugger. In LLDB, this usually means sending an interrupt from the terminal, for example Ctrl+C.
  3. At the LLDB prompt, run thread list.
  4. Run thread backtrace all.

Each thread's backtrace tells you what it is currently doing. If two threads are both blocked in a lock acquisition, and one holds the lock the other is waiting for, and vice versa, you have found the deadlock.

In particular, look for frames such as:

std::sync::Mutex::lock
std::sync::RwLock::read
std::sync::RwLock::write
parking_lot::Mutex::lock

These are the classic signatures of a thread waiting on a lock. If multiple threads are waiting on locks, and no thread holds any lock in a state that could be released, the program is deadlocked.

The debugger does not diagnose the deadlock for you, but it gives you the evidence. From there, you can reason about the lock ordering and identify which pair of locks is the culprit.

Thread panic diagnostics

When a thread panics, the runtime unwinds that thread's stack. The other threads are unaffected (unless the panic strategy is abort). Under LLDB, the stop occurs on the panicking thread, and the other threads are frozen at whatever they were doing.

A useful pattern:

  1. Run the program.
  2. The panic occurs. The debugger stops.
  3. Run thread list. Note which thread has the stop reason.
  4. Run bt on that thread.
  5. Find the first frame belonging to your own code. That is the panic site.
  6. Optionally, run thread backtrace all to see where the other threads were at the moment of panic. This is often useful for debugging interactions between threads.

When a thread panics, the runtime also marks the thread's state. If the thread was joined by another thread, that other thread receives an Err from join. If you want to observe this, set a breakpoint at the join site and inspect the result.

Rust and async debugging

Async Rust requires a different mental model.

A function such as:

async fn load_config()

does not execute simply as an ordinary function call from beginning to end.

It creates a future.

The executor polls that future.

Execution may suspend at:

.await

and resume later.

Therefore:

A source-level async call chain is not identical to a simple synchronous stack trace.

LLDB may show executor/runtime frames between your application frames.

Do not mistake runtime machinery for the application architecture.

Look for the frames belonging to your crate.

Async debugging: expanded model

Async Rust is not just multithreading. It is a different execution model.

An async fn returns a future. The future is a state machine. Each .await is a possible suspension point.

When you debug async code, LLDB may show:

your application frame
runtime frame
poll frame
waker frame
your application frame again

That is expected.

Do not try to single-step through the entire runtime. Instead, set breakpoints at application boundaries:

request created
request parsed
operation started
await reached
response received
state updated
error converted

Then use continue to move between those boundaries.

A practical async debugging sequence:

breakpoint set --name load_config
run
frame variable
next
step
finish
bt
continue

Look for frames belonging to your crate. Treat Tokio, async-std, or other runtime frames as machinery unless the bug is specifically in the runtime.

The async state machine

To understand why async debugging looks different, it helps to understand what the compiler generates. An async fn such as:

async fn load() -> Config {
    let raw = read().await;
    let parsed = parse(raw).await;
    parsed
}

is compiled into something like a struct with a poll method. The struct has one variant per suspension point:

enum LoadFuture {
    Start,
    AwaitingRead { read_future: ReadFuture },
    AwaitingParse { raw: String, parse_future: ParseFuture },
    Done,
}

Each call to poll advances the future by one step, or returns Poll::Pending if the awaited operation is not ready yet. When the awaited operation completes, the runtime wakes the future and calls poll again, which resumes from where it left off.

When you inspect an async function in the debugger, the compiler-generated struct is what you see. The frame for load is not a conventional stack frame—it is a poll method invocation on the future struct. The frame's local variables include the current state of the future, and the values accumulated so far.

Breakpoints at .await points

In source, a .await is a single token. In the compiled code, it is a call to poll on the future being awaited. If you set a breakpoint at the source line containing the .await, LLDB will typically stop just before the future is polled.

This is a useful observation point. At that moment, the future has been created but not yet polled. Inspecting the future shows its initial state. After the breakpoint, you can step forward or continue, and the runtime will poll the future.

After the future completes, execution resumes on the same line, and the result of the awaited operation is available. To inspect the result, set a breakpoint on the line immediately after the .await.

Debugging an .await

Suppose:

let response = client.get(url).await?;

Break before the line.

Inspect:

url
client

Step.

If execution enters runtime machinery, use:

finish

or continue toward the next breakpoint in your own code.

A practical strategy is to set breakpoints at meaningful application-level boundaries:

request creation
request dispatch
response handling
error conversion
state update

rather than attempting to single-step through the entire async runtime.

Tokio debugging

With Tokio, your application may run inside:

runtime worker threads
scheduler code
polling machinery
waker machinery

Do not attempt to understand all of it immediately.

First identify:

Which task?

Which application function?

Which state?

Which await boundary?

Then investigate only the relevant path.

For asynchronous debugging, breakpoints at your own functions are generally more useful than stepping continuously through runtime internals.

What Tokio frames look like

A typical backtrace when stopped inside async code under Tokio might look like:

frame #0: my_app::fetch_data at src/fetch.rs:42
frame #1: my_app::handle_request::{{closure}} at src/handlers.rs:18
frame #2: tokio::runtime::task::core::Core::poll at ...
frame #3: tokio::runtime::task::harness::Harness::poll_inner at ...
frame #4: tokio::runtime::task::harness::Harness::poll at ...
frame #5: tokio::runtime::task::raw::poll at ...
frame #6: tokio::runtime::scheduler::multi_thread::worker::run at ...
frame #7: tokio::runtime::blocking::pool::spawn_thread::{{closure}} at ...
frame #8: std::sys::pal::unix::thread::Thread::new::thread_start at ...

Frames #0 and #1 belong to your application. Frames #2 through #5 are the Tokio task machinery. Frames #6 and #7 are the runtime worker. Frame #8 is the underlying OS thread.

When you step forward from frame #0, you may end up in frame #2 (the runtime's task poll), which is rarely what you want. Instead, use finish to return from your function, or set a breakpoint in a subsequent application function and use continue.

The pattern is: application frames are the interesting ones; runtime frames are the machinery that drives them. Do not try to reason about the application in terms of the runtime's internal structure.

Naming tasks

Tokio supports naming tasks via tokio::task::Builder. Named tasks appear in logs and, in some cases, in the debugger's output. This is analogous to naming threads: a small effort that greatly helps debugging, particularly in a runtime with many concurrent tasks.

If you have a task that handles HTTP requests, name it http-handler. If you have a task that refreshes a cache periodically, name it cache-refresher. When a panic or a hang occurs, the task name in the backtrace immediately identifies which part of the system was involved.

The Tokio runtime as a thread pool

An important fact about Tokio: it is a thread pool. A small number of OS threads (typically one per CPU core) execute many async tasks. From LLDB's perspective, this means:

  • thread list shows a handful of runtime worker threads, not one thread per task.
  • Each worker thread may be currently executing a different task, and the task it is executing can change between stops.
  • The mapping between a task and a thread is not fixed. A task can migrate between threads.

This is why thread list alone is not sufficient for async debugging. You may see three worker threads and a dozen tasks in flight; the debugger shows you the threads, not the tasks.

To inspect a specific task, you can:

  • Set a breakpoint at the task's entry function. When the breakpoint fires, the thread executing the task is selected, and you can inspect the task's state.
  • Use application-level logging to trace task progress.
  • Use Tokio's built-in task inspection tools, if available.

The key insight is that thread list tells you about OS threads, and OS threads are not the unit of interest in async code. The unit of interest is the task, and tasks are not directly visible in the debugger's thread list.

Debugging a panic in async code

When a panic occurs:

bt

Then separate:

your application frames

from:

Tokio/runtime frames

The important question is:

Which application frame produced the invalid state?

Then inspect:

frame variable

and trace backward.

Panics and task termination

An async task that panics does not necessarily crash the program. By default, Tokio catches panics that occur inside tasks and marks the task as failed. The runtime continues running other tasks. Depending on how the task was spawned, the panic may or may not be propagated:

  • If the task was spawned with tokio::spawn: The panic is caught, and the task's JoinHandle returns an Err containing the panic payload. The rest of the runtime continues.
  • If the task was awaited directly (not spawned): The panic propagates to the awaiting task, which may cause the whole program to abort if it reaches the top of the runtime.
  • If the panic strategy is abort: The program aborts on the first panic, regardless of where it occurs.

When you stop on a panic in async code, the backtrace may show many runtime frames between the panic site and the application frames that led to it. The first application frame is the panic site. Below it, frames show the async task chain, which may be non-contiguous because the task has been suspended and resumed multiple times.

Finding the task that panicked

In a runtime with many tasks, it is not always obvious which task panicked. A few strategies:

  • Look for the task name: If tasks are named, the backtrace may include the name in the task machinery frames.
  • Look at the panic message: The message often references the source location of the panic, which identifies the function that panicked.
  • Look at application frames below the runtime frames: The lowest application frame in the backtrace is usually the entry point of the task, which identifies the task's responsibility.

Once you have identified the task, you can set a breakpoint in its entry function to reproduce the panic in a controlled way.

Threads versus tasks

Do not automatically equate:

thread

with:

async task

A Tokio runtime may execute many tasks on a smaller number of worker threads.

Therefore:

LLDB thread
≠
Tokio task

A thread backtrace can tell you which OS thread is executing.

It does not automatically tell you the complete logical async task history.

For async debugging, combine:

LLDB
+
application logging
+
task identifiers where appropriate
+
targeted breakpoints

Why this matters

The mismatch between threads and tasks affects how you interpret the debugger's output.

  • Thread count is not task count: If you see three worker threads, you cannot conclude that there are three tasks. There may be hundreds of tasks being multiplexed onto those threads.
  • Thread identity is not task identity: If a breakpoint fires on thread #2 and later fires again on thread #2, it does not necessarily mean the same task is executing. It might be a different task that happens to be scheduled on the same thread.
  • Thread backtrace is not task backtrace: The backtrace of a worker thread shows the synchronous call chain of the currently executing task poll. It does not show the async call chain that led to the current state, because that chain is spread across earlier polls of the task, which have already returned.

This is why async debugging benefits enormously from application-level logging and from naming tasks. The debugger alone cannot reconstruct the async call graph; it can only show you the current moment.

Practical advice

When debugging async Rust, keep these principles in mind:

  • Prefer breakpoints at your own functions over stepping through runtime internals.
  • Use continue aggressively to move between meaningful application boundaries.
  • Name your tasks whenever possible, using tokio::task::Builder or equivalent.
  • Log task-level events, such as task start, task end, and task errors. The logs complement the debugger's view.
  • Do not try to follow a single task through all its suspensions. Instead, observe it at each application-level boundary.
  • When a task hangs, look at what it is waiting for: usually an I/O operation, a channel receive, or a lock. The frame below the runtime machinery is the application frame that initiated the wait.

Async vs. sync in the backtrace

One of the most confusing aspects of async debugging is that the backtrace mixes async and sync frames.

In synchronous code, every frame in the backtrace corresponds to a function that is currently executing. In async code, this is still technically true, but the frames do not correspond to the source-level call chain. A frame for load_config at the top of a poll method does not mean that load_config was called from the runtime; it means that the runtime is currently polling the future that load_config returned.

To distinguish the two, look at the names:

  • Synchronous frames: named after the source functions you wrote.
  • Async poll frames: often named poll, or {{closure}}, or contain async_block.
  • Runtime frames: named after the runtime crate, such as tokio::runtime::task::harness::Harness::poll.

A frame like my_app::load_config::{{closure}} is the async state machine for load_config. It is the current point in the async function's execution, being polled by the runtime. The frames below it are the runtime's own stack, which is executing the poll call.

Once you learn to read these frames, async backtraces become much less intimidating.

A worked async example

Consider a small Tokio program:

use tokio::time::{sleep, Duration};

async fn fetch_value(id: u32) -> u32 {
    sleep(Duration::from_millis(100)).await;
    id * 2
}

async fn process(id: u32) -> u32 {
    let value = fetch_value(id).await;
    value + 1
}

#[tokio::main]
async fn main() {
    let result = process(21).await;
    println!("result: {}", result);
}

Set a breakpoint inside fetch_value:

(lldb) breakpoint set --name fetch_value
(lldb) run

The breakpoint fires once. Inspect the thread list:

(lldb) thread list

You will see several worker threads, but only one is currently stopped (the one that is polling this task). Note the thread name—if it is the Tokio runtime's thread, it may be named something generic.

Inspect the backtrace:

(lldb) bt

You will see fetch_value at the top, then the async closure, then the runtime's task poll machinery. Below that, the runtime's worker.

Inspect the argument:

(lldb) frame variable id

The value is 21. The task was created with this specific id. If you had several tasks with different ids, you could set a conditional breakpoint to isolate one.

Continue:

(lldb) continue

Execution proceeds to sleep, which suspends the task. The runtime may poll other tasks in the meantime. Eventually, sleep completes, and the task resumes. If you had set a breakpoint after the .await, it would fire at that point, showing that the task has resumed.

Quit:

(lldb) quit

This example demonstrates the key pattern: the debugger stops at each application boundary where you have set a breakpoint, and the runtime handles suspension and resumption invisibly to the debugger's view.

When async debugging requires logging

In a complex async program with hundreds of concurrent tasks, even careful breakpoint placement may not be enough. The runtime multiplexes tasks in ways that make single-task debugging difficult. In these cases, logging becomes the primary tool, and the debugger becomes a supplement.

A practical combination:

  • Structured logging: Log each task's start, end, and error paths. Include a task identifier in every log entry.
  • Correlation IDs: Assign a unique ID to each request or unit of work, and propagate it through the logs. This makes it possible to reconstruct a single task's history even when it interleaves with others.
  • Targeted debugger use: When the logs narrow the problem to a specific task and time, set a conditional breakpoint that fires only for that task.
  • Selective task injection: If the runtime supports it, use the ability to spawn tasks with specific settings (single-threaded runtime, or a specific scheduler) to reduce nondeterminism during debugging.

This combination is standard practice in production Rust systems. The debugger and logging are complementary, not alternatives.

Rust 2024 notes on threads and async

A few Rust 2024 specifics affect thread and async debugging.

Async closures and 2024

Rust 2024 stabilizes async closures, which allow closures that are themselves async. From a debugging perspective, the compiled representation of an async closure is similar to an async function: a state machine with a poll method. The frame for an async closure may include additional compiler-generated names, but the essential structure is the same as for async fn.

When you set a breakpoint inside an async closure, the source-line breakpoint is often the most reliable way to reach it. Name-based breakpoints on closure names can be fragile because closure names are not part of the stable API.

Async in traits and 2024

Rust 2024 continues to support async fn in traits, either via the trait's async fn syntax or via the async-trait crate. When debugging async trait methods, the backtrace shows the concrete implementation being called, wrapped in the state machine for the trait method. As with other async code, look for the application frames and ignore the runtime machinery.

Thread-scoped and 2024

Rust's scoped threads (std::thread::scope) allow threads to borrow data from the enclosing scope. This is a source-level change that affects when threads finish: they are guaranteed to finish before the enclosing scope ends. From a debugging perspective, scoped threads appear like ordinary threads in thread list, but the guarantee that they finish before the enclosing scope ends makes their behavior slightly more predictable.

unsafe extern and threads

When Rust code calls into C libraries that spawn or manage threads, the interaction between Rust's thread model and the C library's thread model can be subtle. In Rust 2024, the declaration of the foreign function is inside an unsafe extern block, and any thread-related invariants are the caller's responsibility. From a debugging perspective, this means that threads created inside C code may not have Rust names and may not appear as standard Rust worker threads. They will still appear in thread list, but their names may be empty or generic.

Summary

In this chapter, we covered debugging concurrent Rust programs:

  • Threads: how to list them, select one, read its backtrace, and inspect its frames. Named threads greatly simplify this process.
  • Multithreaded workflow: the pattern of list, select, inspect, continue. Each thread has its own stack; the selected thread determines which stack you see.
  • Deadlocks: the debugger does not diagnose them, but it provides the evidence. If multiple threads are blocked on lock acquisitions, and no thread can make progress, the program is likely deadlocked.
  • Async Rust: a different execution model, where an async fn returns a future and an executor polls it. The debugger shows runtime machinery between application frames; this is expected and not a bug.
  • Tokio: a thread pool that runs many tasks on a few threads. thread list shows threads, not tasks. Prefer application breakpoints and logging over stepping through runtime internals.
  • Panics in async code: caught by the runtime in most cases, propagated via the JoinHandle. The first application frame in the backtrace identifies the panic site.
  • Threads vs. tasks: a thread is not a task. A single OS thread may execute many tasks over time. The debugger's thread selection tells you about OS threads, not logical tasks.
  • Async vs. sync frames: async state machine frames are named after the async function with compiler-generated suffixes. Runtime frames are named after the runtime crate.
  • Rust 2024 specifics: async closures and async-in-trait are stabilized, scoped threads give stronger guarantees, and unsafe extern for C thread functions affects how foreign threads appear.

The unifying principle for all concurrent debugging: the debugger shows you the machine's view, but the questions you ask are about the program's behavior. Translating between the two is what makes concurrent debugging productive.
