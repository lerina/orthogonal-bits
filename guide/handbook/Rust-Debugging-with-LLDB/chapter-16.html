Chapter 16: Unsafe Rust, Memory, and FFI

Unsafe Rust, raw memory, and foreign function interfaces are the areas of the language where the debugger’s view is often more valuable than the source’s. This is a reversal of the usual situation: in most Rust code, the source is clear and the runtime is where bugs hide. In unsafe code, the source is terse and the invariants it depends on are not written down. The debugger is often the only way to observe whether those invariants actually hold.

This chapter is about debugging at the lowest level of Rust: raw pointers, uninitialized memory, buffer lengths, alignment, and the boundary between Rust and C. These are areas where a mistake can lead to memory corruption, undefined behavior, or a segmentation fault that occurs far from the code that caused it. In such cases, careful observation is what separates a productive debugging session from a long search for a phantom bug.

We will not teach unsafe Rust from scratch. We assume you understand what unsafe means and have written some unsafe code. The focus of this chapter is how to debug it.

Unsafe Rust: expanded context

Unsafe Rust does not mean “no rules.” It means the compiler is not enforcing all the rules for you.

When debugging unsafe code, ask:

What invariant is assumed here?
Where was this pointer created?
What guarantees its validity?
What is the length?
What is the capacity?
What is the alignment?
Who owns this memory?
Who may mutate it?
When does it become invalid?

LLDB can show you the runtime state:

frame variable ptr
memory read ptr
memory region ptr

But LLDB cannot prove the invariant. That is source-level reasoning.

For unsafe code, combine:

code review
tests

Miri is especially useful for detecting undefined behavior in Rust before it becomes a mysterious runtime bug.

The five unsafe superpowers and their debug signatures

Rust’s unsafe keyword grants five specific abilities that safe Rust does not have. Each of them has a characteristic debugger signature, and knowing them helps you recognize what is happening at a breakpoint.

  1. Dereferencing a raw pointer: *const T and *mut T. In the debugger, raw pointers appear as plain addresses, not as dereferenced values. To see the value, you must dereference explicitly.
  2. Calling an unsafe function: Functions declared unsafe fn can only be called from within unsafe blocks. In the backtrace, the frame for an unsafe function looks the same as for any other function, but its source may have different invariants.
  3. Accessing or modifying a mutable static variable: In Rust 2024, references to static mut are disallowed. Access is through raw pointers or interior-mutability primitives. In the debugger, you see the pointer or the wrapper type, not a bare reference.
  4. Implementing an unsafe trait: Traits such as Send and Sync are unsafe to implement because a wrong implementation breaks the language’s guarantees. In the debugger, there is no runtime signature of an unsafe trait implementation; the consequences appear as data races, incorrect sharing, or memory corruption.
  5. Accessing fields of a union: Unions allow multiple fields to share storage. Reading a field that was not the last one written is undefined behavior. In the debugger, a union shows all its fields as overlaying the same memory, and it is not always obvious which one is valid.

Each of these has a distinct debugging pattern. The rest of this chapter treats them in order of how often they appear in real Rust programs.

Observing unsafe invariants

Every unsafe block is built on at least one invariant: a promise about memory that the compiler cannot verify. Common invariants include:

  • A pointer is non-null.
  • A pointer points to initialized memory.
  • A pointer is aligned for its type.
  • A slice’s length does not exceed the allocation’s capacity.
  • Two pointers do not alias when they should not.
  • A value is not aliased mutably while also being read.
  • A Vec’s length and capacity are consistent.
  • A reference does not outlive its data.

When debugging an unsafe block, the first task is to identify which invariant is expected and then to check whether it holds at the point of the unsafe operation. A breakpoint just before the operation is usually the right place to check.

For each invariant, there is a specific inspection:

  • Non-null: frame variable ptr shows the address. Check that it is not zero.
  • Initialized: This is hard to check from the debugger. You may need to trace back to where the memory was allocated and confirm that the initialization path ran.
  • Aligned: Inspect the address. Rust types have alignment requirements; for a type T, the address must be a multiple of align_of::<T>().
  • Length and capacity: Inspect the len and cap fields of the Vec or slice.
  • Aliasing: Check the backtrace and source for other references to the same data that may be active.

The debugger does not check invariants for you. It gives you the values; you interpret them.

Useful commands include:

Use these when ordinary Rust variable inspection is insufficient.

For normal Rust application debugging, prefer:

Reading memory

The memory read command reads a specified number of bytes at a given address and formats them according to a chosen type.

(lldb) memory read --format hex --size 4 --count 16 0x5555559e0a10

This reads sixteen 4-byte values starting at the given address and displays them in hexadecimal. The output is a dense representation, useful for spotting patterns such as repeated values or unexpected zeroes.

Common options:

  • --format: hex, decimal, binary, character, string. Use string for C-style null-terminated strings, decimal for integers, hex when you need to see raw bytes.
  • --size: The size of each element. 1 for bytes, 4 for u32, 8 for u64.
  • --count: How many elements to display.

A useful combined form: memory read --format string (or -f s) followed by an address, to inspect a C string. This is the primary way to verify what a *const c_char pointer is actually pointing to when debugging FFI.

Memory regions

The memory region command tells you what kind of memory an address belongs to.

(lldb) memory region 0x5555559e0a10
[0x00005555559e0000-0x0000555555a00000) rw- /path/to/binary

The output includes the address range, the permissions (r for read, w for write, x for execute), and the backing file if any. This is useful for identifying:

  • Whether an address is in a valid memory region at all.
  • Whether it is writable (if you are investigating a write to read-only memory).
  • Which binary or shared library the memory belongs to.

If a pointer points to an address that is not in any region reported by memory region, the pointer is invalid and dereferencing it will crash. This check is a fast way to confirm a suspected dangling pointer.

Examining a Rust Vec in memory

A Rust Vec<T> is a struct with three fields: ptr, len, and cap. Under normal inspection, frame variable shows the elements. But when debugging unsafe code that manipulates a Vec directly, you may need to inspect its raw fields.

(lldb) frame variable items.ptr
(lldb) frame variable items.len
(lldb) frame variable items.cap

With the pointer, length, and capacity in hand, you can do the following:

  1. Confirm that len <= cap (a fundamental invariant).
  2. Confirm that the pointer is non-null when the capacity is greater than zero.
  3. Read the raw element bytes at the pointer to see what is actually stored.
  4. Check that the pointer is aligned for the element type.

When unsafe code violates the len <= cap invariant, downstream operations can read past the allocation, write into unallocated memory, or crash. This is one of the most common causes of memory corruption in unsafe Rust, and it is very hard to find without the debugger.

Examining a String in memory

A String is a wrapper around a Vec<u8>, so the same invariants apply. The interesting extra detail is that a String must be valid UTF-8. If unsafe code produces a String whose bytes are not valid UTF-8, reading the string later can cause undefined behavior.

To inspect the raw bytes of a String:

(lldb) frame variable s.vec.ptr
(lldb) memory read --format hex --size 1 --count 16 <ptr>

The bytes shown are the raw UTF-8 encoding of the string. If you see a byte sequence that is not valid UTF-8 (for example, a leading byte without the expected continuation bytes), the String was constructed incorrectly, and any later use of it is undefined behavior.

Checking for buffer overflow

Buffer overflow is one of the classic vulnerabilities in unsafe code. In Rust, it usually appears as a mismatch between an index or length used in unsafe code and the actual allocation.

Suppose you have:

unsafe {
    let slice = std::slice::from_raw_parts(ptr, len);
    let first = slice[0];
}

If len is larger than the allocation that ptr points to, from_raw_parts creates a slice that reaches past the end of valid memory. Reading slice[0] is fine, but reading slice[len - 1] is undefined behavior.

A practical check:

  1. At the breakpoint, inspect ptr and len.
  2. Use memory region on ptr to find the end of the region.
  3. Compare ptr + len to the region end. If ptr + len exceeds the region, the slice is out of bounds.

This is a low-level but effective way to confirm a buffer overflow before it manifests as a crash.

Using Miri instead of, or in addition to, LLDB

For many unsafe bugs, the right first tool is not LLDB but Miri. Miri is an interpreter that runs Rust code at the intermediate representation level and detects undefined behavior that would not be detectable by running the compiled binary.

Install and run Miri:

rustup +nightly component add miri
cargo +nightly miri test

Miri can detect:

  • Out-of-bounds accesses, even when they do not crash.
  • Use of uninitialized memory.
  • Data races in unsafe code.
  • Invalid pointer arithmetic.
  • Violations of aliasing rules.
  • Reading from a pointer with the wrong provenance.

Miri is slower than running the compiled binary, so it is best used on a small, targeted test case. When Miri finds an issue, it prints a detailed diagnostic that is often more informative than anything the debugger can produce, because Miri has access to the full semantics of the program.

A practical workflow:

  1. Reproduce the bug in a small unit test.
  2. Run the test under Miri. If Miri reports undefined behavior, fix the bug there.
  3. If Miri does not reproduce the bug, run the same test under LLDB to inspect runtime state.

LLDB and Miri are complementary. Miri detects violations of the abstract semantics; LLDB shows you the concrete machine state at a particular moment.

Address Sanitizer and ASan

Rust supports the AddressSanitizer (ASan), a runtime instrumentation that detects memory errors such as use-after-free and buffer overflow. To use ASan, build with the appropriate flag:

RUSTFLAGS="-Zsanitizer=address" cargo +nightly build -Zbuild-std --target x86_64-unknown-linux-gnu

The exact invocation depends on your toolchain and target. ASan produces a report when a memory error is detected, including the allocation stack, the use stack, and the type of error.

ASan is useful for:

  • Finding memory errors in unsafe code that does not crash immediately.
  • Detecting errors in FFI interactions, where the C side may have its own memory bugs.
  • Confirming a suspected buffer overflow at runtime.

ASan is more expensive than normal execution, often two to three times slower, so it is used on test builds, not production. But for debugging memory corruption, it is one of the most valuable tools available.

FFI debugging

Rust interacting with C introduces another debugging boundary.

You may see:

Rust
→ extern "C"
→ C function
→ Rust callback

Use breakpoints at the boundary.

Inspect:

Rust arguments
C arguments
return values
pointers
lengths
ownership assumptions

If the problem crosses the language boundary, LLDB becomes particularly useful because it can follow the native execution rather than treating Rust as an isolated world.

Identifying the FFI boundary in the backtrace

A backtrace that crosses the Rust-C boundary looks like this:

frame #0: c_library::process_buffer at c_library.c:42
frame #1: my_app::call_c_function at src/ffi.rs:15
frame #2: my_app::main at src/main.rs:10
frame #3: std::rt::lang_start_internal at ...

Frames #1 and #2 belong to Rust. Frame #0 belongs to C. The boundary is between frame #1 and frame #0. If the bug is a mismatch between what Rust passed and what C expected, the interesting inspection points are:

  • Frame #1: Inspect the Rust arguments and the pointer, length, and other values being passed.
  • Frame #0: Inspect the C arguments and the pointer, length, and values that C actually received.

Comparing the two inspections reveals whether the mismatch happened on the Rust side (the argument was already wrong when Rust called C) or on the C side (the argument arrived correctly but C used it incorrectly).

Inspecting C strings across the boundary

A *const c_char pointer is displayed by LLDB as a plain address. To see the string contents, use memory read with the string format:

(lldb) memory read --format string 0x7fffffffe100

Or, use the frame variable display which often renders const char * as a string with quotes:

(lldb) frame variable name
(const char *) name = 0x... "Alice"

For *const c_char that comes from Rust’s CString, the pointer is null-terminated and the string is valid as long as the CString is alive. For *const c_char received from C, the string is valid according to the C library’s contract; you may need to consult the C documentation to know how long it remains valid.

The most common FFI bug involving strings is a lifetime mismatch: Rust passes a pointer to a CString that is dropped before C finishes using it. The debugger may show a valid-looking string if the memory has not yet been overwritten, but later the same address may contain garbage. If a suspicious string reading appears, check whether the CString that owned the memory is still alive at the point of use.

Verifying pointer arguments to C functions

Before stepping into a C function, verify that the pointer you are passing is valid and points to the expected data.

Steps:

  1. At the breakpoint just before the FFI call, inspect the pointer: frame variable ptr.
  2. Check that it is not null.
  3. Check that it is aligned appropriately for the target type.
  4. Use memory region to confirm the pointer is in a valid region.
  5. Use memory read to inspect the data at the pointer.

If any of these checks fail, the FFI call is likely to crash or produce garbage. The cause is usually upstream in Rust: a slice was created with the wrong length, a Vec was reallocated after the pointer was taken, or a value was moved while C was still holding a pointer to it.

Observing the return value from a C function

When the C function returns, step out of it and inspect the return value in the Rust caller:

(lldb) finish
(lldb) frame variable result

The returned value is what C produced. If it does not match the expected value, the mismatch is on the C side (unless the C function is correct and the expected value was wrong).

For functions that return a status code (int), the debugger shows the raw integer. You may need to consult the C library’s documentation to interpret it: is 0 success? Is -1 a generic error? What do specific error codes mean?

Rust callbacks called from C

When C calls back into Rust, the call direction reverses. The backtrace looks like:

frame #0: my_app::rust_callback at src/ffi.rs:42
frame #1: c_library::invoke_callback at c_library.c:88
frame #2: my_app::call_c_function at src/ffi.rs:15
frame #3: my_app::main at src/main.rs:10

Frame #0 is the Rust callback. Its arguments are what C passed. Frame #1 is the C library invoking the callback. Frame #2 is the original Rust call into C.

Set a breakpoint on the Rust callback function. When it fires, inspect the arguments. These are values that came from C, and they may not match the Rust types you expect. A common bug is passing a Rust struct by pointer to C, then C mutating it before invoking the callback, causing the callback to see inconsistent state.

If the callback is invoked from a C-created thread, the thread has no Rust thread name. thread list shows it as an unnamed thread. This is expected; the Rust runtime does not know about threads created by C code.

FFI and panics

A Rust panic that crosses an FFI boundary is undefined behavior. Historically, Rust had no way to enforce this at compile time, so it was the programmer’s responsibility to ensure that any panics in FFI functions were caught before returning to C.

Rust 2024 changes this. All extern blocks are now unsafe extern, and this is a signal to the programmer that the functions declared there have unsafe contracts. If a Rust function exposed with #[unsafe(no_mangle)] and pub extern "C" panics, the panic will attempt to unwind across the FFI boundary, which is undefined behavior.

When debugging such a case, the runtime may exhibit:

  • A crash inside the C library, not in Rust, because the C library cannot handle the Rust unwinding.
  • A message about “Rust cannot catch foreign exceptions” or similar runtime diagnostics.
  • A stack that appears truncated or inconsistent because unwinding across the boundary is not supported.

To debug this, set a breakpoint on the panic machinery before it unwinds. The panic is the root cause; the C-side crash is a symptom.

The fix is to catch panics at the FFI boundary:

use std::panic;

#[unsafe(no_mangle)]
pub extern "C" fn safe_ffi_entry(input: *const u8, len: usize) -> i32 {
    let result = panic::catch_unwind(|| {
        // Actual logic here
        0
    });

    match result {
        Ok(code) => code,
        Err(_) => -1, // Panic was caught; return an error code to C
    }
}

With this pattern, no panic ever crosses the FFI boundary. The debugger will still show the panic site if you break on the panic machinery, but the program will not exhibit undefined behavior.

Inspecting Rust 2024 unsafe extern blocks

In Rust 2024, an extern block is written as unsafe extern:

unsafe extern "C" {
    fn c_function(input: *const u8, len: usize) -> i32;
}

From a debugging perspective, nothing changes in the machine code. The symbol c_function is a foreign function, and LLDB resolves breakpoints on it as it would for any external symbol.

What changes is the source-level contract. The unsafe extern block signals that:

  • The functions declared inside have unsafe preconditions.
  • The programmer is responsible for verifying those preconditions.
  • Individual items inside the block can be marked safe or unsafe to indicate their specific contract.

When you see an unsafe extern block in the source, treat it as a signal to check every argument carefully at the FFI boundary. The debugger is the natural place to do this.

A practical FFI example

Consider a Rust program that calls a C library to compute a checksum:

// Rust side
unsafe extern "C" {
    fn compute_checksum(data: *const u8, len: usize) -> u32;
}

fn call_checksum(input: &[u8]) -> u32 {
    unsafe { compute_checksum(input.as_ptr(), input.len()) }
}

Suppose the program crashes inside compute_checksum.

Set a breakpoint at the call site:

(lldb) breakpoint set --file src/main.rs --line 8
(lldb) run

At the breakpoint, inspect the arguments:

(lldb) frame variable input
(...) input = size=N { ... }

(lldb) frame variable input.as_ptr()
(const unsigned char *) = 0x7fff...

Verify:

  • The pointer is not null.
  • The pointer is aligned for u8 (always true for byte data).
  • The length is not zero.
  • The pointer is in a valid memory region.

Then step into compute_checksum:

(lldb) step

Inside the C function, inspect the arguments again. If they match what Rust passed, the bug is on the C side. If they do not match, the bug is at the boundary.

If the C function is not compiled with debug information, LLDB may not have source-level information for it. You can still step through its machine code, but the display will be assembly. In that case, use memory read to inspect the buffer at the pointer, and compare it with what Rust expected to pass.

Debugging FFI libraries without debug info

Many C libraries are compiled without debug information or with limited debug information. When debugging such a library, you will see:

  • Mangled or unclear function names in the backtrace.
  • Missing source lines for C frames.
  • Arguments displayed as raw registers or memory.

You can still debug effectively by using the following techniques:

  • Set breakpoints on symbol names: Use image lookup --name to find the exact symbol name in the C library.
  • Inspect arguments manually: At the entry of a C function, the argument registers (on x86_64, rdi, rsi, rdx, and so on) hold the arguments. Use register read to inspect them.
  • Read memory at the pointers: Use memory read to see what the C function is working with.
  • Step through assembly: Use stepi (step instruction) to step one machine instruction at a time. Combined with the register inspection, this lets you follow the C function’s logic even without source.
  • Look up the C library’s documentation: A function’s documented behavior tells you what to expect. If the debugger shows something that contradicts the documentation, you have found a suspect.

Debugging assembly is harder than debugging source, but it is sometimes unavoidable. The skills transfer: you still set breakpoints, inspect values, and trace execution. Only the display format changes.

Inspecting Rust 2024 static mut alternatives

Rust 2024 disallows references to static mut. If you are debugging code that previously used &static mut, you will now see one of the alternatives in the source and in the debugger:

  • Raw pointers: The address is a *mut T that must be dereferenced inside an unsafe block. In the debugger, the pointer appears as an address. Dereference explicitly to inspect the value.
  • Interior-mutability primitives: Mutex<T>, RwLock<T>, AtomicUsize, and UnsafeCell<T>. In the debugger, the wrapper is shown, and the wrapped value is shown as its field. For a Mutex<T>, you can inspect the inner value without needing to lock it in the debugger, but the value is only meaningful if the lock is currently held or the mutex is not contended.
  • Atomic types: For example, AtomicUsize. The debugger shows the atomic’s internal value. This is the current value of the atomic, which is exactly what you want to see, but remember that the value could change at any moment if other threads are running.

The practical difference for debugging is that you now have a wrapper type to inspect, rather than a bare reference. This is a small inconvenience in exchange for the safety and clarity that Rust 2024 provides.

Rust 2024 notes on unsafe and FFI

A few Rust 2024 specifics affect debugging unsafe code and FFI.

unsafe extern blocks

In Rust 2024, all extern blocks are unsafe extern. This is a source-level change that makes the FFI boundary more explicit. From a debugging perspective, the machine code is unchanged. The breakpoints, backtraces, and memory inspections work the same way as in earlier editions.

However, the item-level safety annotations (items inside an unsafe extern block can be marked safe or unsafe) give you a hint about the FFI contract. When you see an item marked safe, it means the compiler considers its preconditions to be checked at the call site. When it is marked unsafe, the caller must uphold the preconditions manually. This affects where you should set breakpoints and what you should inspect.

Unsafe attributes

#[no_mangle], #[export_name], and #[link_section] are now written #[unsafe(no_mangle)], #[unsafe(export_name = "...")], and #[unsafe(link_section = "...")]. This change matters for debugging because:

  • A #[unsafe(no_mangle)] function appears under its exact source name in the symbol table. Breakpoints on the unmangled name resolve reliably.
  • A #[unsafe(export_name = "custom_name")] function appears under custom_name in the symbol table, not under the Rust source name. To set a breakpoint, use the custom name.
  • A #[unsafe(link_section = "...")] function or data may be placed in a non-standard section. The debugger’s memory region command can help identify the section if needed.

unsafe_op_in_unsafe_fn

Rust 2024 warns when unsafe operations appear inside an unsafe fn without an explicit unsafe { ... } block. This is a source-level change, but it affects debugging because the explicit unsafe blocks give natural breakpoint locations. You can place a breakpoint at the opening of an unsafe block to stop just before the unsafe operation begins.

This is a small but useful improvement for debugging unsafe code: the source now marks its unsafe regions explicitly, and you can navigate them accordingly.

Reference to static mut

Rust 2024 disallows references to static mut. This is a fundamental source-level change that affects both how you write and how you debug global mutable state. The debugger will show:

  • Raw pointers, when global state is accessed via *mut.
  • Interior-mutability types, when global state is wrapped in Mutex, RwLock, AtomicUsize, or UnsafeCell.
  • No simple references to global mutable memory.

When debugging such code, the source-level rules still apply: references to static mut are not allowed. If you see a reference in the debugger, it may be a stale memory read from before the restriction was applied, or a raw pointer disguised as a reference in the debugger’s display. In either case, treat it with the appropriate caution.

Edition 2024 and Miri

Miri supports the Rust 2024 edition. In fact, Miri is often ahead of the stable compiler in enforcing new semantics. If you are using Rust 2024 features (such as the new unsafe extern rules), Miri is an excellent way to confirm that your unsafe code does not violate the new semantics.

Run Miri with the 2024 edition set in your project:

rustup +nightly component add miri
cargo +nightly miri test

Miri will check your unsafe code against the 2024 semantics, including the new unsafe extern rules and the stricter handling of raw pointers.

Summary

In this chapter, we covered debugging at the lowest level of Rust:

  • Unsafe Rust: every unsafe block depends on an invariant. The debugger’s job is to show you the state, not to verify the invariant. Combined with Miri and sanitizers, the debugger is one of several tools for finding unsafe bugs.
  • The five unsafe superpowers: raw pointers, unsafe functions, static mut (now restricted in Rust 2024), unsafe traits, and unions. Each has a distinct debug signature.
  • Memory debugging: memory read and memory region are the tools for inspecting raw memory when source-level inspection is not enough. Use them to verify pointers, check alignment, and confirm buffer bounds.
  • Vec and String in memory: both are structs with ptr, len, and cap fields. Checking the len <= cap invariant is a fast way to catch memory corruption.
  • Buffer overflow: compare ptr + len to the end of the memory region reported by memory region. If the pointer + length exceeds the region, the slice is out of bounds.
  • Miri: a Rust interpreter that detects undefined behavior, including use-after-free, out-of-bounds access, uninitialized reads, and data races. Prefer Miri for detecting undefined behavior; use LLDB for inspecting concrete runtime state.
  • Address Sanitizer: a runtime instrumentation that detects memory errors. Slower than normal execution but extremely effective at catching bugs that would otherwise be silent.
  • FFI debugging: the boundary is between the Rust and C frames in the backtrace. Inspect arguments on both sides, verify pointers, and check pointer + length against the memory region. In Rust 2024, all extern blocks are unsafe extern, and item-level safety annotations provide more explicit contracts.
  • FFI and panics: a panic across the FFI boundary is undefined behavior. Catch panics at the boundary with panic::catch_unwind. Under LLDB, break on the panic machinery before unwinding begins.
  • Debugging without debug info: even without source lines for a C library, you can inspect argument registers, read memory at pointers, and step through assembly.
  • Rust 2024 specifics: unsafe extern blocks, unsafe attributes, and the static mut restriction change the source and the debugger’s view, but not the fundamental mechanics of debugging.

The unifying principle for unsafe and FFI debugging: identify the invariant, observe the runtime state, and compare. The debugger cannot prove that unsafe code is correct, but it can show you the state that determines whether it is.
