Chapter 3: Why Rust Debugging Is Different

Rust adds several complications that do not appear in a simple C or C++ debugging session.

Understanding these complications up front saves a great deal of confusion later. When LLDB behaves in a way that seems strange, it is almost always because one of the factors in this chapter is at play.

The purpose of this chapter is not to teach you how to solve all of these problems yet. It is to give you the vocabulary to recognize them when they appear, so that you can respond calmly rather than assuming that the debugger is broken or that you have made a mistake.

Name mangling

Rust functions are often compiled into symbols with mangled names. A source-level name like:

parse_config

may become something like:

_ZN7my_crate12parse_config17h...

The mangled form encodes the crate name, the module path, the function name, the generic parameters, and a hash to disambiguate between overloads and instantiations. This is not unique to Rust. C++ has its own mangling scheme, and languages that support generics and modules generally need some way to encode the extra information in the linker symbol.

LLDB can often match the human name, but not always. This is why source-line breakpoints are sometimes more predictable than function-name breakpoints.

When a name-based breakpoint fails to resolve, the practical alternatives are:

  • Use breakpoint set --file src/main.rs --line 42 to break by source location instead of by name.
  • Use image lookup --name parse_config to ask LLDB what symbols actually exist that might match.
  • Use nm or rustfilt on the binary to inspect the symbol table directly.

A related complication: generic functions and trait methods can produce multiple concrete instantiations, each with its own mangled name. A single source-level name like process<T> may correspond to many distinct symbols in the binary. When you break on process, LLDB may resolve the breakpoint to every instantiation at once, or it may pick one arbitrarily.

Optimization

Rust’s optimizer can:

inline functions
reorder instructions
remove variables
merge values
specialize generics
eliminate branches

When optimization is aggressive, a variable may be unavailable, a step may jump unexpectedly, or a backtrace may omit frames.

This is not LLDB failing. It is LLDB observing optimized machine code.

Some specific examples of what optimization does to source-level debugging:

  • Inlining: A small function may be compiled directly into its caller, with no separate stack frame. A backtrace that “should” show three frames may show only one, because the two inner frames were inlined into the outer one.
  • Variable elimination: A variable whose value can be computed from other variables may be eliminated entirely. When you try to inspect it, LLDB will say the variable is not available. The compiler was not required to keep it around, and it did not.
  • Code reordering: Machine instructions may be reordered so that a source line that appears earlier runs later, or vice versa. Stepping line by line may produce a sequence that does not match the visual order in the source file.
  • Value propagation: A constant that was computed at runtime in your source may be computed at compile time in the optimized binary. You will see the value appear as a literal in the machine code, without any corresponding runtime computation.

The practical consequence: when you are debugging, prefer the dev profile unless you have a specific reason to debug an optimized binary. We will return to this in the chapter on optimized builds.

The expression evaluator is not Rust

LLDB’s expression command does not use rustc. It has some Rust support, but it is not a Rust compiler.

Expressions involving:

iterators
closures
trait methods
generic bounds
async machinery
macros

may fail or behave differently from Rust source.

Use frame variable for inspection. Use expr only when you need it.

What makes the expression evaluator different from the compiler?

  • It runs inside the debugger, not inside rustc. It does not have access to the full Rust language semantics, trait resolution, or macro expansion.
  • It evaluates in a limited context: the current frame, with limited access to locals, no ability to create new local variables of arbitrary types, and no way to resolve complex lifetime or borrow constraints.
  • It may need to call functions in the target process. Those calls can have side effects, can block, can panic, or can corrupt state.
  • It may not understand the exact same syntax as Rust source. For example, method call syntax that relies on trait resolution may not work, because the evaluator does not perform full trait resolution.

For simple inspection of a value, use frame variable. It does not evaluate anything. It reads existing storage and formats the value using debug information. That is what you want most of the time.

Async Rust

An async fn does not execute as a simple synchronous call. It creates a future. An executor polls that future. Execution can suspend at .await and resume later.

So an async source call chain is not the same as a synchronous stack trace. LLDB may show runtime frames between your application frames.

Consider a simple asynchronous function:

async fn load_config() -> Config {
    let raw = fetch_raw().await;
    let parsed = parse(raw).await;
    parsed
}

In source, this looks like a sequence of steps. At runtime, however, the compiled form is a state machine with explicit states for each suspension point. When LLDB shows you a backtrace while this function is suspended at an .await, you may see:

  • A frame for the runtime scheduler that polled this future.
  • A frame for the future’s poll method, whose name may be compiler-generated and hard to read.
  • Your own application frames interspersed among these runtime frames.

This is why async debugging requires a slightly different discipline. Rather than single-stepping through every frame, you place breakpoints at application-level boundaries and let execution flow through the runtime between them.

We will cover async debugging in detail in a dedicated chapter.

Generics and traits

Generic code can be compiled into multiple specializations. A breakpoint on a generic function may resolve to one or more concrete instantiations.

For example, this function:

fn process<T: Display>(value: T) {
    println!("{}", value);
}

When instantiated with i32 and String, produces two concrete functions in the binary. A name-based breakpoint on process may match both, or may match neither, depending on how LLDB handles the mangled symbols.

Trait method calls may dispatch dynamically. The source line may show:

handler.handle(request)

but the runtime may enter a completely different concrete implementation. When handler is a Box<dyn Handler>, the concrete type is not visible in the source line at all. LLDB has to be told, either by inspecting the value’s vtable pointer or by setting breakpoints on each candidate implementation.

The practical takeaway: when a breakpoint on a generic or trait method does not work as expected, do not assume the debugger is broken. It may simply be that the source-level name corresponds to more than one thing in the compiled binary.

Macros

Macros expand before compilation. A breakpoint on a macro invocation may not correspond to a clean source line. Often it is better to break on the expanded function or the code the macro generates.

Consider:

let result = my_macro!(x, y);

By the time the binary exists, the macro has expanded into some sequence of statements, which may include local variables with compiler-generated names, temporary values, and control flow that does not appear in the source.

When you set a breakpoint on the line containing the macro invocation, LLDB may stop at the first statement the macro expands into, or it may not stop at all, depending on how the debug information maps the macro expansion back to source.

For most debugging, this is fine: you do not need to see the internal expansion. But when the bug is inside the macro itself, or when the macro’s expansion is producing surprising behavior, you may need to inspect the expansion directly. The cargo expand tool is useful for seeing what a macro expands into.

Ownership is static; runtime state is dynamic

Ownership, borrowing, and lifetimes are checked at compile time. LLDB observes runtime memory and values. It cannot explain why the borrow checker rejected your code.

Use the compiler for static rules. Use LLDB for runtime behavior.

This distinction is worth dwelling on, because it is one of the most common sources of confusion for programmers who are new to Rust.

When you write:

let s1 = String::from("hello");
let s2 = s1;
println!("{}", s1);

the compiler will reject this program with an error. LLDB has nothing to say about it, because there is no program to run. The error is not about runtime state. It is about the static analysis the compiler performs before generating any code.

Conversely, when you write a program that compiles, and it produces the wrong output because a Vec is empty when you expected it to be populated, LLDB is exactly the right tool. The compiler has no opinion about the runtime contents of the vector. Only the running program can tell you what went wrong.

The two questions are complementary:

  • “Does this program satisfy Rust’s static rules?” is answered by the compiler.
  • “What does this program do when it runs?” is answered by LLDB.

When you encounter a problem, the first step is always to ask which question you are asking. Many debugging struggles arise from applying the wrong tool to the wrong question.

Moves and runtime state

A related complication: in Rust, a value that has been moved may still be physically present in memory for some time. The compiler knows that the value is no longer valid at the source level, but the bytes may not have been overwritten. When you inspect the original variable in the debugger, you may see its last value, even though using it in source would be a compile error.

For example:

let s1 = String::from("hello");
let s2 = s1;
// s1 is moved here; the compiler will not let you use it.
// But the bytes of the String metadata may still be on the stack,
// and LLDB may show them if you ask.

If you see a moved value in the debugger and wonder why the compiler rejected your use of it, remember: the compiler is not looking at memory. It is looking at the ownership graph. The debugger is looking at memory. They see different things.

Panic handling and unwinding

Rust panics have a specific runtime behavior that affects debugging. By default, a panic unwinds the stack: it runs destructors on the way up, freeing resources and running cleanup code. The panic ultimately terminates the thread, or the program if the panic occurs on the main thread.

Under LLDB, a panic may stop the debugger at the underlying signal (SIGABRT or similar), not at the Rust source line where panic! was invoked. This is because Rust panics eventually reach the C++ exception machinery, which raises a signal.

When you stop on a panic, the backtrace may show the unwinding frames, not the original panic site. This is why, in panic debugging, it is often useful to set a breakpoint on the panic symbol itself, or on the specific function where you suspect the panic originates, rather than relying on the default stop.

We will explore panic debugging in detail in a later chapter.

The Rust 2024 edition and unsafe

Because this manual targets Rust 2024, a few edition-specific details affect what you see when debugging unsafe code or FFI:

  • unsafe extern blocks: All extern blocks are now unsafe extern. When you see one in a Rust 2024 codebase, remember that the block being unsafe does not mean every item inside is unsafe. Individual items may be marked safe or unsafe. In the debugger, this matters because the safety contract for each symbol is defined at the item level.
  • Unsafe attributes: #[no_mangle], #[export_name = "..."], and #[link_section = "..."] are now written #[unsafe(no_mangle)], #[unsafe(export_name = "...")], and #[unsafe(link_section = "...")]. This matters when you inspect symbol names in the debugger, because a symbol that is exposed to C via #[unsafe(no_mangle)] will appear under its unmangled name, while ordinary Rust functions appear under their mangled names.
  • unsafe_op_in_unsafe_fn: An unsafe fn no longer implicitly allows unsafe operations in its body. Each unsafe operation must be inside an explicit unsafe { ... } block. This makes the source more explicit about where the unsafe boundary is, which is exactly the information you want when debugging unsafe code.
  • No references to static mut: Rust 2024 disallows references to static mut items. If you debug code that needs shared mutable global state, you will see raw pointers or interior-mutability primitives (Mutex, AtomicUsize, and so on) rather than &static mut. This affects what you see in the debugger when inspecting global state.

None of these changes alter the fundamental mechanics of debugging. They alter what the source looks like, which in turn alters what the debugger’s output will look like when it maps machine code back to source.

Summary

Rust debugging is different from debugging in a simpler language, for several concrete reasons:

  • Name mangling means function names in the debugger may not match source names.
  • Optimization can inline, reorder, and remove code, making the machine code diverge from the source.
  • The expression evaluator is not Rust. It has partial support for Rust syntax but is not a compiler.
  • Async Rust is a state machine, not a synchronous call chain. Backtraces show runtime frames, not just application frames.
  • Generics and traits can produce multiple instantiations and dynamic dispatch, so a source-level name may correspond to more than one runtime symbol.
  • Macros expand before compilation, so the source line and the compiled code do not map one-to-one.
  • Ownership is static; the debugger sees dynamic runtime state, not the compiler’s ownership graph.
  • Moves may leave stale bytes in memory, which the debugger can see but the compiler considers invalid.
  • Panics use the C++ exception machinery, which can affect where the debugger stops and what the backtrace shows.
  • Rust 2024 edition changes some syntactic details around unsafe and FFI, which in turn change what appears in the debugger.

None of these differences are obstacles. They are simply facts about the environment, and knowing them lets you interpret what you see. In the next chapter, we will look at the tools that make up the Rust debugging stack and how they fit together.
