Chapter 1: Prerequisites and Setup on Debian

Before we can debug Rust programs with LLDB, we need a working environment. This chapter sets up everything you need on Debian: LLDB itself, the Rust toolchain, the rust-lldb wrapper, and the debug information that connects compiled machine code back to your Rust source.

If you already have Rust and LLDB installed, you can skim this chapter. But even then, the section on debug information is worth reading carefully, because the quality of your debugging session depends heavily on the debug information available in the binary you are running.

Install LLDB

On Debian, install LLDB and a recent Clang toolchain:

sudo apt update
sudo apt install -y lldb clang

Verify:

lldb --version

You should see something like lldb version 18.1.8 (the exact version depends on your Debian release). LLDB is the debugger itself. It lives in the machine world: registers, memory, instructions, and threads. Rust debug information will translate that machine world back into Rust terms.

Debian also packages rust-lldb separately. That package contains Rust-specific pretty-printers and a wrapper script for invoking LLDB on Rust binaries[reference:0]. You can install it directly from Debian:

sudo apt install -y rust-lldb

However, if you installed Rust via rustup (as described in the next section), the rust-lldb wrapper is already included in your Cargo bin directory. In that case, you do not need the Debian package. The rustup-provided wrapper is generally preferred because it stays in sync with your Rust toolchain version.

Install Rust and Cargo

If Rust is not already installed, the recommended way is to use rustup, the official Rust toolchain installer:

curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source "$HOME/.cargo/env"

Verify:

rustc --version
cargo --version

Rust 2024 edition: The Rust 2024 edition is stable as of Rust 1.85.0 (released February 20, 2025)[reference:1]. Throughout this manual, we use edition = "2024" in all Cargo.toml examples. If you are using an older toolchain, update with:

rustup update stable

To verify that your toolchain supports Rust 2024, check the version:

rustc --version

The output should show 1.85.0 or newer.

Rust 2024 changes relevant to debugging and FFI: Several changes in the 2024 edition affect how you write code that interacts with the machine world, which is exactly what debugging reveals. The most important ones for this manual are:

  • unsafe extern blocks are mandatory: Starting in Rust 2024, all extern blocks must be marked as unsafe. Items within them may be marked as safe or unsafe[reference:2][reference:3]. This matters for FFI debugging: when you see an extern "C" block in a Rust 2024 codebase, it will appear as unsafe extern "C".
  • Unsafe attributes: The export_name, link_section, and no_mangle attributes must now be written as #[unsafe(no_mangle)], #[unsafe(export_name = "...")], and #[unsafe(link_section = "...")][reference:4]. You will encounter these when debugging code that exposes Rust symbols to C or the linker.
  • unsafe_op_in_unsafe_fn warns by default: In Rust 2024, an unsafe fn no longer implicitly allows unsafe operations in its body. You must write explicit unsafe { ... } blocks inside the function[reference:5]. This makes the unsafe boundaries in your code more visible, which is helpful when debugging unsafe code.
  • References to static mut are disallowed: Rust 2024 disallows references to static mut items. Use raw pointers or interior-mutability primitives instead[reference:6]. This affects low-level and FFI code that might previously have used &static mut.

These changes do not alter how LLDB works, but they do alter what the source code looks like when you inspect it during a debugging session. Being aware of them prevents confusion.

Install Rust debugging components (recommended)

For a better debugging experience, add two Rustup components:

rustup component add rust-src llvm-tools-preview

The rust-src component provides the standard library source code, which lets debuggers and IDEs step into standard-library functions when debug information is available. The llvm-tools-preview component includes LLVM utilities that are useful for inspecting binaries, symbols, and debug information[reference:7].

These are optional but strongly recommended, especially if you plan to investigate standard-library behavior or use tools such as llvm-symbolizer to improve symbolication in stack traces.

Verify rust-lldb

Rust ships a wrapper called rust-lldb:

rust-lldb --version

If the command is not found, ensure Cargo’s bin directory is on your PATH:

echo "$PATH"

Usually that means:

export PATH="$HOME/.cargo/bin:$PATH"

If you installed rust-lldb via apt instead of rustup, the wrapper may be at /usr/bin/rust-lldb. Both wrappers launch LLDB with Rust-oriented settings and pretty-printers. The rustup wrapper is preferred because it corresponds exactly to your installed Rust version.

rust-lldb is a wrapper, not a separate debugger. It launches lldb with additional Rust-specific configuration. When you debug Rust, prefer:

rust-lldb

over manually launching:

lldb

The wrapper is what loads the Rust pretty-printers, which format complex Rust values such as String, Vec<T>, and enums in a readable way. Without them, you would see raw memory layouts instead of human-readable values.

Understand debug information

Debug information is the bridge between machine code and Rust source.

Without debug information, LLDB may still run the program, but it cannot reliably answer:

Which Rust function is this?
Which source line is this?
What is this variable?
What type does it have?

Cargo’s default debug profile normally includes debug information:

cargo build

The release profile normally does not:

cargo build --release

If you need a release-like build with debug information:

[profile.release]
debug = true

You can also choose a lighter level:

[profile.release]
debug = "line-tables-only"

That gives line numbers without full variable information.

Debug information levels

The debug setting in a Cargo profile controls the -C debuginfo flag passed to rustc. The valid levels are:

  • 0 or false (or "none"): No debug information at all.
  • 1 or "line-tables-only": Line tables only. Sufficient to generate backtraces that include line numbers, but no variable or type information.
  • 2 or true: Full debug information, including variable names, types, and source-level information[reference:8][reference:9].

The default dev profile uses debug = true (level 2). The default release profile uses debug = false (level 0). For debugging, you almost always want level 2. Level 1 is useful when you need smaller binaries but still want meaningful stack traces.

A note on release builds with debug information: Adding debug = true to [profile.release] does not disable optimizations. The optimizer may still inline functions, remove variables, and reorder instructions. Debug information tells LLDB what the source looked like, but optimization can make the mapping between source and machine code imperfect. We will discuss the consequences of optimization in a later chapter.

Rust 2024 edition in Cargo.toml

When creating or updating a project for Rust 2024, your Cargo.toml should include:

[package]
name = "my_debugging_project"
version = "0.1.0"
edition = "2024"

[dependencies]

If you are migrating an existing project, you can use cargo fix --edition to automate most of the changes[reference:10]. After migration, verify that your project compiles:

cargo check

If your code uses FFI, pay particular attention to the unsafe extern requirement and the new unsafe attribute syntax. The compiler will tell you exactly what needs to change.

Confirm the binary

Before launching LLDB, confirm which executable you are debugging:

ls -l target/debug/

Then:

rust-lldb target/debug/your_program

Debugging the wrong binary is a common source of misleading evidence. This is especially true in workspaces with multiple packages, in projects with both library and binary targets, and in projects where you have built both debug and release artifacts. Always verify that the path you pass to rust-lldb is the executable produced by the build you intended to debug.

A useful habit is to check the modification time of the binary:

ls -lt target/debug/ | head

If the binary you are about to debug is older than your most recent source change, you may be looking at stale code. Rebuild first:

cargo build

This simple check prevents a surprising number of confusing debugging sessions.

A minimal verification program

To confirm that your entire setup works, create a small Rust program, build it, and load it in LLDB.

Create a new project:

cargo new debug_setup_check --bin
cd debug_setup_check

Edit Cargo.toml to use Rust 2024:

[package]
name = "debug_setup_check"
version = "0.1.0"
edition = "2024"

[dependencies]

Edit src/main.rs:

fn main() {
    let greeting = String::from("Hello, LLDB!");
    let length = greeting.len();

    println!("{} (length: {})", greeting, length);
}

Build:

cargo build

Confirm the binary exists:

ls -l target/debug/debug_setup_check

Launch LLDB:

rust-lldb target/debug/debug_setup_check

At the (lldb) prompt, set a breakpoint on main and run:

(lldb) breakpoint set --name main
(lldb) run

Execution stops at the entry of main. Inspect the frame:

(lldb) frame info

Step to the next line:

(lldb) next

Inspect the local variable:

(lldb) frame variable greeting

You should see the string value rendered by the Rust pretty-printer. If you see raw internal fields instead of a readable string, the pretty-printers are not loaded. That usually means rust-lldb was not used, or the Debian rust-lldb package and the Rust toolchain version are mismatched.

Continue and quit:

(lldb) continue
(lldb) quit

If all of that worked, your environment is ready. If something failed, the troubleshooting appendix at the end of this manual covers the most common causes.

Summary

In this chapter, we set up a complete Rust debugging environment on Debian:

  • LLDB was installed via apt, providing the debugger itself.
  • Rust and Cargo were installed via rustup, ensuring we have the Rust 2024 edition and the latest stable toolchain.
  • rust-lldb was verified, giving us Rust-aware debugging with pretty-printers.
  • Debug information was explained: the dev profile includes it by default, while the release profile does not unless configured.
  • Rust 2024 changes relevant to debugging were reviewed, including unsafe extern blocks and the new unsafe attribute syntax.
  • A minimal verification program confirmed that the entire toolchain works end to end.

With this foundation in place, we can now turn to the question that drives everything else: what debugging actually is, and how LLDB fits into the Rust development loop.
