Chapter 14: Debugging Tests, Examples, and Workspace Binaries

So far, we have debugged what we might call the “main” executable: the binary produced by a project’s src/main.rs. But Cargo produces many other executables as well: test binaries, example binaries, benchmark binaries, and one binary per package in a workspace. Any of these can be debugged directly, and often the smallest one is the easiest to investigate.

This chapter is about debugging those smaller executables. We will see how to find them, how to launch them under LLDB, and how to use the fact that a test or an example is a minimal, self-contained reproduction of a bug.

Why smaller executables matter

A common mistake in debugging is to always debug the largest binary. The main binary may contain thousands of lines of startup code, configuration loading, logging setup, and other machinery that has nothing to do with the bug. Every breakpoint in that binary is a breakpoint in a busy environment.

A test binary, by contrast, contains exactly one test and the code that test exercises. Its startup is minimal. Its execution is deterministic. Its output is usually a single pass/fail line. When a bug can be reproduced in a test, the test binary is almost always the best place to debug it.

The same is true of examples. An example binary contains exactly the code needed to demonstrate a specific feature. If the example reproduces a bug, it is often a much cleaner environment than the full application.

The general principle:

Debug the smallest executable that reproduces the problem.

Everything in this chapter is a consequence of that principle.

Debugging tests

Rust tests are ordinary executable code from the debugger's perspective.

Build tests without running them:

cargo test --no-run

Then identify the test executable.

You can use Cargo's test output and artifacts to locate the executable.

Launch it with:

rust-lldb path/to/test-executable

Alternatively, use Cargo's debugger support when available in your environment.

The important idea is:

A test is a small executable specification that can be debugged directly.

Debugging tests: expanded workflow

Build tests without running them:

cargo test --no-run

Cargo will print the test executables. If you need machine-readable output:

cargo test --no-run --message-format=json

Look for executable paths.

Then launch one:

rust-lldb path/to/test-executable

Inside LLDB:

breakpoint set --name test_name
run
frame variable
bt

A test is just an executable. Debugging one test is usually easier than debugging the whole workspace.

If you know the test name:

cargo test test_name

If it fails, debug the executable that contains that test.

How Cargo outputs test executables

When you run cargo test --no-run, Cargo compiles one test binary per test target and reports the path of each. A simple output looks like this:

   Compiling my_crate v0.1.0 (/path/to/my_crate)
    Finished `test` profile [unoptimized + debuginfo] target(s) in 1.23s
  Executable unittests src/lib.rs (target/debug/deps/my_crate-4a5b6c7d8e9f0a1b)
  Executable tests/integration.rs (target/debug/deps/integration-1a2b3c4d5e6f7a8b)

Each line beginning with Executable names the test target and the path of the compiled binary. You can launch either of them under LLDB.

The naming convention is important to notice: my_crate-4a5b6c7d8e9f0a1b. The hexadecimal suffix is a hash that Cargo uses to distinguish between different builds of the same target. If you change your source, the hash may change, and the binary path changes with it. Always re-run cargo test --no-run before launching, so you have the current path.

A practical note: the JSON output is more stable for scripting. The executable field in each JSON record is the path you want. If you are building a shell alias or an editor integration, this is the field to parse.

Unit tests vs. integration tests

Rust has two kinds of tests that produce separate binaries:

  • Unit tests: located inside the crate, in mod tests blocks within src/. They are compiled into a single test binary, typically named after the crate with a hash suffix.
  • Integration tests: located in the tests/ directory at the crate root. Each file in tests/ produces its own test binary, named after the file.

Both kinds are debugged the same way, but they have different properties:

  • Unit tests have access to the crate's private items, so they can test internal functions directly. Their binary usually contains many tests.
  • Integration tests only have access to the crate's public API. Each binary is typically smaller than the unit-test binary, because it exercises a narrower surface area.

For debugging, this means:

  • To debug a unit test, launch the unit-test binary and set a breakpoint on the specific test function.
  • To debug an integration test, launch the binary corresponding to the integration test file.

In both cases, the workflow is the same as debugging any other executable. The only difference is that you have chosen a smaller executable that contains exactly the code you care about.

How test functions are compiled

Understanding a small detail about how tests are compiled helps when setting breakpoints.

A Rust test function such as:

#[test]
fn test_addition() {
    assert_eq!(2 + 2, 4);
}

is compiled into a function that the test harness will call. The test harness itself is generated by Cargo and drives all the test functions in a single binary. It parses command-line arguments (which tests to run, whether to shuffle, and so on), invokes the selected tests, and prints a summary.

From the debugger's perspective:

  • If you break on test_addition, you will stop when that specific test is invoked.
  • If you break on the harness function (which has a compiler-generated name), you will stop before any test runs. This is rarely what you want.
  • If you run the binary without arguments, all tests will run. To run just one, pass the test name as an argument (see below).

The practical rule: always break on the specific test function you want, and always pass the test name as an argument when launching under LLDB.

Passing test names to the test binary

When you launch a test binary, you can pass it the name of the test you want to run. This is the same mechanism cargo test test_name uses internally, but without the Cargo wrapper.

Inside LLDB, use the -- separator to pass arguments to the test binary:

(lldb) settings set target.run-args test_addition --exact --nocapture
(lldb) run

The arguments after the target name are passed to the test harness. In this example:

  • test_addition is the test name.
  • --exact tells the harness to match the name exactly rather than as a substring.
  • --nocapture tells the harness not to swallow println! output, so you see it in the terminal.

Common test-harness flags you may want to pass:

  • --exact: exact name match.
  • --nocapture: do not capture test output.
  • --test-threads=1: run tests sequentially (useful for debugging concurrency-related tests).
  • --ignored: also run tests marked #[ignore].
  • --list: list all tests without running them (useful before debugging to confirm the test name).

By combining a specific test name with --exact and --test-threads=1, you get a minimal, deterministic environment for debugging.

Debugging a single test

Start with:

cargo test test_name

If it fails, determine:

which package?
which test target?
which test executable?

Then debug that executable.

This is usually easier than debugging the entire workspace.

A practical sequence:

  1. Run cargo test --no-run and note the executable that contains test_name.
  2. Launch that executable under LLDB.
  3. Set a breakpoint on test_name.
  4. Set the run-args to include test_name --exact.
  5. Run. The program will execute only the one test and stop at the breakpoint.

This sequence gives you the smallest possible environment for the bug: one test, one binary, one process.

Debugging integration tests

Integration tests live under:

tests/

Each integration-test file can produce its own test executable.

The workflow is:

cargo test --no-run
→ identify executable
→ rust-lldb executable
→ breakpoint
→ run

The exact executable path can vary with the project and target configuration.

Use Cargo's build output rather than guessing the path.

Integration tests as alternative entry points

An important property of integration tests: they are separate crates. Each integration-test file is compiled as its own crate that depends on your library. From the debugger's perspective, this means:

  • The integration-test binary does not contain your library's private functions.
  • It does contain your library's public API, plus the test code from the integration-test file.
  • Its main function is generated by Cargo's test harness, not by you.

This makes integration tests excellent for debugging bugs that involve the public API, because they reproduce the way a real user would use your library. They are less useful for debugging private internals, because those are simply not present in the binary.

If your bug is in a private function, you have two options:

  1. Write a unit test that exercises the private function, and debug the unit-test binary.
  2. Expose the private function temporarily (via a feature flag or a pub(crate) visibility change) and debug through an integration test.

The first is usually preferable, because it does not require source changes to the library itself.

Helper modules in integration tests

Integration tests often share helper code. Cargo's convention is to place shared helpers in tests/common/mod.rs, and each integration-test file uses mod common; to include them.

From a debugging perspective, this means the helper module's functions are compiled into each integration-test binary that uses them. Breakpoints on helper functions resolve to the binary that contains them. If you have several integration-test binaries, and a helper is used by more than one, you will need to launch the specific binary you care about, or set a breakpoint in each.

Because integration tests compile separately, the same helper may exist in multiple binaries. This is a place where name-based breakpoints can fire in unexpected places if you are not careful about which binary is loaded.

Test output and LLDB

By default, the Rust test harness captures output from passing tests and shows it only for failing tests. This is convenient in a normal cargo test run, but under LLDB it can hide output you want to see.

Two useful flags:

  • --nocapture: prints all output, even from passing tests. Useful when you want to see what println! is producing without stopping the debugger.
  • --test-threads=1: runs tests sequentially. Useful when debugging tests that share resources, or when you want deterministic output ordering.

Combined:

(lldb) settings set target.run-args test_name --exact --nocapture --test-threads=1
(lldb) run

This gives you a clean, deterministic run of one test, with all its output visible.

Tests and panics

A failing test in Rust typically fails by panicking on an assertion. Under LLDB, a panic stops the debugger, and the workflow is the same as for any other panic: find the first frame belonging to your own crate, select it, and inspect its state.

One difference: test functions often have small, focused bodies. The panic site is usually close to the test's entry. This makes tests particularly good for debugging panics, because the state at the panic point is often the state the test just constructed.

For assert_eq! failures, the panic message includes the left and right values:

thread 'test_addition' panicked at src/lib.rs:8:5:
assertion `left == right` failed
  left: 5
 right: 4

Under LLDB, you can inspect those values directly. Set a breakpoint in the test function, run, and inspect the locals at the assertion. This lets you see not just the values but also their provenance: how they were computed.

Debugging tests with external dependencies

Some tests require external services: a database, a network connection, a file on disk. Debugging such tests requires that the external dependency be available during the debug session.

Two approaches:

  • Spin up the dependency before launching LLDB: Start the database, ensure the network service is reachable, and place the needed files. Then launch the test binary under LLDB as usual.
  • Use a test double: Replace the external dependency with an in-process stub. This is often more reliable for debugging, because it removes the variability of the external service.

The second approach is more work initially but pays off during debugging, because the test becomes fully deterministic. When a bug depends on a specific response from the external service, the stub can be programmed to return exactly that response, and the debug session becomes reproducible.

A common pattern in Rust: define a trait for the external dependency, implement the real version for production and a stub version for tests. The test binary then uses the stub. Breakpoints inside the stub reveal what the test expected the dependency to do; breakpoints inside the production code reveal how it responded to the stub's data.

Debugging examples

Cargo examples can be built with:

cargo build --example example_name

Then:

rust-lldb target/debug/examples/example_name

This is useful when the example reproduces an API or integration problem more simply than the main application.

When examples are better than tests

An example is a small program that demonstrates one aspect of a library. Unlike a test, an example has a main function, so it can be run directly. It is not run as part of cargo test unless you ask for it explicitly.

Examples are useful for debugging when:

  • The bug appears when using the library in a specific way that a test does not cover.
  • You want to step through the library's behavior in a real use case rather than in a test.
  • The example is already a minimal reproduction of a bug reported by a user.
  • You want a debugging session with a main function that you fully control, rather than with a test harness that you do not.

Because an example has a main, it behaves like any other binary. You can set a breakpoint on main and step through the example from the beginning, which is not possible with a test binary in the same way.

How Cargo builds examples

Examples live in the examples/ directory at the crate root. Each file in examples/ is compiled as a separate binary, named after the file. Cargo places them in:

target/debug/examples/

The file name is the example name. For example, examples/parse_config.rs becomes target/debug/examples/parse_config.

Build a single example:

cargo build --example parse_config

Build all examples:

cargo build --examples

Run an example:

cargo run --example parse_config

Debug an example:

rust-lldb target/debug/examples/parse_config

Examples can take command-line arguments in the same way as a main binary. Pass them after --:

(lldb) settings set target.run-args input.json --verbose
(lldb) run

Examples as debugging scaffolds

One of the best uses of examples is as a temporary debugging scaffold. When a bug is reported against a library you maintain, and the report includes a reproduction script, the fastest way to debug is often to turn the reproduction into an example. Then you have a binary that reproduces the bug, in a controlled environment, with full debug information.

The steps:

  1. Create a new file in examples/ with the reproduction code.
  2. Build it: cargo build --example bug_repro.
  3. Launch it under LLDB.
  4. Set breakpoints, step through, inspect state.
  5. When done, either delete the example or keep it as a regression test (renamed to reflect its purpose).

This pattern is so common in the Rust ecosystem that many crates ship with an examples/ directory full of files that were originally created for debugging a specific issue.

Examples with features

If your crate defines Cargo features, an example can specify which features to enable:

cargo build --example parse_config --features tracing

This is important when the bug appears only under certain feature combinations. By building the example with the exact feature set that reproduces the bug, you get the smallest binary that exhibits the problem.

In the debugger, the example looks the same as any other binary. The features affect which code is compiled in, but not how the debugger interacts with it.

Debugging examples in a workspace

In a workspace, examples belong to a specific package. To build the examples of a specific package:

cargo build -p my_package --examples

To build a specific example:

cargo build -p my_package --example parse_config

The resulting binary is still placed under target/debug/examples/ at the workspace root, unless the workspace has custom target directory configuration.

When debugging in a workspace, be precise about which package's example you are building. Two packages in the same workspace may have examples with the same name, and Cargo will disambiguate with a suffix or refuse to build until you specify the package explicitly.

Debugging binaries in a workspace

For a workspace:

cargo build -p package_name

Then identify the binary produced by that package.

Run:

rust-lldb target/debug/binary_name

The key is to debug the smallest executable that reproduces the problem.

Understanding workspace structure

A Cargo workspace is a collection of packages that share a single Cargo.lock and a single target/ directory. Each package can have its own binaries, libraries, tests, and examples. When you build the workspace as a whole, Cargo produces all the artifacts under the workspace's target/ directory.

A typical workspace has multiple members:

[workspace]
members = [
    "crates/server",
    "crates/client",
    "crates/common",
]

Each member is a full crate with its own Cargo.toml. The server crate might have a binary target, the client crate might have a library and an example, and the common crate might be a pure library shared between them.

From the debugger's perspective, this means there are many possible executables. To debug one, you need to know:

  • Which package you want to debug.
  • Which binary within that package you want to debug.
  • Where that binary is located in the workspace's target/ directory.

Cargo's build output tells you all three of these.

Building and locating workspace binaries

Build a specific package:

cargo build -p server

Cargo places the binary under target/debug/ at the workspace root:

target/debug/server

If the package has multiple binaries, each is named after the [[bin]] entries in its Cargo.toml:

[[bin]]
name = "server"
path = "src/bin/server.rs"

[[bin]]
name = "admin"
path = "src/bin/admin.rs"

After building, both binaries are under target/debug/. To debug the admin binary:

rust-lldb target/debug/admin

This is the standard workflow. Cargo's output directory is shared across the workspace, and each binary is placed under a name derived from its [[bin]] configuration.

Choosing which binary to debug

When a workspace has several binaries, the first question is: which one exhibits the bug?

The answer is almost always: the one that is closest to the bug. If the bug is in the server's request handling, debug the server binary. If it is in an administrative tool, debug the admin binary. If the same bug can be reproduced in either, prefer the smaller one.

A useful heuristic: the smaller the binary, the cleaner the debugging session. A binary that does not load the full application's startup code, background tasks, and configuration will produce less noise. If you can reproduce the bug in a small CLI tool that shares the same library, the CLI tool is a better debugging target than the full server.

Shared libraries in a workspace

In a workspace, shared libraries are compiled into each dependent binary. There is no dynamic linking between workspace crates by default; each binary contains its own copy of the code from the libraries it depends on.

From a debugging perspective, this means:

  • Breakpoints inside a shared library will fire in the binary you are debugging, not in a separate library process.
  • Source paths inside the shared library will be relative to its package, not to the binary's package. LLDB uses debug information to map them correctly, but if you are inspecting multiple binaries, it can be helpful to remember which package each source file belongs to.
  • If you build multiple binaries, they may share the same compiled library artifacts on disk, but each binary has its own copy in memory.

When you set a breakpoint on a shared library function, LLDB resolves it to the copy inside the binary you are running. If you then switch to a different binary, the same breakpoint may resolve to a different address.

Workspace configuration tips

A few Cargo settings affect how easy it is to find and debug workspace binaries:

  • default-members: Specifies which packages are built when you run cargo build without -p. Setting this to the package you debug most often makes the default build produce the binary you want.
  • workspace.target-dir: Overrides the location of the target/ directory. Useful when you want workspace artifacts in a specific place, but remember to adjust your LLDB launch commands accordingly.
  • profile.release.debug: When enabled, release binaries include debug information. This applies to all packages in the workspace.
  • profile.dev.package."*".debug = true: Enables debug information for dependencies even if the profile would otherwise reduce it. Useful when debugging through a dependency's code.

These settings are configured in the workspace's root Cargo.toml:

[workspace]
members = ["crates/*"]
default-members = ["crates/server"]

[workspace.target-dir]
# or workspace.target-dir = "..." in some Cargo versions

[profile.dev.package."*"]
debug = true

Understanding these settings saves you from repeatedly typing long -p flags or searching for binaries in unexpected directories.

Debugging benches and other targets

Cargo also supports benchmarks, custom build targets, and other kinds of executables. The general pattern is the same:

  1. Build the target without running it, using the appropriate cargo build --... --no-run invocation (if available) or cargo build with the appropriate target selection.
  2. Locate the produced binary from Cargo's output.
  3. Launch it under LLDB.
  4. Set breakpoints and debug as usual.

Benchmarks in particular are worth knowing about. A benchmark binary is essentially a test binary that runs measurement code instead of assertions. If a benchmark is failing or producing unexpected results, you can debug it the same way you would debug a test: launch the binary, break on the benchmark function, and step through.

Custom build targets (such as [[bin]] entries with custom names or paths) produce binaries whose names are determined by the name field in the target configuration. These binaries are placed under target/debug/ like any other binary, and are debugged the same way.

Practical considerations

Stale binaries

One of the most common causes of confusing debugging sessions is a stale binary. If you have edited the source but not rebuilt, the binary on disk does not reflect your changes, and every observation in the debugger is about the old code.

Always rebuild before launching LLDB:

cargo test --no-run
cargo build --example parse_config
cargo build -p server

A quick check: compare the modification time of the binary to the modification time of the source files. If the binary is older, rebuild.

Multiple binaries

In a workspace or a package with multiple [[bin]] targets, it is easy to launch the wrong binary. Verify the path before launching:

ls -l target/debug/

Then launch the specific binary you want:

rust-lldb target/debug/specific_binary

If you have several similar binaries, their names will help you pick the right one. If the names are ambiguous, look at the source file each binary was built from, or check the modification times.

Debug symbols and shared libraries

When debugging through dependencies, ensure that debug symbols are enabled for those dependencies. This is controlled by Cargo profiles:

[profile.dev]
debug = true

[profile.dev.package."*"]
debug = true

The first setting enables debug information for your own package. The second enables it for all dependencies. In a workspace, the same settings apply to all members.

With these settings, breakpoints in dependency crates resolve to readable source locations. Without them, you may see mangled names or missing line information, making the dependency's behavior harder to interpret.

Deterministic debugging

Many bugs appear only under specific circumstances. Test binaries and example binaries are often more deterministic than the full application, because they have fewer moving parts. But even in a test, the following can introduce nondeterminism:

  • Parallel test execution: By default, Cargo runs tests in parallel. Use --test-threads=1 to force sequential execution.
  • Time-dependent logic: Tests that depend on wall-clock time may behave differently on different runs. Use a mock time source if possible.
  • Random number generation: Tests that use randomness should use a seeded RNG so the test is reproducible.
  • File system state: Tests that read or write files should use temporary directories and clean up after themselves.
  • Network access: Tests that make network calls are inherently nondeterministic. Prefer stubs.

For debugging, minimizing nondeterminism is essential. The fewer variable factors, the more reliably a breakpoint, an inspection, or a step will correspond to the bug you are investigating.

Attaching to a running test

Sometimes you cannot launch a test under LLDB from the beginning. This happens with tests that are launched by a CI runner, a custom test harness, or a parent process you do not control.

In such cases, you can attach LLDB to an already-running test process:

rust-lldb -p <pid>

Or, from inside LLDB:

(lldb) process attach --pid <pid>

This requires the following:

  • The test process to be running (not exited).
  • Permission to attach, which on Linux typically requires ptrace_scope to be configured or the debugger to be run with the appropriate privileges.
  • The binary to have debug information, which is the case for a normal cargo test --no-run build.

Attaching is useful for tests that run in the background or that are launched by an external tool. It is less useful than launching under LLDB directly, because you have no opportunity to set breakpoints before the program starts. But you can still set breakpoints and continue after attaching, as long as the interesting code has not already run.

Rust 2024 notes on testing and debugging

A few Rust 2024 specifics affect debugging tests, examples, and workspace binaries.

Edition 2024 and test binaries

The Rust 2024 edition does not change the fundamental way test binaries are produced. Each test binary is still a separate executable with a generated harness. What may change slightly is the standard-library source paths shown in backtraces, and the exact names of compiler-generated functions, but the debugging workflow is unchanged.

Test harness and edition 2024

The default test harness behavior is governed by the edition of the crate under test. In Rust 2024, the same test harness runs, with the same flags (--exact, --nocapture, --test-threads, and so on). Breakpoint and inspection behavior is identical.

Workspace inheritance and 2024

Cargo workspaces can share dependencies, profiles, and edition settings across members. If a workspace sets edition = "2024" at the workspace level, every member that opts into inheritance uses the 2024 edition without repeating the setting in each package's Cargo.toml.

For debugging, this means all binaries in the workspace are compiled with the same edition, and the debugger's view is consistent. If you mix editions across workspace members (which is allowed), debug information may differ slightly between members, though the underlying debugging mechanics remain the same.

unsafe extern and test binaries

If a crate has an unsafe extern block that declares foreign functions used by its tests, the test binary will contain references to those foreign symbols. When debugging tests, if a breakpoint inside the FFI boundary does not resolve, it may be because the external library is not linked into the test binary, or because the symbol name differs from what you expect. Use image lookup to confirm the symbol's presence in the binary.

Integration tests and edition 2024

Integration tests are compiled as separate crates that depend on your library. In Rust 2024, the same unsafe extern and unsafe attribute rules apply to integration tests as to any other crate. If the integration test declares foreign functions, the declarations must be inside unsafe extern, and any no_mangle attributes must be written #[unsafe(no_mangle)]. This is a source-level change with no impact on the debugging workflow.

Summary

In this chapter, we covered debugging the many executables that Cargo produces:

  • Tests: built with cargo test --no-run, launched under LLDB, and broken on specific test functions. The test name is passed as an argument to the test binary, along with flags such as --exact, --nocapture, and --test-threads=1.
  • Unit tests vs. integration tests: unit tests are compiled into the crate's test binary and can access private items; integration tests are separate crates that use only the public API. Both are debugged the same way, but they have different properties that affect what you can inspect.
  • Examples: built with cargo build --example name, launched directly under LLDB. Examples have their own main and are excellent as temporary debugging scaffolds for reproduction scripts.
  • Workspace binaries: built with cargo build -p package_name and located under the workspace's shared target/ directory. Each package's binaries are named after their [[bin]] entries.
  • Benches and custom targets: debugged the same way as tests and examples, using the appropriate Cargo build command and then launching the produced binary under LLDB.
  • Practical considerations: rebuild before launching to avoid stale binaries; verify the path to avoid launching the wrong binary; enable debug information for dependencies when debugging through them; minimize nondeterminism by using sequential test execution and stubs; attach LLDB to running test processes when launching from the start is not possible.
  • Rust 2024 notes: the edition changes source-level details (unsafe extern, unsafe attributes) but does not change the underlying workflow of debugging tests, examples, or workspace binaries.

The unifying principle: debug the smallest executable that reproduces the problem. A test or example binary is often the smallest such executable, and choosing it makes the debugging session shorter, more focused, and easier to reason about.
