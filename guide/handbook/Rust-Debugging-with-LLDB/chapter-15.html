Chapter 15: Traits, Generics, Closures, Iterators, and Macros

Rust’s expressive features—traits, generics, closures, iterators, and macros—are what make the language pleasant to write and hard to debug at the same time. They are pleasant because they let us express intent compactly. They are hard to debug because the compiled code no longer looks like the source. Each of these features generates compiler-level artifacts that the debugger has to interpret: monomorphized generic functions, trait dispatch, closure structs, iterator adapter chains, and macro-expanded code.

This chapter is about debugging all of these. We will look at what each feature compiles into, what the debugger shows for it, and how to inspect it effectively. The goal is not to understand the compiler’s internals, but to know what to expect when a breakpoint lands inside code that was written in a way that does not match what you see.

Debugging traits

A trait call such as:

handler.handle(request)

can hide the concrete implementation.

Text search can show possible implementations.

LLDB shows what actually executes at runtime.

Set a breakpoint on candidate implementations.

Then run.

The implementation whose breakpoint fires is evidence of the runtime path.

This is particularly useful with:

trait objects
dynamic dispatch
generic abstractions
plugin systems
dependency injection

Static dispatch versus dynamic dispatch

Rust dispatches trait method calls in two ways, and they behave very differently in the debugger.

Static dispatch occurs when the concrete type is known at compile time. The compiler generates a direct call to the specific implementation. For example:

fn process<T: Handler>(handler: T, request: Request) {
    handler.handle(request); // compiled as a direct call to T::handle
}

When you set a breakpoint on Handler::handle or on the concrete implementation, it resolves to the specific instantiation for the type used at that call site. The backtrace shows the concrete implementation’s frame.

Dynamic dispatch occurs when the call goes through a trait object:

fn process(handler: &dyn Handler, request: Request) {
    handler.handle(request); // compiled as a vtable lookup
}

Here the concrete type is not known at compile time. The compiled code loads a function pointer from the trait object’s vtable and calls it. In the debugger, a breakpoint on Handler::handle may not resolve at all, because there is no single function with that symbol—there are multiple concrete implementations, one per type that implements the trait.

A practical technique: set breakpoints on each candidate implementation, then run the program. The breakpoint that fires tells you which implementation was actually selected at runtime.

Finding trait implementations

Before setting breakpoints, you need to know which types implement a given trait. A few approaches:

  • Text search: Search for impl TraitName for in the codebase. This finds every implementation in your source.
  • Documentation: For traits from crates, the generated documentation lists “Implementors.”
  • cargo doc --open: Build and open the local documentation, which includes a list of implementors for each trait.
  • IDE assistance: rust-analyzer in most editors shows implementors when you hover over a trait or use “go to implementations.”

Once you have the list, set breakpoints in each implementation’s handle method. The one that fires is your answer.

Inspecting a trait object

For a trait object such as Box<dyn Handler>, the debugger can show you the concrete type stored inside.

(lldb) frame variable handler
(Box<dyn Handler>) handler = {
    pointer = 0x...
    vtable = 0x...
    // pretty-printed contents, if the pretty-printer knows the concrete type
}

The exact display depends on the pretty-printer configuration and the amount of debug information. In some cases, the concrete type is shown. In others, the pretty-printer cannot determine the concrete type, and you see the raw pointer and vtable.

If the display is ambiguous, set a breakpoint on each implementation of the trait method. The one that fires is the concrete type. You can then inspect the corresponding fields of that concrete type by using the correct type’s field names, or by using a debugger expression that casts the pointer.

Trait methods and default implementations

A trait method can have a default implementation, which a type may or may not override. When a type does not override the method, the default implementation is called. In the debugger:

  • A breakpoint on the trait’s default implementation will fire when a type without an override calls the method.
  • A breakpoint on a specific override will fire only when that override is called.

If you are debugging a method and are not sure whether it was overridden, set breakpoints on both the default implementation and the overrides. Whichever fires tells you the runtime path.

Supertraits in debugging

Supertraits such as trait PrintableSummary: Display require implementors to implement both traits. In the debugger, this matters when you are searching for the source of a call: a call such as println!("{}", summary) may dispatch through Display, not through the supertrait’s method. Set breakpoints on the actual trait method being called, not just the supertrait.

A useful heuristic: when you are not sure which trait method is called, look at the source line. The method name in source corresponds to the trait that declares it. Set a breakpoint on the concrete implementation of that method.

Object safety in debugging

Some traits are object-safe, meaning they can be used as dyn Trait. Others are not. This matters when you are debugging because a trait that is not object-safe cannot appear as a trait object in source, and therefore never appears as a vtable dispatch in the debugger.

If a breakpoint on a trait method does not resolve and the trait is not object-safe, the issue is likely that the method was inlined or that it was monomorphized into the caller. Use a source-line breakpoint inside the method body instead.

Debugging trait objects

For:

Box<dyn Handler>

the concrete type is not necessarily obvious from the source line.

Inspect the value.

Then inspect the call path.

If necessary:

breakpoint set

on candidate implementations.

Run the program.

The breakpoint that resolves and fires gives you a concrete runtime observation.

The vtable as debugging evidence

A trait object in Rust is a “fat pointer”: it consists of a data pointer and a vtable pointer. The vtable is a static table of function pointers, one for each method of the trait. It also typically includes a pointer to the type’s Drop implementation and, for some traits, size and alignment information.

Under the debugger, you can inspect the vtable to see the addresses of the methods that will be called for that concrete type. This is a low-level technique but occasionally useful when you want to confirm exactly which implementation is bound to a trait object.

(lldb) frame variable handler
(Box<dyn Handler>) handler = {
    pointer = 0x5555559e0a10
    vtable = 0x5555557a3c40
}

You can then inspect the vtable’s contents, or use image lookup on the address to find out which function it points to. This is rarely necessary—setting breakpoints on candidate implementations is usually faster—but it is useful when the trait object is passed across a boundary (FFI, C code) and the debugger cannot follow it automatically.

Identifying the concrete type

A common debugging question is: “What concrete type is actually stored in this Box<dyn Trait>?”

Several techniques, in order of increasing intrusiveness:

  1. Pretty-printer output: Try frame variable handler and see whether the pretty-printer identifies the concrete type. This works when the pretty-printer knows the type.
  2. Set breakpoints on each candidate: Run the program and see which one fires. This is the most common technique and often the fastest.
  3. Use type name introspection: Some codebases provide a method on the trait (such as fn type_name(&self) -> &'static str) that returns a string identifying the concrete type. This is a runtime feature rather than a debugger feature, but it is often more reliable than inspecting the vtable.
  4. Inspect the vtable manually: As described above.

For most debugging, the second technique is the right one. Breakpoints on candidate implementations are simple, reliable, and require no source changes.

Trait objects and lifetime erasure

A trait object such as Box<dyn Handler + 'static> erases the concrete type and, optionally, the lifetime. In the debugger, this means:

  • The concrete type is not visible in the type name of the variable.
  • The lifetime bound is not visible at all (lifetimes are compile-time only and do not appear in debug information).
  • If the trait object holds borrowed data, the concrete type’s fields that reference borrowed data will still be inspectable, but the borrow relationship itself is not visible.

This is one of the cases where the debugger’s view is genuinely less informative than the source. The source may say Box<dyn Handler + Send>, but the debugger only shows the trait object layout. If you need to know the concrete type, use the techniques described above.

A practical example

Consider a plugin system:

trait Formatter {
    fn format(&self, value: i32) -> String;
}

struct DecimalFormatter;
struct HexFormatter;

impl Formatter for DecimalFormatter {
    fn format(&self, value: i32) -> String {
        format!("{}", value)
    }
}

impl Formatter for HexFormatter {
    fn format(&self, value: i32) -> String {
        format!("0x{:X}", value)
    }
}

fn main() {
    let formatters: Vec<Box<dyn Formatter>> = vec![
        Box::new(DecimalFormatter),
        Box::new(HexFormatter),
    ];

    for formatter in &formatters {
        println!("{}", formatter.format(255));
    }
}

Set breakpoints on both implementations:

(lldb) breakpoint set --name DecimalFormatter::format
(lldb) breakpoint set --name HexFormatter::format
(lldb) run

The first stop is inside DecimalFormatter::format. Continue:

(lldb) continue

The second stop is inside HexFormatter::format. The two breakpoints together confirm that both implementations are being called, in the order expected.

If only one of the breakpoints fires, that tells you something about the loop or the vector’s contents. This is exactly the kind of observation that dynamic dispatch debugging is good at.

Debugging generics

Generic Rust code can produce specialized machine code.

For:

fn process<T>(value: T)

the debugger may display instantiated types rather than the source-level abstraction you are thinking about.

When debugging generic code, ask:

What concrete type is being used here?

Which instantiation am I actually executing?

What value entered this specialization?

The source tells you the generic design.

The debugger shows you a concrete execution.

Monomorphization and debug info

Rust’s monomorphization strategy means that each generic function is compiled once per concrete type that is actually used. For a function called with i32 and String, the binary contains two separate compiled functions, each with its own mangled name.

The debug information keeps track of the source-level name and the concrete type parameters. When you inspect a frame inside a generic function, LLDB uses this information to show you a name like:

my_app::process<i32>
my_app::process<alloc::string::String>

Or, in some cases, it shows the demangled form. Either way, you can see which instantiation you are in. This is exactly what you want when a generic function has multiple call sites with different types.

Breakpoints on generic functions

A breakpoint on a generic function can resolve in several ways:

  • All instantiations: LLDB resolves the breakpoint to every instantiation that matches the source-level name. This can produce many locations, one per concrete type.
  • One instantiation: LLDB picks one instantiation, often the first it finds. The behavior is version-dependent.
  • No resolution: If the function is fully inlined, no separate symbol exists for any instantiation.

To control which instantiation a breakpoint targets, either use a source-line breakpoint (which is unaffected by monomorphization) or use a fully qualified symbol name with the concrete type, if you know it. The latter requires familiarity with Rust’s mangling scheme and is rarely worth the effort—source-line breakpoints are simpler and more reliable.

Observing type-specific behavior

One of the most useful debugging techniques for generic code is to observe the behavior of a single instantiation. Suppose:

fn largest<T: PartialOrd + Copy>(items: &[T]) -> Option<T> {
    if items.is_empty() {
        return None;
    }
    let mut max = items[0];
    for &item in items {
        if item > max {
            max = item;
        }
    }
    Some(max)
}

Call it with i32 and with char. The two calls produce two instantiations of largest. Set a source-line breakpoint on the line if item > max. The breakpoint fires for each instantiation in turn.

Inspect the values at that line:

(lldb) frame variable item max

The values are shown with their types. When the breakpoint is in the i32 instantiation, you see integers. When it is in the char instantiation, you see characters. This is how you observe type-specific behavior at the same source line.

If the same breakpoint fires twice at the same source line with different types, the second stop is the second instantiation. You can distinguish them by the type shown in the frame info or by inspecting the argument values.

Trait bounds as debugging clues

When a function has a trait bound such as T: PartialOrd + Copy, the bound tells you what operations the generic code can perform. When debugging, this is a clue about what the compiled code will do: comparisons and copies.

If a type implements a trait with unusual behavior—for example, a custom PartialOrd with non-standard ordering—the debugger will show the actual values but not the comparison logic. To understand the comparison, set a breakpoint inside the trait method’s implementation for that specific type.

For example, if item > max is behaving unexpectedly, set a breakpoint on the concrete implementation of PartialOrd::gt for the type in question. This is often the fastest way to see the comparison’s actual behavior.

Const generics

Rust’s const generics allow generic parameters that are constant values, such as array sizes:

fn process_array<const N: usize>(values: [i32; N]) {
    for value in values {
        // ...
    }
}

The compiler generates one instantiation per distinct N. In the debugger, a breakpoint on process_array may resolve to all instantiations. The source-line breakpoint approach applies here as well: place the breakpoint on a specific line, and it will fire for each instantiation that reaches that line.

Inspect the array size by looking at the frame information or by inspecting the array variable. Depending on LLDB’s configuration, the size may appear in the type name or in the array’s length field.

Debugging closures

Closures can produce compiler-generated names and frames.

Do not depend on memorizing their internal names.

Instead:

break at the source line
→ step
→ inspect values
→ use bt

Treat compiler-generated frames as implementation details unless you specifically need to investigate them.

What closures compile into

A closure in Rust is compiled into an anonymous struct that implements one or more of the Fn, FnMut, and FnOnce traits. The struct captures the variables the closure uses, and the closure’s body becomes the body of the call method of the corresponding trait implementation.

For example:

let factor = 10;
let multiply = |x| x * factor;

compiles into something like:

struct MultiplyClosure {
    factor: i32,
}

impl Fn<(i32,)> for MultiplyClosure {
    extern "rust-call" fn call(&self, (x,): (i32,)) -> i32 {
        x * self.factor
    }
}

The exact structure is compiler-specific, but the pattern is consistent. A closure is a struct with captured fields, and its body is a method on that struct.

In the debugger, the closure’s frame shows a compiler-generated name such as main::{{closure}} or my_function::{{closure}}::{{closure}}. The frame’s locals include the captured variables as fields of the closure struct. Inspecting the closure value shows the captured data.

Setting breakpoints in closures

Because closures do not have stable names, name-based breakpoints on closures are unreliable. Use source-line breakpoints inside the closure body instead:

(lldb) breakpoint set --file src/main.rs --line 12

If the closure is defined on that line, the breakpoint will fire when the closure is called. You can then inspect the closure’s captured variables and its arguments.

A common pattern: closures are passed to iterator methods or thread constructors. When you break inside a closure, the backtrace shows the closure frame and the calling frame (often the iterator or thread machinery). Look for the frame of your own crate to understand the context in which the closure is being called.

Captured variables in the debugger

Inside a closure’s frame, the captured variables are accessible as fields of the closure struct. Depending on the LLDB version and pretty-printers, you may see them as:

  • Directly as locals named after the captured variables (factor).
  • As fields of a compiler-generated struct (self.factor or __0.factor).
  • Merged with the closure’s arguments in a way that requires careful inspection.

In the well-supported case, frame variable factor gives you the captured value directly. In less well-supported cases, you may need to look at the closure’s internal structure to find the captured data. This is one of the areas where the debugger’s view is less convenient than the source’s.

A practical workaround: when you are debugging a complex closure, temporarily refactor it into a named function that takes the captured variables as explicit arguments. This makes the closure’s behavior easier to inspect, at the cost of a small source change that you can revert once the bug is fixed.

Closures and move

A move closure takes ownership of the variables it captures. In the debugger, this means:

  • The captured variables are moved into the closure’s struct.
  • If you inspect the original variable after the closure was created, its value may be stale or uninitialized (as with any move).
  • Inside the closure, the captured variables are owned by the closure and are valid.

This is exactly the same pattern as for moved values in general. The debugger’s view is consistent with the source-level rules, with the caveat that moved-from memory may still show the old bytes.

The three closure traits

A closure implements one or more of Fn, FnMut, and FnOnce, depending on how it uses its captured variables. This affects the debugger in the following ways:

  • Fn: The closure captures by shared reference. The captured values are read-only inside the closure. In the debugger, they are inspectable but immutable.
  • FnMut: The closure captures by mutable reference. The captured values can be modified. In the debugger, you can observe the mutation as you step through the closure.
  • FnOnce: The closure consumes the captured values. After the closure has been called, the captured values are gone. In the debugger, the closure itself may be invalid after its first call.

When you are inspecting a closure in the debugger, remember which trait it implements. This tells you whether you should expect its captures to be read-only, mutable, or consumed.

Debugging iterators

Iterator chains can be difficult to single-step because Rust may represent them as nested types and optimized code.

For example:

items
    .iter()
    .filter(...)
    .map(...)
    .collect()

A debugger may not provide a pleasant source-level experience for every intermediate stage.

A useful debugging technique is temporarily introducing named intermediate values:

let filtered = items.iter().filter(...);
let mapped = filtered.map(...);
let result = mapped.collect::<Vec<_>>();

Now you have concrete source-level landmarks.

This is not a debugging failure.

It is making the program easier to observe.

Why iterator chains are hard to debug

An iterator chain is a composition of adapter types. Each adapter is a struct that wraps the previous adapter and adds behavior. For example:

items.iter().filter(predicate).map(transform).collect()

compiles into something like:

Map {
    inner: Filter {
        inner: Iter { ... },
        predicate: ...,
    },
    transform: ...,
}.collect()

Each adapter is a distinct type with its own next method. When you step into the chain, the debugger descends into nested adapter types, showing frames such as Map::next, Filter::next, and Iter::next. This is technically informative but does not correspond to any single line of your source code.

Understanding this structure helps you decide when to step into the chain and when to observe it from the outside.

Inspecting an iterator chain

The most common problem with iterator chains is that they produce the wrong number of items, or produce items with wrong values. Two useful inspection strategies:

  1. Inspect the result of collect: Set a breakpoint on the line after the chain and inspect the collected result. If the result is wrong, this tells you that the bug is in the chain but not where.
  2. Insert named intermediates: Split the chain into multiple bindings, then inspect each binding. This localizes the bug to a specific stage of the chain.

The second technique is often the fastest. Instead of trying to step through nested adapter types, you observe the intermediate values directly:

let filtered: Vec<_> = items.iter().filter(...).collect();
let mapped: Vec<_> = filtered.iter().map(...).collect();
let result: Vec<_> = mapped;

Now set breakpoints at each of the three lines. If filtered is correct but mapped is wrong, the bug is in the map stage. If filtered is already wrong, the bug is in the filter stage. This is direct evidence about which stage is at fault.

The cost of named intermediates

Named intermediates are not free. They typically allocate a new Vec at each stage, which changes the memory usage and possibly the performance of the program. This makes them unsuitable for production code, but they are excellent for debugging.

A practical workflow:

  1. When a chain produces wrong output, temporarily refactor it into named stages.
  2. Debug using the named stages.
  3. Once the bug is identified, fix it.
  4. Refactor back into a single chain, using the same logic.

The single chain is the production version; the named stages are the debugging version. Both express the same computation, but the debugging version makes it easier to observe.

Closure frames inside iterators

When you step into an iterator chain, the debugger often ends up inside the closure you passed to filter or map. The frame for the closure shows its captured variables and its argument.

For a map closure such as |x| x * 2, the argument x is the current element. Inspecting it tells you which element the closure is processing. If the closure returns the wrong value, you can see why by inspecting both the argument and the captured variables.

For a filter closure such as |&&n| n > 3, the argument is the current element (a double reference, hence &&n), and the closure returns a Boolean. Inspecting the argument tells you what was tested; inspecting the return value tells you whether the element was kept.

Source-line breakpoints inside the closure body are the most reliable way to reach the closure. Once there, frame variable gives you the closure’s state.

Iterator adapters that do not allocate

Some adapter methods do not allocate. For example, take, skip, filter, map, enumerate, and zip are lazy and produce new iterators without allocating. A chain of these can be stepped through, but the frames are nested adapters.

Other methods do allocate. collect, sum, fold, any, and all are consuming methods that drive the iterator to completion. These methods appear as single frames and are easier to inspect because they have clear arguments and return values.

The dividing line is: adapter methods return iterators (hard to debug), consuming methods return concrete values (easy to debug). For debugging, prefer to observe the boundary between adapters and consumers.

A worked example

Consider:

fn process(numbers: &[i32]) -> Vec<i32> {
    numbers
        .iter()
        .filter(|&&n| n > 5)
        .map(|&n| n * 2)
        .collect()
}

fn main() {
    let input = vec![1, 3, 5, 7, 9, 11];
    let output = process(&input);
    println!("{:?}", output);
}

The expected output is [14, 18, 22]. Suppose the program produces [].

Refactor the chain temporarily:

let filtered: Vec<_> = numbers.iter().filter(|&&n| n > 5).collect();
let mapped: Vec<_> = filtered.iter().map(|&n| n * 2).collect();
mapped

Set breakpoints on the filtered and mapped lines. Run. If filtered is empty, the bug is in the filter. If filtered is correct but mapped is empty, the bug is in the map.

In this case, if the filter is wrong, inspect the closure’s argument:

(lldb) frame variable n

You may see 1, which is the first element. The comparison n > 5 should be false for 1, so the element should be filtered out. That is correct behavior. Continue to the next element. If all elements are being filtered out, check the comparison.

What you often find in real debugging is that the closure is comparing against the wrong value, or that the argument is a reference where a value was expected. The named intermediates make this observation possible without navigating the nested iterator structure.

Debugging macros

Macros can obscure the source location.

If a macro expands into unexpected behavior:

identify the macro call
→ inspect the generated behavior
→ locate the relevant expansion if necessary
→ debug the resulting function

For ordinary debugging, prefer the source-level macro invocation as the initial breakpoint.

Only investigate macro expansion when the expansion itself is the problem.

How macros affect debug info

Macros are expanded before compilation. The compiler sees the expanded code, not the macro invocation. Debug information maps the expanded code back to the macro invocation site as much as possible, but the mapping is imperfect.

For a simple macro such as println! or vec!, the mapping is usually good. A breakpoint on the line containing the macro may fire inside the macro’s expansion, or it may not fire at all, depending on how the compiler attributes the expansion.

For a complex procedural macro or a macro that generates control flow (such as a custom try_ or an async state machine macro), the mapping can be very imperfect. The debugger’s frames may show compiler-generated functions whose names do not correspond to any source code you wrote.

Understanding this limitation is the key to debugging macros effectively. You are not debugging the macro; you are debugging the code the macro expanded into. When that code is not visible in the source, the debugger’s view will be less useful than usual.

Debugging declarative macros

Declarative macros (macro_rules!) are expanded by pattern matching on tokens. When they produce wrong behavior, the fastest way to understand them is often to see the expansion directly.

Use cargo expand to view the expanded code:

cargo install cargo-expand
cargo expand --lib

The expanded output is the source your macro produced. You can read it as ordinary Rust code, which is usually much easier to reason about than the macro itself.

Once you have the expanded code, set breakpoints on its lines as if they were your own. The source location may show as the macro invocation, but the line numbers will correspond to the expansion.

Note that the source locations in debug information for macro-generated code are often attributed to the macro invocation site, not to the expansion site. A breakpoint on the macro invocation may fire several times, once for each statement in the expansion, because the compiler attributes all of them to the same source location.

Debugging procedural macros

Procedural macros run at compile time. They are not present in the binary you are debugging, because they have already done their work. To debug a procedural macro, you debug the macro’s expansion, not the macro itself.

Two approaches:

  • Expand and inspect: Use cargo expand to see the output, and debug the generated code as regular Rust.
  • Debug the macro implementation: If the macro itself is producing wrong code, the right tool is not LLDB but a macro-debugging workflow, such as printing the generated tokens, or writing unit tests for the macro that compare its output against expected tokens.

LLDB is not the right tool for debugging macro implementations. It is the right tool for debugging the code that macros produce, once they produce it.

The panic! macro

The panic! macro expands into a call to the panic function with a formatted message. When you stop on a panic, the frame immediately below the panic machinery is usually the function that contains the panic! invocation. This is the frame to inspect.

Because panic! is so common, its expansion is well-supported by debug info. Breakpoints on the line containing panic! usually work correctly, and the backtrace shows the panic site with the correct source location.

Other macros that generate panic-like behavior (such as assert_eq! or unwrap) work similarly. The expansion is visible enough in debug info to identify the source location.

The ? operator as a macro-like construct

Strictly speaking, the ? operator is not a macro; it is a language construct. But it behaves like a macro in the sense that it expands into control flow that is not visible in the source. The expansion is roughly:

match expr {
    Ok(value) => value,
    Err(e) => return Err(From::from(e)),
}

When debugging code that uses ?, you may see frames corresponding to this expansion. The frame for the function is your source-level function; the frames below it are the From::from conversion, if the error type is being converted.

To inspect the error being propagated, set a breakpoint on the line after the ? expression or inspect the caller’s return value. The conversion itself is often inlined, so you may not see a separate frame for it.

When to refactor to avoid macros

If a macro is causing more debugging difficulty than it is worth, consider refactoring the code to use a regular function or a trait instead. Macros are powerful, but they are not always the best choice. A regular function has a stable name, a clear stack frame, and full debug info support. A macro has none of these.

The main cases where macros are worth the cost:

  • Syntax extensions: Macros that extend the language, such as println! or vec!. There is no non-macro equivalent.
  • Code generation for data structures: Macros that generate boilerplate for many types, such as serde’s derive. The boilerplate would otherwise be large and repetitive.
  • Domain-specific languages: Macros that implement a small DSL, such as the html! macro in the Yew framework.

In other cases, a function or a trait is usually preferable. If you find yourself debugging a macro’s expansion more often than the code that uses it, that is a sign the macro may be doing too much work for a compile-time construct.

A combined worked example

To bring the ideas in this chapter together, consider a small program that uses all the features at once:

trait Formatter {
    fn format(&self, value: i32) -> String;
}

struct Decimal;

impl Formatter for Decimal {
    fn format(&self, value: i32) -> String {
        format!("{}", value)
    }
}

fn process<F: Formatter>(items: &[i32], formatter: &F) -> Vec<String> {
    items
        .iter()
        .filter(|&&n| n > 0)
        .map(|&n| formatter.format(n))
        .collect()
}

fn main() {
    let items = vec![-1, 0, 1, 2, 3];
    let formatter = Decimal;
    let result = process(&items, &formatter);
    println!("{:?}", result);
}

This program uses a trait (Formatter), a generic function (process), a closure in filter, a closure in map, and an iterator chain. It is a small but representative example of what real Rust debugging involves.

Suppose you want to know why the output is not what you expect. Several debugging questions arise:

  1. Is the filter working? Set a source-line breakpoint inside the filter closure. Inspect the argument n. You should see values in order: -1, 0, 1, 2, 3. The closure should return false for -1 and 0, and true for 1, 2, 3.
  2. Is the map working? Set a source-line breakpoint inside the map closure. Inspect n. It should be 1, 2, 3 (the values that passed the filter). The closure calls formatter.format(n) and returns the result.
  3. Is the trait method being called correctly? Set a breakpoint on Decimal::format. It should fire for each element. Inspect value to confirm the value being formatted.
  4. What type is F? Inside process, F is Decimal. The debugger’s frame info shows the concrete type. If there were multiple implementations, you could confirm which one is being used by setting breakpoints on each.
  5. Is the iterator chain producing the right number of items? Set a breakpoint on the collect line. Inspect the resulting Vec<String>. It should have three elements.

Working through this exercise with the debugger is more educational than reading about it. Each question corresponds to a specific breakpoint, a specific inspection, and a specific answer from the running program.

Once you have completed the exercise, try introducing a bug: for example, change the filter to n > 1 instead of n > 0. Re-run the exercise. Notice which breakpoint reveals the bug and which do not. This kind of deliberate experimentation builds debugging intuition faster than reading about it.

Rust 2024 notes

A few Rust 2024 specifics affect debugging these features.

Async closures and debugging

Rust 2024 stabilizes async closures, which combine the closure and async state machine features. An async closure is a closure that returns a future. In the debugger, its frame structure reflects both: the closure struct holds captured variables, and the future returned by the closure is a separate state machine.

When you break inside an async closure, the frame shows the closure’s captures and the future’s current state. This is analogous to debugging an async fn with captured variables. The same techniques apply: source-line breakpoints inside the closure body, inspection of captured variables, and stepping through the awaited operations.

impl Trait in argument position and 2024

Rust 2024 continues to support impl Trait in argument position, which is syntactic sugar for a generic parameter. From a debugging perspective, this is identical to writing the generic parameter explicitly: the compiler monomorphizes, producing one instantiation per concrete type. Breakpoints on the function behave as they would on any generic function.

Edition 2024 and iterator traits

The 2024 edition introduces a new trait, IntoIterator for arrays, which allows arrays to be used directly in for loops without needing a reference or an explicit .iter() call. From a debugging perspective, the compiled code is similar to the reference case; the main difference is that the loop consumes the array by value. Breakpoints inside the loop behave the same way.

unsafe extern and macros

Macros that generate FFI code must generate unsafe extern blocks in Rust 2024. This is a source-level change. From a debugging perspective, the compiled code is the same as before: the foreign functions are called with the C ABI, and breakpoints inside the FFI boundary behave as they always have. The difference is purely in the source syntax you would use if you expanded the macro manually.

gen blocks and gen fn

Rust 2024 stabilizes gen blocks and gen fn, which are syntactic forms for creating iterators and generators. From a debugging perspective, a gen block compiles into a state machine similar to an async state machine: each yield is a suspension point, and the compiler generates a struct with a state field to track progress.

When you debug a gen block, the frame structure looks similar to an async state machine. The yield points are analogous to .await points. The application-level frames are the important ones; the state machine’s internal poll method is the compiler-generated layer.

Summary

In this chapter, we covered debugging Rust’s most expressive features:

  • Traits: static dispatch compiles to direct calls; dynamic dispatch compiles to vtable lookups. For dynamic dispatch, set breakpoints on candidate implementations and let the one that fires identify the runtime path.
  • Trait objects: the concrete type is erased in the source. Inspect the vtable for low-level evidence, or set breakpoints on each candidate implementation for runtime evidence.
  • Generics: monomorphization produces one instantiation per concrete type. Breakpoints on generic functions may resolve to all instantiations or one. Source-line breakpoints work reliably in all cases.
  • Closures: compiled into structs with captured fields. Name-based breakpoints are unreliable; use source-line breakpoints inside the closure body. Captured variables appear as fields of the closure struct.
  • Iterators: chains compile to nested adapter types. Stepping through them is rarely productive. Insert named intermediates to localize the bug to a specific stage of the chain.
  • Macros: expanded before compilation. Debug the code the macro produced, not the macro itself. Use cargo expand to see the expansion. Breakpoints on macro invocations may fire multiple times or at unexpected locations.

The unifying principle: for each feature, understand what it compiles into. Then you know what the debugger can show and what it cannot. This understanding turns confusing debug sessions into predictable ones.

In the next chapter, we turn to a lower-level set of features: unsafe code, raw memory, and FFI. These require a different style of debugging, focused on memory and pointers rather than on source-level control flow.
