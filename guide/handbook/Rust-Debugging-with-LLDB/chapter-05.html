Chapter 5: First Debugging Session

Reading about a debugger is not the same as using one. In this chapter, we will walk through a complete first debugging session, step by step. The goal is not to teach every command. It is to give you the shape of a debugging session so that later, when you are debugging your own code, you know what to expect.

We will use a very small Rust program. Complexity would only obscure the flow. The point of this chapter is the sequence itself: build, launch, break, run, inspect, step, inspect, continue, quit.

The program

Create a new Rust project. From your terminal:

cargo new first_session --bin
cd first_session

Edit Cargo.toml to use the Rust 2024 edition:

[package]
name = "first_session"
version = "0.1.0"
edition = "2024"

[dependencies]

Replace the contents of src/main.rs with:

fn add(a: i32, b: i32) -> i32 {
    a + b
}

fn main() {
    let x = 10;
    let y = 20;
    let result = add(x, y);

    println!("{result}");
}

This program is deliberately simple. It has a main function, a helper function called add, two local variables, and a function call. That is enough structure to demonstrate breakpoints, stepping, and variable inspection.

Build the program

Build it:

cargo build

Cargo produces an executable at target/debug/first_session. Confirm that the file exists:

ls -l target/debug/first_session

If Cargo reports any errors, fix them before continuing. A debugger session on a broken build is wasted effort.

Before launching the debugger, confirm that the binary is newer than your source changes. If it is not, run cargo build again. Working with a stale binary is a common source of confusing debugging sessions.

Launch with rust-lldb

Launch the debugger with the Rust wrapper:

rust-lldb target/debug/first_session

You should reach the LLDB prompt:

(lldb)

You have now entered the debugger. Nothing has run yet. The program has been loaded, but execution has not begun.

If you see a wall of startup output instead of the prompt, do not worry. LLDB sometimes prints version information and configuration messages. Scroll past them to the prompt.

If the command fails with “command not found,” the Cargo bin directory is probably not on your PATH. See Chapter 1 for setup instructions.

Set a breakpoint on main

At the LLDB prompt, set a breakpoint at the entry of main:

(lldb) breakpoint set --name main

LLDB will respond with something like:

Breakpoint 1: where = first_session`first_session::main, address = 0x...

This tells you three things:

  • Breakpoint 1: The breakpoint has been assigned an ID. You will use this ID later if you want to modify or delete it.
  • where: The address and symbol where the breakpoint resolved. Note that the symbol is displayed in demangled form (first_session::main), which means the Rust demangler is active.
  • address: The exact machine address where the breakpoint will fire. You rarely need this, but it is useful for advanced diagnosis.

The word resolved matters. A breakpoint can exist without yet being resolved to a concrete address. When it is resolved, LLDB has found a matching instruction. When it is pending, LLDB is still looking for it, or it does not exist.

Run the program

Start the program:

(lldb) run

The program begins executing and immediately hits the breakpoint:

Process 12345 stopped
* thread #1, name = 'first_session', stop reason = breakpoint 1.1
    frame #0: first_session`first_session::main at src/main.rs:6

Let’s read that output carefully:

  • Process 12345 stopped: The debugger has paused the program. The number is the process ID, which varies by run.
  • thread #1, name = 'first_session': The currently selected thread is thread 1, and its name is the program name. In a single-threaded program, this is the only thread.
  • stop reason = breakpoint 1.1: The stop was caused by breakpoint 1, location 1. A single breakpoint can have multiple locations if it resolved to multiple addresses.
  • frame #0: first_session`first_session::main at src/main.rs:6: The top of the call stack is main, at line 6 of src/main.rs. That is the first line of the main function body.

This is the moment where the debugger starts being useful. The program is paused at a specific point, and we can inspect its state.

Inspect the frame

Ask LLDB where you are:

(lldb) frame info

You should see:

frame #0: first_session`first_session::main at src/main.rs:6

This confirms that you are in main, at line 6. The frame number (#0) tells you that this is the top of the call stack. There are no caller frames above it, because the program is stopped at the very entry of main.

For a screen-reader workflow, this single line is often all you need to establish your location.

Step to the next line

Use the next command to execute the current line:

(lldb) next

LLDB reports the new position:

frame #0: first_session`first_session::main at src/main.rs:7

You are now at line 7, which is:

let y = 20;

The next command executed the statement let x = 10; and stopped at the next line. Because x was created at line 6, it is now available as a local variable in the current frame.

Step again:

(lldb) next

You are now at line 8:

let result = add(x, y);

Two local variables exist at this point: x and y.

Inspect local variables

Inspect all local variables in the current frame:

(lldb) frame variable

You should see something like:

(int) x = 10
(int) y = 20

This is the first moment in the session where the debugger tells you something the compiler could not: the runtime value of a local variable at a specific point in the program.

For a cleaner output, ask for one variable at a time:

(lldb) frame variable x

This returns just the value of x. In longer functions with many locals, this focused approach reduces output significantly.

One important observation: the pretty-printer has formatted the value as (int) x = 10. The type shown is int, which is the C-level type that corresponds to Rust’s i32. LLDB is showing the machine-level type, which happens to have the same layout as the Rust type in this case.

Step into the function

Use the step command to enter the function call:

(lldb) step

LLDB reports:

frame #0: first_session`first_session::add at src/main.rs:2

You are now inside add, at line 2, which is:

a + b

This demonstrates the key difference between next and step. next executed let result = add(x, y); without entering add. step entered the function and paused at its first executable line.

The frame number is still #0 because this is the top of the stack. The previous frame (main) is still there, but it is now frame #1.

Inspect the function arguments

Inspect the arguments of add:

(lldb) frame variable a b

You should see:

(int) a = 10
(int) b = 20

Function arguments are part of the current frame. This is one of the most useful debugging behaviors: when you stop at the entry of a function, you can immediately see what it received.

Ask the fundamental question:

What entered this function, and does it look correct?

In this case, a and b are both correct. In a real bug, the answer might be different, and that would be the first concrete piece of evidence.

Read the backtrace

Ask LLDB how you got here:

(lldb) bt

The output should look like:

* frame #0: first_session`first_session::add at src/main.rs:2
  frame #1: first_session`first_session::main at src/main.rs:8
  frame #2: first_session`std::rt::lang_start_internal at ...
  frame #3: first_session`std::rt::lang_start at ...
  frame #4: first_session`main at ...
  frame #5: first_session`__libc_start_main at ...

Read this from the top:

  • frame #0: You are currently in add, at line 2 of src/main.rs.
  • frame #1: add was called from main, at line 8.
  • frame #2 and beyond: The frames below main are Rust runtime and C library startup frames. These are the machinery that started your program.

This is what a backtrace looks like in a real Rust program. The first two frames are yours. The remaining frames belong to the runtime. When you investigate a bug, focus on the frames belonging to your crate.

If the backtrace is very long, you can limit it:

(lldb) bt 3

This shows only the first three frames. Useful for a screen-reader workflow, where smaller output is easier to process.

Finish and return

Run until the current function returns:

(lldb) finish

LLDB reports:

frame #0: first_session`first_session::main at src/main.rs:10

You are back in main, at line 10, which is:

println!("{result}");

The finish command ran add to completion and returned to the caller. The value result is now available. Inspect it:

(lldb) frame variable result

You should see:

(int) result = 30

The function returned 30, and the caller received it correctly.

Continue to the end

Resume execution:

(lldb) continue

The program runs to completion. You should see the program’s output:

30
Process 12345 exited with status = 0 (0x00000000)

The number 30 is the program’s output. The exit status 0 tells you that the program finished normally.

Quit the debugger

Exit LLDB:

(lldb) quit

You are back at your shell prompt.

The shape of the session

The exact commands in a debugging session vary, but the shape is consistent:

break
run
inspect
step
inspect
continue
quit

In our session, that sequence was:

  • break: breakpoint set --name main
  • run: run
  • inspect: frame info, frame variable
  • step: next, step, finish
  • inspect: frame variable, bt
  • continue: continue
  • quit: quit

Once you have this shape internalized, debugging any Rust program becomes a matter of adapting it to the problem at hand: choose a better breakpoint, inspect a different variable, trace a longer path.

A slightly larger session

The session above is minimal. A slightly more realistic one might add:

  • A second breakpoint inside a loop, to watch a value change across iterations.
  • Inspection of a String or Vec, to see how the pretty-printers render them.
  • A breakpoint at a line that is never reached, to confirm that a branch is not taken.
  • A conditional breakpoint, to stop only when a value satisfies a condition.

We will explore all of these in later chapters. For now, the goal is to have completed one full cycle: break, run, inspect, step, inspect, continue, quit.

What to do if something goes wrong

Even in this very simple session, a few things can go wrong. Here is how to interpret them.

The breakpoint does not resolve

If LLDB reports something like:

Breakpoint 1: no locations (pending).

the breakpoint did not find a matching address. Common causes:

  • The function name is misspelled. Double-check it against your source.
  • The function was inlined and no longer exists as a separate symbol. Use a source-line breakpoint instead.
  • The name is mangled in an unexpected way. Use image lookup --name main to see what symbols actually exist.

The most reliable workaround is to break by file and line:

(lldb) breakpoint set --file src/main.rs --line 6

A variable is not available

If LLDB says:

error: no variable named 'result' in this frame

check that you are in the frame where result exists. Use bt and frame select to move to the correct frame.

Stepping seems to jump around

If a next or step command moves execution in a way that does not match the visual order of the source, you may be debugging a build with optimizations enabled. Confirm which binary you are debugging:

ls -l target/debug/first_session

If you are debugging a release binary, switch to the debug build. We will cover optimization in detail in a later chapter.

The loop is the lesson

What makes a debugging session work is not any individual command. It is the loop: stop, look, act. The commands are the vocabulary. The loop is the grammar.

In our session, we did the following:

  1. Stopped at a known location (main).
  2. Looked at the current state (frame info).
  3. Moved forward one step (next).
  4. Looked at what changed (frame variable).
  5. Moved deeper (step) into a function call.
  6. Looked at the arguments (frame variable a b).
  7. Traced the call path (bt).
  8. Returned to the caller (finish).
  9. Looked at the result (frame variable result).
  10. Ran to the end (continue).

This is what every debugging session looks like, regardless of how complex the program is. The loop scales. What changes is the choice of breakpoints and the set of values you inspect.

Summary

In this chapter, we ran a complete first debugging session on a small Rust program. We covered:

  • Building the program with Cargo and confirming the artifact.
  • Launching the debugger with rust-lldb, which gives us Rust-aware output.
  • Setting a breakpoint on main and confirming that it resolved.
  • Running the program and reading the stop output.
  • Inspecting the frame to know where we are.
  • Stepping through the program with next, step, and finish.
  • Inspecting local variables and function arguments.
  • Reading a backtrace and separating application frames from runtime frames.
  • Continuing to the end and confirming the program’s output and exit status.
  • Quitting the debugger cleanly.

We also reviewed the shape of a debugging session, and what to do when a breakpoint does not resolve, a variable is not available, or stepping seems to jump around.

In the next chapter, we will look at the essential commands in more detail, so that you have a solid vocabulary for the sessions that follow.
