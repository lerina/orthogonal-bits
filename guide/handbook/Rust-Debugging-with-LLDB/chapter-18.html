Chapter 18: Debugging as Experimental Science

The previous chapter described debugging strategy at the level of individual decisions: which breakpoint, which value, which hypothesis. This chapter takes a step back and describes the larger activity that those decisions add up to. Debugging, at its best, is experimental science applied to running software. The object of study is a program. The method is controlled observation. The goal is a verified explanation of behavior.

Thinking about debugging in this way changes how a session feels. Instead of a struggle against a bug, debugging becomes a series of small experiments. Each experiment either confirms a hypothesis or rejects it. Either outcome is progress. The bug is not defeated by a clever guess; it is cornered by a sequence of specific observations that narrow the space of possibilities.

This chapter is about that frame: the experimental loop, the relationship between debugging and logging, the role of the debugger in a broader investigation, and the discipline of turning observations into a durable understanding of a program’s behavior.

Debugging as experimental science

A strong debugging session resembles an experiment.

Start with:

Observation:
The parser returns None.

Hypothesis:

The input path is empty.

Experiment:

breakpoint set --name parse_config
run
frame variable input

Result:

input is correct.

Hypothesis rejected.

New hypothesis:

The configuration lookup fails.

Next experiment:

breakpoint set --name find_config
continue

This is much more effective than randomly stepping through the program.

The scientific method in microcosm

The debugging loop is the scientific method compressed into minutes. It has the same structure as any controlled experiment:

  • Observation: something happened that we want to explain.
  • Hypothesis: a specific, testable explanation of the observation.
  • Prediction: what we expect to see if the hypothesis is true.
  • Experiment: a breakpoint, an inspection, a step, or a watchpoint that tests the prediction.
  • Observation of result: what actually happened in the experiment.
  • Conclusion: whether the hypothesis was confirmed or rejected.
  • Next hypothesis: based on the conclusion, the next specific question to test.

The parallel is not decorative. A debugging session that follows this structure converges quickly. A debugging session that ignores it wanders. The difference is not intelligence; it is method.

The great advantage of the debugger over other tools is that it makes the experimental step extremely cheap. Setting a breakpoint, running to it, and inspecting a value takes seconds. Because experiments are cheap, the method can be applied many times in a single session, and each application narrows the search space.

Why the experiment framing matters

It is easy to think of debugging as a hunt for a “bug”—as if the bug were a physical object somewhere in the source that just needs to be found. This framing is misleading. A bug is not an object. It is a behavior of the running program that differs from expectation. The purpose of debugging is not to find the bug as an object but to produce an explanation that accounts for the behavior.

Under the hunt framing, a session fails when the bug is not “found.” Under the experiment framing, a session succeeds as long as it produces a verified conclusion, even if that conclusion is “the bug is not where I thought it was.” Each rejected hypothesis is progress.

The experiment framing also makes debugging less personal. When a hypothesis is rejected, it is the hypothesis that is rejected, not the programmer. This matters because debugging sessions are often long and frustrating, and the personal framing makes them more so.

The role of failure in an experiment

In experimental science, a failed experiment is not a failed hypothesis. It is a fact. It constrains the space of possible explanations.

The same is true in debugging. A rejected hypothesis is not a wasted session; it is evidence. It eliminates one explanation and leaves the remaining space smaller. As long as hypotheses are specific enough to be testable, each rejection narrows the search.

What makes a debugging session wasteful is not rejection; it is vagueness. A vague hypothesis such as “something is wrong in the parser” cannot be tested because it does not make a specific prediction. An hour spent in vague exploration has less value than a minute spent on a specific hypothesis that gets rejected.

This is why the discipline of writing down hypotheses is so useful. It forces each hypothesis to be specific enough to write down, and thus specific enough to test.

Bias and the debugger

Human beings are not neutral observers. When debugging, several biases can interfere with the investigation:

  • Confirmation bias: the tendency to look for evidence that supports a hypothesis and to overlook evidence against it. The debugger helps here by producing evidence whether or not it supports the hypothesis. But the risk remains: it is possible to see the value you expect to see rather than the value that is actually there.
  • Anchoring: the tendency to fix on the first hypothesis and to return to it even after it has been rejected. When a hypothesis is rejected, it should be set aside. Returning to it without new evidence wastes time.
  • Availability: the tendency to consider hypotheses that come easily to mind—the code you just looked at, the bug you saw last week, the error message you read recently. The most likely hypothesis is not always the one that comes first.
  • Overconfidence: the tendency to trust your intuition about where the bug is. Intuition is useful as a source of hypotheses, but it is not evidence. Only the program is evidence.

The debugger does not eliminate these biases, but it provides a mechanism to counter them. By insisting that each hypothesis be tested against actual runtime state, the debugger keeps the investigation grounded in evidence rather than in prior belief.

A practical countermeasure: after every confirmed hypothesis, ask what the evidence would look like if the hypothesis were false. If the evidence would look the same, the inspection did not actually test the hypothesis.

Debugging versus logging

Logging answers:

What happened over time?

LLDB answers:

What is happening here, right now?

Tests answer:

Can I reproduce this behavior reliably?

Compiler diagnostics answer:

Why does this Rust program violate the language rules?

Use them together.

When logging is the better tool

Logging is better than the debugger in several situations:

  • Long-running execution: if the bug occurs after minutes or hours of execution, running under the debugger for that entire time is impractical. Logging captures the relevant events as they happen.
  • High event density: if an event occurs millions of times, a breakpoint will fire millions of times. Logging can sample the events without pausing the program.
  • Timing-sensitive behavior: stopping at a breakpoint can change the timing of the program, hiding a race condition. Logging has less impact on timing.
  • Production systems: you cannot attach a debugger to a running server without affecting its behavior. Logging is the only way to observe it.
  • Historical record: log output can be archived and analyzed after the fact. A debugging session only exists while it is happening.

The debugger and logging are not rivals. They are complementary tools, and mature developers use both.

When the debugger is the better tool

The debugger is better than logging in its own set of situations:

  • Inspection of complex state: a log message can only show what the developer thought to log. The debugger can inspect any value in the frame, including values that were not anticipated.
  • Stepping through logic: when the bug is in the flow of control, not in a value, stepping is the only way to follow it.
  • Reproducible bugs on the developer’s machine: if the bug can be reproduced locally in a controlled environment, the debugger is usually faster than iterative logging.
  • Examination of a specific moment: for a bug that manifests as a single wrong value at a specific point, the debugger gives a direct view. Logging would require adding a message at just the right place.

A useful heuristic: if you know the value you need, logging is often sufficient. If you do not know which value you need, the debugger is the tool that lets you find out.

The debug-then-log cycle

A common workflow combines the two tools:

  1. Reproduce the bug under the debugger.
  2. Identify the specific value or state that is wrong.
  3. Add a log message that captures this value.
  4. Run the program normally, without the debugger, and collect the logs.
  5. Analyze the logs to see the pattern across many runs.
  6. If the pattern is still unclear, return to the debugger with a more specific question.

The debugger tells you what to log; logging tells you how often it happens. Each step of the cycle refines the question.

Logging in Rust

Rust’s standard logging tools are the log crate and a backend such as env_logger. The log crate provides macros for each level:

use log::{error, warn, info, debug, trace};

fn process(value: u32) {
    debug!("processing value {}", value);
    if value > 100 {
        warn!("value {} is unusually large", value);
    }
    // ...
    trace!("processing complete");
}

The behavior of the logger is controlled by an environment variable at runtime:

RUST_LOG=debug cargo run
RUST_LOG=my_crate=trace cargo run

This makes logging very flexible during debugging: you can leave a rich set of log statements in the code, and choose at runtime how verbose the output is. This is often more efficient than adding and removing println! statements for each investigation.

An important point about Rust 2024: the log crate and env_logger work the same way as in previous editions. The only changes are the underlying language features, not the logging interface itself.

What good logs look like

A good log message has several properties:

  • It is at the right level: error! for problems that affect the user, warn! for things that look wrong but do not fail, info! for lifecycle events, debug! for values that are useful when investigating, trace! for very detailed step-by-step output.
  • It has enough context: “processing value 42” is less useful than “processing value 42 for user alice”. The extra context is what lets you correlate the log with a specific request or task.
  • It uses structured fields: the tracing crate extends the logging model with structured fields, which are easier to query and analyze later.
  • It does not flood: a log message inside a tight loop, at debug level, will produce a flood of output. Use trace level or remove the message for production builds.

Good logs are the foundation of post-mortem debugging. When a bug cannot be reproduced, the logs are often the only evidence available.

Combining tools effectively

A mature debugging workflow uses all the tools available, each for what it does best:

  • Compiler diagnostics for static questions about types, ownership, and lifetimes.
  • Unit tests to reproduce bugs in a controlled, minimal environment.
  • Debugger for direct inspection of runtime state at a specific moment.
  • Logging for long-running or high-frequency observations.
  • Miri and sanitizers for detecting undefined behavior in unsafe code.
  • Benchmarks for measuring performance and detecting regressions.
  • Profiling for understanding where time is spent and where allocations occur.

The workflow is not “use the debugger for everything.” It is “use the right tool for the question.” Often, the fastest path is to switch tools mid-investigation: use the debugger to identify what to log, use the logs to identify when the bug occurs, use a test to reproduce it, and use the debugger again to inspect the specific moment.

The experimental loop in practice

The debugging loop can be written as a short sequence. Applying it repeatedly is what makes a debugging session productive.

The shape of the loop

1. Observe
2. Hypothesize
3. Predict
4. Experiment
5. Compare
6. Conclude
7. Repeat

Each step has a specific purpose:

  • Observe: notice something that differs from expectation. This can be an unexpected output, an unexpected state, a wrong value, a hang, or a crash.
  • Hypothesize: propose a specific explanation for the observation. The hypothesis must be specific enough to test.
  • Predict: state what you expect to see if the hypothesis is true. The prediction is what the experiment will test.
  • Experiment: choose a breakpoint, an inspection, a watchpoint, or a step that will either confirm or refute the prediction.
  • Compare: look at the result and compare it against the prediction.
  • Conclude: state whether the hypothesis is confirmed or rejected. Record the conclusion.
  • Repeat: use the conclusion as input to the next hypothesis.

The loop can complete in seconds for a simple question, or in hours for a complex one. What matters is that each iteration of the loop narrows the space of possibilities.

From observation to hypothesis

The transition from observation to hypothesis is the most creative step. It is where the skill of the debugger shows.

An observation is a fact: “the program prints ‘no config’ when I run it with a valid config file.” A hypothesis is a specific, testable explanation for that fact.

Several hypotheses could explain the same observation:

  • The config file path is wrong.
  • The config file is not being read.
  • The config file is read but not parsed.
  • The config file is parsed but discarded.
  • The output is correct, but the file’s contents are not what I expect.

Each hypothesis suggests a specific experiment. The first suggests inspecting the path. The second suggests inspecting the result of the read. The third suggests inspecting the result of the parse. The fourth suggests inspecting the flow of control after the parse. The fifth suggests inspecting the file itself.

To find the hypothesis most likely to be fruitful, ask: which explanation would, if true, produce the observation most directly? Start with that one. The debugger will tell you quickly whether you were right.

From prediction to experiment

A hypothesis without a prediction cannot be tested. The prediction is what makes the experiment meaningful.

Consider the hypothesis “the config file path is wrong.” The prediction is: “if I inspect the path variable, it will not match the expected path.” This prediction can be tested by a single inspection.

Consider the vaguer hypothesis “something is wrong with the config loading.” There is no specific prediction here. The experiment is unspecified. The result will be interpreted based on what is found, rather than compared against a stated expectation.

The discipline of stating the prediction before the experiment is what keeps the loop from degenerating into aimless inspection.

The prediction as a double check

The prediction serves a second purpose: it catches sloppy hypotheses. If you cannot state what you expect to see, the hypothesis is not yet specific enough to test. Refine it until you can.

Example of a hypothesis without a clear prediction:

“The config loading is broken.”

Refined into two hypotheses with clear predictions:

“The config path variable will be empty.” (Prediction: inspecting it shows "".)

“The config file open will fail.” (Prediction: inspecting the result of the open call shows Err.)

Each refined hypothesis has a clear experiment and a clear result. Each iteration of the loop is meaningful.

When the loop does not converge

Sometimes, the loop seems to go on forever. Each hypothesis is rejected, but no progress is visible. Several causes are common:

  • Wrong frame: the inspection is looking at the wrong function or the wrong invocation. Verify the location with bt and frame info.
  • Wrong binary: the debugger is running an old build of the program. Verify the path and the modification time.
  • Wrong assumption about source: the code being debugged does not match the source that is being read. This can happen with macros, generated code, or stale source files.
  • Wrong assumption about behavior: the hypothesis is not specific enough to be tested reliably, and the results are being interpreted loosely.
  • The observation itself is wrong: the bug does not reproduce the way it was thought to. Re-verify the observation before continuing.

When the loop stalls, step outside it. Re-examine the observation. Re-verify the environment. A few minutes spent confirming the basic facts is often faster than continuing to iterate on a flawed foundation.

The Rust debugging loop

Use:

1. Reproduce
2. Stop
3. Locate
4. Inspect
5. Trace
6. Hypothesize
7. Test
8. Fix
9. Reproduce again
10. Add a regression test

The final step matters.

A bug that has been fixed but cannot be reproduced by a test is easier to reintroduce.

Why each step is necessary

Each step in the Rust debugging loop has a purpose:

  • Reproduce: if the bug cannot be reproduced, no debugging session can find it. Reproduction can be manual, scripted, or via a failing test.
  • Stop: pause the program at a specific point. Without a stop, there is nothing to inspect.
  • Locate: know where you are. Without location, the inspection has no context.
  • Inspect: see the state. Without inspection, there is no evidence.
  • Trace: understand how you got here. The path of execution is often as important as the current state.
  • Hypothesize: form a specific explanation. This is the creative step.
  • Test: run an experiment that confirms or rejects the hypothesis.
  • Fix: change the code based on the verified conclusion. A fix without a verified cause is a guess.
  • Reproduce again: confirm that the original symptom no longer occurs. This catches fixes that only appeared to work.
  • Add a regression test: capture the bug in a test that will catch its return. This is what makes the fix durable.

Skipping steps often costs more than it saves. Skipping reproduction leads to debugging a bug that is not there. Skipping verification leads to fixes that do not work. Skipping the regression test leads to bugs that return.

Reproduce: what makes a good reproduction

A good reproduction has several properties:

  • Deterministic: it produces the bug reliably, not intermittently. If the bug is intermittent, the reproduction should acknowledge this and describe the conditions under which it occurs.
  • Minimal: it uses the smallest possible input, configuration, and code that still triggers the bug. Minimal reproductions are easier to debug and easier to convert into tests.
  • Self-contained: it does not depend on external systems or state that is not part of the reproduction. Dependencies should be documented or replaced with stubs.
  • Fast: it runs in seconds, not minutes. Fast reproductions can be run many times during a debugging session.

A failing test is often the best reproduction because it is deterministic, minimal, self-contained, and fast. When a bug report includes a failing test, debugging becomes much more direct.

Fix: what a good fix looks like

A good fix has several properties:

  • Addresses the verified cause, not a symptom. If the cause is unknown, the fix is a guess.
  • Minimal: it changes as little as possible. Large fixes introduce new bugs and make the diff hard to review.
  • Consistent with existing patterns: if the codebase uses a particular pattern for the same kind of problem, the fix should follow it.
  • Tested: it comes with a regression test that fails without the fix and passes with it.
  • Documented if the fix addresses a subtle issue that could recur.

A common mistake is to make the fix large because the investigation touched many places. But the investigation may have narrowed the bug to a single line. If so, the fix should be a single line.

Reproduce again: why this step matters

After applying a fix, run the original reproduction again. Confirm that the bug no longer occurs. This seems obvious, but it is often skipped under the assumption that the fix obviously works.

Two failure modes are caught by this step:

  • Fixes that hide the symptom without addressing the cause: the symptom disappears from one path but reappears from another. Running the original reproduction catches this if the reproduction exercises the other path.
  • Fixes that introduce new bugs: the original bug is fixed but a new one appears. The original reproduction no longer triggers the bug, but a modified reproduction does.

A good practice: run the original reproduction, run the full test suite, and run any regression tests that were added. Only after all pass should the fix be considered done.

Add a regression test: why this step matters

The final step is the one that makes the debugging work durable. A bug that has been fixed but not tested is a bug that can return. The test is the artifact that prevents its return.

A good regression test:

  • Reproduces the original bug: it fails without the fix and passes with it.
  • Is specific: it tests the exact condition that triggered the bug, not a broader condition that might pass for other reasons.
  • Is fast and deterministic: it can be run as part of the regular test suite.
  • Has a clear name: a name that describes the condition being tested, so that future readers understand what it is for.

In Rust, the natural place for a regression test is either in the mod tests block for a unit-level bug, or in the tests/ directory for an integration-level bug. Both are appropriate; the choice depends on the scope of the bug.

The runtime model

A runtime model is a mental picture of how a program behaves when it runs. It is different from a reading of the source. The source shows what the program could do; the runtime model shows what it actually does in the cases you have observed.

Building a runtime model involves several activities:

  • Following an execution path: pick a specific operation and trace it from entry to output. Record the functions it passes through and the values that flow between them.
  • Mapping the major components: identify which functions belong to which subsystem. The runtime model groups functions by responsibility.
  • Identifying the data flow: for each important type, note where it is created, transformed, stored, and consumed. The data flow often reveals the architecture better than the call graph.
  • Noting the boundaries: identify where the program crosses a boundary (file, network, thread, FFI). Boundaries are the places where assumptions change.
  • Recording the surprises: when the runtime behavior differs from what the source suggested, record the surprise. These are the places where the runtime model will need revision.

The runtime model is a living document. It is refined each time the program is debugged, and each refinement makes future debugging faster.

Using breakpoints to learn

A breakpoint is not only a way to inspect a known value. It is a way to discover what is happening at a point you do not understand.

An example learning workflow:

  1. Pick an entry point you understand: main, a public API function, a message handler.
  2. Set a breakpoint at the entry.
  3. Run the program and observe what happens next. Which function is called? What arguments are passed?
  4. Set a breakpoint at the next function.
  5. Repeat until you have a picture of the primary execution path.

This is sometimes called “tracing” the program. It is slower than reading source, but it produces a runtime model that reading cannot. The runtime model includes information about which branches are taken, which callbacks fire, and which values actually appear at runtime—information that the source alone does not show.

The difference between reading and observing

Reading source and observing execution are complementary activities, and they answer different questions.

Reading source answers:

  • What could happen?
  • What types are involved?
  • What are the public interfaces?
  • What is the ownership structure?
  • What conditions are checked?

Observing execution answers:

  • What did happen in this run?
  • Which branches were taken?
  • Which values actually appeared?
  • Which callbacks fired?
  • Which errors were produced?

Neither alone is sufficient. Reading without observing leaves uncertainty about which paths actually run. Observing without reading leaves uncertainty about why the observed behavior is possible.

The most productive debugging sessions alternate between the two: read a piece of code, observe its execution, return to the source with new questions, and continue.

The model as a debugging tool

Once you have a runtime model, debugging becomes much faster. When a bug appears, you already know where the relevant code is likely to be, and you can go directly to the right place.

The model also makes surprises more visible. When the runtime behavior does not match the model, that mismatch is itself a signal. It often means the model is incomplete or wrong, and correcting it is a step toward understanding the bug.

This is why experienced developers sometimes debug faster than beginners even when both are equally unfamiliar with the specific bug. The experienced developer has a richer runtime model of the system, built up over many sessions. The model tells them where to look, and it makes unexpected behavior more noticeable.

ripgrep for finding

ripgrep (rg) is the fastest way to answer “where does this name appear?” It handles symbol searches, error message searches, configuration searches, and test searches. It is the tool you reach for before every session, to build a map of where the code lives.

In a Rust codebase, common rg invocations include:

rg 'fn main'
rg 'pub fn'
rg 'impl TraitName for'
rg 'enum MyEnum'
rg 'trait MyTrait'
rg 'Err\('
rg 'unwrap\(\)'
rg 'expect\('

Each search produces a list of locations. The list is not a conclusion; it is input to the next step of the investigation.

ast-grep for structure

ast-grep searches for patterns in the syntax tree rather than in the raw text. It answers questions such as:

  • Which functions return a specific type?
  • Which structs contain a specific field?
  • Which implementations provide a specific trait?
  • Which calls are made inside a specific kind of block?

For Rust, ast-grep complements rg by finding relationships that are structural rather than textual. The two tools work well together: rg finds the candidates, and ast-grep narrows them by structure.

Cargo for packages

Cargo answers questions about the build:

  • Which packages exist in this workspace?
  • Which dependencies does each package have?
  • Which features are enabled?
  • Which binaries and libraries does each package produce?
  • Which profile is being used?

These questions often arise when the bug involves an unexpected dependency, a feature that changes behavior, or a binary that is not the one being debugged. Cargo’s output (cargo metadata, cargo tree, cargo build --verbose) provides the answers.

Rust compiler for static rules

The compiler answers questions about types, ownership, and lifetimes. It is the only tool that can answer questions about why a program does not compile. When a bug involves type errors, borrow checker errors, or lifetime issues, the compiler is the first tool to use.

In Rust 2024, the compiler also enforces the new edition rules (unsafe extern, unsafe attributes, and so on). Errors related to these are also compiler-level and should be addressed before any runtime debugging begins.

LLDB for runtime

LLDB answers questions about runtime state: which value, which branch, which thread, which call path. It is the tool for questions the compiler cannot answer because they depend on a specific execution.

The division of labor is clear: static questions go to static tools; dynamic questions go to LLDB. When a session starts with LLDB and the question turns out to be static, the answer is not in LLDB. When a session starts with the compiler and the question turns out to be dynamic, the compiler cannot help. Recognizing the kind of question is the first step.

Git for history

Git answers questions about how the code got to its current state:

  • When was this line added?
  • What was the commit message?
  • Who made the change?
  • What else changed in the same commit?

These questions are especially useful when a bug appears after a recent change. git bisect can find the exact commit that introduced a bug, using a script that tests whether the bug is present at each commit. This is a form of automated experimental investigation, in the same spirit as the debugging loop.

Combining tools in one session

A single debugging session might use all of these tools in sequence:

  1. Read the source with rg to find the relevant function.
  2. Check the types and ownership with the compiler.
  3. Set a breakpoint with LLDB to observe the runtime state.
  4. Use the debugger to identify a specific value that is wrong.
  5. Check the history with git log to see whether the value was recently changed.
  6. Add a failing test that reproduces the bug.
  7. Fix the bug and confirm with the test.

The tools are not rivals. Each answers a question the others cannot.

The debugging notebook revisited

The debugging notebook, introduced in the previous chapter, is the record of the experimental loop. Each entry is one iteration of the loop.

A longer worked example

Consider a bug in a small HTTP server. The server accepts requests, parses them, and returns responses. A user reports that some requests return “500 Internal Server Error” when they should return “200 OK”.

A notebook of the investigation might look like this:

Observation:
  Some requests return 500 when they should return 200.
  The pattern is not obvious from the logs.

Hypothesis 1:
  The handler panics for specific inputs.
Prediction:
  Panics appear in the log with a stack trace.
Experiment:
  Check the server logs for panic traces.
Result:
  No panic traces.
Conclusion:
  Hypothesis rejected.

Hypothesis 2:
  The request parser returns Err for some inputs.
Prediction:
  A breakpoint on the parse function will show Err for failing requests.
Experiment:
  Break at parse, run the failing request.
Result:
  parse returns Ok with the expected structure.
Conclusion:
  Hypothesis rejected.

Hypothesis 3:
  The response serializer fails for some responses.
Prediction:
  A breakpoint in the serializer will show Err.
Experiment:
  Break at serialize, run the failing request.
Result:
  serialize returns Err(TooLarge) for responses above 4 KB.
Conclusion:
  Hypothesis confirmed. The serializer has a size limit that was not accounted for.

Fix:
  Increase the serializer buffer size, or stream the response.

Regression test:
  A test that sends a response above 4 KB and asserts that it is returned successfully.

Verify:
  The failing request now returns 200.

Each entry in the notebook is a complete iteration of the loop. The notebook shows the full investigation, including the rejected hypotheses, which are as informative as the confirmed one.

What the notebook shows

Several things stand out when the notebook is viewed as a whole:

  • The investigation is a sequence of specific hypotheses, not a vague exploration.
  • Rejected hypotheses are recorded, so future investigators know what has already been ruled out.
  • Each experiment is tied to a specific prediction, so the results are interpretable.
  • The fix follows from the confirmed hypothesis, not from a guess.
  • The regression test is derived from the confirmed hypothesis, which ensures it tests the right thing.

This is what a well-conducted experimental investigation looks like. It is not a talent; it is a discipline.

From notebook to postmortem

For production systems, the notebook becomes part of the postmortem. When a bug affects users, the postmortem records what happened, why it happened, and how it was fixed. A good notebook makes the postmortem almost automatic: it contains the timeline, the hypotheses, the evidence, and the fix.

For personal use, the notebook is a record of your debugging habits. Reviewing it after a few months reveals patterns: which kinds of bugs you tend to find quickly, which ones take longer, which tools you reach for first. This kind of self-observation is a powerful way to improve your debugging over time.

Rust 2024 notes on experimental debugging

A few Rust 2024 specifics affect the experimental loop.

unsafe_op_in_unsafe_fn and inspection

The Rust 2024 edition requires explicit unsafe { ... } blocks inside unsafe fn bodies. This is helpful for the experimental loop because it makes the boundaries between safe and unsafe code explicit. When a hypothesis involves an unsafe operation, the opening of the unsafe block is a natural experiment location.

unsafe extern and the FFI boundary

Because all extern blocks are now unsafe extern, the FFI boundary is more explicit in source. When a hypothesis involves a foreign call, the source shows exactly where the boundary is. The experiment is to set a breakpoint just before the call and inspect what is passed across.

static mut and global state

The restriction on static mut references means global state investigations use interior-mutability primitives. When a hypothesis involves global state, the experiment is to inspect the wrapper type (Mutex, Atomic, UnsafeCell) at a breakpoint. The value inside the wrapper is the runtime state of the global.

Async closures and inspection

Rust 2024 stabilizes async closures. When a hypothesis involves an async closure, the experiment is to break at the source line inside the closure, inspect the captured variables, and step through the awaited operations. The frame structure is the same as for async fn: application frames interleaved with runtime machinery.

Edition 2024 and Miri

Miri supports the Rust 2024 edition and is often ahead of the stable compiler in enforcing new semantics. For hypotheses involving undefined behavior, Miri is often a better tool than LLDB, because it can detect violations that do not manifest as runtime symptoms. The experimental loop can use both: Miri for detecting the violation, and LLDB for inspecting the state at the moment of violation.

Summary

In this chapter, we framed debugging as experimental science:

  • The experimental loop: observe, hypothesize, predict, experiment, compare, conclude, repeat. Each iteration of the loop narrows the space of possibilities.
  • Hypothesis quality: a good hypothesis is specific, testable, and falsifiable. Vague hypotheses cannot be tested reliably.
  • Bias in debugging: confirmation bias, anchoring, availability, and overconfidence all interfere with the investigation. The debugger provides a mechanism to counter them by grounding conclusions in runtime evidence.
  • Debugging versus logging: logging answers “what happened over time,” the debugger answers “what is happening right now.” Each tool has situations where it is the better choice. Mature workflows use both.
  • The Rust debugging loop: reproduce, stop, locate, inspect, trace, hypothesize, test, fix, reproduce again, add a regression test. The final step is what makes the fix durable.
  • Runtime models: debuggers are not only for bug fixing. They are also for building a mental picture of how a program behaves when it runs. This picture is what makes future debugging faster.
  • Static plus dynamic tools: ripgrep, ast-grep, Cargo, the Rust compiler, LLDB, and Git each answer different questions. Combining them produces a stronger investigation than any single tool.
  • The debugging notebook: record observations, hypotheses, predictions, experiments, and conclusions. The notebook is the durable artifact of the investigation, and it becomes the source material for regression tests and postmortems.
  • Rust 2024 specifics: the experimental loop is unaffected by the edition, but the new rules around unsafe extern, unsafe attributes, unsafe_op_in_unsafe_fn, and static mut change what appears in the source and in the debugger.

The unifying theme: debugging is a discipline, not a talent. The tools are the same for everyone; the method is what separates a productive session from a frustrating one. An experimental framing makes the method explicit and reproducible.

In the next chapter, we consider the limits of the debugger: when it is not the right tool, and how to recognize the situations where other approaches—logging, tests, sanitizers, static analysis—are more appropriate.
