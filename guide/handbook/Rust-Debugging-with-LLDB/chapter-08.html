Chapter 8: Stepping, Frames, and Backtraces

A breakpoint stops the program at a chosen point. Once it is stopped, the debugger gives you three interlocking tools to explore what happened and what is about to happen:

  • Stepping: moving execution forward one instruction, one line, or one function at a time.
  • Frames: the individual levels of the call stack, each with its own function, locals, and arguments.
  • Backtraces: the full list of frames, from the current function outward to the program entry.

Mastering these three tools turns a session from a sequence of isolated stops into a continuous, readable narrative of execution. In this chapter, we will look at each in turn, with attention to the ways Rust makes them different from debugging a simpler language.

The three step commands

LLDB provides three step commands for source-level navigation:

  • next — step over the next source line.
  • step — step into the next function call.
  • finish — run until the current function returns.

Each answers a different question. Learning the distinction is more important than memorizing dozens of LLDB commands.

Step over: next

Suppose execution is stopped here:

let result = add(x, y);

Use:

next

or:

n

LLDB executes the current source line without entering the called function.

This is:

Execute this line and stay at this level.

Use next when:

  • You trust the called function.
  • You want to see what happens after the call.
  • You want to avoid stepping through library code.

After next, execution is on the following line of the same function. Any side effects of the call have occurred, but you did not observe them from inside.

Step into: step

Use:

step

or:

s

When the current line calls another function, LLDB attempts to enter that function.

For:

let result = add(x, y);

step takes you into:

fn add(...)

This is:

Show me what happens inside this call.

Use step when:

  • You suspect the bug is inside the called function.
  • You need to inspect the arguments the function received.
  • You need to see how the function transforms its input.

In Rust, step may enter code the compiler generated. When stepping into a method call on a trait object, for instance, LLDB steps into the concrete implementation that is actually invoked. When stepping into an iterator chain, LLDB may enter a next implementation for one of the intermediate adapters. This is rarely what you want; use next to step over these calls, or place a source-line breakpoint inside the specific function you care about.

Step out: finish

If you are inside a function and have seen enough:

finish

This runs until the current function returns.

Conceptually:

main
  ↓
add
  ↓
finish
  ↓
main

LLDB documents this as thread step-out.

Use finish when:

  • You have seen enough inside the current function.
  • You want to know what the function returns.
  • You want to return to the caller.

When finish returns, LLDB prints the return value of the function that just completed, if it can determine it. This is often a fast way to see what a function produced without stepping through its body.

In Rust, this is particularly useful for small helper functions such as parsers, converters, or constructors. You set a breakpoint at the entry, inspect the arguments, call finish, and observe the return value. The whole function has been checked in three commands.

The mental model

next   → stay at this level
step   → go down one level
finish → go up one level

Three commands, three directions. Once this is internalized, most source-level navigation becomes a matter of choosing the right direction for the question you are asking.

Stepping in the presence of Rust constructs

A few Rust constructs make stepping behave in ways you might not expect:

  • Inlined functions: When a small function is inlined by the optimizer, step may not descend into it at all. The source line still shows the call, but the compiled code has no separate symbol for the callee. In the debug build, inlining is less aggressive, so this is mostly a release-mode issue.
  • Iterator chains: A single source line such as items.iter().filter(...).map(...).collect() expands into multiple nested calls. step into this line can lead you through several layers of adapter code. It is often more productive to introduce a named intermediate value or to set a breakpoint inside the closure you want to inspect.
  • Trait method dispatch: When you step into a call on a trait object, the function you enter is the concrete implementation of the trait method for the value’s runtime type. In source, you saw a trait method call; in the debugger, you are inside a specific struct’s method.
  • Macros: A call inside a macro may appear as a single source line at the macro invocation. Stepping may jump to the expansion site instead of the invocation site, or vice versa, depending on how the macro expanded and how debug information was generated.
  • Async functions: Stepping into an async fn call does not enter the function body in the way you might expect. The async fn returns a future immediately; execution of the body only happens when the future is polled. We cover this in more detail in the async chapter.

None of these are bugs in LLDB. They reflect the shape of the compiled code that Rust produces. Knowing what to expect makes stepping productive rather than frustrating.

Frames

A frame is one level of the call stack. When the debugger is stopped, exactly one frame is selected: the current frame, conventionally numbered #0. The other frames are the callers of the current frame, and their callers, and so on, out to the program entry.

What a frame contains

Every frame contains:

  • A function: which function this frame corresponds to.
  • A source location: which file and line the current instruction belongs to.
  • Arguments: the values the function was called with.
  • Locals: the variables in scope at the current point.
  • A return address: where execution will go when this function returns.

When you ask LLDB to inspect variables, it inspects the variables of the selected frame. Understanding this is the single most important lesson about frames: if a variable does not exist in the selected frame, LLDB cannot show it to you.

Where am I in the call stack?

When the debugger stops, ask:

Where is execution?

Use:

thread backtrace

or:

bt

A backtrace shows the call stack.

For example:

frame #0  parse_config
frame #1  load_application
frame #2  main

Read this as:

main
→ load_application
→ parse_config

The current location is the first frame.

LLDB’s official tutorial uses thread backtrace to inspect the current call stack.

Read the current frame

Use:

frame info

This gives information about the current stack frame.

You want to know:

Which function?

Which source file?

Which line?

Which module?

This is the first orientation step after every unexpected stop.

The output typically includes the frame number, the function name, the file and line, and sometimes the source line itself. In compact form, it is one line:

frame #0: first_session`first_session::main at src/main.rs:6

For a screen-reader workflow, this line is a compact orientation point that you can read on every stop without overwhelming output.

Selecting a frame

Suppose a backtrace shows:

frame #0
frame #1
frame #2
frame #3

Select frame 2:

frame select 2

Then:

frame variable

Now the variables belong to frame 2.

This is extremely important. If you inspect a variable and LLDB says it is unavailable, first ask:

Am I in the frame where this variable exists?

Selecting a frame changes the target of subsequent inspection commands. frame variable, frame info, expression, and most other inspection commands operate on the selected frame.

Moving up and down the call stack

You can move through frames without counting indices.

Up toward the caller:

up

Down toward the callee:

down

Or explicitly:

frame select 3

The conceptual direction is:

callee
↑
caller
↑
caller

When investigating a failure, move outward until you find the frame where the relevant state was created.

For a screen-reader workflow, up and down are convenient because they do not require you to remember the frame index. They simply move the selection one level in the corresponding direction. The two commands are symmetric: if up moves you from frame 1 to frame 2, down moves you back from frame 2 to frame 1.

Frames in Rust: what to expect

Rust programs have a few predictable patterns in their call stacks:

  • The bottom of the stack contains the C runtime startup: __libc_start_main, followed by Rust runtime frames such as std::rt::lang_start and std::rt::lang_start_internal.
  • The next frames up contain the main symbol, which is Rust’s main function or the wrapper the runtime generates around it.
  • Application frames begin above main. These are the frames from your own code and from the libraries you use.
  • The top of the stack (frame #0) is where execution is currently stopped.

In a debugging session, the frames you care about are almost always the application frames. Runtime and C library frames are the machinery that started and is now driving your program. Unless the bug is specifically in the runtime, you can ignore them.

One practical consequence: when a program panics, the backtrace may show many runtime frames above the panic site. The first frame belonging to your own crate is usually the one worth inspecting; the runtime frames above it are unwinding the stack.

Frames and inlining

When the optimizer inlines a function, that function no longer has its own frame. The backtrace shows the caller instead, and the source location may still point to a line inside the inlined function, depending on how debug information was generated.

In a debug build, inlining is usually minimal, so the backtrace reflects your source-level call structure closely. In a release build, inlining can collapse many frames into one. If a backtrace does not show a function you expected, ask whether that function was inlined. The answer is almost always yes if the function was small and the build was optimized.

LLDB sometimes indicates inlined frames in the backtrace with an annotation such as [inlined]. If you see such a frame, you know the compiler merged the call into its caller, and the frame is provided purely from debug information.

Backtraces

A backtrace is the list of frames from the current location outward to the program entry. It answers the question:

How did execution reach this point?

Reading a backtrace as a map

When stopped unexpectedly:

bt

is often the first useful command.

Read it as a path:

frame #0
current failure

frame #1
caller

frame #2
caller of caller

...

Do not immediately read every frame.

Ask:

Which frame belongs to my code?

Then inspect that frame.

For a Rust program, the frames belonging to your code are usually easy to recognize: they show your crate name and your source file. Frames from the standard library and third-party crates show their own crate names. Frames from the C runtime show C-style names.

Limiting backtrace output

A backtrace in a large program can contain dozens of frames. For a screen-reader workflow, reading dozens of frames at once is overwhelming and often unnecessary.

Limit the output:

bt 5

This shows the five most recent frames. If you need more, ask for more:

bt 15

You can also use the repeat-with-Enter behavior to page through a longer backtrace one screen at a time, as described in Chapter 6. For a screen-reader workflow, controlling the size of each output is often more important than controlling the total amount, because it keeps the mental model current.

Backtraces and async code

Async code produces backtraces that are not the same as synchronous call stacks. In an async program, the “caller” of a function may be the runtime scheduler, not another application function. The frames you see in a backtrace may include:

  • Runtime frames from the executor (Tokio, async-std, or another runtime).
  • Poll frames from the future’s state machine.
  • Waker machinery frames from the runtime.
  • Your own application frames, which may appear in a different order than in synchronous code.

We will cover async debugging in a dedicated chapter. For now, the important point is that a backtrace in async code is a snapshot of the current stack at the moment of the stop, not a full logical trace of the async task. The logical trace may be split across multiple polls at different times.

Backtraces in panic situations

When a Rust program panics and you are running under LLDB, the debugger may stop on the underlying signal that the panic ultimately raised. At that point, bt shows the current stack, which is often the unwinding stack rather than the panic site.

To find the panic site, look for the deepest frame that belongs to your own crate and that is inside the function you suspect. Frames above it are the panic machinery; frames below it are the application code that led to the panic.

We will cover panic debugging in detail in a later chapter. For now, the discipline is the same: read the backtrace as a map, identify the frames that belong to your code, and inspect them one at a time.

Backtraces across threads

Rust programs can have multiple threads. Each thread has its own stack, and the currently selected thread determines which stack bt shows.

To see the backtrace for all threads at once:

thread backtrace all

For programs with many threads, this output can be very long. A more focused workflow is:

  1. Use thread list to see the threads.
  2. Identify the thread you care about by its stop reason or its name.
  3. Use thread select N to select it.
  4. Use bt to see its backtrace.

This is the same workflow we will use in the chapter on threads and async Rust. The backtrace itself is per-thread; the thread selection determines which backtrace you see.

Stepping and frames together

Stepping and frames are not separate tools. They work together. Every step either stays in the current frame, moves to a new frame, or returns to an old frame.

A worked example

Consider this short program:

fn double(x: i32) -> i32 {
    x * 2
}

fn quadruple(x: i32) -> i32 {
    let doubled = double(x);
    double(doubled)
}

fn main() {
    let value = 5;
    let result = quadruple(value);
    println!("{result}");
}

Set a breakpoint on quadruple and run. The debugger stops at the entry of quadruple.

Backtrace:

frame #0  quadruple
frame #1  main
frame #2  std::rt::lang_start_internal
...

Step over to the first call to double:

(lldb) next

Now you are at the call let doubled = double(x);. Step into it:

(lldb) step

Now the backtrace shows:

frame #0  double
frame #1  quadruple
frame #2  main
frame #3  std::rt::lang_start_internal
...

Inspect the argument x:

(lldb) frame variable x

You see the value 5. Step over the multiplication:

(lldb) next

Finish and observe the return value:

(lldb) finish

You are back in quadruple. The value doubled is now 10.

Step over to the next call:

(lldb) next

Step into the second call:

(lldb) step

Inspect x again:

(lldb) frame variable x

Now you see 10, the doubled value. This is a concrete demonstration of how each call carries different data into the same function.

Finish:

(lldb) finish

Back in quadruple. The final value is 20.

Finish again:

(lldb) finish

Back in main. Inspect result:

(lldb) frame variable result

You see 20.

This small session demonstrates the interplay of stepping and frames:

  • Every step pushed a new frame onto the stack.
  • Every finish popped the current frame and returned to the caller.
  • The frame selection always matched the current execution point, so frame variable always showed the right locals.

Frame selection in practice

A subtle but useful technique: when the program stops inside a function, the frame selection is automatically set to the top frame. But you can then manually select a caller frame to inspect its state, without changing where execution is stopped.

For example, suppose you are stopped inside double, and you want to see what value quadruple passed. You already know it from inspecting x, but for a more complex case, you might want to inspect quadruple’s local doubled before double modified anything. Use:

(lldb) frame select 1

Now inspect doubled:

(lldb) frame variable doubled

The current execution point is still inside double. You have not moved execution. You have simply changed which frame your inspection commands target. When you are done, you can use frame select 0 to return to the top frame, or down if you are only one level up.

This is a very useful discipline: frame selection is separate from execution position. It lets you look at caller state without disturbing the program.

When stepping is not the right tool

Stepping is powerful, but it is not always the best tool.

Consider a loop that runs ten thousand times. Stepping through each iteration would take hours. Set a conditional breakpoint, or break only when a value satisfies a condition, or use a watchpoint. These are covered in a later chapter.

Consider a piece of code that you trust, but that calls many functions you do not trust. Use next to step over the trusted code and place a breakpoint inside the functions you want to inspect. This avoids stepping through thousands of lines you do not care about.

Consider async code with a long chain of .await calls. Stepping through each await would lead you into runtime machinery. Instead, place breakpoints at meaningful application boundaries and use continue.

The general rule:

Stepping is for tracing a short, specific path. Breakpoints are for selecting exactly where to stop in a long or branching path.

Knowing when to step and when to break is one of the marks of a mature debugging practitioner.

Rust 2024 notes on stepping and frames

A few Rust 2024 specifics affect how stepping and frames behave.

unsafe blocks as stepping landmarks

Because Rust 2024 requires explicit unsafe { ... } blocks inside unsafe fn bodies (via the unsafe_op_in_unsafe_fn lint), a function that previously had a single implicit unsafe region now has one or more explicit ones. This is useful when stepping: a breakpoint or step into the opening of an unsafe block marks the transition from safe to unsafe code. In a backtrace, this transition is often visible as a frame belonging to a function with an unsafe precondition, which is exactly the kind of frame you want to inspect first when debugging unsafe logic.

No references to static mut

Rust 2024 forbids references to static mut. If you are debugging code that reads or writes global state, you will now see accesses through raw pointers or through interior-mutability primitives such as Mutex, AtomicUsize, or UnsafeCell. When you step through code that updates a global, the update will appear as a method call on one of those types rather than as a simple assignment to a mutable reference. This changes what you see as you step, but it does not change the fundamental mechanics of stepping or frame inspection.

#[unsafe(no_mangle)] and frame names

A function exposed with #[unsafe(no_mangle)] appears in the debugger with its exact source name. When you step into such a function from C or from another Rust crate, the frame name will be readable and predictable. This is particularly useful when debugging FFI, where you want to see the boundary between the Rust and C portions of the program clearly.

Async and 2024

The Rust 2024 edition does not change the fundamental shape of async execution: an async fn still returns a future, and an executor still polls it. What it does change is the visual structure of async code, particularly around async blocks and closures, and around async in traits. When you step through async code compiled with the 2024 edition, you may see slightly different compiler-generated names for futures and poll methods, but the debugging discipline is the same as for earlier editions.

Summary

In this chapter, we covered the three interlocking tools of source-level execution control:

  • Stepping: next stays at the current level, step descends into a call, and finish ascends back to the caller. The mental model is one level down, one level up, or stay put.
  • Frames: the levels of the call stack. Each frame has its own function, arguments, and locals. Selecting a frame changes the target of subsequent inspection commands.
  • Backtraces: the full list of frames, read as a map from the current location outward to the program entry.

We looked at how stepping interacts with Rust-specific constructs such as inlining, iterator chains, trait dispatch, macros, and async functions. We also worked through a small example that demonstrated the interplay of stepping and frame selection across multiple function calls.

We saw that frame selection is separate from execution position: you can inspect any frame in the stack without disturbing the program’s location. This is one of the most useful and least obvious features of a source-level debugger, and it is often the key to understanding a bug that lives in a caller rather than in the current function.

Finally, we reviewed the Rust 2024 specifics that affect stepping and frames: unsafe blocks as explicit landmarks, the disappearance of &static mut, the readability of #[unsafe(no_mangle)] frames, and the shape of async code under the new edition.

In the next chapter, we will turn to inspecting Rust values in detail: structs, enums, Option, Result, references, and the ways that Rust’s types show up in the debugger.
