Chapter 11: Ownership, References, and Optimized Builds

Rust’s ownership model is the feature that most distinguishes it from other systems languages. At compile time, the borrow checker reasons about who owns each value and how it may be accessed. At runtime, that reasoning is over: the program either obeys the rules or it does not exist. The debugger sees the runtime side of this, and only the runtime side.

This chapter is about the interaction between these two views. We will look at the boundary between static ownership and dynamic runtime state, at what moves leave behind in memory, at how references and mutable references look when inspected, and at the effect of optimized builds on what the debugger can show you.

Much of what follows is about avoiding two common confusions:

  • Expecting the debugger to explain a compiler error about ownership.
  • Being surprised when the debugger shows something that the compiler considers invalid.

Understanding where the boundary lies turns both of these from sources of frustration into ordinary facts of Rust debugging.

Ownership is static; runtime state is dynamic

Ownership, borrowing, and lifetimes are checked at compile time. LLDB observes runtime memory and values. It cannot explain why the borrow checker rejected your code.

Use the compiler for static rules. Use LLDB for runtime behavior.

A static question

Consider:

fn main() {
    let s1 = String::from("hello");
    let s2 = s1;
    println!("{}", s1); // error: borrow of moved value: `s1`
}

The compiler rejects this program with an error. LLDB has nothing to say about it, because there is no program to run. The error is not about runtime state. It is about the static analysis the compiler performs before generating any code.

The right tools for this question are:

  • cargo check, which produces the diagnostic.
  • rustc --explain E0382, which explains the specific error code.
  • Reading the source, understanding that ownership of the heap data moved from s1 to s2.

LLDB cannot help, because there is no binary to load.

A dynamic question

Now consider:

fn main() {
    let mut items = Vec::new();
    items.push(10);
    items.push(20);

    println!("{:?}", items);
}

This program compiles. If it produces the wrong output because the vector is unexpectedly empty, or because it contains the wrong elements, the compiler has no opinion. The bug is in the runtime contents of the vector, and the right tool is the debugger.

Set a breakpoint after the pushes and inspect the vector:

(lldb) frame variable items
(std::vector<int, ...>) items = size=2 {
    [0] = 10
    [1] = 20
}

If the elements are correct here, the bug is later. If they are wrong here, the bug is earlier. The debugger answers a question the compiler cannot see.

A useful practice

Before starting a debugging session, ask:

Is this a static question or a dynamic question?

If the program does not compile, it is a static question. The compiler is the first stop.

If the program compiles and produces the wrong behavior, it is a dynamic question. The debugger is the first stop.

Many frustrating sessions come from mixing the two: reaching for the debugger on a program that will not compile, or reaching for the compiler on a program that compiles but runs incorrectly. Keeping the categories straight saves time and keeps the investigation focused.

Moves and runtime state

A related complication: in Rust, a value that has been moved may still be physically present in memory for some time. The compiler knows that the value is no longer valid at the source level, but the bytes may not have been overwritten. When you inspect the original variable in the debugger, you may see its last value, even though using it in source would be a compile error.

For example:

let s1 = String::from("hello");
let s2 = s1;
// s1 is moved here; the compiler will not let you use it.
// But the bytes of the String metadata may still be on the stack,
// and LLDB may show them if you ask.

If you set a breakpoint after the move and inspect s1, LLDB may show:

(lldb) frame variable s1
(std::string) s1 = "hello"

Even though s1 is invalid at the source level, the debugger shows the bytes it used to hold. This is not a bug in the debugger. It is a consequence of the fact that Rust does not guarantee that moved-from memory is cleared immediately. The compiler may reuse the memory later, or it may not. When you see this in the debugger, remind yourself that the source-level rules still apply: the compiler will reject any attempt to use s1, regardless of what the bytes currently contain.

Some compilers do insert code to clear moved-from values in certain cases, especially when the type contains pointers that could be misused if the memory were later re-read. Other compilers leave the bytes alone. Either behavior is valid. The point is that you cannot rely on the debugger’s display of a moved-from variable to mean anything about the program’s correctness.

When this matters

The moved-from memory issue matters in a few specific cases:

  • Debugging unsafe code: If you are debugging unsafe code that reads moved-from memory (which is itself a bug), the debugger will show you the stale bytes. Understanding that they are stale is essential to interpreting the result.
  • Debugging after a move: If you inspect a variable that has been moved, and it looks like it still has a value, do not conclude that the move failed. The move happened; the memory was just not cleared.
  • Debugging FFI: If Rust passes a value to C by value, the Rust variable is moved. The C code receives a copy or a move, depending on the FFI contract. The Rust variable may still show its old value in the debugger, even though the Rust source cannot use it.

The general rule is:

Do not use the debugger’s display of a moved-from value as evidence about correctness. Use the source-level rules.

The difference from C

In C, a moved-from value would typically be a pointer that you set to NULL manually. In Rust, the compiler tracks moves without modifying the bytes. This is one of the ways Rust delivers zero-cost abstractions: it does not pay for clearing moved-from values unless the optimizer decides that clearing is beneficial.

For debugging, this means that inspecting a moved-from value requires a different mental model. It is not the same as inspecting a freed pointer in C, where the value is genuinely gone. It is closer to inspecting a variable that has gone out of scope: the storage exists, but the source says the value is not valid there.

References and borrows

Rust code frequently contains:

&T
&mut T

When debugging, distinguish:

the reference

from:

the value referenced

If:

fn update(config: &mut Config)

is stopped inside the function, inspect:

(lldb) frame variable config

Then inspect relevant fields:

(lldb) frame variable config.field

The question is:

What state does this mutable reference currently expose?

Then step forward and determine where the mutation occurs.

Most of the time, the Rust pretty-printers dereference the reference for you: inspecting config shows the value of the struct, not its address. But sometimes the display shows the raw pointer, or a value that does not match what you expect. In those cases, it is useful to know which view you are looking at.

Dereferencing explicitly

When you are not sure whether LLDB is showing you the reference or the value, dereference explicitly:

(lldb) frame variable (*config).field

or:

(lldb) frame variable config->field

Both forms tell LLDB to follow the pointer before accessing the field. If the explicit form works but the implicit form does not, you were looking at the pointer.

For references to &str, the pretty-printer shows the string contents directly. For references to slices (&[T]), it shows the slice elements. For references to owned types such as String or Vec<T>, it shows the dereferenced value.

Mutable references

A &mut T is displayed the same way as a &T: as the value it points to. The difference is that as you step forward, the value changes. This makes the debugger particularly useful for tracking mutations: you can set a breakpoint before the mutation, step to the line where it occurs, and inspect the value afterward.

An example:

fn apply_discount(price: &mut u32, percent: u32) {
    let reduction = *price * percent / 100;
    *price -= reduction;
}

Set a breakpoint at the entry of apply_discount. Inspect:

(lldb) frame variable price
(unsigned int *) price = 0x... {
    500
}

Step over both lines, then inspect again:

(lldb) frame variable price
(unsigned int *) price = 0x... {
    425
}

The value changed from 500 to 425, reflecting the discount. This is what a mutable reference lets you do: observe the mutation at the point where it happens.

For a more careful investigation, you can set a watchpoint on the referenced value (covered in a later chapter). The watchpoint stops execution whenever the value changes, giving you a precise observation of the mutation site.

References in frames

A reference held by a function may outlive the frame that created it. For example:

fn get_name(user: &User) -> &str {
    &user.name
}

fn main() {
    let user = User { name: String::from("Alice") };
    let name = get_name(&user);
    println!("{name}");
}

When get_name returns, the frame is gone, but the returned reference still points into the user value in main. If you inspect name in main, it displays as "Alice", because the debugger follows the reference to the underlying data.

In some cases, if you inspect a reference that points into a frame that has been popped, the value is genuinely invalid. The debugger may still show stale bytes, but the source-level rules say the reference is invalid. This is exactly the kind of case where the borrow checker prevents you from writing the code in the first place.

Ownership bugs

A compiler error such as:

borrow of moved value

is usually better investigated first with:

rustc --explain E0382

rather than LLDB.

LLDB is for runtime behavior.

The compiler is for static ownership rules.

Use the tools together:

Compiler
→ explains why the program cannot compile.

LLDB
→ explains what a compiled program actually does.

This distinction saves time.

What compiler errors mean

Some common ownership errors and their meanings:

  • E0382: borrow of moved value: The value was moved, and now the code tries to use it. The fix is usually to borrow (&s1) instead of moving, or to clone (s1.clone()) if a separate copy is genuinely needed.
  • E0502: cannot borrow as mutable because it is also borrowed as immutable: Two references of different kinds were active at the same time. The fix usually involves narrowing the scope of one of the borrows.
  • E0499: cannot borrow as mutable more than once at a time: Two mutable references were active at the same time. The fix usually involves restructuring the code so that only one is active at a time.
  • E0597: borrowed value does not live long enough: A reference outlives the data it points to. The fix usually involves changing the lifetime structure of the function, or returning an owned value instead of a reference.
  • E0515: cannot return reference to local variable: A function tries to return a reference to a value it owns locally. The fix is to return an owned value, or to accept the data as a parameter and return a reference into it.

Each of these is a static question. The compiler has the answer. The debugger does not need to be involved.

When to use LLDB for ownership questions

There is one scenario where LLDB is useful for an ownership-related question: when you want to observe a move or a drop at runtime. For example:

  • You want to know whether a particular Drop implementation ran.
  • You want to see the exact moment a value was moved into a new location.
  • You want to confirm that a resource is released at the point you expect.

In these cases, the question is not “is this static-correct?” but “what does this compiled program actually do?” That is exactly what LLDB is for.

A practical example: set a breakpoint in a Drop implementation to observe when a resource is freed:

impl Drop for Connection {
    fn drop(&mut self) {
        // ...
    }
}

Break on Connection::drop. When the breakpoint fires, inspect the backtrace. The frame below the drop call is the point where the value went out of scope. This tells you exactly where the resource is being released, which can be valuable when tracking down a resource leak or an unexpected release.

Debug assertions

Rust debug builds can contain debug assertions.

The Rust compiler enables cfg(debug_assertions) automatically at optimization level 0 unless explicitly configured otherwise.

This means the debug build may behave differently from a release build.

When debugging a problem, record which profile you are running.

Typical development build:

cargo build

Typical release build:

cargo build --release

If the bug only appears in release mode, reproduce it under:

rust-lldb target/release/your_program

Optimization can make debugging substantially harder.

What debug assertions do

Several standard-library checks are enabled only in debug builds:

  • Integer overflow checks: In debug builds, arithmetic overflow panics. In release builds, it wraps by default (unless overflow-checks = true is set in the profile).
  • Bounds checks: Slice and array indexing is bounds-checked in both debug and release builds, but the checks may be optimized away when the compiler can prove they are unnecessary.
  • Debug assertions in user code: The debug_assert! and debug_assert_eq! macros only run when debug_assertions is enabled. In release builds, they are compiled out entirely.
  • Uninitialized memory checks: Some parts of the standard library have stricter checks in debug builds that detect use of uninitialized memory.

Because of these differences, a bug that appears in one profile may not appear in the other. When a bug reproduces only in release mode, it is often because the debug build’s extra checks catch the problem earlier, converting what would have been a silent misbehavior into a clear panic.

A common pattern

Suppose a program runs correctly in debug but crashes in release. Common causes:

  • Integer overflow that wraps silently in release but panics in debug.
  • Undefined behavior in unsafe code that the optimizer exploits in release but does not trigger in debug.
  • Race conditions that only manifest when timing is different, which optimization can cause.
  • Uninitialized memory that happens to be zero in debug but has garbage in release.

To debug such a bug, build the release binary with debug information:

[profile.release]
debug = true

This does not disable optimizations, but it allows LLDB to map addresses back to source. The optimizer will still move and eliminate values, but the debug information reduces how often you see <optimized out>.

Then run the release binary under rust-lldb:

rust-lldb target/release/your_program

Set breakpoints at the points where the program misbehaves, and inspect what you can. This is harder than debugging the debug build, but it is the right approach when the bug does not reproduce in debug.

Disabling overflow checks

For an important class of bugs, it is useful to know whether the bug depends on the overflow check behavior:

  • Debug build: overflow panics.
  • Release build: overflow wraps.

You can force the release build to keep overflow checks:

[profile.release]
overflow-checks = true

This can be useful when you want to reproduce a debug-only bug in a release-like build. If the bug appears with the overflow check enabled but disappears when the check is disabled, the bug is very likely an arithmetic overflow.

Conversely, you can enable overflow checks in debug builds that already have them, or disable them explicitly for a specific experiment.

Debugging optimized Rust

When variables appear unavailable or source stepping behaves strangely, optimization may be involved.

A useful debugging build is:

cargo build

rather than:

cargo build --release

If you specifically need a release-like build with better debugging information, configure the Cargo profile accordingly.

For example:

[profile.release]
debug = true

This keeps release optimization while generating debug information.

Rust’s compiler documentation distinguishes several levels of debug information and notes that removing debug information can make debugger use ineffective.

What optimization does to values

In an optimized build, the following can happen:

  • A value is kept in a register: LLDB may still show it correctly, if it can map the register to the source variable.
  • A value is eliminated: If the compiler can prove that a value is never needed, it may not allocate storage for it. LLDB shows <optimized out>.
  • A value is merged with another: Two source-level variables may share the same storage. LLDB may show one or the other, or neither.
  • A value is split across storage: A single source-level variable may be represented by multiple registers or memory locations. LLDB may show only one part.
  • A function is inlined: The function no longer has its own frame. Stepping into it may not work; the source line still shows the call, but execution does not pass through a separate frame.
  • Instructions are reordered: The order of source lines no longer matches the order of machine instructions. next may jump to unexpected lines.

The general rule: in an optimized build, expect the debugger to be less accurate. Use frame variable and inspect what is available. Do not assume that a missing value means the program is broken; the compiler may simply have decided not to keep it.

Strategies for optimized debugging

When you must debug an optimized build, a few strategies help:

  • Enable debug information: Set debug = true in the release profile. This keeps optimization but provides enough debug information for LLDB to map addresses to source.
  • Use a partial optimization profile: Configure a custom profile with opt-level = 1 and debug = true. This is less aggressive than the default release profile and preserves more variables.
  • Isolate the suspicious function: Write a small test program that reproduces the bug with the same optimization settings. Debugging a small program is easier than debugging a large one.
  • Use black_box: The std::hint::black_box function prevents the compiler from optimizing away a value that you want to inspect. It is a hint, not a guarantee, but it is often effective.
  • Inspect only what is available: When a value is optimized out, do not try to force it. Move to a nearby breakpoint where the value is still used, and inspect it there.

Example: using black_box

Consider:

fn compute(x: i32, y: i32) -> i32 {
    let intermediate = x * y;
    intermediate + 1
}

In a release build, intermediate may be eliminated, because the compiler folds the multiplication and the addition into a single expression. If you try to inspect intermediate, LLDB may say it is optimized out.

To force the compiler to keep the value:

use std::hint::black_box;

fn compute(x: i32, y: i32) -> i32 {
    let intermediate = x * y;
    black_box(intermediate);
    intermediate + 1
}

The black_box call tells the compiler to assume that the value has been observed, preventing it from being eliminated. This is a temporary modification for debugging; remove it when the investigation is done.

Note that black_box is a hint. It greatly increases the likelihood that the compiler keeps the value, but it is not an absolute guarantee. If you still see <optimized out>, try enabling debug information, or restructure the code so the value is genuinely needed at the point you want to inspect it.

A common mistake

A common mistake when debugging optimized code is to assume that a value shown by the debugger is the exact value the source-level variable held at that line. In an optimized build, the debugger is showing you what it can reconstruct from debug information and current machine state. The reconstruction is usually correct, but not always. When the reconstruction is uncertain, the debugger may show a value that differs slightly from the source-level one, because the source-level value has been transformed away.

If you suspect that a shown value is not reliable, consider:

  • Switching to a debug build to confirm the actual value.
  • Adding a temporary println! or logging call at the point of interest.
  • Using black_box to force the compiler to keep the value.

The debugger is one of several tools, and the others are sometimes more appropriate for a specific question.

Building debuggable releases

A practical recommendation: if your project has a release build that is used in production, add a separate profile for debugging, or enable debug information on the release profile. This makes it possible to inspect a production-like binary without compromising optimization.

A typical configuration:

[profile.release]
debug = true
# optional: reduce optimization slightly to preserve more variables
# opt-level = 2

[profile.release-debug]
inherits = "release"
debug = true
opt-level = 1
lto = "off"

The release-debug profile inherits from release but reduces the optimization level. This preserves more variables and reduces inlining, at a small cost in runtime performance. It is useful for reproducing bugs that appear only under optimization, without losing all the information the debugger needs.

Build with the custom profile:

cargo build --profile release-debug

The resulting binary is placed in target/release-debug/. You can debug it with:

rust-lldb target/release-debug/your_program

This is often the best compromise between fidelity to production behavior and observability in the debugger.

Rust 2024 notes on ownership and optimization

A few Rust 2024 specifics affect what you see when debugging ownership and optimized code.

unsafe_op_in_unsafe_fn and optimization

Rust 2024 warns when unsafe operations appear inside an unsafe fn without an explicit unsafe { ... } block. This is a source-level change, but it has a subtle effect on debugging optimized code: explicit unsafe { ... } blocks create natural boundaries that the optimizer respects more often than implicit unsafe regions. When you set a breakpoint at the opening of an unsafe block, you are less likely to find that the block was inlined into its caller, because the unsafe boundary is a stronger optimization barrier.

static mut and optimization

Rust 2024 forbids references to static mut. Code that previously used &static mut now uses raw pointers or interior-mutability primitives. From an optimization perspective, this can change what the compiler assumes about aliasing and may change what the debugger sees. Raw pointer accesses are harder for the compiler to optimize aggressively, so you may find that values related to global state are more reliably inspectable in Rust 2024 builds than they were in earlier editions.

Edition 2024 and generics

The Rust 2024 edition tightens several rules around generic code, particularly around lifetime capture in impl Trait and the meaning of certain trait bounds. From a debugging perspective, this mostly affects which instantiations exist in the binary, and therefore which breakpoints are meaningful. When you break on a generic function, LLDB may resolve the breakpoint to a specific instantiation, or to all of them. If the resolution is ambiguous, source-line breakpoints remain the most reliable alternative.

Summary

In this chapter, we covered the interaction between Rust’s static ownership rules and the runtime state that LLDB observes:

  • Static vs. dynamic: Ownership is a static question, answered by the compiler. Runtime state is a dynamic question, answered by LLDB. Keeping the two categories straight avoids wasted effort.
  • Moves and stale memory: A moved-from value may still have its bytes in memory. The debugger can show them, but they do not mean the value is valid. Trust the source-level rules, not the debugger’s display.
  • References and borrows: The debugger shows the referenced value by default. When in doubt, dereference explicitly with (*expr).field or expr->field. Mutable references change as you step forward, which makes them useful for tracking mutations.
  • Ownership bugs: These are compiler errors. Use rustc --explain for common ones such as E0382, E0502, E0499, E0597, and E0515. Use LLDB only when the question is about runtime behavior (for example, when does a Drop run).
  • Debug assertions: Debug builds enable overflow checks and other runtime checks that release builds may disable. This is why a bug may appear in one profile but not the other.
  • Optimized builds: Optimization can eliminate values, inline functions, reorder code, and change the shape of the machine program. Debugging an optimized build is harder, but possible with the right settings and strategies.
  • Debuggable releases: A separate profile that inherits from release but enables debug information and reduces optimization is often the best compromise.
  • Rust 2024 specifics: unsafe blocks are stronger optimization barriers, static mut restrictions change global-state access patterns, and tightening of generic rules affects which instantiations exist in the binary.

The unifying theme: the debugger is a runtime instrument, and runtime behavior is the domain of dynamic questions. For everything static, the compiler is the tool. Learning to move fluently between the two views is what makes Rust debugging productive.

In the next chapter, we turn to two tools that extend the debugger’s reach: conditional breakpoints, which stop only when a specific condition is met, and watchpoints, which stop when a value changes. Both are essential for debugging bugs that appear only in rare circumstances or depend on subtle state changes.
