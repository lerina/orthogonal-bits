Chapter 6: The Essential Commands

The previous chapter gave you one complete debugging session. This chapter gives you the vocabulary to run many. It focuses on the small set of commands you will use in nearly every session, and it explains the grammar that ties them together.

You do not need to memorize every command in LLDB. The debugger has hundreds of them, and most are specialized. What matters is fluency with the small core: the commands that start the program, stop it, move it forward, and inspect what is there.

The first commands to learn

Learn these first:

run
breakpoint set
continue
next
step
finish
frame variable
bt
quit

Their common short forms are:

r
b
c
n
s
finish
frame variable
bt
q

LLDB supports convenient aliases for many common debugger commands.

For a screen-reader workflow, the full command names are often easier to remember semantically. When you hear “breakpoint set” you know what you are doing. When you hear “b” you have to translate. When you type “breakpoint set” and the debugger echoes it back, you can confirm what you intended. The typed characters are the same length either way for most commands; only the mental overhead differs.

In practice, most developers end up mixing the two: full names for commands they use infrequently, short forms for commands they type many times in a session. Either style is fine. Choose the one that keeps you oriented.

LLDB command grammar

LLDB commands usually follow this shape:

noun verb --option value

Examples:

breakpoint set --name main
breakpoint set --file src/main.rs --line 8
thread backtrace
frame variable
watchpoint set variable config

Many commands have short forms:

b main
c
n
s
bt

But full names are often easier to remember and easier to hear with a screen reader.

The noun-verb structure is not a coincidence. LLDB organizes its commands as a tree. The first word is a category. The second word is the operation within that category. This is why help works so well: you can explore the tree, one level at a time, and let the debugger teach you its own vocabulary.

Options are named consistently across commands. Wherever a command takes a target, you can usually find --file, --line, --name, --address. This consistency means that learning one command in depth gives you leverage on many others.

Help is part of the interface

Use:

help

For a specific command:

help breakpoint set
help frame variable
help watchpoint

LLDB’s help system is detailed. You do not need to memorize every option.

When you use help, you get a compact reference: a one-line description, the syntax, the available options, and often a note about the short form and any related commands. For a screen-reader user, this is often more useful than reading a large manual page, because the help output is structured and predictable.

A common workflow is: you know roughly what you want to do, you type help followed by a keyword, and you scan the output for the option you need. Over time, the ones you use most often become second nature.

Command completion

Start typing a command and use completion to discover subcommands:

breakpoint

Conceptually, LLDB exposes a command tree:

breakpoint
    set
    list
    delete
    modify
    command

frame
    info
    variable
    select

thread
    list
    select
    backtrace

This is useful because the debugger itself can teach you its vocabulary.

Completion works not only for commands but also for some option values. For example, typing part of a filename after --file can trigger filename completion. This is especially helpful when you have several source files with similar names.

Repeat with Enter

Pressing Enter on an empty command line repeats the previous command. This is useful for paging through a backtrace:

bt 5

Then press Enter to see more.

Be careful: an empty Enter is still a command.

For a screen-reader workflow, this repeat behavior is a double-edged tool. It makes it easy to page forward without retyping. But it also means that a stray Enter can trigger a command you did not intend. If you need a moment to think, it is safer to type a command that does nothing, such as help with no argument, or simply to accept the repetition as long as you remember where the last command left off.

Start the program

Inside LLDB:

run

or:

r

The program starts.

If it finishes immediately, you may see something like:

Process exited with status = 0

That means the debugger worked.

There was simply nothing that caused execution to stop.

You can pass arguments to the program using -- as a separator. Everything after -- is passed to the program itself, not to LLDB:

(lldb) run -- input.json --verbose

The program sees input.json and --verbose as its arguments. Without the separator, LLDB would try to interpret those tokens itself and produce a syntax error.

You can also set arguments persistently before running:

(lldb) settings set target.run-args input.json --verbose
(lldb) run

This is useful when you will run the program many times during a session and want to avoid retyping the arguments.

Rust 2024 note: If your Rust program uses std::env::args(), the arguments after -- will appear as you expect. The debugger does not interfere with the process argument vector once the program has been launched.

Set your first breakpoint

A breakpoint tells LLDB:

Stop execution here.

For example:

breakpoint set --name add

Short form:

b add

Then:

run

Execution stops when add is entered.

LLDB officially supports setting breakpoints by function name and by file and line.

When a name-based breakpoint succeeds, LLDB prints the address it resolved to. When it fails, LLDB prints no locations (pending). Pending breakpoints are not useless. They are waiting for a matching symbol to load, which can happen later, for example when a dynamically loaded library is opened. But for most cases, a pending breakpoint on a user function indicates that the name did not match any symbol.

Break at a Rust source line

You can specify a file and line:

breakpoint set --file src/main.rs --line 8

Short form:

breakpoint set -f src/main.rs -l 8

This is useful when you already know the suspicious location.

For Rust code, source-line breakpoints have several advantages over name-based breakpoints:

  • They are unaffected by name mangling.
  • They are unambiguous when multiple functions share a name in different modules.
  • They target a specific line, which is often exactly what you want.
  • They work correctly inside closures, iterator chains, and generic functions, where a name-based breakpoint might match multiple instantiations.

The main limitation is that you need to know the line number in advance. If the code is in flux, or if you want to break at a function whose location you have forgotten, a name-based breakpoint is faster.

A useful habit is to combine the two: start with a name-based breakpoint to confirm the function is reachable, then add source-line breakpoints for specific lines inside it.

List breakpoints

Use:

breakpoint list

This answers:

What breakpoints exist?

Are they enabled?

Did LLDB resolve them?

Where are they located?

The distinction between a breakpoint being created and having a resolved location is important.

A breakpoint can exist before LLDB can resolve it to executable code.

When you have many breakpoints, the list output can become long. To focus on one:

breakpoint list 3

This shows only breakpoint 3. A common workflow is to list all breakpoints when you are setting them up, then list individual ones when you want to check their status mid-session.

Delete a breakpoint

Delete one breakpoint:

breakpoint delete 1

Delete all breakpoints:

breakpoint delete

Be careful with the second form.

It removes the entire breakpoint set.

If you are unsure what is currently set, list first:

breakpoint list
breakpoint delete 3

For a screen-reader workflow, the pattern of “list, then delete by ID” is safer than “delete all and re-add.” It avoids the risk of accidentally removing breakpoints you still want, and it produces less output than re-creating a set of breakpoints after a mass deletion.

Continue

When stopped:

continue

or:

c

Execution resumes until:

another breakpoint
a signal
a crash
program termination

or another debugger stop condition occurs.

The continue command is how you get from one interesting point to the next. In a session with several breakpoints, you will use continue many times, pausing at each breakpoint to inspect the state.

If the program exits while you continue, LLDB will report the exit status:

Process 12345 exited with status = 0 (0x00000000)

After that, you can run again from the beginning. The breakpoints remain in place unless you delete them.

Step over

Suppose execution is stopped here:

let result = add(x, y);

Use:

next

or:

n

LLDB executes the current source line without entering the called function.

This is:

Execute this line and stay at this level.

Step into

Use:

step

or:

s

When the current line calls another function, LLDB attempts to enter that function.

For:

let result = add(x, y);

step takes you into:

fn add(...)

This is:

Show me what happens inside this call.

Step out

If you are inside a function and have seen enough:

finish

This runs until the current function returns.

Conceptually:

main
  ↓
add
  ↓
finish
  ↓
main

LLDB documents this as thread step-out.

When finish returns, LLDB prints the return value of the function that just completed, if it can determine it. This is a fast way to see what a function produced without stepping through its entire body.

The most important difference

These three commands answer different questions:

next

What happens on the next line at this level?

step

What happens inside this function call?

finish

What happens after this function returns?

Learning this distinction is more important than memorizing dozens of LLDB commands.

The three step commands in context

The distinction between next, step, and finish is the core of source-level navigation.

Suppose you are here:

let result = add(x, y);

next

next

Executes the line. If the line calls add, LLDB does not enter add. It stays in main.

Use when:

you trust add
you want to see what happens after the call
you want to avoid stepping through library code

step

step

Executes the line. If the line calls add, LLDB enters add.

Use when:

you suspect the bug is inside add
you need to inspect add’s arguments
you need to see how add transforms its input

finish

finish

Runs until the current function returns.

Use when:

you have seen enough inside the function
you want to know what it returns
you want to return to the caller

The mental model:

next   → stay at this level
step   → go down one level
finish → go up one level

Where am I?

When the debugger stops, ask:

Where is execution?

Use:

thread backtrace

or:

bt

A backtrace shows the call stack.

For example:

frame #0  parse_config
frame #1  load_application
frame #2  main

Read this as:

main
→ load_application
→ parse_config

The current location is the first frame.

LLDB’s official tutorial uses thread backtrace to inspect the current call stack.

Read the current frame

Use:

frame info

This gives information about the current stack frame.

You want to know:

Which function?

Which source file?

Which line?

Which module?

This is the first orientation step after every unexpected stop.

The output typically includes the frame number, the function name, the file and line, and sometimes the source line itself. In compact form, it is one line:

frame #0: first_session`first_session::main at src/main.rs:6

For a screen-reader workflow, this line is a compact orientation point that you can read on every stop without overwhelming output.

Read local variables

Use:

frame variable

This displays variables available in the current frame.

For a specific variable:

frame variable result

or:

frame variable config

This is one of the most important LLDB commands for Rust.

LLDB’s frame variable command is designed specifically for inspecting arguments and local variables in the current frame.

Unlike expression, it does not evaluate anything. It reads the current storage and formats it using debug information. This means it is fast, safe, and reliable. It does not call user code, so it does not have side effects or risk of deadlock.

When you have a long function with many locals, requesting only the variable you care about is much more efficient than dumping all of them. For a screen-reader workflow, this focused approach is often the difference between a usable session and an overwhelming one.

Inspect Rust values

Suppose:

let user = User {
    name: String::from("Alice"),
    age: 30,
};

At a breakpoint:

frame variable user

You may see a structured representation of the value.

For a field:

frame variable user.name

or:

frame variable user.age

This lets you investigate one piece of a larger Rust value without dumping everything.

When the Rust pretty-printers are active, a String field will render as the string contents, not as a length/pointer/capacity triple. A Vec<T> will render as its elements, not as a raw heap pointer. An Option<T> will render as Some(...) or None, not as a discriminant byte plus a union.

If the pretty-printers are not active, you will see the raw layout instead. In that case, launch the debugger via rust-lldb instead of plain lldb.

Inspect nested values

Suppose:

config.server.port

You can ask LLDB for:

frame variable config.server.port

This is especially useful with configuration structures.

Instead of dumping:

Config

inspect:

config.server
config.server.port
config.server.host

The goal is controlled output.

For screen-reader use, smaller results are usually easier to process.

Nested field access also helps when a struct is large. If a struct has thirty fields and you only care about one, frame variable config.server.port gives you exactly that one value, in one line, without any surrounding noise.

Arguments

Function arguments are part of the current frame.

For:

fn parse(input: &str, strict: bool)

use:

frame variable

or inspect them individually:

frame variable input
frame variable strict

Ask:

What entered this function?

Is it already wrong?

Or does it become wrong here?

This is a fundamental debugging question.

The answer determines the direction of the next investigation. If the argument is already wrong on entry, the bug is upstream, in the caller. If the argument is correct on entry, the bug is either inside this function or downstream, after the function passes the value on.

Arguments are especially useful as debugging landmarks because they are always present at the entry of a function. Even if some locals have been optimized away, the arguments are usually accessible. This makes a breakpoint at a function entry a reliable observation point.

A few extra commands worth knowing

Beyond the core set, three additional commands are worth introducing early because they appear frequently in real sessions.

image lookup

When a name-based breakpoint does not resolve, image lookup shows you what symbols actually exist:

image lookup --name parse_config

This searches the loaded binaries for any symbol matching the name. If it finds one, it prints the symbol’s address and source location. If it finds many, it prints all of them. This tells you whether the symbol exists at all, and if so, under what name.

For Rust programs, this is often the fastest way to diagnose a breakpoint that refuses to resolve. The output shows the mangled symbol form, so you can see exactly how the compiler encoded the function.

frame select

When you are stopped and you want to inspect a different frame in the call stack, use:

frame select 2

Now frame variable shows the locals of frame 2 instead of frame 0. This is essential when you want to inspect state in a caller, not in the current function.

A common pattern is: stop at a failure, look at the current frame, see that the failure is caused by bad input from the caller, use bt to find the caller’s frame number, then frame select to that frame and inspect its locals.

settings show

LLDB has a large configuration space. When something behaves unexpectedly, it is often useful to inspect the current settings:

settings show target.run-args
settings show stop-line-count-before
settings show stop-disassembly-count

This is not something you need often, but it is valuable when the debugger behaves in a way that does not match the defaults you expect. For example, stop-line-count-before controls how many lines of source LLDB shows before the current line when it stops.

Rust 2024 notes on symbols

In Rust 2024, a few syntactic changes affect the symbols that appear in the debugger:

  • #[unsafe(no_mangle)] symbols appear under their exact source name, because no_mangle tells the compiler not to mangle the symbol. If you are debugging FFI code that uses #[unsafe(no_mangle)], a name-based breakpoint on the unmangled name will resolve. This is often easier than name-based breakpoints on ordinary Rust functions.
  • unsafe extern "C" blocks introduce extern symbols. When you break on a symbol declared inside an unsafe extern block, the symbol name comes from the external library, not from the Rust source. Use image lookup to find the exact symbol form.
  • Ordinary Rust functions remain mangled. Name-based breakpoints on ordinary functions generally work, because LLDB understands the mangling scheme. But for heavily generic or heavily nested code, source-line breakpoints are more predictable.

None of these change the fundamental command set. They change which technique is best for a given case.

The core in one place

If you take nothing else from this chapter, take this:

breakpoint set --name FN
breakpoint set --file FILE --line LINE
breakpoint list
run
continue
next
step
finish
bt
frame info
frame variable
frame variable NAME
frame select N
quit

That is enough to perform a large amount of practical Rust debugging. Every other command in LLDB is an extension of this core.

Summary

In this chapter, we covered the essential LLDB commands for Rust debugging:

  • Command grammar: LLDB commands follow a noun-verb structure, with options that are named consistently across commands.
  • Help and completion: help and command completion let the debugger teach you its own vocabulary.
  • Starting and stopping: run and continue move the program forward, while breakpoint set stops it at chosen locations.
  • The three step commands: next stays at the current level, step descends into a call, and finish ascends back to the caller.
  • Orientation: frame info tells you where you are, bt tells you how you got there.
  • Inspection: frame variable reads existing state without evaluating expressions. It is the safest, most reliable way to look at Rust values.
  • Supporting commands: image lookup, frame select, and settings show are useful when the core commands do not quite cover the situation.

With this vocabulary in hand, the next chapters will apply it to specific classes of problems: breakpoints in depth, frames and backtraces, inspecting Rust values, and the specific shapes of Option, Result, and panic debugging.
