Chapter 4: The Rust Debugging Stack

A normal Rust debugging session involves several tools.

Each tool has a specific job. Understanding what each one does, and where the boundaries are between them, is the difference between a debugging session that flows and one that fights you.

In this chapter, we will look at the stack from top to bottom: Cargo, rustc, rust-lldb, LLDB, and the debug information that connects them all. We will also look at the boundary between the Rust world and the machine world, which is where most debugging confusion originates.

Cargo

Cargo builds and runs the project.

cargo build
cargo run
cargo test

For debugging, the important point is that Cargo knows how to build the correct Rust target.

Cargo does not just compile code. It orchestrates an entire build pipeline:

  • It reads Cargo.toml and resolves dependencies.
  • It downloads and compiles external crates.
  • It chooses a profile (dev or release) and applies the corresponding compiler flags.
  • It invokes rustc with the correct edition, features, and target.
  • It runs any build.rs build scripts that the project or its dependencies define.
  • It links the final binary or library.
  • It places the output in a predictable location such as target/debug/ or target/release/.

When you launch LLDB, you are launching it on the artifact that Cargo produced. If Cargo is configured incorrectly, or if you are debugging a stale artifact, no amount of LLDB skill will produce useful results. This is why the first step of any debugging session is to confirm that Cargo has produced a fresh, correct binary.

A quick sanity check:

cargo build
ls -lt target/debug/ | head

If the binary is older than your most recent source change, rebuild before debugging.

Rust 2024 edition: When a project uses edition = "2024", Cargo will pass --edition 2024 to rustc automatically. If you inspect a build with cargo build -v, you will see the actual compiler invocation, including the edition flag. This is useful when you want to confirm exactly what toolchain is being used.

rustc

rustc compiles Rust source code.

The -g option is equivalent to:

-C debuginfo=2

and enables debug information.

Cargo's normal debug profile provides debug information suitable for ordinary debugging.

The compiler is responsible for several things that affect debugging:

  • Name mangling: The compiler encodes source-level names into linker symbols. When LLDB displays a symbol, it is showing you the mangled form, unless a Rust-aware demangler is active.
  • Monomorphization: The compiler generates a separate instance of each generic function for each concrete type used. This means one source-level generic function can become many binary symbols.
  • MIR and LLVM IR lowering: Between your Rust source and the final machine code, the compiler produces intermediate representations. Debug information is generated along the way, but the correspondence between a given machine instruction and a source line is not always one-to-one.
  • Optimization: When optimizations are enabled, the compiler may rearrange, eliminate, or merge code. Debug information is adjusted to reflect the optimized code, but the adjustment is not perfect.
  • Panic strategy: The compiler chooses whether panics unwind or abort. This choice affects what LLDB sees when a program panics.

You will rarely invoke rustc directly for debugging. Cargo passes the right flags for you. But knowing that rustc is doing this work helps you interpret the debugger's output.

rust-lldb

Rust distributions provide:

rust-lldb

This launches LLDB with Rust-oriented debugger support. Rust has provided rust-gdb and rust-lldb specifically for this purpose.

For Rust work, prefer:

rust-lldb

over manually launching:

lldb

when the Rust wrapper is available.

What does rust-lldb actually do?

  • It finds the LLDB binary that ships with your Rust toolchain, or the system LLDB if the toolchain version is configured that way.
  • It sets up the Rust-specific pretty-printers, which format complex Rust values in a readable way.
  • It sets some environment variables that help LLDB find Rust source files, standard-library sources, and symbol demanglers.
  • It may load additional configuration from the Rust installation, such as a .lldbinit file tailored to Rust.

The effect of this is that when you type:

(lldb) frame variable greeting

you see something like:

(std::string) greeting = "Hello, LLDB!"

rather than a pile of pointers, lengths, and capacities. Both representations are technically the same value, but one is far more readable than the other.

If you launch plain lldb and see raw memory layouts, the most common cause is that the pretty-printers were not loaded. Launching via rust-lldb fixes this.

LLDB

LLDB controls the running program.

It can:

start the program
stop execution
set breakpoints
step through instructions
inspect variables
inspect stack frames
inspect threads
evaluate expressions
watch memory changes
continue execution
inspect crashes

The Rust compiler produces the program.

LLDB investigates the program.

LLDB is a general-purpose debugger. It was not built specifically for Rust. It supports C, C++, Objective-C, Swift, and many other languages through a combination of language plug-ins, expression evaluators, and pretty-printers. The Rust integration in LLDB is provided by:

  • An LLDB language plug-in for Rust that understands how to parse certain Rust symbols and values.
  • A demangler that can translate mangled Rust symbols back to readable names.
  • Pretty-printers that format common Rust types such as String, Vec<T>, Option<T>, and Result<T, E>.
  • Integration with debug information generated by rustc.

Because this integration is layered on top of a general-purpose debugger, there are places where the Rust view is imperfect. When LLDB cannot understand something, it falls back to raw machine-level inspection. This is normal, and it is not a sign that anything has gone wrong.

The Rust/LLDB boundary

Think of the debugging stack as two worlds:

Rust world
    source code
    types
    ownership
    modules
    async tasks

Machine world
    registers
    memory
    instructions
    threads
    addresses

Debug information is the map between them.

LLDB lives in the machine world. It reads debug information to translate:

address → source line
symbol → function name
stack slot → variable
type ID → Rust type

When that translation works, debugging feels source-level.

When it breaks, you see the machine world:

?? 
no variable available
optimized out
unknown type
mangled symbol

That does not mean the debugger is useless. It means the map is incomplete for that point in the program.

rust-lldb is a wrapper that launches LLDB with Rust-oriented support. Prefer it over plain lldb when debugging Rust, because it can load Rust-specific pretty-printers and settings.

Examples of the boundary in action

Several concrete situations illustrate what happens when the translation is imperfect:

  • A variable shows <optimized out>: The compiler decided not to keep the variable around at this point. Debug information says the variable existed, but no storage is currently associated with it. LLDB is doing its best, but there is nothing to read.
  • A frame shows ?? as its function name: The debug information for this frame is missing or does not correspond to the current address. This often happens in library code compiled without debug information, or in dynamically generated code.
  • A Rust type shows as an opaque blob: The pretty-printer for this type is not loaded, or the type is generic in a way the pretty-printer does not support. LLDB falls back to showing the raw memory layout.
  • A symbol shows as a mangled string: The Rust demangler did not process this symbol. This can happen for symbols that come from older Rust versions, from a mixed-language binary, or from code compiled with #[unsafe(no_mangle)] that overrides the mangled name.

In all of these cases, the right response is not to assume the debugger is broken. The right response is to recognize that the translation between worlds has partially failed, and to fall back to a coarser form of observation: inspecting the address, the symbol table, or the raw memory.

How this stack compares to other languages

If you have debugged C, C++, or Go with a debugger, you may wonder how the Rust stack differs. The differences are mostly about the information available at the boundary.

  • C and C++: Debug information for C and C++ is well understood and has been for decades. Name mangling exists in C++ as well, but LLDB has extensive support for demangling. The main complication is that C and C++ do not enforce memory safety, so bugs often manifest as memory corruption, which the debugger can see but not always explain.
  • Go: Go's runtime is highly dynamic, with its own scheduler, garbage collector, and goroutine model. Debugging Go is different because much of the interesting state lives inside the Go runtime, not in the application frames. Rust has no garbage collector and no built-in scheduler, so the runtime is generally thinner.
  • Rust: The distinctive features of Rust debugging are monomorphization (leading to many instantiations of generic functions), the async state machine (leading to runtime frames between application frames), and the strict separation between static ownership and dynamic runtime state.

None of these are obstacles. They are simply the shape of the territory. Once you know what to expect, you can plan your debugging strategy accordingly.

When each tool matters

Each tool in the stack is best suited to particular kinds of questions:

  • Cargo answers: Which target am I building? Which profile? Which dependencies? Where is the artifact?
  • rustc answers: Is the source well-typed? Does it satisfy ownership rules? What will the mangled symbol look like? Will this panic unwind or abort?
  • rust-lldb answers: What does the Rust-aware view of this program look like inside the debugger?
  • LLDB answers: What is the runtime state right now? What is on the stack? Which thread is executing? What does this memory address contain?

Understanding which tool to reach for is a large part of becoming effective at debugging Rust. Many frustrating debugging sessions come from using the wrong tool for the question: reaching for LLDB when the compiler had already given the answer, or asking Cargo a question that only LLDB could resolve.

A worked example of the full stack

To see how the tools fit together, consider a small project with a single binary and a single library.

Cargo.toml:

[package]
name = "debug_stack_demo"
version = "0.1.0"
edition = "2024"

[lib]
name = "debug_stack_demo"
path = "src/lib.rs"

[[bin]]
name = "debug_stack_demo"
path = "src/main.rs"

src/lib.rs:

pub fn add(a: i32, b: i32) -> i32 {
    a + b
}

src/main.rs:

use debug_stack_demo::add;

fn main() {
    let x = 10;
    let y = 20;
    let result = add(x, y);

    println!("{result}");
}

Build with Cargo:

cargo build

Now examine the artifact. Cargo has produced a binary at target/debug/debug_stack_demo. The library code was compiled into the same binary, but the symbol for add exists in the binary’s symbol table.

Ask rustc a static question by introducing a temporary type error and observing the compiler output. Undo the change. The compiler answered a static question.

Ask Cargo a packaging question by running:

cargo metadata --format-version 1 | head

The output describes the workspace. Cargo answered a packaging question.

Now launch the debugger with the wrapper:

rust-lldb target/debug/debug_stack_demo

At the (lldb) prompt:

(lldb) breakpoint set --name add
(lldb) run

Execution stops at the entry of add. Inspect the arguments:

(lldb) frame variable a b

You see the values 10 and 20, formatted by the Rust pretty-printers. Now inspect the backtrace:

(lldb) bt

You see the call chain from main to add. If the mangled name were displayed instead of add, the demangler would not be working. Since it displays correctly, the Rust integration is functioning.

Continue:

(lldb) continue

Now ask LLDB a dynamic question that the compiler could not answer: which line of the source produced the current machine instruction? LLDB answers by combining the current program counter with debug information.

Quit:

(lldb) quit

The point of this example is not to teach the individual commands. It is to show that each tool has a role. Cargo produced the artifact. The compiler answered static questions. LLDB answered dynamic questions. rust-lldb made the LLDB output readable to a Rust programmer.

Summary

The Rust debugging stack has four layers:

  • Cargo builds the artifact, resolving dependencies, choosing profiles, and running build scripts.
  • rustc compiles the source, performs monomorphization, generates debug information, and selects a panic strategy.
  • rust-lldb launches LLDB with Rust-aware configuration, loading pretty-printers and demanglers.
  • LLDB controls the running program, sets breakpoints, inspects memory, and reports runtime state.

The boundary between the Rust world (source, types, ownership) and the machine world (registers, memory, threads) is bridged by debug information. When that bridge is complete, debugging feels source-level. When the bridge is incomplete—because of optimization, missing debug information, or unsupported language features—LLDB falls back to the machine world, and you see raw addresses, mangled symbols, or opaque memory layouts.

Understanding this stack is the foundation for everything that follows. In the next chapter, we will take a first debugging session and put the pieces together into a concrete workflow.
