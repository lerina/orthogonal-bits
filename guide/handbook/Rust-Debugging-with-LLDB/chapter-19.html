Chapter 19: When to Stop Using the Debugger

The debugger is a powerful instrument, but it is not always the right one. Some of the most frustrating debugging sessions are the ones where the wrong tool was used for the question at hand. A programmer reaches for LLDB when the problem is static, and the compiler already had the answer. Or the programmer uses LLDB for a long-running observation when logging would have been simpler. Or the programmer tries to reproduce a bug under the debugger when the bug only appears in production, where no debugger is available.

This chapter is about recognizing those situations. It is not about diminishing the debugger; it is about using it where it belongs and using other tools where they are better.

The chapter is organized around the question: for this specific kind of problem, is the debugger the right tool, or is another approach more appropriate?

When to stop using the debugger

LLDB is not always the best tool.

Use ordinary logging when:

you need long-running observations
you need to see many events
timing changes the behavior
the bug occurs only after a long execution

Use tests when:

the behavior can be isolated
you need repeatability
you want a regression test

Use compiler diagnostics when:

the problem is ownership
types
lifetimes
trait bounds
borrow checking

Use LLDB when:

the program compiles
the problem occurs at runtime
you need to observe actual execution state

The core question

Before every debugging session, ask:

What kind of question is this?

The answer determines the right tool. There are four broad categories:

  • Static questions: about the code as written. “Will this compile? Is this sound? Does this satisfy the type system?”
  • Runtime questions: about a specific execution. “What value does this variable hold? Which branch did this take? Which thread is doing what?”
  • Historical questions: about how the behavior evolved over time. “What events happened before the crash? How many requests triggered the bug? What was the state of the system an hour ago?”
  • Reproducibility questions: about whether a behavior can be reliably observed. “Can I reproduce this in a test? What is the minimal input that triggers the bug?”

The debugger is the primary tool for runtime questions. For static questions, the compiler is the primary tool. For historical questions, logging is the primary tool. For reproducibility questions, tests are the primary tool.

Many productive sessions use more than one. But the choice of which to reach for first depends on the kind of question.

The cost of the wrong tool

Using the wrong tool is not merely inefficient; it can be actively harmful.

  • Using the debugger for a static question: if the program does not compile, the debugger cannot help at all. Time spent trying to load a broken binary is wasted. The compiler must be the first stop.
  • Using the debugger for a historical question: if the bug depends on events that occurred over the past hour, stopping at a breakpoint means the events may never occur. The debugger changes the timing and often the behavior of long-running programs.
  • Using the debugger for a reproducibility question: if you cannot reproduce the bug reliably, a debugging session produces observations about a run that may not be representative. Tests are the tool for reproducibility; the debugger is a tool for inspecting a program that has already been made reproducible.
  • Using the debugger for a production question: if the bug only occurs in production, attaching a debugger may be impossible (due to permissions), may pause the service (affecting users), or may change the system’s behavior enough that the bug no longer appears.

The cost of the wrong tool is not just lost time; it is also the risk of drawing wrong conclusions from a session that was never well-suited to the problem.

The right tool for the question

A simple table summarizes the mapping from question to tool:

Question Best Tool
Does this compile? Does this satisfy ownership rules? Rust compiler
What does this value hold at this point in this run? LLDB
Which branch was taken here? LLDB
How many times does this happen over an hour? Logging
Can I reproduce this reliably? Tests
Is this behavior undefined according to Rust semantics? Miri
Which commit introduced this bug? git bisect
Why did this run take three times longer than usual? Profiler
What is happening inside this C library I did not write? LLDB (with symbol inspection and memory read)

This table is not exhaustive, but it illustrates the pattern: different questions have different tools. The debugger is best at the runtime-specific questions.

Logging as an alternative

Logging is often the better tool. Consider the following situations.

Long-running observation

Suppose a server has a bug that only manifests after several hours of uptime. Debugging this under LLDB would mean keeping the debugger attached for hours, which is impractical for a running service.

Logging is the right approach. Add log statements at the interesting points, run the server, and inspect the logs after the bug appears. The logs show the sequence of events that led to the bug, without requiring the debugger to be running at the moment.

With the log crate and env_logger, the level of logging can be adjusted at runtime. You can leave diagnostic messages in the code at debug! or trace! level, and enable them only when needed:

RUST_LOG=my_crate=debug cargo run
RUST_LOG=my_crate=trace cargo run

This is a form of runtime debugging that requires no debugger at all. It is particularly appropriate for services and for any long-running process.

High event density

A function that is called ten thousand times per second is not a good place to set a breakpoint. The breakpoint would fire continuously, and the program would progress only as fast as you can press continue.

Logging handles this case gracefully. Log messages are written to a buffer and processed asynchronously. The program’s execution is not blocked by each message, and the resulting log contains the sequence of all events.

If the log would be too large, use sampling or a filter. Log every hundredth call, or log only when a condition is true, or log at a lower level so the messages are ignored unless debugging is explicitly enabled.

Timing-sensitive behavior

Stopping a program at a breakpoint changes its timing. In concurrent programs, this can change the interleaving of threads, and the bug may not appear at all under the debugger. This is one of the most frustrating experiences in debugging: the bug is present in a normal run and vanishes as soon as the debugger is attached.

Logging has a much smaller impact on timing. It still adds some overhead, but it does not pause the program, and it does not force a specific interleaving of threads. For concurrency bugs and other timing-sensitive issues, logging is often the only tool that reproduces the bug at all.

A practical workflow:

  1. Reproduce the bug with logging.
  2. Identify the timing pattern in the logs.
  3. Once you have a hypothesis about the timing, use the debugger to confirm specific values at specific points.
  4. Return to logging to observe the pattern across many runs.

The debugger is a microscope; logging is a telescope. You need both to understand a complex system.

Production systems

Attaching a debugger to a production service is usually not an option. Even if you have the permissions, the debugger will pause the service, which affects users. And the very act of pausing can change the behavior enough that the bug disappears.

Logging is the tool for production. A well-designed logging system captures the events you care about, at a level of detail that is useful without being overwhelming. When a bug occurs in production, the logs are the evidence you have.

The workflow for production bugs:

  1. Observe the symptoms from user reports or monitoring alerts.
  2. Inspect the logs for the relevant time window.
  3. Form a hypothesis based on the logs.
  4. Reproduce the hypothesis in a test or a local environment.
  5. Debug the local reproduction under LLDB if needed.
  6. Fix the bug and add a regression test.
  7. Deploy the fix and verify with logs.

This workflow uses the debugger only in step 5, where it is appropriate. The rest of the investigation happens with logs, tests, and static tools.

What good logging looks like

A good logging system has several properties that make it a better tool than the debugger for the situations listed above:

  • Structured: each log message has fields that can be filtered and analyzed, such as request_id, user_id, duration_ms.
  • Correlated: each message carries an identifier that links it to the request or task that produced it.
  • Leveled: each message is at a level (trace, debug, info, warn, error) that can be used to control verbosity.
  • Cheap: emitting a log message that is filtered out is fast, so you can leave detailed logging in production without significant overhead.
  • Rotated and retained: log files are rotated and retained for a defined period, so you can investigate bugs that occurred recently.

With these properties, logging becomes a rich source of evidence. It is not a substitute for the debugger, but in the situations listed above, it is often the only source of evidence available.

Tests as an alternative

Tests are the tool for reproducibility. When a bug has been observed but not yet reproduced, the next step is often to write a test that triggers it.

Why tests are the first reproduction tool

A test is a minimal, deterministic reproduction. It has several advantages over running the full program:

  • Fast: a test runs in milliseconds or seconds, not minutes.
  • Deterministic: a test can control the inputs and environment, eliminating sources of nondeterminism.
  • Self-documenting: a test states the expected behavior explicitly, which is itself a form of documentation.
  • Permanent: a test remains in the codebase as a regression check, so the bug cannot return unnoticed.
  • Composable: tests can be run in any order, in parallel, or in isolation.

When a bug can be reproduced in a test, debugging the test is almost always easier than debugging the full application. The test binary is smaller, the startup is faster, and the environment is controlled.

Writing a test before debugging

A common and effective workflow is to write a failing test before starting the debugging session:

  1. Observe the bug in the running program.
  2. Write a test that asserts the correct behavior. The test fails.
  3. Debug the test under LLDB.
  4. Fix the bug.
  5. The test now passes. Keep it as a regression test.

This workflow has several advantages:

  • The debugging session has a clear, specific goal: make the test pass.
  • The reproduction is minimal, so the debugging session is focused.
  • The test remains in the codebase, providing long-term value.
  • If the fix does not actually fix the bug, the test will still fail, which is immediate feedback.

This is closely related to Test-Driven Development (TDD), but it is applied to bugs rather than to new features. The principle is the same: write the test first, and let it guide the fix.

Tests for timing-sensitive bugs

Timing-sensitive bugs are harder to reproduce in a test, but not impossible. Techniques include:

  • Deterministic scheduling: some concurrency libraries provide test utilities that allow deterministic scheduling. For example, Tokio provides tokio::test and tools for controlling the runtime.
  • Time mock: if the bug depends on a clock, replace the clock with a mock that advances deterministically.
  • Stress tests: run the test many times to increase the chance of reproducing the timing. This is not deterministic, but it can find bugs that appear rarely.
  • Looms: a “loom test” runs the code under many possible interleavings, systematically exploring the space. The loom crate provides this for Rust.

Once a timing-sensitive bug is reproduced reliably, it can be debugged like any other bug. The difficulty is in the reproduction, not in the debugging itself.

Tests for unsafe and undefined behavior

For unsafe code and undefined behavior, tests can be combined with Miri:

#[test]
fn test_unsafe_operation() {
    // Exercise the unsafe code
}

Then run the test under Miri:

cargo +nightly miri test

Miri interprets the test at the MIR level and detects undefined behavior that the compiled code might not manifest. If Miri reports a problem, you have direct evidence of a bug, often with a much clearer diagnostic than the debugger can produce.

The workflow:

  1. Write a test that exercises the unsafe code.
  2. Run the test under Miri.
  3. Fix the bug that Miri found.
  4. Run the test normally to confirm that the fix works in the compiled code.

Miri and tests together are often a better tool for unsafe bugs than LLDB alone.

When tests are not enough

Tests are not always the right tool either. A test may be:

  • Too slow to run repeatedly: for example, a test that spins up a database or a network service.
  • Too complex to set up: for example, a bug that requires a specific sequence of external events.
  • Not representative: the test may pass while the bug is present in production, because the test environment differs in some important way.
  • Not possible: some bugs depend on hardware, on network topology, or on user behavior that cannot be reproduced in a test.

In these cases, the debugger or logging becomes the primary tool, and the test becomes a supplement.

Static analysis as an alternative

Static analysis tools inspect the source code without running it. For certain classes of bugs, they are more effective than the debugger because they find all instances of a problem, not just the ones exercised by a specific execution.

The Rust compiler as a static analyzer

The Rust compiler is one of the most powerful static analyzers in any language. It checks:

  • Types: every value has a well-defined type, and operations are type-correct.
  • Ownership: every value has a single owner, and ownership is transferred according to the rules.
  • Borrowing: references are valid and follow the aliasing rules.
  • Lifetimes: references do not outlive the data they point to.
  • Trait bounds: types satisfy the traits they are used with.
  • Const evaluation: constant expressions are evaluated at compile time and checked for validity.

When a bug is related to any of these areas, the compiler is the right tool. The error message tells you exactly what is wrong and where. Attempting to debug such a bug at runtime is impossible, because the program does not compile.

Clippy

Clippy is the official Rust linter. It analyzes the source for common mistakes, non-idiomatic patterns, and suspicious code that compiles but is likely to be wrong.

Run Clippy with:

cargo clippy --all-targets --all-features

Clippy catches a wide range of issues:

  • Redundant clones and unnecessary allocations.
  • Inefficient iterator chains.
  • Unused or shadowed variables.
  • Comparisons that are always true or false.
  • Patterns that can be simplified.
  • Common mistakes in unsafe code.
  • Non-idiomatic API design.

For classes of bugs that Clippy can detect, running Clippy is faster than running the debugger. Clippy finds the bug in the source; the debugger would find the same bug by watching the program behave incorrectly at runtime. Clippy is preferable because it catches the bug before the code is even run.

Rustfmt

Rustfmt formats source code according to a consistent style. It does not find bugs, but it reduces style-based noise in the codebase, which makes other analysis tools and code reviews more effective. A consistent style is a small but real contributor to overall code quality.

Custom lints

For larger projects, custom lints can enforce project-specific rules. For example, a lint might forbid the use of unwrap in production code, or require that every public function has a doc comment, or forbid a particular pattern that has caused bugs in the past.

Custom lints are typically implemented with tools such as Dylint, which allows writing lints in Rust. They are a way to encode lessons from past bugs into rules that the compiler enforces on all future code.

For Rust 2024, custom lints may also enforce edition-specific rules such as the correct usage of unsafe extern or #[unsafe(no_mangle)].

Miri as a static runtime analyzer

Miri is a hybrid tool: it runs your code (like a runtime), but it does so under an interpreter that checks the abstract semantics of Rust (like a static analyzer). This makes Miri uniquely capable of finding bugs that neither pure static analysis nor normal runtime observation would catch.

Examples of what Miri detects:

  • Accessing memory that has been freed (use-after-free).
  • Reading uninitialized memory.
  • Data races on shared memory (in unsafe code or when using raw pointers).
  • Violations of the aliasing rules for references.
  • Integer overflow in code paths that would otherwise wrap silently.
  • Pointer arithmetic that goes out of bounds.

Miri is especially valuable for unsafe code, where the debugger can observe the machine state but cannot determine whether the code violates Rust’s abstract rules. Miri provides the rules.

For Rust 2024 projects, Miri supports the current edition and the new unsafe rules. Running tests under Miri is a standard part of the workflow for crates that contain unsafe code.

Sanitizers

Sanitizers are runtime instrumentation tools that detect memory errors and other issues at runtime. They are more expensive than normal execution but far more thorough.

Common sanitizers:

  • AddressSanitizer (ASan): detects use-after-free, buffer overflow, and other memory errors.
  • ThreadSanitizer (TSan): detects data races.
  • MemorySanitizer (MSan): detects use of uninitialized memory.
  • UndefinedBehaviorSanitizer (UBSan): detects undefined behavior such as integer overflow and misaligned pointers.

For Rust projects, sanitizers are available via the nightly toolchain:

RUSTFLAGS="-Zsanitizer=address" cargo +nightly test -Zbuild-std --target x86_64-unknown-linux-gnu

Sanitizers are best used on test suites, not on production code. They add significant overhead, often two to ten times slowdown, but they find bugs that normal runs miss entirely.

For Rust 2024 code that interacts with C libraries, sanitizers are especially valuable because they instrument both Rust and C code, catching bugs at the boundary that neither side’s tools would find alone.

Performance and profiling as an alternative

Some bugs are not about correctness but about performance. A program might produce the right answer, but take too long, use too much memory, or make too many system calls. For these bugs, the debugger is not usually the right tool.

Profiling for CPU

A profiler tells you where the program spends its time. For Rust, common profilers include:

  • perf (Linux): a system-level sampling profiler.
  • cargo flamegraph: produces a flame graph of the program’s CPU usage.
  • pprof: a Rust crate for profiling within the application.
  • tracing: for instrumenting specific code paths.

A profiler answers: “where does the time go?” The debugger can set breakpoints and inspect state, but it cannot measure aggregate performance across a long run. For performance, profiling is the tool.

Memory profiling

A memory profiler tells you where the program allocates memory and how much. For Rust, tools include:

  • Heap profilers: track allocations and frees to detect leaks and identify hot allocation sites.
  • Custom allocators: replace the global allocator with a tracking allocator to record allocation statistics.
  • dhat and similar crates: provide heap profiling from within the program.

Memory bugs are not the same as memory correctness bugs. A program can have perfectly correct memory usage that is also inefficient, allocating and freeing too much for a hot path. These bugs are found with profiling, not with the debugger.

Benchmarking

Benchmarks measure the performance of specific operations. For Rust, common approaches include:

  • criterion: a statistical benchmarking framework for Rust.
  • iai: instruction-count-based benchmarking.
  • Simple timing loops: for quick measurements of individual operations.

Benchmarks answer: “did this change make the code faster or slower?” They are the right tool for performance regressions, which the debugger cannot detect.

When profiling and debugging combine

Profiling and debugging can be used together. A profiler identifies a hot path; the debugger then inspects that path in detail. For example:

  1. Use a profiler to identify that a particular function consumes 40% of the CPU.
  2. Set a breakpoint inside that function.
  3. Inspect the arguments and internal state to understand why it is called so often or so expensively.
  4. Optimize the function or reduce the number of calls.
  5. Re-run the profiler to confirm the improvement.

This combination is much more effective than either tool alone. The profiler narrows the target; the debugger inspects it.

Git and historical investigation

Some bugs are best understood by examining the history of the code, not its current state. Git provides tools for this kind of investigation.

git blame

git blame shows the last commit that changed each line of a file. When a bug is in a specific line, git blame tells you which commit introduced it, which commit message describes it, and who wrote it.

git blame src/parser.rs

The commit message and the author often provide context that is not visible in the code itself. If the line was changed as part of a bug fix, the fix may have introduced a new bug elsewhere; git blame can reveal this connection.

git log

git log shows the sequence of commits. For a specific file, it shows the history of that file:

git log --oneline src/parser.rs

This is useful when you want to understand how a file evolved. The sequence of commit messages often reveals the sequence of changes in behavior, which helps contextualize the current bug.

git bisect

git bisect performs a binary search through the commit history to find the commit that introduced a bug. You provide a script that returns “good” or “bad” for a given commit, and Git runs the script against a sequence of commits until it finds the boundary.

git bisect start
git bisect bad          # current commit is bad
git bisect good v1.0    # this old commit was good
# Git checks out a middle commit; you test and run:
git bisect good         # or git bisect bad
# Repeat until the first bad commit is found
git bisect reset        # return to the original branch

If the test can be automated, git bisect run can run the whole search without manual intervention:

git bisect run cargo test --quiet test_failing_case

This is a form of automated experimental investigation. Instead of inspecting the code at every commit manually, you write a test that distinguishes good from bad and let Git find the boundary.

git bisect is often the fastest way to find a regression that was introduced in a large codebase with many recent commits. It replaces hours of manual investigation with a few minutes of automated search.

git diff

git diff shows the changes between two versions of the code. When a bug appeared after a recent change, comparing the current code against the previous version highlights what changed. This is often much faster than reading the whole file.

git diff HEAD~1 HEAD -- src/parser.rs
git diff main feature-branch -- src/handler.rs

A common pattern: after the bug is fixed, the fix diff shows exactly what changed. If the diff is small, the fix was targeted. If the diff is large, the fix may be addressing more than the bug.

When Git is not enough

Git tells you when a change was made, but not why the changed code behaves as it does. For that, you still need the debugger or another runtime tool. Git is a tool for historical investigation; it does not replace tools for static or runtime questions.

When the debugger is really the right tool

After all this discussion of alternatives, it is worth restating the situations where the debugger is the best tool.

A compiled program with a runtime bug

When the program compiles and the bug appears at runtime, the debugger is usually the fastest way to inspect the state that produces the bug. Static analysis cannot see runtime values; logging can only see what has been logged. The debugger can inspect anything in the current frame.

Control-flow questions

When the question is “which branch was taken,” “how did execution reach this function,” or “what is the call stack at this moment,” the debugger is the primary tool. Control flow is not visible in logs unless explicitly recorded, and it is not visible in static analysis for specific executions.

Data questions

When the question is “what value does this variable hold at this point,” the debugger provides the answer directly. Logging can answer it for values that were logged; static analysis cannot answer it at all. The debugger is the tool of choice.

Short reproductions

When the bug reproduces in a short-lived program, the debugger is ideal. The program starts, stops at a breakpoint, and the interesting state is inspected. No logging infrastructure is needed; no test framework is needed. The debugger itself is the minimal environment.

Unsafe and FFI inspection

For unsafe code and FFI, the debugger gives you the machine state that the compiler cannot reason about. Combined with Miri for correctness checking and sanitizers for runtime detection, the debugger completes the toolkit. It is especially valuable when you need to inspect pointers, lengths, and raw memory.

No source available

When debugging a binary for which you do not have source code (a third-party library, a system tool, a legacy binary), the debugger is one of the few tools available. You can still set breakpoints on symbols, inspect memory, and step through assembly. Static analysis and logging are not options for code you cannot modify.

Learning how a program works

When you want to understand what a program does at runtime, the debugger is one of the best tools available. Breakpoints, stepping, and inspection reveal the actual behavior of the program, which is often different from what the source suggests. This is as true for your own code as for code you did not write.

The tool selection matrix

A compact way to summarize this chapter is a matrix. For each kind of question, the matrix lists the tools most likely to help.

The matrix

Question Type First Tool Second Tool
Does this compile? Rust compiler —
Is this ownership correct? Rust compiler —
Is this idiomatic? Clippy Code review
What is this value at runtime? LLDB Logging
Which branch was taken? LLDB Logging
How many times did this happen? Logging Metrics
Can I reproduce this? Tests Loom / stress tests
Is this undefined behavior? Miri Sanitizers
Where does time go? Profiler Benchmarks
Where does memory go? Heap profiler Custom allocator
When was this line changed? git blame git log
Which commit broke this? git bisect git log
What happened in production? Logging Monitoring / metrics

No single tool appears in every row. Each tool has its place, and the skill of an experienced debugger is knowing which tool to reach for based on the question.

Using the matrix

When starting a debugging session, ask:

Which row of the matrix does my question belong to?

Then start with the first tool in that row. If the tool is not enough, move to the second. If neither is enough, consider whether the question is really a combination of multiple rows, and address each component separately.

A common mistake is to default to the debugger for every problem. The matrix makes the alternatives visible, so that the choice becomes deliberate.

Mixing tools is often the right answer

In practice, most substantial investigations use several tools. The matrix is not a rule about which single tool to use, but a starting point for choosing the first tool. The investigation often moves through several rows, each with its own first tool.

A typical sequence for a bug in a production service:

  1. Logging identifies the symptoms and the time window.
  2. Tests reproduce the bug locally.
  3. LLDB inspects the runtime state that produces the bug.
  4. Miri or sanitizers confirm the underlying cause if it involves unsafe code.
  5. git bisect finds the commit that introduced the bug.
  6. A regression test is added to prevent the bug from returning.

This sequence uses six tools, each appropriate for its step. The debugger is one of them, not the whole answer.

The role of experience

Choosing the right tool is a skill that develops with experience. A few principles help.

Start with the cheapest tool

Some tools are cheaper than others: they require less setup, run faster, and produce answers more quickly. In general, start with the cheapest tool that can answer the question:

  • The compiler is very cheap: just run cargo check.
  • Clippy is cheap: just run cargo clippy.
  • Static search with rg is cheap: one command, immediate results.
  • Tests are moderately cheap: if a test already exists, running it is trivial.
  • Logging requires instrumentation but is cheap to run.
  • LLDB requires a debug build and a launch but produces detailed evidence.
  • Miri is slower than the compiled code but faster than manually testing many interleavings.
  • Profiling and benchmarking require a workload and analysis.

Starting with the cheapest tool is efficient. If the question is static, the compiler answers it instantly. Only if the compiler cannot answer does the investigation proceed to more expensive tools.

Prefer evidence over assumption

Each tool provides evidence of a different kind. The compiler provides evidence about the source; the debugger provides evidence about the runtime; logs provide evidence about the history. When choosing a tool, ask which kind of evidence the question requires, and choose the tool that provides it.

Assumptions fill the gap when no evidence is available. But every assumption is a potential bug. The job of the debugging process is to replace assumptions with evidence.

Be willing to switch

No tool is right for every question. A session that starts with the debugger and then switches to logging, or starts with logging and switches to a test, or starts with a test and switches to the compiler, is not failing. It is adapting to what the investigation has revealed.

The worst failure mode is to insist on using the same tool for a question it cannot answer. This wastes time and produces misleading conclusions. Recognizing when to switch is a mark of experience.

Document the choice

For complex investigations, document which tool was used for which question. This helps when reviewing the investigation later, and it helps when explaining the investigation to others.

An example entry in a notebook:

Question: Is the parser returning Err for valid inputs?
Tool: LLDB
Reasoning: Need to inspect the runtime state at parse time.
Result: Yes, the parser returns Err(InvalidUtf8) for inputs that are valid UTF-8.
Next: Use a unit test to isolate the parser.

The entry records not just the tool and result, but also the reasoning behind the tool choice. This is the kind of record that makes a debugging session useful months later.

Rust 2024 notes on tool selection

Rust 2024 changes the source in ways that affect tool selection in specific cases.

unsafe extern blocks and FFI debugging

Because all extern blocks are unsafe extern in Rust 2024, the FFI boundary is more explicit. This makes it easier to decide when LLDB is the right tool: whenever a question involves crossing the FFI boundary, LLDB is likely needed, because neither pure static analysis nor logging can easily follow into foreign code. The new syntax highlights exactly where this boundary is.

Unsafe attributes and symbol inspection

The new #[unsafe(no_mangle)] and #[unsafe(export_name = "...")] syntax changes what symbols appear in the binary. This matters for tool selection because:

  • A symbol exposed with #[unsafe(no_mangle)] appears under its exact source name, making name-based breakpoints reliable.
  • A symbol exposed with #[unsafe(export_name = "custom_name")] appears under the custom name, requiring the debugger to know the custom name.
  • When integrating with C code, the FFI boundary is often the place where tool choice matters most—LLDB is the tool that can follow into C, whereas Miri cannot.

static mut and tool selection

The Rust 2024 restriction on static mut references means global state must be accessed through raw pointers or interior-mutability primitives. For tool selection:

  • LLDB remains the primary tool for inspecting global state at runtime.
  • Miri can detect misuse of the new primitives (UnsafeCell, atomics) at the semantic level.
  • Sanitizers can detect data races on shared state, complementing the debugger.

None of these change the fundamental principle: choose the tool based on the question, not based on the habit.

Async and gen and tool selection

Rust 2024 stabilizes async closures and gen blocks. These features produce state machines similar to async fn. For tool selection:

  • For runtime questions about a specific state machine, LLDB remains the primary tool.
  • For questions about the state machine’s logic in aggregate (which interleavings are possible, whether a state can be reached), tests with a deterministic scheduler (Tokio’s test utilities, Loom) are often better.
  • For questions about async state in production, logging and distributed tracing are often the only options.

The pattern is the same: choose the tool that matches the question, not the tool that matches the language feature.

Clippy and the 2024 edition

Clippy supports the Rust 2024 edition and includes lints specific to the new rules. Running cargo clippy on a 2024 edition project will flag any patterns that violate the new semantics, such as missing unsafe blocks inside unsafe fn, or references to static mut. These lints are another static tool in the toolkit, useful before any runtime debugging begins.

Summary

In this chapter, we surveyed the alternatives to the debugger and the situations where each is the better tool:

  • Logging for long-running observations, high event density, timing-sensitive behavior, and production systems. Logging captures what happened over time; the debugger captures what is happening now.
  • Tests for reproducibility. When a bug can be reproduced in a test, debugging the test is almost always easier than debugging the full application. Tests also provide the long-term value of a regression suite.
  • Static analysis: the Rust compiler for type, ownership, and lifetime questions; Clippy for idiomatic issues and common mistakes; Miri for undefined behavior; sanitizers for memory and concurrency errors.
  • Profiling for performance questions. A profiler answers where time goes; a memory profiler answers where memory goes. Neither is answered by the debugger.
  • Git for historical questions: git blame for who changed a line, git log for the evolution of a file, git bisect for finding the commit that introduced a regression, git diff for understanding what changed recently.
  • When the debugger is really the right tool: for compiled programs with runtime bugs, for control-flow questions, for data questions, for short reproductions, for unsafe and FFI inspection, when no source is available, and for learning how a program works at runtime.
  • The tool selection matrix: a compact reference for which tool to reach for first given a specific kind of question.
  • The role of experience: start with the cheapest tool that can answer the question, prefer evidence over assumption, be willing to switch tools mid-investigation, and document the choice of tools in the investigation notebook.
  • Rust 2024 specifics: unsafe extern, unsafe attributes, static mut restrictions, async closures, and gen blocks affect the source and the debugger’s view, but do not change the fundamental principle of choosing a tool for the question rather than the language feature.

The unifying theme: no single tool is the answer to every question. Debugging is not the exclusive province of the debugger; it is a discipline that uses all available tools to reduce uncertainty about the program’s behavior. The debugger is one of the most powerful tools, but only when it is the right one.
