Appendix A: Common Pitfalls in Rust Programming (Online)

Welcome to Appendix A!

This appendix is designed to be a companion to your Rust learning journey. Throughout this book, you’ve seen the language’s strengths, its elegant solutions to hard problems, and its strict but fair compiler. You’ve also, quite likely, run into moments where Rust seemed to be fighting back.

This appendix addresses those moments. It is a curated collection of the most common challenges, mistakes, and misunderstandings that developers encounter when learning Rust. Rather than being a list of “gotchas” designed to scare you, it is intended to be a friendly reference you can return to whenever you feel stuck.

About this appendix

Some of the pitfalls we cover here are subtle traps that even experienced developers fall into from time to time. Others are simple misunderstandings that arise from bringing habits and mental models from other programming languages into Rust. In all cases, we have aimed to do three things:

  • Explain what the pitfall is in clear, plain language. We describe the symptom you’ll see (usually a compiler error), what is actually going on under the hood, and why Rust is designed the way it is.
  • Show the correct, idiomatic way to handle the situation. Each pitfall comes with concrete, runnable examples that demonstrate the fix.
  • Share community insights. Many of these pitfalls have been discussed, documented, and refined over years by the Rust community. We have drawn from those shared experiences so that you don’t have to rediscover the same lessons yourself.

You might read this appendix straight through, or you might treat it as a reference that you dip into whenever you hit a specific problem. Both approaches are perfectly valid.

A preview of common pitfalls

To give you a taste of the kind of content covered in the full appendix, here are a few of the most frequently encountered pitfalls that we explore in depth:

Pitfall 1: Trying to use a value after it has been moved

A classic mistake for newcomers is assigning a variable to another and then trying to use the original. For types that do not implement the Copy trait (such as String or Vec<T>), this is a move, not a copy. The original is invalidated.

// This will NOT compile:
fn main() {
    let s1 = String::from("hello");
    let s2 = s1; // `s1` is moved into `s2`
    println!("{}", s1); // Error: borrow of moved value: `s1`
}

The fix is either to borrow (let s2 = &s1;) or to clone (let s2 = s1.clone();) when you genuinely need two independent copies. The full appendix explains when each is appropriate and the performance implications of each choice.

Pitfall 2: Borrowing mutably while an immutable borrow is active

Rust’s borrow checker enforces that you can have either one mutable reference or any number of immutable references, but not both at the same time in the same scope.

// This will NOT compile:
fn main() {
    let mut v = vec![1, 2, 3];
    let first = &v[0]; // Immutable borrow
    v.push(4);         // Error: cannot borrow `v` as mutable
    println!("{}", first);
}

This pitfall is often surprising because it appears to be harmless at first glance. The full appendix walks through the reasoning (it’s actually protecting you from a dangling reference if the vector needed to reallocate) and several idiomatic patterns for restructuring your code to satisfy the borrow checker without unnecessary clones.

Pitfall 3: Using unwrap() liberally in production code

During learning, unwrap() and expect() feel like convenient shortcuts. But they turn recoverable errors into unrecoverable panics, which can crash your program and leave your users frustrated.

// Fragile:
let config = std::fs::read_to_string("config.toml").unwrap();

// More robust:
let config = std::fs::read_to_string("config.toml")
    .context("Failed to read config.toml")?;

The full appendix explores a broader set of error-handling patterns, including when unwrap() is appropriate (such as in tests, prototypes, or after an invariant has been checked), how to use ? and custom error types, and how the anyhow and thiserror crates fit into a robust strategy.

Pitfall 4: Cloning everything to satisfy the borrow checker

When the borrow checker pushes back, a tempting quick fix is to sprinkle .clone() everywhere. This usually works, but it silently hurts performance and hides design issues.

// Inefficient: cloning data unnecessarily
fn process(data: &Vec<i32>) {
    let owned = data.clone();
    // ... use owned ...
}

// Better: work with the borrow directly
fn process(data: &[i32]) {
    // ... use data (a slice) without cloning ...
}

The full appendix devotes a section to the various reasons developers over-clone, and offers a set of alternative techniques: passing slices, restructuring ownership, using Rc/Arc for shared ownership, and using interior mutability patterns such as RefCell when they are truly warranted.

Pitfall 5: Forgetting the move keyword in thread closures

When spawning a thread that needs data from the surrounding scope, the closure must take ownership of that data. Otherwise, the compiler cannot guarantee the data will outlive the spawned thread.

use std::thread;

fn main() {
    let name = String::from("worker");
    // The `move` keyword is required here:
    let handle = thread::spawn(move || {
        println!("Hello from {}", name);
    });
    handle.join().unwrap();
}

The full appendix explains the reasoning behind the move keyword, common mistakes around it (such as accidentally moving a variable you wanted to keep), and how this interacts with the Send and Sync traits.

Pitfall 6: Confusing String with &str (and Vec<T> with &[T])

Beginners often reach for String when a function parameter could just accept &str. The result is unnecessary ownership transfers and awkward call sites.

// Less flexible:
fn greet(name: String) {
    println!("Hello, {}!", name);
}

// More flexible (accepts &str, String, and string literals):
fn greet(name: &str) {
    println!("Hello, {}!", name);
}

The full appendix covers idiomatic guidelines for choosing between owned and borrowed types in function signatures, methods, structs, and APIs, including the important convention that generic parameters accepting string-like types should use AsRef<str> or impl Into<String> when appropriate.

How to use this appendix effectively

A few tips for getting the most out of this appendix:

  • Don’t try to memorize it. Rust is learned by doing, and it’s perfectly normal to hit the same pitfall more than once as your projects grow in complexity. Treat this appendix as a reference, not as required reading.
  • Pay attention to compiler error codes. Rust’s compiler messages include helpful error codes (such as E0382 for “use of moved value”). These codes are searchable, and they map directly to the pitfalls discussed in the full appendix.
  • Embrace the frustration. As we mentioned in the Preface, the compiler is a bit like an “annoying grandma.” Every compiler error you work through is teaching you something about Rust’s memory model, and those lessons compound over time.
  • When you find a solution, write it down. Many developers keep a personal “Rust notes” file where they jot down the fixes for pitfalls they’ve encountered. Over time, this becomes a personalized reference that is more valuable than any generic list.

A final encouragement

If you are reading this appendix, it likely means you are still actively learning Rust, or you are working through a project and have hit a snag. That is wonderful news. The fact that you are engaging with the harder parts of the language means you are on exactly the right path.

Rust’s design philosophy pushes back on old habits precisely because those habits lead to bugs that are hard to find in production. Every time the compiler stops you, it is helping you write software that is faster, safer, and more reliable. Over time, the pitfalls become familiar, and the solutions become second nature.

We hope this appendix, together with the online version, serves you well. Happy coding, and enjoy your Rust journey!
