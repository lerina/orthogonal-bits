PART 1

Method

1. The Purpose of This Manual

A programmer working with a screen reader needs efficient ways to interrogate source code.

The goal is not to read every file from beginning to end.

The goal is to ask precise questions and reduce the codebase until the relevant piece becomes clear.

Typical questions include:

Where is this function defined?

Where is this type defined?

Who calls this function?

Where is this struct constructed?

What modules import this type?

Where is this trait implemented?

What functions return Result?

Where is this error created?

Where does this value come from?

Where does this value go?

Which files changed?

Which dependency provides this type?

Why does this compiler error occur?

What code actually runs for this case?

Different tools answer different kinds of questions.

The basic progression is:

Literal text
    ↓
Regex
    ↓
ripgrep
    ↓
Helix
    ↓
ast-grep
    ↓
Rust compiler and rust-analyzer
    ↓
Manual code tracing

The important skill is choosing the simplest tool that can answer the question reliably.

2. Query the Codebase Instead of Scanning It

A source tree is a database of information.

Instead of asking:

"How do I read this repository?"

ask:

"What do I need to know?"

Then turn the question into a query.

For example:

Question:
Where is Router defined?

Query:
rg 'struct Router|enum Router|type Router' -t rust

Then:

Question:
Who creates Router?

Query:
rg 'Router::|Router\s*\{' -t rust

Then:

Question:
Who calls the constructor?

Query:
rg 'Router::new' -t rust

Then:

Question:
What does Router depend on?

Query:
Read the definition and its fields.

This produces a chain of increasingly precise questions.

The basic method is:

Question → Query → Evidence → Narrow the search → Understand

PART 2

Regex Fundamentals

3. Regex as a Text Query Language

Regular expressions let you search for patterns rather than only literal strings.

For a screen reader user this is valuable because the search engine can identify the relevant text without requiring visual scanning.

Regex is useful for finding:

  • function definitions,
  • struct definitions,
  • enum definitions,
  • trait definitions,
  • imports,
  • error messages,
  • TODO comments,
  • attributes,
  • type names,
  • macros,
  • logging calls,
  • common syntax patterns.

Regex is a language for describing text.

It is not a programming-language parser.

That distinction is fundamental.

4. Rust's Regex Syntax

Helix and ripgrep use Rust's regex technology, but their commands and search interfaces are different.

The Rust regex syntax intentionally leaves out some features found in other regex engines, including look-around and backreferences. ([Docs.rs][2])

5. Basic Regex Syntax

The dot

.

matches any single character except a newline by default.

For example:

a.b

can match:

aab
acb
a1b

Digits

\d

matches a Unicode decimal digit by default.

For ASCII digits specifically:

[0-9]

This distinction matters.

Rust's regex engine is Unicode-aware by default. ([Docs.rs][2])

Word characters

\w

matches a Unicode word character by default.

For source-code searches, this is sometimes broader than what you actually mean.

When searching Rust identifiers, a literal pattern or a more specific character class may be preferable.

Whitespace

\s

matches Unicode whitespace by default.

For ASCII whitespace specifically, use an explicit class such as:

[ \t]

Line start

^

matches the beginning of a line when multiline mode is active.

In line-oriented command-line searches, it is commonly used to find lines beginning with a particular pattern.

Example:

^\s*fn

Line end

$

matches the end of a line when multiline mode is active.

Example:

;$

matches lines ending with a semicolon.

Character classes

[abc]

matches one character from the set.

[a-z]

matches one character in the ASCII range a through z.

[^0-9]

matches one character that is not an ASCII digit.

Alternation

error|warning

matches either error or warning.

For related Rust declarations:

struct|enum|trait

6. Quantifiers

Quantifiers control repetition.

*

means zero or more. Example: \d*

+

means one or more. Example: \w+

?

means zero or one. Example: pub\s+fn with (pub\s+)? when pub is optional.

{n}

means exactly n repetitions. Example: \d{3}

{n,m}

means between n and m repetitions. Example: \d{2,4}

7. Character Classes and Boundaries

Rust's regex engine provides:

\d    digit
\D    non-digit
\w    word character
\W    non-word character
\s    whitespace
\S    non-whitespace
\b    word boundary
\B    non-word-boundary position

These are Unicode-aware by default. ([Docs.rs][2])

For ASCII-only behavior, use explicit classes or disable Unicode mode locally.

For example:

(?-u:\d)

matches an ASCII digit.

8. Word Boundaries

\b

matches a word boundary.

For example:

\bResult\b

searches for Result as a word rather than matching it inside a larger word.

Because Rust's default word definition is Unicode-aware, \b is also Unicode-aware. ([Docs.rs][2])

For ordinary Rust source navigation, this is usually sufficient.

9. Anchors for the Whole Input

Rust's regex engine also provides:

\A

for the beginning of the entire input. And:

\z

for the end of the entire input.

These differ conceptually from line-oriented ^ and $.

Use ^ and $ when thinking about lines. Use \A and \z when thinking about the entire input.

10. Capture Groups

Parentheses create capture groups.

Example:

(fn)\s+(\w+)

For:

fn main

the groups contain:

Group 1: fn
Group 2: main

Named captures use:

(?P<name>\w+)

Capture groups become particularly useful when a search result is being processed by another tool.

ripgrep can also use capture groups for output replacement with its --replace option, but that replacement affects printed output rather than modifying files. ([ripgrep][3])

11. Regex Features Missing from Rust's Regex Engine

Rust's regex crate does not support general lookahead or lookbehind.

These are unavailable:

(?=pattern)
(?!pattern)
(?<=pattern)
(?<!pattern)

Backreferences are also unsupported.

This is intentional. The engine trades some expressive features for predictable search performance. ([Docs.rs][2])

When a search requires such logic, consider:

Reformulate the regex.

Run two searches.

Pipe one search into another.

Use rg filtering.

Use awk, sed, or another text-processing tool.

Use ast-grep.

Use rust-analyzer or compiler information.

Inspect the relevant source directly.

12. Regex Is a Heuristic for Rust

Consider:

^\s*fn\s+\w+

This is a useful search for likely Rust function declarations.

It is not a Rust parser.

Rust permits syntax that makes simple regex searches incomplete.

For example, the function name may involve syntax that your pattern does not anticipate.

Therefore:

Regex answers "where does text resembling this occur?"

It does not reliably answer:

"What does the Rust program mean?"

Use regex to locate candidates.

Then inspect or parse the candidates.

PART 3

Helix

13. Helix Search

Helix uses / for forward regex search.

Example:

/^\s*fn\s+\w+

Search backward with:

?pattern

Useful commands include:

n

for the next match. And:

N

for the previous match.

Helix also provides selection-based searching.

The * command searches the current selection using word boundaries, while Alt-* searches the current selection directly. ([GitHub][4])

For screen-reader use, selection-based searching can be particularly useful because it avoids manually retyping a long identifier.

14. Helix Search Settings

Helix's search configuration supports smart case.

The current default is:

smart-case = true

This means searches are generally case-insensitive until the pattern contains uppercase characters. ([Helix Editor][5])

For a precise code query, be aware of this behavior.

If case matters, make the query explicit.

PART 4

ripgrep Basics

15. ripgrep Basics

The basic command is:

rg 'pattern'

It searches recursively from the current directory while respecting normal ignore rules.

Always quote regex patterns in the shell:

rg '^\s*fn\s+\w+'

This ensures that the shell does not interpret special characters before ripgrep receives them.

16. The Most Useful ripgrep Options

Case-insensitive:

rg -i 'error'

Smart case:

rg -S 'Parser'

Fixed literal search:

rg -F 'Router::new'

Whole-word search:

rg -w 'Result'

Print filenames only:

rg -l 'TODO'

Count matching lines:

rg -c 'TODO'

Show two lines after each match:

rg -A 2 'TODO'

Show two lines before:

rg -B 2 'TODO'

Show two lines around:

rg -C 2 'TODO'

Numbered output is enabled by default in normal terminal output when appropriate, but it can be made explicit with:

rg -n 'pattern'

17. Restrict Searches to Rust

One of the most useful habits is restricting a search to the language you actually care about.

Use:

rg 'pattern' -t rust

For example:

rg 'struct\s+\w+' -t rust

You can inspect available file types with:

rg --type-list

ripgrep also allows exclusions:

rg 'unsafe' -t rust -T test

This can be useful when searching implementation code while excluding test files. ([ripgrep][3])

18. Restrict Searches with Globs

You can use globs directly.

Only Rust source:

rg 'pattern' -g '*.rs'

Rust and TOML:

rg 'pattern' -g '*.rs' -g '*.toml'

Exclude tests:

rg 'pattern' -g '!tests/**'

Exclude a generated directory:

rg 'pattern' -g '!target/**'

Globs are useful when the repository's normal ignore rules are not enough. ([ripgrep][3])

19. Find Files Before Searching Them

Sometimes the first question is simply:

What files exist?

Use:

rg --files

Rust source files:

rg --files -g '*.rs'

Cargo manifests:

rg --files -g 'Cargo.toml'

Markdown:

rg --files -g '*.md'

This is often easier than navigating a large directory tree.

PART 5

Rust-Specific Queries

20. Search by Rust Declaration

Find functions:

rg '^\s*(pub\s+)?fn\s+\w+' -t rust

Find structs:

rg '^\s*(pub\s+)?struct\s+\w+' -t rust

Find enums:

rg '^\s*(pub\s+)?enum\s+\w+' -t rust

Find traits:

rg '^\s*(pub\s+)?trait\s+\w+' -t rust

Find implementations:

rg '^\s*impl\b' -t rust

Find public declarations:

rg '^\s*pub\b' -t rust

These are navigation queries, not complete parsers.

21. Find a Specific Rust Symbol

Suppose the symbol is:

Router

Start with a literal search:

rg -F 'Router' -t rust

Then narrow the question.

Definition candidates:

rg 'struct\s+Router|enum\s+Router|type\s+Router|trait\s+Router' -t rust

Construction:

rg 'Router\s*\{' -t rust

Associated functions:

rg 'Router::' -t rust

Imports:

rg 'use .*Router' -t rust

The important principle is:

Start literal. Add structure only when the literal search produces too much noise.

22. Find Function Callers

Suppose you have:

parse_config()

Start with:

rg -F 'parse_config(' -t rust

Then distinguish the definition:

rg 'fn\s+parse_config\b' -t rust

and the likely calls:

rg -F 'parse_config(' -t rust

This is usually enough for ordinary Rust functions.

For methods:

router.handle()

search:

rg -F '.handle(' -t rust

Then investigate the receiver's type.

This is an important limitation:

Text search can find likely callers, but it cannot reliably determine which method implementation Rust's type system selects.

For that, compiler-backed tools are preferable.

23. Find Where a Struct Is Constructed

Suppose:

struct Config {
    path: PathBuf,
    debug: bool,
}

Search:

rg 'Config\s*\{' -t rust

Also search:

rg 'Config::' -t rust

Then search for functions returning it:

rg '->\s*(Result<)?\s*Config\b' -t rust

The question is not merely:

"Where is Config defined?"

The more useful questions are:

Where is Config defined?

Where is Config constructed?

Who owns each Config?

Where is Config passed?

Where is Config transformed?

Where is Config destroyed or consumed?

This is source-code archaeology.

24. Find Trait Implementations

Suppose you want implementations of:

Display

Start:

rg 'impl\s+Display\s+for\s+\w+' -t rust

For a specific type:

rg 'impl\s+Display\s+for\s+User' -t rust

Also search:

rg 'impl.*Display' -t rust

The regex is useful for finding candidates.

The compiler remains the authority for whether a particular implementation is actually applicable.

25. Find Error Creation and Propagation

Rust error investigation benefits from several searches.

Find Result:

rg '\bResult\b' -t rust

Find ?:

rg '\?' -t rust

Find explicit errors:

rg 'Err\s*\(' -t rust

Find common error constructors:

rg 'Error::|Error\s*\{' -t rust

Find unwrap:

rg '\.unwrap\(\)' -t rust

Find expect:

rg '\.expect\(' -t rust

Then trace the error backward:

Where is the error created?

Who returns it?

Who receives it?

Who converts it?

Who handles it?

Where does it become user-visible?

26. Search for Ownership and Borrowing Clues

Regex cannot understand Rust's ownership model, but it can locate relevant syntax.

Search references:

rg '&\w+' -t rust

Search mutable references:

rg '&mut\b' -t rust

Search cloning:

rg '\.clone\(\)' -t rust

Search moves into closures:

rg '\bmove\b' -t rust

Search explicit lifetimes:

rg "'[a-zA-Z_][a-zA-Z0-9_]*" -t rust

These searches locate places worth investigating.

They do not explain ownership.

Use compiler diagnostics for that.

27. Compiler Errors Are Queries

A Rust compiler error is already a highly specific query.

For example:

error[E0382]

can be investigated with:

rustc --explain E0382

The general pattern is:

rustc --explain E####

This is often more useful than immediately searching the entire internet.

First understand the compiler's classification of the problem.

Then inspect your code.

Then search external documentation if necessary.

28. Cargo as a Source-Code Query Tool

Cargo contains useful information about the architecture of a Rust project.

List workspace packages:

cargo metadata --no-deps --format-version 1

Inspect dependency relationships:

cargo tree

Find why a dependency exists:

cargo tree -i crate_name

Inspect enabled features:

cargo tree -e features

Check the project without building executable output:

cargo check

Check a specific package:

cargo check -p package_name

Run a specific test:

cargo test test_name

Run tests for a package:

cargo test -p package_name

Cargo is therefore not only a build tool.

It is also a source and dependency investigation tool.

29. Search the Dependency Source

When your code calls something from another crate, the answer may not be in your repository.

Ask:

What does this dependency actually do?

First identify the dependency:

cargo tree

Then locate its source through Cargo's registry/cache or your IDE tooling.

For a specific type or function, search the dependency source:

rg -F 'TypeName' /path/to/dependency

The important shift is:

A dependency is part of the program's behavior even when its source is outside your repository.

When understanding a difficult API, reading the implementation can be more informative than repeatedly guessing from the call site.

PART 6

ast-grep

30. ast-grep: Structural Search

Regex searches text.

ast-grep searches parsed source structure using AST patterns.

This makes it useful when formatting, whitespace, comments, or superficial textual differences should not matter.

For example:

ast-grep -l rs -p '$OBJECT.unwrap()'

can search for unwrap() calls structurally.

The short form:

ast-grep -p 'pattern'

is equivalent to:

ast-grep run -p 'pattern'

according to the current CLI documentation. ([Ast Grep][6])

31. ast-grep Metavariables

A single-dollar metavariable:

$NAME

matches one AST node.

Example:

ast-grep -l rs -p '$OBJECT.unwrap()'

Here:

$OBJECT

can represent different receiver expressions.

A triple-dollar metavariable:

$$$ARGS

matches a sequence of AST nodes.

For example:

ast-grep -l rs -p 'process($$$ARGS)'

can find calls to process regardless of the number of arguments.

This is one of the main advantages of structural search.

32. ast-grep Outline

ast-grep outline provides a compact structural overview of source code.

For one file:

ast-grep outline src/main.rs

For a directory:

ast-grep outline src

For exported items:

ast-grep outline src --items exports

For structures and functions:

ast-grep outline src --type struct,enum,function

For signatures:

ast-grep outline src --view signatures

For a more detailed view:

ast-grep outline src/main.rs --view expanded

Current ast-grep documentation describes outline as a compact source-code map of items, imports, exports, and direct members. ([Ast Grep][1])

33. An Important ast-grep Limitation

ast-grep outline is syntax-aware but local.

It does not:

resolve types,
follow references,
build a call graph,
infer ownership,
or understand the complete meaning of the program.

This distinction matters.

Use outline to ask: What is structurally present here?

Use ast-grep run to ask: Where does this structural pattern occur?

Use rg to ask: Where does this text occur?

Use rust-analyzer / compiler to ask questions requiring semantic information.

The current ast-grep documentation explicitly describes outline as intentionally local and recommends other tools for reference and call-graph questions. ([Ast Grep][7])

34. ast-grep Rules

For repeated structural checks, ast-grep supports YAML rules.

Example:

id: find-unsafe-blocks
language: rust
rule:
  pattern: unsafe { $$$BODY }

Then:

ast-grep scan -r find-unsafe.yaml

Rules become useful when a one-off search becomes a recurring code-quality query.

PART 7

Choosing Tools & The Ladder

35. When Regex Becomes the Wrong Tool

Use regex when the question is about text.

For example:

Where is TODO used?

Where does this error message occur?

Where is this identifier written?

Which files contain unwrap()?

Use ast-grep when the question is about syntax structure.

For example:

Find every call with this shape.

Find this kind of function invocation.

Find this AST pattern regardless of formatting.

Use compiler-backed tools when the question is semantic.

For example:

Which implementation does this method call?

What type does this expression have?

Where is this symbol actually defined?

What references this symbol?

Why does this borrow fail?

This distinction prevents a lot of increasingly complicated regex.

36. The Rust Source-Query Ladder

When investigating unfamiliar Rust code, use the lowest level that can answer the question.

Start with:

1. Literal search

Example:

rg -F 'Router'

Then:

2. Regex search

Example:

rg 'struct\s+Router' -t rust

Then:

3. Restricted search

Example:

rg 'Router' -t rust -g '!tests/**'

Then:

4. Structural search

Example:

ast-grep -l rs -p 'Router::new($$$ARGS)'

Then:

5. Syntax outline

Example:

ast-grep outline src

Then:

6. Compiler-backed investigation

Use rust-analyzer, compiler diagnostics, or IDE symbol/reference information.

Finally:

7. Read the relevant implementation.

The objective is not to stay at the most sophisticated level.

The objective is to stop as soon as the question has been answered reliably.

PART 8

Relationship & Tracing

37. Query by Relationship

A powerful way to understand Rust is to stop searching only for names.

Search for relationships.

For a type:

Where is it defined?

Who constructs it?

Who owns it?

Who receives it?

Who modifies it?

Who returns it?

Who stores it?

Who converts it?

Who destroys or consumes it?

For a function:

Where is it defined?

Who calls it?

What does it call?

What arguments does it receive?

What does it return?

What errors can it produce?

What state does it modify?

For a module:

Who imports it?

What does it import?

What does it expose?

Who calls its public functions?

What types does it own?

This is much closer to understanding architecture than simply searching for keywords.

38. Trace One Value

When the behavior of a program is confusing, choose one important value.

For example:

Config

Then trace:

Where is Config created?

        ↓

What fields are initialized?

        ↓

Where is it passed?

        ↓

Which functions transform it?

        ↓

Where is it stored?

        ↓

Where is it consumed?

Use searches to find each transition.

This is often more manageable than trying to understand the entire repository simultaneously.

39. Trace One Function

For a function:

handle_request()

build the smallest useful call chain.

Start:

rg -n -F 'handle_request(' -t rust

Find the definition:

rg -n 'fn\s+handle_request\b' -t rust

Read the function signature.

Identify:

inputs
outputs
errors
state
dependencies
called functions

Then investigate the most important called function.

Repeat only as far as necessary.

This prevents uncontrolled code reading.

40. Trace a Construction Path

A particularly useful Rust question is:

Who creates this object?

Suppose:

Router

Start:

rg -n 'Router\s*\{' -t rust

Then:

rg -n 'Router::' -t rust

Then inspect functions returning it:

rg -n '->\s*Router\b' -t rust

Then follow callers.

You are building:

creator
    ↓
constructor
    ↓
object
    ↓
consumer

This often reveals ownership and architecture faster than reading modules sequentially.

PART 9

Git & Diff

41. Search Git History

Source-code understanding sometimes requires historical information.

Find recent changes:

git log --oneline --all

Inspect a file's history:

git log -- path/to/file.rs

Inspect a specific change:

git show COMMIT

Find when a line changed:

git blame path/to/file.rs

Search commit messages:

git log --all --grep='router'

Search removed or historical code:

git log -S'Router::new' --all -- path/to/file.rs

Search for changes matching a regex:

git log -G'Router::new' --all -- path/to/file.rs

History can answer questions that the current source cannot.

For example:

Why is this strange workaround here?

The current code may show what it does.

Git history may show why it exists.

42. Query the Current Diff

Before and after a change:

git diff

List changed files:

git status --short

Show names only:

git diff --name-only

Inspect a particular file:

git diff -- path/to/file.rs

Then use source queries against the changed area.

For example:

git diff --name-only | xargs rg 'TODO'

This can help keep investigation focused on what actually changed.

PART 10

Output Control

43. Search Without Producing Too Much Output

Screen-reader workflows benefit from controlling output volume.

Prefer:

rg -n 'pattern'

over dumping entire files.

Restrict the scope:

rg 'pattern' src/

Restrict the language:

rg 'pattern' -t rust

Restrict the files:

rg 'pattern' -g '*.rs'

Show only filenames:

rg -l 'pattern'

Show a small context:

rg -C 2 'pattern'

Sort when deterministic output helps:

rg --sort path 'pattern'

The goal is:

Enough output to answer the next question, not enough output to overwhelm the reader.

44. Multiline ripgrep Searches

Normal ripgrep searches operate line by line.

If the query genuinely requires multiple lines:

rg -U 'pattern'

or:

rg --multiline 'pattern'

Multiline searches can be useful for source structures that span lines.

But they also increase complexity.

Start with a line-oriented search.

Use multiline mode when the problem actually requires it.

45. Search Context Is a Tool

When a match appears, context can often answer the next question immediately.

Use:

rg -C 3 'pattern'

Then adjust:

rg -C 10 'pattern'

if necessary.

This is often better than opening the entire file.

A good progression is:

match
→ small context
→ larger context
→ exact source range
→ full function

Read only as much as the question requires.

PART 11

Search Direction & Landmarks

46. Search from General to Specific

A good source query usually starts broad.

Example:

Router

Then:

Router::

Then:

Router::new

Then:

Router::new(...)

Then:

Who calls Router::new?

Then:

What type does Router::new return?

Then:

What does that caller do with the returned value?

Each query should reduce uncertainty.

47. Search from Specific to General

The reverse is also useful.

If you find:

ConfigError::MissingPath

search:

rg -n -F 'ConfigError::MissingPath' -t rust

Then:

rg -n 'enum\s+ConfigError' -t rust

Then inspect:

Who creates the error?

Who propagates it?

Who handles it?

Where does it become visible?

This moves from a concrete observation toward the surrounding architecture.

48. Use Search Results as Landmarks

Search results should become landmarks.

For example:

src/config.rs:42
src/parser.rs:81
src/loader.rs:117

Now you know:

config.rs
    definition

parser.rs
    transformation

loader.rs
    consumer

You do not need to remember the entire repository.

You only need to maintain the current chain of landmarks.

This is especially useful for auditory code reading.

49. Build a Small Vocabulary While Investigating

When exploring an unfamiliar repository, maintain a small dictionary.

For example:

Router
    central request dispatcher

Config
    application configuration

Loader
    creates Config from external input

Parser
    converts text into internal representation

Handler
    performs request-specific work

Then extend it:

Router owns HandlerRegistry.

Loader creates Config.

Parser produces Request.

Router passes Request to Handler.

This turns disconnected search results into a model of the program.

PART 12

Architecture & Config

50. Search for Architecture, Not Just Syntax

Useful architectural searches include:

rg 'mod\s+' -t rust

for module declarations.

rg 'use\s+' -t rust

for imports.

rg 'pub\s+' -t rust

for public API.

rg 'trait\s+' -t rust

for abstractions.

rg 'impl\s+' -t rust

for implementations.

rg '#\[derive\(' -t rust

for derived behavior.

rg '#\[cfg' -t rust

for conditional compilation.

rg '#\[feature' -t rust

for feature-related declarations.

These queries help expose the architecture behind the individual functions.

51. Search Cargo Configuration

The program's behavior can also be controlled by Cargo configuration.

Search:

rg '^\[dependencies\]' -g 'Cargo.toml'

Search workspace declarations:

rg '^\[workspace\]' -g 'Cargo.toml'

Search features:

rg '^\[features\]' -g 'Cargo.toml'

Search dependency names:

rg 'some_crate' -g 'Cargo.toml'

Then compare the manifest with:

cargo tree

The manifest tells you what the project declares.

The dependency tree tells you what Cargo actually resolves into the dependency graph.

52. Search Conditional Compilation

Rust code can exist only under particular configurations.

Search:

rg '#\[cfg' -t rust

and:

rg '#\[cfg_attr' -t rust

Then inspect Cargo features:

cargo tree -e features

When code seems to "disappear," ask:

Is it behind cfg?

Is it feature-gated?

Is it platform-specific?

Is it test-only?

Is it generated?

Is it conditionally compiled?

This can prevent incorrect conclusions from searching only the default source path.

53. Generated Code

When a symbol cannot be found where expected, consider generated code.

Search:

rg 'include!\(' -t rust

and:

rg 'include_str!\(' -t rust

and:

rg 'include_bytes!\(' -t rust

Also inspect:

build.rs

and:

Cargo.toml

A build script may generate Rust source or other artifacts.

54. Macros

Macros can make source queries misleading.

Search:

rg 'macro_rules!' -t rust

Search macro invocations:

rg '\w+!' -t rust

Then distinguish:

What is written?

What does the macro expand to?

Where is the macro defined?

Which crate provides it?

For difficult macro behavior, compiler diagnostics and rust-analyzer are generally more reliable than regex.

55. Tests as Executable Queries

Tests are another form of source-code documentation.

Search:

rg '#\[test\]' -t rust

Search test modules:

rg 'mod\s+tests' -t rust

Search a behavior:

rg 'empty|invalid|error|timeout' -t rust

Then run the relevant test:

cargo test test_name

A test can answer:

What behavior does the author consider important?

This is often more useful than comments.

56. Documentation as a Query Target

Search documentation:

rg 'Router' -g '*.md'

Search examples:

rg 'Router' -g '*.rs' -g '*.md'

Search TODOs:

rg 'TODO|FIXME' -g '*.rs' -g '*.md'

Search design terminology:

rg 'architecture|design|pipeline|backend|frontend' -g '*.md'

The code explains implementation.

Documentation may explain intent.

Both are part of understanding the system.

PART 13 · FINAL

Protocol, Rules & Mantra

57. A Practical Investigation Protocol

When a Rust codebase is unfamiliar:

Step 1 — Map the files

rg --files -t rust

Step 2 — Map the public structure

ast-grep outline src --items exports

Step 3 — Find the relevant symbol

rg -n -F 'SymbolName' -t rust

Step 4 — Find its definition

Use regex or ast-grep.

Step 5 — Find its callers or constructors

rg -n -F 'SymbolName(' -t rust

or an appropriate structural query.

Step 6 — Read the definition

Read the signature first. Then the fields. Then the body.

Step 7 — Follow the important dependency

Choose one function, type, or module that determines the behavior.

Step 8 — Verify assumptions

Use:

cargo check

or:

cargo test

or a more specific command.

Step 9 — Record the model

Write:

Definition:
Creator:
Caller:
Input:
Output:
Owner:
Important dependency:
Next question:

This produces an external memory of the investigation.

58. The Query Escalation Rule

Use this escalation order:

1. Exact literal

2. Fixed-string search

3. Simple regex

4. Restricted regex search

5. Search with context

6. ast-grep structural search

7. ast-grep outline

8. Cargo dependency information

9. Compiler diagnostics

10. rust-analyzer semantic information

11. Direct source reading

12. Git history

The order is not absolute.

Choose the cheapest reliable method.

A complicated AST query is unnecessary if:

rg -F 'Router::new'

already answers the question.

Likewise, a complicated regex is unnecessary when the question requires semantic information.

59. Common Search Mistakes

Searching too broadly

Instead of:

rg 'error'

try:

rg 'error' -t rust src/

Using regex when literal search is enough

Instead of:

rg 'Router::new'

if the string is literal, use:

rg -F 'Router::new'

Reading entire files too early

First find:

definition
caller
constructor
dependency

Then read the relevant ranges.

Treating search results as proof

A regex match is evidence. It is not necessarily semantic truth.

Trying to make regex parse Rust

When the query becomes a miniature Rust parser, switch tools. Use ast-grep or compiler-backed information.

Following too many branches

Choose one important value, function, or type. Trace it. Return to the broader system only when necessary.

60. The Core Mental Model

Think of source-code querying as asking progressively stronger questions.

Literal search asks: Where does this text occur?

Regex asks: Where does text matching this shape occur?

ripgrep asks: Where does this pattern occur across the project?

ast-grep asks: Where does this syntactic structure occur?

Cargo asks: What packages, dependencies, and features make up this project?

The compiler asks: What does Rust determine this program means, and where is it invalid?

rust-analyzer asks: Where are these semantic symbols and references connected?

Reading asks: What does this particular implementation actually do?

Git asks: How and why did this code become what it is?

61. The Master Rules

  1. Start with the question, not the tool.
  2. Start with a literal search when possible.
  3. Use regex when the shape of the text matters.
  4. Quote regex patterns in the shell.
  5. Remember that Rust's \d, \w, \s, and \b are Unicode-aware by default. ([Docs.rs][2])
  6. Use explicit ASCII classes when ASCII behavior is what you actually mean.
  7. Use -F when you want literal text.
  8. Restrict ripgrep with -t rust, -g, or a directory path.
  9. Use context options to control output volume.
  10. Use rg --files to discover the source tree.
  11. Use ast-grep when the question is structural rather than textual.
  12. Use ast-grep outline to map local source structure.
  13. Remember that ast-grep outline does not resolve references or build call graphs. ([Ast Grep][7])
  14. Use Cargo to investigate packages, dependencies, and features.
  15. Use compiler diagnostics for semantic Rust questions.
  16. Use rust-analyzer for symbol and reference relationships.
  17. Use Git history when the current source does not explain why something exists.
  18. Treat search results as evidence, not proof.
  19. Narrow the search after every useful discovery.
  20. Read only enough source to answer the current question.
  21. Trace relationships: definition, creator, caller, owner, consumer.
  22. When a regex starts becoming a parser, change tools.
  23. When the tool cannot answer the semantic question, ask the compiler.
  24. When the compiler cannot explain the design intent, read the implementation and history.

62. The Source-Code Investigation Mantra

When entering an unfamiliar Rust codebase, ask:

What am I trying to understand?

What is the smallest query that could answer that?

Where is the relevant definition?

Who creates it?

Who calls it?

What does it depend on?

What depends on it?

What happens to the data?

What does the compiler say?

What does the test prove?

Why was the code written this way?

What remains unknown?

The essential loop is:

Question → Query → Evidence → Narrow → Trace → Verify → Understand

Regex is one instrument in that process.

ripgrep is another.

Helix is the working environment.

ast-grep exposes syntax structure.

Cargo exposes the project and dependency system.

The compiler exposes semantic truth.

Git exposes history.

And the programmer connects the evidence into an understanding of the system.

63. Final Principle

Source-code navigation is not primarily a reading task.

It is an investigation task.

A large Rust repository becomes manageable when you stop asking:

"How do I read all of this?"

and start asking:

"What question do I need answered next?"

Then query the code.

Reduce the result.

Trace the relationship.

Verify the conclusion.

Move to the next question.

That is the foundation of practical code archaeology for a blind Rust programmer.
