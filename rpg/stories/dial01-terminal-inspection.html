# Terminal Code Inspection and Navigation

A BVI Rust programmer can treat the terminal as a code-discovery and navigation layer in front of Helix.

The basic division is:

  • rg — find text.
  • ast-grep — find syntactic structure.
  • ast-grep outline — map the structure of a file or directory.
  • Helix — open, read, navigate, select, and edit.
  • Tree-sitter — provide syntax-aware navigation inside Helix.
  • rust-analyzer — provide semantic information when syntax alone is insufficient.
  • Orca — read the resulting screen.

The goal is not to dump entire source files into the terminal.

The goal is to progressively narrow the codebase until only the relevant code remains.

The overall workflow is:

DISCOVER
LOCATE
STRUCTURE
OPEN
NAVIGATE
READ
UNDERSTAND

1. The Inspection Pipeline

Think of code archaeology as a sequence of questions.

Start with the codebase:

What am I looking for?

Use rg: Where is it?

Use ast-grep: What syntactic structure is involved?

Use Helix: Let me open and inspect it.

Use Tree-sitter navigation: Let me move through its structures.

Use rust-analyzer: What are the semantic relationships?

Use Orca: Read the current screen to me.

The tools therefore have distinct roles:

  • rg locates.
  • ast-grep identifies structure.
  • ast-grep outline maps code.
  • Helix inspects and edits.
  • Tree-sitter navigates syntax.
  • rust-analyzer explains semantic relationships.
  • Orca provides speech output.

2. rg: Find the Text

Use rg when you know something textual about the code.

Find a name:

rg 'my_function'

Find a function declaration:

rg 'fn my_function'

Find public functions:

rg 'pub fn'

Find use declarations:

rg '^use\s+'

Find a word:

rg 'Todo'

Restrict the search to Rust:

rg -t rust 'Todo'

rg automatically respects common ignore rules such as .gitignore.

3. Add Context

Once rg finds something interesting, inspect a small amount of surrounding source.

Show the match and 15 lines after it:

rg -A 15 'pub fn process_data'

Show five lines before it:

rg -B 5 'pub fn process_data'

Show five lines on both sides:

rg -C 5 'pub fn process_data'

Add line numbers:

rg -n -C 5 'fn process_data'

This is a preview. It helps answer: Is this the code I am looking for? Once you know that it is, move into Helix rather than continually expanding the terminal output.

4. Search for Rust Definitions

Textual searches are useful for rapid discovery.

Find function declarations:

rg -n '^(pub\s+)?fn\s+'

Find structs:

rg -n '^(pub\s+)?struct\s+'

Find enums:

rg -n '^(pub\s+)?enum\s+'

Find traits:

rg -n '^(pub\s+)?trait\s+'

Find type aliases:

rg -n '^(pub\s+)?type\s+'

Find implementation blocks:

rg -n '^impl'

These are textual patterns, not Rust syntax analysis. For example, a regular expression is not the right tool for reliably determining the complete extent of a Rust function containing nested blocks. That is where AST-based inspection becomes useful.

5. Search Imports and Dependencies

Imports are useful when determining how a module connects to the rest of the codebase.

Find imports:

rg -n '^use\s+'

Search for a crate:

rg -n 'use\s+tokio'

Search for a module:

rg -n 'use\s+crate::parser'

Search for references:

rg -n 'Parser'

Search Cargo manifests:

rg -n 'tokio' Cargo.toml

Search all workspace manifests:

rg -n 'tokio' --glob 'Cargo.toml'

This helps answer: Where does this dependency or symbol enter the codebase?

6. Control the Search Scope

Explicitly restrict the files being searched when useful.

Rust source:

rg 'pattern' --glob '*.rs'

Cargo files:

rg 'pattern' --glob '*.toml'

Documentation:

rg 'pattern' --glob '*.md'

Multiple file types:

rg 'pattern' \
  --glob '*.rs' \
  --glob '*.toml'

Exclude a directory:

rg 'pattern' --glob '!target/**'

This makes the inspection boundary explicit.

7. Get Exact Locations

When a match matters, get its location.

rg -n 'fn process_data'

Typical output:

src/parser.rs:42:pub fn process_data(...)

For file:line:column output:

rg --vimgrep 'fn process_data'

Example:

src/parser.rs:42:8:pub fn process_data(...)

The important information is: file, line, column. That turns a repository-wide search result into a navigation target.

8. Open the Target in Helix

Once you have the location:

hx src/parser.rs:42

Helix opens the file at the specified location.

If you already know the file:

hx src/parser.rs

Then search inside Helix:

/process_data

Move between matches:

n

Next match.

N

Previous match.

This establishes an important boundary: rg searches the repository. Helix searches the file you are currently inspecting.

NIGHT TWO — THE READING BOUNDARY

Sections 9 – 14: Configure, Position, Read, Navigate

Night two was the one Dial almost skipped — a whole section on editor configuration, three unfamiliar words deep before a single new command showed up. It turned out to be the part that mattered most.

9. Configure Helix for Orca

Helix and Orca work better together when Helix's scrolling behavior is predictable.

The goal is: Put the line you want to read at the top of the visible editor area, then let Orca read from there.

Configure scrolloff. Edit:

~/.config/helix/config.toml

Under the existing [editor] section, add:

[editor]
scrolloff = 0

If [editor] already exists, add only:

scrolloff = 0

Do not create a second [editor] section. With scrolloff = 0, Helix can place the current line directly against the edge of the editor viewport.

10. Use zt as an Orca Reading Boundary

After searching in Helix:

zt

This positions the current line at the top of the visible editor area. With scrolloff = 0, the current line can occupy the first visible editor line. This is particularly useful for screen-reader work because the current line becomes a deliberate reading boundary.

The workflow is:

Search
zt
Read

11. Orca Laptop Mode Reading Workflow

Orca has its own reading position, while Helix has its cursor and viewport. It is useful to keep these concepts separate:

  • Helix determines what is visible.
  • Orca determines what is spoken.

A practical workflow is:

  1. Search for a structural landmark.
  2. Use zt.
  3. Start Orca's reading.
  4. Listen to the surrounding code.
  5. Interrupt when you have enough information.
  6. Search for the next landmark.
  7. Use zt again.
  8. Resume reading.

In Orca Laptop Mode, use:

Orca + Enter

to start reading the current application window. The important idea is that zt establishes the visual reading boundary, while Orca provides the speech.

12. Helix Regex Search

Use Helix when the search has become local to one file.

Examples:

/parse_expression
/fn\s+\w+
/Result<
/unsafe\s*\{

Then:

n

moves to the next match.

N

moves to the previous match.

The progression is:

rg
repository search

Helix /
file search

n / N
move between matches

This prevents the terminal from becoming a large source-code dump.

13. Helix Textobjects

Helix provides syntax-aware textobjects through Tree-sitter.

Instead of thinking: Select lines 42 through 67.

you can think: Select this function. Or: Select this type. Or: Select this parameter list.

The selection therefore represents a meaningful syntactic region.

The general forms are:

mi + object

Select inside the object.

ma + object

Select around the object.

For example:

mif

selects inside a function.

maf

selects around a function.

For Rust, useful textobjects include structures such as:

f    function
t    type
a    argument
c    comment
T    test

The exact available textobjects depend on Helix's language configuration.

14. Tree-sitter Navigation

Helix also provides Tree-sitter-aware movement.

For example:

]f

moves to the next function.

[f

moves to the previous function.

Likewise:

]t

moves to the next type.

[t

moves to the previous type.

This gives you two different kinds of search:

Text search

/parse_expression

means: Find this text pattern.

Structural navigation

]f

means: Move to the next function.

Use the one that matches the question you are asking.

NIGHT THREE — STRUCTURE

Sections 15 – 19: From Words to Shapes

Everything up to now had been Dial finding words. Night three was the one where the file finally admitted that words were never going to be enough on their own.

15. ast-grep: Find Code Structure

ast-grep becomes useful when the question is structural rather than textual.

The basic form is:

ast-grep -p 'PATTERN'

For example:

ast-grep -p '$OBJECT.unwrap()'

This searches for method calls structurally resembling:

something.unwrap()

The exact receiver can vary. A metavariable such as $OBJECT represents one AST node. A multi-metavariable such as $$$ARGS can represent multiple AST nodes.

16. Structural Function Searches

A function pattern can describe the structure of a Rust function:

ast-grep -p 'fn $NAME($$$ARGS) { $$$BODY }'

A public function:

ast-grep -p 'pub fn $NAME($$$ARGS) { $$$BODY }'

A particular function:

ast-grep -p 'fn process_data($$$ARGS) { $$$BODY }'

The important difference from regex is that ast-grep parses the source and matches its syntax tree. You are describing: a Rust function with this structure rather than attempting to make a regular expression understand nested Rust syntax.

17. Structural Searches for Types

Struct:

ast-grep -p 'struct $NAME { $$$FIELDS }'

Public struct:

ast-grep -p 'pub struct $NAME { $$$FIELDS }'

Enum:

ast-grep -p 'enum $NAME { $$$VARIANTS }'

Trait:

ast-grep -p 'trait $NAME { $$$BODY }'

Implementation:

ast-grep -p 'impl $TYPE { $$$BODY }'

The goal is not to memorize every pattern. The goal is to recognize the progression:

text
regex
AST pattern
semantic analysis

Use the simplest level that answers the question.

18. Search for Calls

Structural searches are especially useful for function and method calls.

Find .unwrap() calls:

ast-grep -p '$OBJECT.unwrap()'

Find .expect(...) calls:

ast-grep -p '$OBJECT.expect($MESSAGE)'

Find println! calls:

ast-grep -p 'println!($$$ARGS)'

The structural pattern can be more useful than searching for the literal text because it describes the syntax you care about.

19. ast-grep outline: Map the Code

Before reading an unfamiliar source file, inspect its structure.

ast-grep outline src/parser.rs

This gives you a structural overview rather than dumping the complete source.

For signatures:

ast-grep outline src/parser.rs --view signatures

For a more detailed view:

ast-grep outline src/parser.rs --view expanded

For a compact view:

ast-grep outline src/parser.rs --view digest

This is especially valuable for a terminal-first workflow. Instead of immediately doing:

cat src/parser.rs

start with:

ast-grep outline src/parser.rs

Then decide which symbol deserves closer inspection.

20. A Code-Archaeology Sequence

When entering an unfamiliar Rust module, progressively reduce the search space.

Step 1: Map the file

ast-grep outline src/parser.rs

Ask: What is in this file?

Step 2: Locate a symbol

rg -n 'Parser'

Ask: Where does this name occur?

Step 3: Identify its structure

ast-grep -p 'struct Parser { $$$FIELDS }' src/parser.rs

Ask: What is the actual syntactic object?

Step 4: Open it

hx src/parser.rs:LINE

Step 5: Position the reading boundary

zt

Step 6: Read with Orca

Orca + Enter

Step 7: Navigate structurally

]f
[f
]t
[t

Step 8: Select a meaningful region when needed

mif
maf
mit
mat

The important point is that you do not begin by reading the entire file. You first establish where you are and what you are looking at.

21. Three Levels of Search

There are three particularly useful levels.

Level 1: Text. Question: Where does this text occur? Tool: rg. Example:

rg -n 'process_data'

Level 2: Syntax. Question: Where does this code shape occur? Tool: ast-grep. Example:

ast-grep -p '$OBJECT.unwrap()'

Level 3: Semantics. Question: What does this symbol mean, and what is related to it? Tool: rust-analyzer. Examples include: finding references, going to definitions, determining types, inspecting diagnostics, understanding symbol relationships.

This distinction is important: ast-grep understands syntax; rust-analyzer understands Rust semantics.

22. Read-Only Inspection Discipline

Keep reconnaissance separate from modification.

Use rg for discovery:

rg ...

Use ast-grep for structural inspection:

ast-grep -p '...'
ast-grep outline ...

Use Helix for reading and navigation. Use Helix when you are ready to edit.

The mental separation is:

DISCOVER
rg

MAP
ast-grep outline

IDENTIFY STRUCTURE
ast-grep

READ
Helix + Orca

UNDERSTAND RELATIONSHIPS
rust-analyzer

EDIT
Helix

This keeps code archaeology safer and cognitively simpler.

23. ast-grep Metavariables

ast-grep metavariables are pattern placeholders. The names are chosen by you. There is no special $OBJECT or $MESSAGE variable.

For example:

$OBJECT.unwrap()

Here $OBJECT is simply a name you chose for the captured AST node.

Single-node capture

$NAME

Matches one AST node. Example:

$OBJECT.unwrap()

Dropped single-node capture

$_

Matches one AST node without giving the capture a useful name. Example:

foo($_)

Named multi-node capture

$$$ARGS

Matches zero or more AST nodes. Example:

console.log($$$ARGS)

Unnamed multi-node capture

$$$

Matches zero or more AST nodes without naming the capture.

Unnamed-node capture

$$OP

This form is useful for matching unnamed syntax nodes such as operators. For example:

$A $$OP $B

24. Metavariable Naming

The important distinction is:

$NAME

captures one node.

$$$NAME

captures zero or more nodes. The identifier is yours to choose.

Examples:

$TYPE
$NAME
$OBJECT
$ARGS
$BODY
$FIELD

The same metavariable can also be reused to require the same AST node. For example:

$A == $A

requires the two sides to match the same captured node. Conceptually:

x == x

matches.

x == y

does not.

26. The Practical Mental Model

Think of the tools as answering different questions.

rg asks: Where is this text?

ast-grep asks: Where is this code shape?

ast-grep outline asks: What is the structure of this file?

Helix asks: How do I move through and inspect this source?

Tree-sitter asks: What syntactic structure am I currently inside?

rust-analyzer asks: What are the semantic relationships?

Orca asks: What is currently on the screen?

The result is a terminal-first code-archaeology workflow:

DISCOVER
LOCATE
MAP
STRUCTURE
OPEN
POSITION
READ
NAVIGATE
UNDERSTAND
EDIT

The terminal becomes the discovery layer. Helix becomes the inspection, navigation, and editing layer. Orca becomes the speech layer.

The key principle is:

Progressively reduce the amount of code you need to hold in attention.

You do not need to read the repository. You need to identify the relevant file, identify the relevant structure, position it predictably, and read only the code necessary to answer the current question.
