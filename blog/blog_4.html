Interlocking systems: composability without the complexity

📅 2026-08-05 ⏱️ 8 min read architecture composition interfaces pragmatism

There is a quiet elegance in a well‑machined gear train. Each gear has a precise number of teeth, a carefully calculated pitch, and a smooth surface. When two gears mesh, they transmit rotational force without slipping or binding. They are independent, yet they work together flawlessly — each turning at its own speed, transmitting power in a predictable way.

That is the vision of interlocking systems in software. Components that fit together like gears — clean interfaces, minimal coupling, and the art of practical composition. This is not about gluing together a thousand microservices with a thousand network calls. It is about building small, focused pieces that interact through simple, well‑defined contracts.

“Interlocking is not integration — it is the absence of friction between independent parts.”

The Gear Metaphor

A gear has a single responsibility: to transmit rotational motion. It does not care about the colour of the shaft, the material of the housing, or the direction of the overall machine. It only cares about the shape of its teeth and the spacing between them — its interface. As long as the interface is consistent, you can replace any gear with another of the same pitch, and the system will continue to function.

In software, this translates to components that expose a clear API (functions, modules, services) and communicate through well‑defined data structures. The internal implementation is opaque — it can be rewritten, optimised, or even rewritten in another language, as long as the public interface remains unchanged.

Principles of Interlocking Design

1. Clean Interfaces

The interface is the contract. It should be simple, intention‑revealing, and stable. Avoid exposing internal state. Prefer immutable data structures. Use plain data types (JSON, protobuf, or simple structs) rather than complex objects with hidden behaviour.

A good interface is like a gear tooth: it is designed to mesh effortlessly with its counterpart. It is not overly specialised, nor is it vague. It is precise enough to be useful, but general enough to be reused.

2. Minimal Coupling

Coupling is the measure of how much one component knows about the internals of another. In a tightly coupled system, changing one part forces changes in many others — a cascade of brittleness. Interlocking systems aim for loose coupling: components know only the interface of the things they interact with, not their implementation details.

This is achieved by programming to interfaces, using dependency injection, and avoiding global state. The UNIX pipe is the ultimate example: each program reads bytes from stdin and writes bytes to stdout. It has no idea where the bytes come from or where they are going — but they fit together perfectly.

3. Practical Composition

Composition is the process of combining simple components to build more complex behaviour. This is the heart of interlocking systems. Instead of creating monolithic blocks, we build small, focused pieces and chain them together.

In UNIX, this is done with pipes. In object‑oriented languages, it is done with decorators, middleware, or functional composition. In distributed systems, it can be done with message queues or lightweight RPC — but the principle remains the same: each component does one thing, and the flow of data connects them.

A Practical Example: A Validator Pipeline

Suppose you need to validate incoming JSON data: check the schema, verify that certain fields are within bounds, and perhaps enrich the data with additional fields. A monolithic validator would do all of this in one function, making it hard to test, extend, or reuse.

An interlocking approach splits the job into separate pieces:

  • SchemaValidator – checks that the JSON matches a JSON Schema.
  • RangeChecker – ensures numeric fields are within allowed ranges.
  • Enricher – adds derived fields (e.g., computed timestamps).

Each component is a function that takes a JSON value and returns either an error or the (potentially modified) value. They can be chained together: 

                    type Result<T> = std::result::Result<T, String>;

                    fn validate_schema(data: serde_json::Value) -> Result<serde_json::Value> { ... }
                    fn check_ranges(data: serde_json::Value) -> Result<serde_json::Value> { ... }
                    fn enrich(data: serde_json::Value) -> Result<serde_json::Value> { ... }

                    fn process(data: serde_json::Value) -> Result<serde_json::Value> {
                        validate_schema(data)
                            .and_then(check_ranges)
                            .and_then(enrich)
                    }

This pipeline is easy to test (each function is isolated), easy to extend (add a new filter), and easy to understand (the flow is linear and explicit). It is interlocking in the best sense — each part fits neatly into the next, but they remain independent.

Interlocking vs. Microservices

The term “microservices” has become synonymous with complexity. Distributed systems bring network latency, partial failures, eventual consistency, and operational overhead. They are not inherently bad — they are sometimes necessary — but they are not the only way to achieve modularity.

Interlocking systems, on the other hand, aim for local composition. The components run in the same process, share the same memory, and communicate through function calls. This is orders of magnitude simpler than network calls, and it still gives you many of the benefits of modularity: testability, reusability, and separation of concerns.

When you do need to scale beyond a single process, you can package your interlocking components as services — but you will have already proven that they work together cleanly. The interface is stable, the logic is encapsulated, and the composition is explicit.

Why This Matters Now

We are living through a wave of complexity fatigue. Teams are drowning in YAML, terraform, and Kubernetes manifests. The promise of microservices — “scale independently” — has been overshadowed by the reality of “debugging distributed failures.”

Interlocking design offers a way out. It is not a rejection of modern tools; it is a mindset that prioritises clarity, simplicity, and maintainability. It asks: “Can I build this as a pipeline of small, focused functions before I spin up a Kafka cluster?” Often, the answer is yes.

“Interlocking is the art of making complexity invisible — not by hiding it, but by structuring it so that each piece is simple on its own.”

Practical Advice for Building Interlocking Systems

  • Start with a pipeline. Before you design a service, design a series of transformations. Chain them together with simple data types.
  • Define interfaces early. The interface is the contract. Make it explicit, versioned, and stable.
  • Prefer pure functions. Functions that have no side effects are easier to reason about and test.
  • Avoid shared mutable state. If you must have state, encapsulate it and access it through a well‑defined API.
  • Keep it local. Run everything in a single process unless you have a proven reason not to. You can always split later.
  • Write tools, not services. Think in terms of small utilities that do one thing and do it well.

These are not new ideas — they are the foundation of the UNIX philosophy. But they are being rediscovered by a generation of engineers who are tired of fighting infrastructure.

Conclusion: The Power of Gears

Interlocking systems are a practical approach to building software that lasts. They embrace complexity by breaking it into manageable, independent pieces that mesh together cleanly. They favour composition over inheritance, interfaces over implementations, and simplicity over ceremony.

The next time you are about to spin up a new service, ask yourself: can I build this as a gear in a larger machine? Can I make it fit with the existing gears without adding a new axle? If the answer is yes, you are on the right track.

⟡ Interlocking is not a silver bullet — it is a choice. And it is a choice that pays dividends in maintainability, clarity, and joy.
