Trains, Tracks, and Pipes: A Pragmatic Alternative to Microservice Bloat

📅 2026-08-03 ⏱️ 8 min read unix architecture local-first pipes

I have a confession to make. When I picture a well‑designed system, I don't see a wall of neatly stacked Lego bricks. I see a model railway — locomotives pulling carriages along fixed tracks, switching points, signals, and the gentle clatter of wheels on rails. And when I think of how software should be composed, I reach for the UNIX pipe before I reach for a service mesh.

This is not a statement against microservices or the cloud. It is simply a preference — one rooted in experience, pragmatism, and a deep respect for the UNIX philosophy: write programs that do one thing and do it well, and connect them with simple, text‑based streams.

The Railway Metaphor

A model railway is a system of independent rolling stock that runs on fixed, predictable tracks. Each carriage has a specific purpose: a coal wagon, a passenger coach, a brake van. They couple together mechanically, but they are self‑contained units. The track provides a clear, unidirectional path — data flows in one direction, step by step, from input to output.

This is the opposite of the "Lego" microservices metaphor, where components snap together arbitrarily and often require complex orchestration, service discovery, and distributed state management. In a railway, the path is determined by the points (switches) and signals — which in software are the pipes and filters that connect small, focused programs.

I find this model more tangible and less abstract. When you chain four Unix programs together with pipes, you can see the data move from left to right, transformed at each stage. There is no hidden state, no service registry, no load balancer — just a deterministic flow of bytes.

“The UNIX pipe is the original microservice — but without the overhead, the network calls, or the YAML.”

Why Trains Over Lego

Lego bricks are modular, sure, but they also encourage tight coupling if you're not careful. A single brick can be replaced, but you often have to disassemble the surrounding structure. In a railway, each carriage is independent; you can swap a coach without lifting the entire train off the tracks. The track itself is the contract — the standardised interface (stdin/stdout) that everyone agrees upon.

This is the essence of the UNIX way: “Write programs that do one thing and do it well. Write programs to work together. Write programs to handle text streams, because that is a universal interface.”

In contrast, the microservices hype has led to sprawling architectures with dozens of moving parts, each requiring its own deployment, monitoring, and scaling strategy. Many of these systems could have been built with a handful of well‑crafted command‑line tools, a few cron jobs, and a well‑designed database — local‑first, running on a single machine or a small cluster, without the need for Kubernetes or a dozen cloud services.

Local‑First, Cloud‑Second (But Not Dogmatic)

I have a strong preference for local‑first software. I like the idea that the data lives on my machine, under my control, and that the applications I use are self‑contained and portable. This is not a religious stance — I use cloud services where they genuinely add value (e.g., global CDN, email delivery, or ephemeral compute). But I am deeply skeptical of the “cloud‑first, always” mentality that leads to vendor lock‑in, unpredictable costs, and architectural over‑engineering.

I believe in data ownership. If a service goes away, I want my data to remain accessible in a standard format (SQLite, CSV, JSON) that I can read with a text editor or a simple script. This is the railway approach: the cargo (data) is independent of the locomotive (the application). You can swap the engine, and the cargo still gets where it needs to go.

That said, I am not dogmatic. If a problem genuinely requires a distributed system, I will use one. If the cloud offers a clear operational advantage (e.g., auto‑scaling for burst traffic), I will adopt it. But I start with the simplest possible solution, often a single‑process program that reads from stdin, writes to stdout, and is composed with other such programs. Only when that proves insufficient do I reach for something heavier.

Example: A Data Pipeline in Rust

To illustrate the railway‑pipe approach, here is a tiny Rust program that reads lines of text, filters out comments, transforms each line to uppercase, and writes the result. It is designed to be used in a pipeline: 

                    use std::io::{self, BufRead};

                    fn main() {
                        let stdin = io::stdin();
                        let handle = stdin.lock();
                        for line in handle.lines() {
                            let line = line.unwrap();
                            if line.starts_with('#') { continue; }
                            println!("{}", line.to_uppercase());
                        }
                    }

You can chain this with grep, sort, or any other Unix tool. The data flows in a single direction, like a train on a track. There is no network, no serialisation, no service discovery — just bytes.

This approach scales surprisingly well. Many data processing tasks that are often pushed to Spark or cloud‑based ETL pipelines can be handled locally with a few well‑chosen Unix tools or small Rust programs, running on a single machine with local files. It is fast, reliable, and cheap.

Conclusion: The Pragmatic Path

I am not here to tell you to abandon microservices or the cloud. I am simply sharing a preference: I find the railway model and the UNIX pipe to be more intuitive, composable, and cost‑effective for a wide range of problems. They encourage minimalism, clarity, and data ownership — values that I hold dear.

If you are tired of YAML‑driven complexity and runaway cloud bills, consider reaching for a simple pipeline. Build a small, focused program. Run it locally. Pipe its output to the next tool. You might be surprised how much you can achieve with a few carriages and a solid track.

⟡ This is not a manifesto — it is a perspective. And like any good engineer, I am happy to be proven wrong by the data.
